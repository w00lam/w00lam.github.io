# 3. Binary Search 작성 요구사항

## 3-1. 이진 탐색이 필요한 이유

순차 탐색은 원소를 하나씩 비교한다.

데이터가 많아지면 최악의 경우 모든 원소를 확인하게 된다.

정렬된 데이터에서는 이진 탐색으로 중간 원소를 기준 삼아
탐색 범위를 절반씩 줄인다.

아래 내용을 글에 담는다.

- 순차 탐색과 이진 탐색의 차이
- 정렬된 데이터가 필요한 이유
- 중간값을 기준으로 탐색 범위를 줄이는 원리
- 정렬 비용과 탐색 비용을 구분해야 하는 이유

정렬되지 않은 배열에 이진 탐색을 적용하면
정확한 탐색 결과를 보장할 수 없다는 점을 설명한다.

## 3-2. 탐색 과정

설명은 다음 변수의 역할을 중심으로 구성한다.

left
right
mid
target

중간 인덱스는 다음처럼 계산한다.

mid = left + (right - left) / 2

target과 중간 원소를 비교한다.

1. arr[mid] == target
   → 탐색 성공

2. arr[mid] < target
   → left = mid + 1

3. arr[mid] > target
   → right = mid - 1

left > right가 되면 탐색에 실패한다.

이번 학습에서는 탐색 범위에서
이미 비교한 mid를 제외하는 이유를 확인했다.

변경된 경계가 왜 필요한지 과정 안에서 설명한다.

## 3-3. 헷갈렸던 부분

이번 학습에서 아래 내용을 확인했다.

- 배열 인덱스는 0부터 시작한다.
- mid를 이미 비교했으므로 다음 탐색 범위에서 제외한다.
- 탐색 구간은 매번 절반 수준으로 줄어든다.
- left와 right의 관계로 종료 여부를 판단한다.
- target이 없는 경우도 처리한다.

처음에는 mid를 다음 탐색에서도 확인해야 하는지 헷갈렸다.

하지만 이미 비교한 원소를 포함하면
탐색 범위가 줄어들지 않을 수 있다는 점을 이해했다.

이 부분은 필요 이상으로 늘이지 않는다.

## 3-4. 시간 및 공간 복잡도

시간 복잡도:

- 최선 O(1)
- 평균 O(log n)
- 최악 O(log n)

범위가 매번 절반으로 가까워지기 때문이다.

반복문 구현:

공간 복잡도 O(1)

재귀 구현:

호출 스택에 따라 공간 복잡도 O(log n)

반복문과 재귀 구현의 차이를 나눠 쓴다.

재귀가 항상 공간을 적게 사용한다는
잘못된 이해가 있었다면 바로잡은 내용을 기준으로 작성한다.

## 3-5. 중복 데이터와 탐색 경계

중복된 값이 존재하면
일반 이진 탐색은 특정 중복 원소의 위치를 보장하지 않는다.

학습한 첫 등장 위치 탐색을 함께 다룬다.

Lower Bound에서는 조건을 만족하는 첫 위치를 찾도록
탐색 경계를 조정한다.

일반 이진 탐색과 경계 탐색의 목적을 구분한다.

범위를 벗어난 새로운 응용 알고리즘은 추가하지 않는다.

## 3-6. Java 코드

반복문 기반 이진 탐색 예제를 넣는다.

코드 길이는 아래 내용을 확인할 수 있는 수준으로 제한한다.

- left/right 초기화
- mid 계산
- target 비교
- 탐색 범위 갱신
- 탐색 실패 시 -1 반환

작은 배열이 도움이 되면 이를 사용해
탐색 성공과 실패 결과를 설명한다.

직접 구현을 완벽히 숙달했다고 표현하지 않는다.

학습 중에는 반복문 구현과
경계 갱신을 보완할 필요가 있었다.

# 4. Binary Search 인터랙티브 시각화

## 목적

탐색 범위가 절반씩 줄어드는 과정을
사용자가 단계별로 직접 확인할 수 있게 한다.

## 삽입 위치

이진 탐색의 동작 원리를 설명한 직후.

## 데이터

배열:

[2, 4, 6, 8, 10, 12, 14]

target = 10

인덱스:

0 1 2 3 4 5 6

## 화면에 표시할 객체

- 배열 원소
- 배열 인덱스
- left
- right
- mid
- target
- 현재 탐색 범위
- 탐색에서 제외된 영역

## 단계별 상태

초기 상태:

left = 0
right = 6
target = 10

1단계:

mid = 3
arr[mid] = 8

8 < 10

그 결과 왼쪽 구간을 제외한다.

다음 탐색 범위:

left = 4
right = 6

2단계:

mid = 5
arr[mid] = 12

12 > 10

그 결과 오른쪽 구간을 제외한다.

다음 탐색 범위:

left = 4
right = 4

3단계:

mid = 4
arr[mid] = 10

탐색 성공.

최종 인덱스는 4다.

## 사용자 조작

- 이전
- 다음
- 초기화

각 단계 화면에는 아래 정보를 고정해 보여 준다.

- 현재 단계 번호
- left/right/mid 값
- 비교한 원소
- 비교 결과
- 제외되는 범위
- 다음 탐색 범위

이전 버튼을 누르면
그 단계의 상태를 그대로 복원한다.

첫 단계와 마지막 단계에서는
해당 방향으로 이동할 수 없는 버튼을 비활성화한다.

## 기술적 주의사항

- 비교하기 전과 후의 상태를 명확하게 구분한다.
- 탐색 범위에서 제외된 원소를 구분한다.
- 이미 비교한 mid를 다시 탐색하지 않는다.
- 단계 번호와 실제 비교 횟수를 맞춘다.
- 색상뿐 아니라 텍스트로 상태를 표시한다.

# 5. Hash Table 구현 작성 요구사항

## 5-1. 해시 테이블이 필요한 이유

배열에서 특정 데이터를 찾으려면
원소를 순차적으로 비교해야 할 수 있다.

해시 테이블은 키를 해시 함수에 전달하고
그 결과를 바탕으로 저장 위치를 결정한다.

아래 용어를 구분한다.

- Key
- Value
- Hash Function
- Hash Value
- Bucket
- Entry

해시값과 버킷 인덱스가
서로 같다고 볼 수 없다는 점을 설명한다.

## 5-2. 저장 및 조회 흐름

저장 흐름:

Key
→ Hash Function
→ Hash Value
→ Bucket Index
→ Bucket
→ Entry

조회할 때 먼저 버킷을 찾고
실제 키를 비교해야 할 수 있다.

해시값이 같다고 해서
반드시 같은 키인 것은 아니다.

이번 학습에서 이 부분을 여러 차례 확인했다.

## 5-3. Hash Collision

서로 다른 키가
같은 버킷 인덱스로 매핑될 수 있다.

이를 Hash Collision이라고 한다.

충돌이 났다고 해서
데이터가 반드시 덮어써지는 것은 아니다.

이번 글에서는 학습한 Separate Chaining을 중심으로 설명한다.

하나의 버킷에 여러 엔트리를 연결하고
실제 키를 비교해 원하는 데이터를 찾는다.

## 5-4. 동일 키와 충돌 키 구분

두 상황을 비교한다.

상황 A:

같은 키로 데이터를 다시 저장한다.

→ 기존 엔트리의 값을 갱신한다.

상황 B:

서로 다른 키가 같은 버킷에 저장된다.

→ 별도의 엔트리로 관리한다.

이때 해시값 또는 버킷 인덱스만으로
두 키가 같은지 판단하지 않는다.

최종 판단에는 실제 키 비교가 필요하다.

## 5-5. equals와 hashCode

두 메서드의 관계를 정확하게 설명한다.

equals()가 true인 두 객체는
같은 hashCode()를 반환한다.

반대로 hashCode()만 같더라도
equals()가 true인 것은 아니다.

해시 충돌이 존재할 수 있기 때문이다.

이번 학습에서는
객체의 주소가 아닌 실제 데이터 비교와
해시값 비교의 차이를 확인했다.

Java HashMap으로 이어 설명한다.

## 5-6. 문자열 해시 계산

이번 학습에서 다룬 문자열 해시 계산식을 풀어 쓴다.

hash = 31 * hash + key.charAt(i)

반복문은 문자열의 각 문자를 차례로 처리한다.

아래 항목을 구분한다.

- 초기 해시값
- 문자 코드값
- 반복 계산
- 정수 오버플로
- 버킷 인덱스 계산

문자열 길이만큼 반복할 때
마지막 문자가 누락되지 않도록 주의한다.

문자열 해시 계산과
버킷 인덱스 계산을 혼동하지 않는다.

## 5-7. 음수 해시값과 인덱스

Java int 연산에서는 오버플로가 발생할 수 있다.

해시값이 음수가 될 수도 있다.

음수 해시값을 그대로 배열 인덱스로 사용하면
범위를 벗어날 수 있다.

버킷 배열 크기가 양수일 때
유효한 인덱스를 계산하는 방법을 설명한다.

예:

Math.floorMod(hash, bucketCount)

단, bucketCount는 0보다 커야 한다.

Integer.MIN_VALUE에 단순히 Math.abs()를 적용하는 방법의 한계는
필요할 때만 짧게 덧붙인다.

## 5-8. 시간 복잡도

평균 조회:

O(1)

충돌이 집중되는 최악의 경우:

O(n)

버킷 선택과
버킷 안에서 키를 비교하는 일을 구분한다.

O(1)이 항상 보장된다고 작성하지 않는다.

## 5-9. 구현과 HashMap의 차이

학습용 배열 기반 해시 테이블 구현과
Java HashMap을 나눠 설명한다.

학습용 구현은
고정된 버킷 배열과 충돌 처리 방식에 집중했다.

Java HashMap은 충돌 처리와
저장 공간 확장 등을 지원한다.

HashMap의 트리화와 리사이징은
학습 범위 안에서만 간략히 연결한다.

내부 구조는 필요 이상으로 확장하지 않는다.

## 5-10. Java 코드

학습 기록 속 구현 예제를 먼저 확인한다.

아래 동작을 이해할 수 있는 예제를 사용한다.

- 해시값 계산
- 버킷 인덱스 계산
- 충돌 처리
- 동일 키 비교
- 기존 값 갱신
- 새로운 엔트리 추가
- 키 조회

학습 기록에 등장한 문자열 등장 횟수 계산은
필요할 때 작은 예제로 연결한다.

data, length, s_data 등의 변수는
원본 코드의 실제 의미를 확인한 뒤 설명한다.

Java HashMap 전체를 직접 구현한 것처럼
작성하지 않는다.

# 6. Hash Table 인터랙티브 시각화

## 목적

해시값 또는 버킷 인덱스가 같더라도
실제 키 비교가 필요하다는 점을 직접 보여 준다.

충돌과 동일 키 갱신의 차이를 시각화한다.

## 삽입 위치

Hash Collision과 Separate Chaining을
설명한 다음 바로.

## 데이터

학습용 버킷 배열 크기:

5

버킷 인덱스:

0, 1, 2, 3, 4

시각화에서는 실제 String.hashCode() 결과와
혼동하지 않게 별도의 단순 해시 함수를 사용한다.

예:

문자열의 문자 코드값 합계를 계산한 뒤
5로 나눈 나머지를 버킷 인덱스로 사용한다.

이 함수가 충돌을 보여 주기 위한
학습용 함수임을 명시한다.

사용할 데이터:

("apple", 100)
("banana", 200)
("apple", 300)

단순 해시 함수 기준:

apple → 0번 버킷
banana → 4번 버킷

추가 충돌 사례:

("grape", 400)

grape → 2번 버킷이므로
apple과 충돌하지 않는다.

실제 충돌을 보여 줄 때는
해시 계산 결과가 같은 버킷으로 연결되는
별도의 키를 선택한다.

예:

("apple", 100)
("elppa", 400)

두 문자열은 문자 코드값 합계가 같으므로
같은 버킷으로 들어간다.

최종 시각화에는 아래 데이터를 사용한다.

1. apple → 100
2. elppa → 400
3. apple → 300
4. apple 조회
5. elppa 조회

## 단계별 상태

초기:

모든 버킷이 비어 있다.

1단계:

apple 저장

해시 계산
→ 버킷 0
→ 새 엔트리 추가

2단계:

elppa 저장

해시 계산
→ 버킷 0
→ 기존 apple과 키 비교
→ 서로 다른 키
→ 새로운 엔트리 연결

3단계:

apple 값을 300으로 변경

해시 계산
→ 버킷 0
→ apple 엔트리 탐색
→ 키 일치
→ 기존 값 100을 300으로 갱신

엔트리 수는 증가하지 않는다.

4단계:

apple 조회

버킷 0에서 키를 비교한다.

결과:

300

5단계:

elppa 조회

버킷 0에서 키를 비교한다.

결과:

400

## 화면에 표시할 객체

- 입력 키
- 입력 값
- 해시 계산 결과
- 버킷 인덱스
- 버킷 배열
- 체이닝 엔트리
- 현재 비교 중인 키
- 조회 또는 갱신 결과

## 사용자 조작

- 이전
- 다음
- 초기화

각 단계 화면에는 아래 정보를 표시한다.

- 현재 수행 중인 연산
- 계산된 버킷 인덱스
- 비교 중인 엔트리
- 키 일치 여부
- 저장·갱신·조회 결과

이전 단계로 이동하면
엔트리의 값과 연결 상태까지 복원한다.

## 기술적 주의사항

- 충돌과 동일 키 갱신을 혼동하지 않는다.
- 서로 다른 키가 같은 버킷에 저장될 수 있어야 한다.
- 동일 키 갱신 시 엔트리 수가 증가하면 안 된다.
- 해시값만으로 키의 동일성을 판단하지 않는다.
- 조회 결과와 버킷 안에서 탐색하는 과정을 구분한다.
- 학습용 해시 함수와 Java HashMap 구현을 구분한다.

# 7. 공통 시각화 구현 기준

두 시각화는 하나의 디자인 시스템을 사용한다.

## 공통 UI

- 카드 형태
- 배경 및 테두리
- 강조색
- 단계 번호
- 설명 영역
- 버튼 디자인
- 버튼 배치
- 객체 선택 및 강조
- 모바일 반응형 처리

기존 Selection Sort 시각화 구현을 기준으로 맞춘다.

별도의 UI 시스템은 새로 만들지 않는다.

## 높이와 레이아웃 안정성

이 항목을 최우선 요구사항으로 본다.

단계를 넘겨도 다음 위치가 달라지면 안 된다.

- 시각화 카드 하단
- 이전·다음·초기화 버튼
- 단계 설명 영역
- 카드 아래쪽 본문

구현할 때 지킬 조건:

1. 동일한 화면 크기에서 카드 높이를 유지한다.
2. 가장 긴 설명을 기준으로 공간을 확보한다.
3. 설명이 길어질 경우 내부 스크롤을 사용한다.
4. 버튼 영역의 위치를 고정한다.
5. 단계를 바꿔도 아래쪽 본문이 밀리지 않게 한다.
6. 데이터가 바뀌어도 카드가 늘어나지 않게 한다.
7. 모바일과 PC는 서로 다른 높이를 사용할 수 있다.
8. 고정 높이 때문에 텍스트가 잘리면 안 된다.
9. 초기 로딩 전후에 레이아웃이 움직이는 일을 최소화한다.

CSS의 height, min-height, overflow 등은
기존 구현 방식에 맞춰 사용한다.

높이를 무조건 고정하는 데 그치지 말고
실제 콘텐츠가 정상적으로 표시되도록 한다.

## JavaScript 상태 관리

단계별 상태를 분명하게 관리한다.

이전 단계로 이동할 때
현재 상태를 되돌리는 역연산을 추측하지 않는다.

가능한 경우 단계별 상태 데이터를 바탕으로
정확하게 다시 렌더링한다.

첫 단계와 마지막 단계에서는
이동할 수 없는 버튼을 비활성화한다.

초기화나 이벤트를 중복 등록하지 않는다.

## 접근성

- 버튼 키보드 조작
- 명확한 포커스 표시
- 충분한 터치 영역
- 색상 외 텍스트 상태 표시
- prefers-reduced-motion 고려
- JavaScript 실패 시 대체 설명

불필요한 애니메이션은 추가하지 않는다.

오늘 배운 내용과 직접 이어지는
이전 알고리즘 게시글을 확인한다.

아래 주제를 중점적으로 검토한다.

해시 테이블은 정렬 없이

두 자료구조의 목적을 비교하되
한쪽이 무조건 더 우수하다고 작성하지 않는다.

# 9. 백엔드 개발과 연결

오늘 학습한 범위를 넘지 않는 선에서 실무 활용을 설명한다.

## Binary Search

정렬된 자료에서 특정 값을 찾는 상황과 연결한다.

다만 실제 백엔드 개발에서는
모든 데이터를 애플리케이션으로 가져와
직접 이진 탐색하는 일이 언제나 이득인 것은 아니다.

아래 비용을 함께 고려한다.

- 데이터베이스 조회
- 네트워크 전송
- 애플리케이션 메모리
- 정렬 비용
- 유지보수 비용

DB 인덱스를 단순히
이진 탐색과 동일한 구현이라고 설명하지 않는다.

## Hash Table

Java HashMap과 연결한다.

다음 활용 사례를 간략히 설명한다.

- 키를 이용한 데이터 조회
- 중복 키 확인
- 등장 횟수 집계

평균 O(1) 조회가 가능한 이유와
충돌 시 추가 비교가 필요한 이유를 함께 설명한다.

프로젝트 경험이나 구현 사례를 새로 덧붙이지 않는다.
