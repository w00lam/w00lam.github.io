Java 코드를 작성하다 보면 다음과 같은 코드를 아무렇지 않게 적는다.

~~~java
User user = new User("wooram");
~~~

처음에는 이 한 줄을 “User 객체를 만든다”라고만 생각하기 쉽다. 하지만 실제로는 `user`라는 참조 변수와 `new User("wooram")`으로 생성된 객체를 구분해야 한다.

이 차이를 알고 나니 Stack과 Heap의 역할도 단순한 저장 위치로 보이지 않았다. 메서드가 호출되는 동안만 필요한 값과 객체가 존재하는 동안 유지되는 상태가 달랐고 더 이상 사용하지 않는 객체라도 참조가 남아 있으면 GC가 수거하지 못했다. Spring Bean의 상태 관리 문제도 결국 이 객체와 참조의 관계에서 출발한다.

이번에는 [변수와 타입](/posts/java-variable-type/)에서 정리한 참조 타입과 [Object 클래스와 객체 동등성](/posts/java-object-equals-hashcode/)에서 살펴본 참조 관계를 JVM 메모리 영역에 연결해 보았다. 공부하면서 궁금했던 지점은 두 가지였다.

> Java 코드가 실행될 때 변수와 객체는 어디에서 관리되는가?
> 메서드 호출이 끝나면 무엇이 사라지고 객체는 언제 GC 대상이 되는가?

## JVM은 왜 메모리 영역을 나누어 관리할까?

학습 초반에는 JVM 메모리 영역을 다음처럼 단순하게 구분했다.

- Stack = 지역 변수
- Heap = 객체
- Method Area = 클래스 정보

이 구분만으로는 실제 코드를 읽을 때 곧바로 막혔다. 메서드가 끝났는데도 객체가 남아 있었고 참조 변수 두 개가 하나의 객체를 함께 가리키기도 했다.

프로그램 안의 데이터는 생명주기가 서로 다르다.

- 메서드가 실행되는 동안에만 필요한 값
- 객체가 존재하는 동안 유지되어야 하는 상태
- 여러 객체가 공통으로 사용하는 클래스 수준의 정보

JVM은 실행에 필요한 데이터를 이런 성격과 생명주기에 맞춰 나누어 관리한다. 오늘은 JVM Stack, Heap, Method Area를 중심으로 살펴본다.

JVM 명세도 이 영역들의 구체적인 물리적 배치나 구현 방식을 하나로 정하지 않는다. 아래 설명은 Java 코드를 이해하기 위한 논리적 모델이며 특정 JVM 구현의 내부 배치와 같다고 단정하지 않는다.

## Stack — 메서드 호출과 함께 만들어지고 사라지는 영역

다음 메서드를 보자.

~~~java
public void createUser() {
    int count = 1;
    User user = new User("wooram");
}
~~~

`createUser()`가 호출되면 해당 메서드 실행에 필요한 **Stack Frame**이 만들어진다. Stack Frame 안에는 지역 변수와 메서드 실행에 필요한 정보가 관리된다. JVM 명세에서도 메서드가 호출될 때 프레임이 만들어지고 메서드 실행이 끝나면 프레임이 제거된다고 설명한다.

여기서 `count`와 `user`를 같은 방식으로 이해하면 안 된다.

~~~java
int count = 1;
User user = new User("wooram");
~~~

`count`에는 정수 값 `1`이 저장된다. 반면 `user`에는 `User` 객체 자체가 들어가는 것이 아니라 Heap에 생성된 객체를 가리키기 위한 참조값이 저장된다.

이 장면을 단순화하면 다음과 같다.

~~~text
Stack Frame
  count = 1
  user ────────> Heap의 User 객체
~~~

“Stack에 객체가 저장된다”라고 말하기보다, 메서드의 지역 참조 변수가 Stack Frame에서 관리되고 그 참조가 Heap의 객체를 가리킨다고 이해하는 편이 정확하다. 참조 변수와 실제 객체는 서로 다르다.

## Heap — 객체가 존재하는 영역

Heap은 클래스의 인스턴스와 배열 같은 객체가 생성되는 영역이며 모든 JVM 스레드가 함께 사용한다. `new User(...)`가 실행되면 실제 `User` 객체는 Heap에 만들어지고 지역 변수에는 그 객체를 가리키는 참조가 들어간다.

이번에는 다음 코드를 보자.

~~~java
User user1 = new User("wooram");
User user2 = user1;
~~~

변수 두 개가 보이니 객체도 두 개라고 생각하기 쉽다. 하지만 `new User("wooram")`이 한 번만 실행되었으므로 생성된 `User` 객체는 하나다.

~~~text
Stack

user1 ─┐
       ├───> User 객체
user2 ─┘        ↑
             Heap
~~~

Stack에는 `user1`과 `user2`라는 두 참조 변수가 있고 Heap에는 하나의 `User` 객체가 있다. 두 변수는 같은 객체를 가리킨다. [Object 클래스와 객체 동등성](/posts/java-object-equals-hashcode/)에서 다룬 참조 동일성도 이 구조로 이해된다.

그래서 변수 수와 객체 수를 같은 숫자로 세면 안 된다. 객체를 몇 번 생성했는지와 현재 그 객체를 몇 개의 참조가 가리키는지는 나누어 생각해야 한다.

![JVM Stack의 참조 변수 두 개가 Heap의 동일한 User 객체를 가리키고 Method Area가 클래스 수준 정보를 관리하는 구조](/assets/images/2026-09-15-jvm-memory-lifecycle/stack-heap-object-lifecycle.svg)

이 차이를 알고 있으면 메서드가 종료될 때 무엇이 사라지고 어떤 객체가 GC 대상이 되는지 자연스럽게 이어진다.

## 메서드가 끝나면 객체도 바로 사라질까?

앞에서 본 코드를 다시 보자.

~~~java
public void createUser() {
    User user = new User("wooram");
}
~~~

메서드가 종료되면 `user`라는 지역 변수가 포함된 Stack Frame은 사라진다. 그렇다고 Heap의 `User` 객체가 메서드가 끝나는 순간 즉시 삭제되는 것은 아니다.

이때 봐야 할 것은 Stack Frame이 사라진 뒤에도 이 객체에 도달할 수 있는 다른 참조가 남아 있는지다.

만약 `user` 외에 객체를 가리키는 참조가 없다면 JVM은 그 객체에 더 이상 도달하지 못한다. 이런 객체는 GC가 수거할 후보가 된다. 다만 “참조가 없어지는 순간 GC가 즉시 실행되어 객체를 삭제한다”는 뜻은 아니다. GC가 정확히 언제 실행되는지는 이 글의 범위를 넘는 JVM의 실행 정책에 해당한다.

반대로 다른 객체의 필드나 Collection이 같은 객체를 계속 참조하고 있다면 지역 변수가 사라져도 Heap 객체에는 계속 도달한다. 메서드의 종료와 객체의 소멸을 같은 사건으로 보면 안 되는 이유다.

객체를 사용하지 않는다는 개발자의 의도보다 JVM이 해당 객체에 여전히 도달할 수 있는지가 중요하다.

## 참조가 남아 있으면 왜 메모리 문제가 생길까?

다음과 같은 `EventStore`가 있다고 하자.

~~~java
class EventStore {

    private final List<Event> events = new ArrayList<>();

    public void add(Event event) {
        events.add(event);
    }
}
~~~

비즈니스 로직에서는 어떤 `Event`가 더 이상 필요하지 않다고 판단했더라도 `events` 리스트가 계속 그 객체를 참조하고 있다면 JVM 입장에서는 도달 가능한 객체다. GC는 해당 `Event` 객체를 수거하지 못한다.

`EventStore` 자체가 오래 살아 있는 객체에 의해 참조되고 있고 `events`에 이벤트가 계속 쌓인다면 리스트와 그 안의 모든 이벤트가 함께 도달 가능한 상태로 남는다. 시간이 지나면서 Heap 사용량이 증가할 수 있는 이유다.

Java의 메모리 누수는 C처럼 개발자가 직접 메모리를 해제하지 않아서만 발생하는 문제가 아니다. GC가 있어도 필요하지 않은 객체를 계속 참조하면 GC가 수거하지 못하는 상황이 생긴다.

백엔드 애플리케이션의 Heap 사용량이 계속 증가할 때는 GC 이상부터 의심하지 않는다. 필요하지 않은 객체를 계속 참조하는 곳이 있는지 먼저 확인한다.

특히 오래 살아 있는 객체의 Collection에 데이터가 제한 없이 쌓이고 있지는 않은지, 객체를 더 이상 사용하지 않게 된 뒤에도 참조를 정리하지 않고 있지는 않은지 살펴본다. Heap Dump나 GC 튜닝은 이후 JVM 학습에서 다룰 주제로 남겨 두고 이번 글에서는 참조가 남아 있으면 객체가 GC 대상이 되지 않는다는 원리만 정리한다.

## Method Area — 객체가 아니라 클래스 수준의 정보

Method Area를 처음엔 메서드가 저장되는 곳 정도로 생각했다. JVM 명세에서 말하는 Method Area는 메서드 코드만 보관하는 공간이 아니었다.

Method Area는 모든 스레드가 공유하는 논리적 런타임 영역이다. 클래스별 구조와 runtime constant pool, 필드와 메서드 정보, 메서드와 생성자의 코드 같은 클래스 수준의 정보를 관리한다.

다음 클래스를 보자.

~~~java
class User {

    static int totalCount;

    private String name;
}
~~~

`totalCount`는 특정 `User` 객체 하나의 값이 아니라 `User` 클래스 수준에서 공유되는 상태다. `User` 객체를 여러 개 만들어도 `totalCount`라는 상태는 클래스에 하나만 존재한다.

반면 `name`은 각 `User` 객체가 가지는 인스턴스 상태다.

~~~text
User 객체 1 ── name = "wooram"
User 객체 2 ── name = "another-user"

User 클래스 ── totalCount
~~~

다만 `static` 값이 무조건 특정 물리적 Method Area에 저장된다고 단정해서는 안 된다. JVM 명세의 Method Area는 논리적인 런타임 영역이며 구체적인 위치와 관리 방식은 구현에 맡겨져 있다. 이번 글에서는 구현 세부 사항보다 `static`은 클래스 수준에서 공유되고 인스턴스 필드는 객체마다 존재한다는 의미에 집중한다.

## 지역 변수와 객체 필드는 왜 생명주기가 다를까?

두 코드를 나란히 놓고 보자.

~~~java
public void save() {
    int count = 1;
}
~~~

~~~java
class UserService {

    private final UserRepository userRepository;
}
~~~

`count`는 `save()` 메서드 실행을 위해 필요한 지역 변수다. 메서드 호출과 함께 만들어진 Stack Frame에서 관리되며 실행이 끝나면 그 Frame과 함께 사라진다.

반면 `userRepository`는 `UserService` 객체가 가지는 필드다. `UserService` 객체가 Heap에 존재하는 동안 그 필드도 객체의 상태로 존재한다. 필드에는 Repository 객체 자체가 들어가는 것이 아니라 Repository 객체를 가리키는 참조가 저장된다.

둘을 다음처럼 외우는 것만으로는 설명이 부족하다.

- 지역 변수 = Stack
- 필드 = Heap

여기서 기준으로 삼을 것은 이 데이터의 생명주기가 무엇과 연결되어 있는지다.

메서드 실행에만 필요한 값은 메서드 호출의 생명주기와 연결된다. 객체가 유지해야 하는 상태는 객체의 생명주기와 연결된다. 클래스 전체에서 공유하는 상태는 클래스 수준의 생명주기와 의미를 함께 봐야 한다.

## String도 특별한 공간에 있는 것이 아니라 객체다

다음 코드를 보자.

~~~java
String name = "wooram";
~~~

`name`은 참조 타입 변수이고 String도 JVM이 관리하는 객체다. 변수에는 문자열 객체를 가리키는 참조가 연결된다. String Pool의 동작이나 문자열 리터럴의 공유 규칙은 [String의 불변성과 불변 객체 설계](/posts/java-string-immutability-design/)에서 이미 자세히 다뤘으므로 여기서는 다시 확장하지 않는다.

String을 다시 짚는 이유는 간단하다. String이라고 해서 JVM 메모리 구조와 별개의 존재가 아니다. 참조 타입 변수로 객체를 가리켜 사용하는 일반적인 Java 객체다.

String을 다룰 때도 변수의 참조와 실제 객체를 구분하면 `==`와 `equals()`의 차이, 객체의 공유와 생명주기가 같은 흐름에서 이해된다.

## Spring Bean도 결국 JVM이 관리하는 객체다

Java 메모리 구조가 Spring 백엔드 개발과 만나는 지점은 Spring Bean이다. Spring Bean이 JVM과 별개의 특별한 메모리 공간에 저장되는 것은 아니다. Spring Container가 생성하고 생명주기를 관리하지만 결국 JVM 위에서 동작하는 Java 객체다.

예를 들어 다음과 같은 Service를 보자.

~~~java
@Service
public class OrderService {

    private int count;

    public void order() {
        count++;
    }
}
~~~

Spring의 기본 singleton Bean은 하나의 Container 안에서 하나의 인스턴스를 여러 요청이 함께 사용한다. 이때 `count`처럼 변경 가능한 인스턴스 필드를 두면 여러 요청이 같은 객체의 상태를 공유하게 된다.

여러 스레드가 동시에 `count++`를 실행하면 값을 읽고 증가시키고 저장하는 과정이 서로 겹친다. 그 결과 요청 횟수가 정확하게 반영되지 않는 경쟁 상태가 생기기도 한다.

Spring Bean은 싱글톤이니까 필드를 쓰면 안 된다는 규칙만 외우기보다 다음 흐름으로 이해하는 편이 낫다.

> Bean도 Heap에 존재하는 객체다.
> → singleton scope라면 여러 요청이 동일한 객체를 사용한다.
> → 객체 내부에 변경 가능한 상태가 있다면 여러 요청이 같은 상태를 수정한다.
> → 가능한 한 Service를 stateless하게 설계하는 편이 안전하다.

모든 필드가 문제가 되는 것은 아니다. 변경되지 않는 의존성을 `final` 필드로 보관하는 것과 요청마다 달라지는 값을 인스턴스 필드에 누적하는 것은 다르다. 중요한 것은 여러 요청이 공유하는 객체에 어떤 변경 가능한 상태를 두었는지다.

JVM 메모리를 공부하다 보면 자연스럽게 서버 코드 설계로 이어진다. 객체가 어디에 있는지만 보는 것이 아니라, 그 객체를 몇 개의 요청이 공유하는지와 상태 변경의 생명주기가 적절한지도 함께 봐야 한다.

## 오늘 헷갈렸던 부분과 수정된 이해

### 참조 변수와 객체

처음엔 다음 한 줄 전체를 하나의 객체처럼 생각하기 쉬웠다.

~~~java
User user = new User();
~~~

하지만 `user`는 객체를 가리키는 참조 변수이고 `new User()`로 만들어지는 실제 객체는 별개다. 변수 두 개가 같은 참조를 가지면 참조 변수는 두 개지만 객체는 하나일 수 있다.

### 지역 변수가 사라지는 것과 객체가 사라지는 것은 다르다

Stack Frame이 제거되어 지역 참조 변수가 사라지는 것과 Heap 객체가 즉시 삭제되는 것은 다르다. 객체를 가리키는 다른 참조가 있는지 확인해야 한다. 더 이상 도달할 수 없을 때 GC가 수거할 후보가 된다.

### GC가 있어도 메모리 누수가 생길 수 있다

필요 없는 객체라도 Collection이나 다른 장기 생존 객체가 계속 참조하고 있으면 GC는 수거하지 못한다. GC는 참조 관계를 무시하고 개발자의 의도를 추측해 객체를 삭제하지 않는다.

### Spring Bean은 특별한 JVM 메모리 영역에 존재하지 않는다

Spring이 Bean의 생성과 생명주기를 관리하더라도 Bean은 결국 Heap에 존재하는 Java 객체다. singleton Bean에 변경 가능한 상태를 두면 여러 요청이 같은 상태를 공유한다는 점을 객체 생명주기와 함께 봐야 한다.

### static과 instance는 저장 위치보다 의미가 중요하다

`static`은 클래스 수준에서 공유되는 상태이고 인스턴스 필드는 각 객체의 상태다. “어느 영역에 저장되는가”만 암기하기보다 어떤 범위에서 상태가 공유되고 무엇의 생명주기와 연결되는지를 함께 본다.

## 실제 백엔드 개발에서 어떻게 연결되는가

### Singleton Bean의 mutable state

여러 요청이 하나의 Bean 객체를 공유하므로 Service 객체에 요청별 변경 상태를 저장하면 동시성 문제가 생길 수 있다. Service를 설계할 때 해당 필드가 정말 객체가 계속 유지해야 하는 상태인지, 메서드 실행 중에만 필요한 값인지 구분한다.

### 메모리 누수 분석

Heap 사용량이 계속 늘면 불필요한 객체를 계속 참조하는 Collection이나 오래 살아 있는 객체가 있는지 확인한다. 객체가 사용되지 않는다는 판단만으로는 부족하다. 실제 참조 관계가 끊겼는지를 봐야 한다.

### 객체 생명주기를 고려한 설계

요청 처리 중 잠시 필요한 상태와 객체의 생명주기 동안 유지할 상태를 구분한다. 이 기준이 명확하면 지역 변수로 둘 값과 필드로 둘 값, 공유 상태로 둘 값의 차이도 자연스럽게 보인다.

JVM 메모리 학습은 단순한 면접 암기가 아니다. 서버 애플리케이션에서 상태를 어디에 두고 얼마나 오래 유지하며 누가 함께 사용하는지 판단하는 기준이 된다.

## 정리

JVM Stack은 스레드별로 메서드 호출과 함께 만들어지는 Stack Frame을 관리하고 지역 변수와 실행 정보를 다룬다.<br>
Heap에는 클래스 인스턴스와 배열 같은 객체가 존재하며 참조 타입 변수는 객체 자체가 아니라 객체를 가리키는 참조를 가진다.<br>
Stack Frame이 제거되어도 Heap 객체가 바로 삭제되는 것은 아니며 더 이상 객체에 도달할 수 없을 때 GC가 수거할 수 있는 대상이 된다.<br>
필요하지 않은 객체라도 Collection 등이 계속 참조하고 있으면 GC가 수거하지 못해 메모리 문제가 생길 수 있다.<br>
Method Area는 클래스 구조와 필드·메서드 정보 같은 클래스 수준의 정보를 관리하는 논리적 영역이며 구체적인 물리적 구현은 JVM 명세가 고정하지 않는다.<br>
`static` 필드는 클래스 수준에서 공유되고 인스턴스 필드는 각 객체의 상태이므로 서로 다른 생명주기와 공유 범위를 가진다.<br>
Spring Bean도 결국 Heap에 존재하는 Java 객체이므로, singleton Bean의 변경 가능한 상태는 여러 요청이 공유하는 객체 상태로 바라봐야 한다.

오늘 공부를 한 문장으로 묶으면 다음 질문으로 남는다.

> 이 값은 누구의 상태인가?
> 언제 만들어지는가?
> 언제 더 이상 필요 없어지는가?
> 누가 이 객체를 참조하고 있는가?

이 질문을 기준으로 보니 Stack과 Heap의 차이뿐 아니라 GC, 메모리 누수, `static`, Spring singleton Bean의 상태 관리까지 하나의 흐름으로 이어졌다. JVM 내부 구현과 GC 알고리즘은 이후 JVM 학습에서 필요할 때 더 공부할 주제로 남겨 둔다.
