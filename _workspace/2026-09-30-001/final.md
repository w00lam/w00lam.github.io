어제 [컴퓨터 구성 요소와 CPU의 명령어 처리 과정](/posts/computer-architecture-cpu-instruction-flow/)을 공부하면서 CPU가 메모리에서 명령어와 데이터를 읽어 처리하는 흐름을 정리했다. 그러다 자연스럽게 다음 질문이 남았다.

> CPU가 필요한 값을 매번 RAM에서 가져온다면 메모리 접근을 기다리는 비용은 어떻게 줄일까?

CPU와 RAM 사이에는 접근 속도 차이가 있다. CPU가 아무리 빠르게 명령어를 실행해도 매번 RAM의 응답을 기다려야 한다면 처리 능력을 충분히 활용하기 어렵다. 오늘은 이 간격을 줄이는 캐시 메모리를 공부했다.

처음에는 캐시를 CPU와 RAM 사이에 끼워 넣은 작은 메모리 정도로 생각했다. 하지만 오늘 모의면접에서 주소와 캐시 라인의 상태를 직접 추적하면서 생각이 조금 달라졌다. 캐시는 단순히 빠른 저장 공간이 아니라 **어떤 데이터를 가까이 둘지와 그 데이터가 요청한 블록인지 판단하는 구조**였다.

## CPU와 RAM 사이에 캐시가 필요한 이유

CPU가 명령어를 실행하거나 데이터를 사용하려면 해당 내용이 CPU가 접근할 수 있는 메모리 계층에 있어야 한다. 가장 단순하게 보면 CPU와 RAM이 직접 데이터를 주고받는 흐름이다. 이때 CPU가 요청할 때마다 RAM까지 다녀오면 메모리 접근 비용이 매번 발생한다.

캐시는 RAM에 있는 데이터의 일부를 CPU에 더 가까운 위치에 보관한다. CPU가 요청한 데이터가 캐시에 있으면 RAM까지 가지 않고 캐시에서 가져온다. 캐시의 용량은 제한되어 있으므로 모든 데이터를 넣는 것이 아니라 다시 사용될 가능성이 높은 데이터와 그 주변을 선택해 보관하는 것이 중요하다.

오늘 이해한 메모리 계층의 흐름은 다음과 같다.

~~~text
CPU의 메모리 요청
        ↓
L1 캐시 확인
        ├─ 히트 → 해당 계층에서 데이터 획득
        └─ 미스 → L2 캐시 확인
                         ├─ 히트 → 데이터 획득
                         └─ 미스 → L3 캐시 확인
                                          ├─ 히트 → 데이터 획득
                                          └─ 미스 → RAM에서 블록을 가져옴
~~~

![CPU가 L1·L2·L3 캐시와 RAM을 차례로 확인하는 히트·미스 흐름](/assets/images/2026-09-30-cpu-cache/memory-hierarchy-cache-flow.svg)

이 글의 L1 → L2 → L3 → RAM 흐름은 오늘 학습한 내용을 위한 단순화된 모델이다. 실제 CPU마다 캐시 계층의 구성과 공유 방식, 접근 경로가 완전히 같다고 단정할 수는 없다. 여기서 중요한 것은 계층의 이름이나 고정된 용량을 외우는 것이 아니다. 가까운 계층에서 요청한 블록을 찾으면 접근 비용을 줄이고, 찾지 못하면 하위 계층으로 내려간다는 흐름이다.

## 작은 캐시가 효과를 내는 이유는 지역성에 있다

캐시는 RAM보다 작다. 그렇다면 모든 데이터를 저장하지 못하는 캐시가 어떻게 도움이 될까? 프로그램이 메모리의 모든 위치를 완전히 무작위로 한 번씩만 사용하는 것이 아니라, 일정한 접근 패턴을 보이는 경우가 많기 때문이다. 이 경향을 지역성(locality)이라고 한다.

### 시간 지역성: 같은 위치를 다시 사용한다

시간 지역성은 최근 접근한 데이터나 명령어를 가까운 시간 안에 다시 사용할 가능성이 높은 성질이다. 핵심은 시간의 흐름을 두고 **같은 위치를 다시 사용한다**는 데 있다.

예를 들어 반복문 안에서 조건을 확인하는 값이나 여러 번 사용하는 누적 변수는 짧은 시간 동안 반복해서 참조될 수 있다. 한 번 사용한 데이터가 곧 다시 필요해질 가능성이 있다면 그 데이터를 CPU 가까이에 두었을 때 다음 접근의 비용을 줄일 수 있다.

### 공간 지역성: 가까운 위치를 이어서 사용한다

공간 지역성은 최근 접근한 위치 주변의 메모리 위치를 이어서 사용할 가능성이 높은 성질이다. 핵심은 **가까운 위치를 이어서 사용한다**는 것이다.

학습 중에는 공간 지역성을 다음처럼 정리했다.

> 한 번 접근한 위치의 주변 위치에 접근할 가능성이 높다.

예를 들어 배열을 처음부터 순서대로 읽는 코드는 가까운 주소에 있는 원소를 이어서 참조하는 패턴을 만든다.

~~~java
int[] values = {1, 2, 3, 4};
int sum = 0;

for (int value : values) {
    sum += value;
}
~~~

이 코드는 배열 원소를 순서대로 읽는다는 점에서 공간 지역성과 연결된다. `sum`처럼 반복해서 사용하는 값은 시간 지역성의 예다. 다만 이 코드를 보고 특정 변수나 원소에서 캐시 히트가 반드시 발생한다고 단정하면 안 된다. 실제 동작은 JVM 최적화와 하드웨어 구현을 포함한 여러 조건의 영향을 받기 때문이다. 이 예제는 캐시 상태를 측정한 코드가 아니라 접근 패턴을 이해하려는 예제다.

시간 지역성과 공간 지역성은 모두 “자주 사용하는 데이터”라고 뭉뚱그리면 안 된다. 시간 지역성은 **같은 위치를 다시 찾는 패턴**이고 공간 지역성은 **접근한 위치 근처를 이어서 찾는 패턴**이다. 이 둘을 구분하면 캐시가 왜 주변 데이터를 함께 가져오는지도 자연스럽게 연결된다.

## 캐시 라인은 왜 주변 데이터까지 가져올까?

CPU가 메모리에서 값 하나를 요청했다고 해서 캐시가 그 값 하나만 따로 저장한다고 생각하기 쉽다. 하지만 캐시는 일반적으로 일정 크기의 메모리 블록을 단위로 데이터를 가져오고 저장한다. 이 전송·저장 단위를 캐시 라인(cache line)과 연결해 이해한다.

두 문장을 비교하면 차이가 분명해진다. **필요한 값 하나만 저장한다**와 **필요한 값이 포함된 메모리 블록을 가져온다**는 서로 다른 설명이다.

오늘 최종적으로 이해한 것은 두 번째에 가깝다. 요청한 값이 포함된 블록을 캐시 라인으로 가져오면 그 주변에 있던 값도 함께 캐시에 들어온다. 이후 프로그램이 인접한 위치를 요청하면 이미 가져온 같은 블록 안에서 찾을 수 있어 히트가 발생할 가능성이 생긴다.

물론 함께 가져온 모든 데이터를 반드시 사용한다는 뜻은 아니다. 다음 접근이 주변 위치로 이어지지 않으면 캐시에 들어온 일부 데이터는 사용되지 않을 수도 있다. 공간 지역성이 자주 나타나는 프로그램에서는 이 방식이 효과적이지만 언제나 이득을 보장하는 규칙은 아니다.

캐시 라인의 크기는 특정 CPU에서 정해진 구현 세부 사항이므로 모든 시스템의 보편적인 값처럼 말하면 안 된다. 이 글의 뒤쪽 예제에서 사용하는 4바이트는 매핑 원리를 설명하기 위해 정한 학습용 가정이다.

## 캐시 히트와 미스는 무엇으로 판단할까?

캐시 히트는 요청한 데이터가 해당 캐시 계층에 있어서 그 계층에서 얻을 수 있는 상태다. 캐시 미스는 해당 계층에서 요청한 데이터를 찾지 못해 하위 계층에 접근해야 하는 상태다.

여기서 캐시 라인에 어떤 데이터가 들어 있다는 사실만으로 히트라고 판단하면 안 된다. 요청한 메모리 블록이 그 라인에 저장된 블록과 같은지 확인해야 한다. 이를 위해 주소를 요청한 블록을 식별하는 정보와 캐시 안에서 확인할 위치를 가리키는 정보로 나누어 본다.

| 주소 구성 | 확인하는 것 | 역할 |
| --- | --- | --- |
| Index | 캐시 라인 또는 세트 | 요청한 블록을 확인할 위치를 찾는다 |
| Tag | 저장된 블록의 식별 정보 | 그 위치에 요청한 블록이 있는지 구분한다 |
| Offset | 블록 내부의 위치 | 블록 안에서 실제로 필요한 값을 찾는다 |

실제로는 해당 캐시 라인이 유효한 상태인지도 함께 확인해야 한다. 따라서 히트 여부는 대략 다음 조건으로 판단한다.

~~~text
유효한 캐시 라인인가?
        그리고
저장된 Tag가 요청한 블록의 Tag와 같은가?
        그리고
블록 안에서 Offset으로 필요한 위치를 찾을 수 있는가?
~~~

특히 같은 Index에 매핑된다는 사실과 같은 메모리 블록이라는 사실은 다르다. 같은 Index를 가진 두 블록은 캐시에서 확인할 위치가 같을 뿐이다. Tag가 다르면 서로 다른 메모리 블록이다. 따라서 **Index만 같다고 히트가 되는 것이 아니라 유효성 확인과 Tag 비교가 함께 필요하다.**

## 캐시 매핑 방식은 무엇이 다를까?

매핑 방식은 메모리 블록을 캐시 어디에 저장할 수 있는지와 요청이 왔을 때 어느 범위의 Tag를 비교하는지를 정한다.

| 방식 | 저장 위치 | 탐색 범위 | 특징 |
| --- | --- | --- | --- |
| Direct Mapped | 각 블록에 대응하는 캐시 라인 하나 | 정해진 한 라인 | 확인할 위치를 바로 찾지만 같은 라인끼리 교체가 발생한다 |
| Fully Associative | 캐시 내부의 어느 라인 | 캐시 내부 후보 라인 전체 | 저장 위치는 자유롭지만 여러 라인의 Tag를 비교해야 한다 |
| Set Associative | 정해진 세트 안의 여러 라인 중 하나 | 정해진 세트 안의 라인 | 저장 위치와 비교 범위를 Direct와 Fully 사이에서 조절한다 |

### Direct Mapped

Direct Mapped에서는 각 메모리 블록이 들어갈 캐시 라인이 하나로 정해진다. 요청이 오면 Index로 확인할 라인을 바로 찾고 그 라인의 Tag를 비교한다. 확인할 위치가 정해져 있어 빠르게 판단할 수 있지만 서로 다른 블록이 같은 라인에 매핑되면 기존 블록이 교체될 수 있다.

### Fully Associative

Fully Associative에서는 메모리 블록을 캐시 내부의 어느 라인에나 저장한다. “RAM의 아무 위치에 저장한다”는 의미가 아니다. 저장 위치가 자유로운 범위는 캐시 안에 있는 라인이다.

특정 Index 하나로 확인할 라인이 정해지는 방식이 아니므로 요청한 블록을 찾으려면 캐시 내부 후보 라인들의 Tag를 비교해야 한다. Direct Mapped처럼 한 라인만 확인하는 것과는 탐색 범위가 다르다.

### Set Associative

Set Associative에서는 메모리 블록이 들어갈 세트는 정해진다. 다만 해당 세트 안에서는 여러 라인 중 하나에 저장한다. 요청이 오면 Index로 세트를 찾고 그 세트 안의 여러 라인에 저장된 Tag를 비교한다.

그래서 Set Associative는 Direct Mapped보다 저장 위치의 제약이 적고 같은 세트 안에서 교체 충돌을 줄일 여지가 있다. Fully Associative보다는 비교 범위가 작다. 세 가지 방식의 차이는 복잡한 구현 회로를 외우는 데 있지 않고 **저장 위치의 제약과 Tag를 확인하는 범위가 어떻게 달라지는지**에 있다.

## 작은 주소 예제로 충돌 미스를 추적해 보기

매핑 방식을 글로만 읽을 때는 같은 Index와 같은 블록을 다시 혼동했다. 그래서 오늘 학습한 원리를 설명하려고 작은 Direct Mapped 캐시 상태를 재구성했다. 실제 대화에서 사용한 주소와 동일한 문제라고 가정한 예제가 아니다.

### 예제 가정

~~~text
캐시 라인 수: 4개
한 라인에 저장하는 블록 크기: 4바이트
매핑 방식: Direct Mapped
초기 상태: 캐시가 비어 있음
접근 종류: 모두 읽기

메모리 블록 번호 = 주소 / 4의 정수 몫
Index = 메모리 블록 번호 % 4
Tag = 메모리 블록 번호 / 4의 정수 몫

접근 순서: 0 → 1 → 16 → 0
~~~

Offset은 주소를 블록 크기로 나눈 나머지로 생각한다. 표의 결과는 Index만 보지 않고 Valid와 Tag가 일치하는지까지 확인해 판단했다.

| 주소 | 블록 번호 | Index | Tag | Offset | 결과 | 이유 |
| ---: | ---: | ---: | ---: | ---: | --- | --- |
| 0 | 0 | 0 | 0 | 0 | 미스 | 처음 접근한 블록이므로 가져온다 |
| 1 | 0 | 0 | 0 | 1 | 히트 | 앞서 가져온 같은 블록 안에 있다 |
| 16 | 4 | 0 | 1 | 0 | 미스 | 다른 블록이 같은 라인에 매핑되어 기존 블록을 교체한다 |
| 0 | 0 | 0 | 0 | 0 | 충돌 미스 | 블록 0이 블록 4에 의해 교체되어 더 이상 없다 |

![Direct Mapped 캐시에서 Index 0의 블록 0이 블록 4로 교체되는 상태 변화](/assets/images/2026-09-30-cpu-cache/direct-mapped-conflict-miss.svg)

첫 번째 주소 `0`은 블록 번호 `0`을 처음 요청했으므로 콜드 미스다. 블록 0을 캐시의 Index 0 라인에 가져온 뒤 주소 `1`을 요청하면 주소는 다르지만 블록 번호는 여전히 `0`이다. Offset만 `0`에서 `1`로 달라졌고 같은 캐시 라인의 같은 블록 안에 있으므로 히트가 된다.

주소 `16`은 블록 번호 `4`에 해당한다. 블록 4도 `4 % 4 = 0`이므로 Index 0에 매핑되지만 Tag는 `1`이다. 이 주소의 첫 접근 자체는 블록 4를 처음 요청한 것이므로 콜드 미스다. 동시에 Direct Mapped 규칙에 따라 Index 0의 기존 라인에 있던 블록 0이 블록 4로 교체된다.

여기서 미스의 분류와 교체 발생을 구분해야 한다. 주소 `16`에서 발생한 미스는 블록 4의 첫 접근이라는 관점에서는 콜드 미스다. 이 접근이 같은 Index의 기존 라인을 덮어쓴 사건은 다음 접근의 충돌 미스를 만들어 내는 원인이 된다.

마지막 주소 `0`은 이미 한 번 가져왔던 블록 0을 다시 요청한다. 하지만 Index 0 라인에는 이제 Tag 1인 블록 4가 들어 있다. Index는 같지만 Tag가 다르므로 블록 0이 있다고 판단하면 안 된다. 블록 0이 같은 Index에 매핑된 블록 4와 충돌해 교체되었기 때문에 마지막 접근은 충돌 미스다.

처음에는 이 상황의 원인을 다음처럼 표현했다.

> 캐시에 저장되었다가 값이 바뀌고 태그가 달라졌기 때문이다.

하지만 읽기만 수행한 이 예제에서 원본 데이터의 값이 수정된 것은 아니다. 더 정확한 설명은 다음과 같다.

> 같은 인덱스에 매핑된 다른 메모리 블록이 들어오면서 기존 캐시 라인이 교체되었기 때문이다.

값이 바뀐 것과 캐시 라인이 보관하는 블록이 바뀐 것은 다른 사건이다. 이 차이를 구분하면 주소 `0`이 왜 다시 미스가 되었는지 설명된다.

콜드 미스는 해당 블록을 처음 가져오는 경우다. 충돌 미스는 캐시 전체에 여유가 남아 있더라도 매핑 규칙 때문에 여러 블록이 같은 위치를 두고 경쟁하다가 필요한 블록이 교체된 뒤 발생한다. 용량 미스는 캐시 전체 용량의 한계로 필요한 블록을 유지하지 못하는 경우라는 수준에서 구분하면 된다. 이 예제의 마지막 접근은 캐시 전체가 가득 차서 발생한 것이 아니라 Index 0에서 블록 0과 블록 4가 충돌한 결과이므로 용량 미스로 설명하면 안 된다.

## 오늘 헷갈렸던 내용을 다시 연결하기

오늘은 매핑 방식에 따라 확인할 범위도 달라진다는 점을 예제에 대입했다. Direct Mapped에서는 Index가 가리키는 정해진 라인 하나를 확인한다. Fully Associative에서는 캐시 내부 어느 라인에나 저장할 수 있으므로 후보 라인들의 Tag를 비교해야 한다. Set Associative에서는 Index로 정해진 세트 안의 라인들을 확인한다.

같은 Index와 같은 블록을 구분하는 기준도 다시 정리했다. Index는 확인할 위치를 정하고 Tag는 그 위치에 요청한 블록이 있는지 구분한다. Offset은 해당 블록 안에서 필요한 위치를 찾는다. 따라서 Index만 같다는 이유로 히트라고 판단하면 안 된다.

이 과정을 따라가면서 캐시 미스를 “값이 변경되어 태그가 달라진 상태”로 설명했던 표현도 고쳤다. 오늘의 읽기 예제에서는 값이 변경된 것이 아니라 캐시 라인이 다른 메모리 블록으로 교체되었다. 캐시의 상태와 원본 메모리의 데이터를 같은 것으로 취급하지 않게 된 것이 오늘 가장 큰 변화였다.

## CPU 캐시와 Redis 캐시는 같은 계층이 아니다

앞서 [JVM 메모리 영역 — 변수와 객체의 생명주기는 왜 다를까?](/posts/java-jvm-memory-lifecycle/)에서 본 Heap은 Java 프로그램 안의 논리적 메모리 영역이었다. CPU 캐시는 JVM Heap과 같은 종류의 메모리 영역이 아니라 CPU가 명령어와 데이터를 가져오는 하드웨어 메모리 계층의 일부다. JVM 객체가 Heap에 있다는 설명과 CPU가 그 프로그램의 명령어·데이터 블록을 캐시한다는 설명은 서로 다른 층위에 있다.

캐시라는 이름을 함께 사용하더라도 CPU 캐시와 Redis 캐시를 같은 계층의 저장 공간으로 보면 안 된다. 공통점은 반복 접근 비용을 줄인다는 데 있지만 무엇을 저장하고 어디에서 동작하며 누가 관리하는지가 다르다.

CPU 캐시는 CPU가 사용할 명령어와 데이터의 메모리 블록을 가까운 하드웨어 계층에 보관한다. 캐시 라인과 매핑 위치, Tag 비교 같은 동작은 하드웨어가 관리한다. 프로그램이 CPU 캐시의 키나 만료 시간을 직접 설계하는 구조가 아니다.

Redis를 애플리케이션 캐시로 사용하면 조회 결과나 계산 결과 등을 저장해 반복적인 DB 조회와 계산 비용을 줄일 수 있다. 이때 애플리케이션은 무엇을 캐시할지, 어떤 키로 찾을지, 언제 만료시키고 언제 갱신할지를 설계한다. Redis를 조회하는 과정에도 애플리케이션과 Redis 사이의 통신 및 처리 비용이 든다.

브라우저 캐시나 저장장치 관련 캐시도 반복 접근 비용을 줄인다는 공통점은 있지만 동작하는 계층과 관리 주체는 각각 다르다. “캐시는 빠른 곳에 저장한다”는 공통 문장만 기억하면 서로 다른 캐시의 역할을 섞게 된다. 저장 대상과 접근 경로까지 함께 봐야 한다.

## 오늘 이해한 내용

오늘 캐시 메모리를 공부하면서 캐시를 단순히 “빠른 메모리”라고 설명하는 데서 멈추지 않게 됐다. CPU와 RAM 사이의 접근 비용을 줄이기 위해 캐시는 지역성이 있는 접근 패턴을 활용하고, 요청한 값이 포함된 메모리 블록을 캐시 라인 단위로 가까이 보관한다.

히트와 미스는 캐시 라인이 존재하는지만 보고 판단하지 않는다. Index로 확인할 위치를 찾고 Valid 상태와 Tag를 비교한 뒤 Offset으로 블록 안의 위치를 찾는다. 같은 Index에 매핑된 블록이라도 Tag가 다르면 서로 다른 블록이며 기존 라인이 교체된 뒤 다시 요청하면 충돌 미스가 발생한다.

CPU 캐시와 Redis 캐시의 비교도 같은 기준으로 정리했다. 둘 다 반복 접근 비용을 줄이지만 CPU 캐시는 하드웨어가 명령어와 데이터 블록을 관리하고 Redis 캐시는 애플리케이션이 조회 결과와 키 및 만료·갱신 정책을 설계한다. 저장 대상과 동작 계층이 다르므로 같은 종류의 캐시로 설명하면 안 된다.

오늘 공부를 한 문장으로 묶으면 다음과 같다. 캐시는 반복 접근 비용을 줄이기 위해 다시 사용될 가능성이 있는 데이터를 가까이 보관하고, 요청한 블록이 실제로 있는지는 매핑 위치와 Tag를 함께 비교해 판단하는 구조다.

이미 가져온 블록도 같은 위치에 매핑된 다른 블록으로 교체되면 다시 미스가 된다는 점까지 확인했다. 다음에는 오늘 사용한 학습용 주소 계산을 실제 캐시 구조의 더 다양한 조건과 비교해 볼 수 있겠다. 우선은 값을 수정한 것과 캐시 라인을 교체한 것을 구분하는 기준을 남겨 둔다.
