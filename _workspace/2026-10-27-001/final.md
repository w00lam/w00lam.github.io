TCP가 데이터를 신뢰성 있게 전달하려면 수신 측 버퍼 상태와 네트워크의 혼잡 상태를 함께 고려해야 하는데, 두 상태는 전송량 조절에서 어떻게 다르게 반영될까? 처음에는 흐름 제어와 혼잡 제어가 모두 송신량을 조절하는 방식처럼 보여 비슷하게 느껴졌다. 공부를 이어 가며 하나는 수신 측을 보호하고 다른 하나는 네트워크 경로를 보호한다는 점을 나누어 보게 됐다. 오늘은 그 차이에서 출발해 UDP가 TCP와 다른 방식으로 데이터를 전달하는 이유까지 살펴보았다.

오늘 글에서는 다음 질문에 답해 본다.

- 흐름 제어와 혼잡 제어는 각각 무엇을 보호하는가?
- `rwnd`와 `cwnd`는 어떤 문제를 해결하며 전송량에 어떻게 함께 영향을 주는가?
- UDP는 왜 연결을 사전에 만들지 않고 데이터그램을 전달하는가?
- UDP 헤더의 네 필드와 길이 값은 무엇을 의미하는가?
- 전달의 신뢰성과 데이터의 최신성은 전송 방식 선택에 어떤 기준이 되는가?

## 1. 흐름 제어와 혼잡 제어가 필요한 이유

두 제어가 헷갈렸던 이유는 둘 다 송신 측의 전송량에 영향을 주기 때문이다. 하지만 송신 측이 바라보는 상태가 다르다. 흐름 제어는 데이터를 받을 끝점의 상태를 보고 혼잡 제어는 그 사이를 지나는 네트워크의 상태를 본다.

흐름 제어는 송신 측이 수신 측의 처리 능력보다 빠르게 보내 수신 버퍼가 넘치는 상황을 막는다. 수신 애플리케이션이 데이터를 읽기 전에 송신 측이 계속 보내면 버퍼의 여유가 사라지고 뒤이어 온 데이터가 버려진다. 이 제어에서 중요한 질문은 수신 측이 지금 얼마나 받아들일 수 있는가이다.

혼잡 제어는 네트워크 경로에 데이터가 몰려 손실과 재전송이 늘어나는 상황을 막는다. 양 끝의 버퍼가 충분해도 중간 라우터나 링크가 감당할 양보다 많은 데이터가 한꺼번에 흐르면 네트워크는 혼잡해진다. 이때 살펴야 하는 것은 수신 측의 버퍼가 아니라 경로 전체가 감당할 수 있는 정도다.

흐름 제어는 수신 측의 처리 속도 차이를 조절하고 혼잡 제어는 네트워크의 처리 용량을 살핀다. 전송량을 제한한다는 결과는 같아도 출발점과 보호 대상은 다르다.

## 2. 흐름 제어와 수신 윈도우

흐름 제어에서는 수신 측이 자신의 버퍼 상태를 송신 측에 알려 준다. 수신 측은 현재 받아들일 범위를 수신 윈도우인 `rwnd`로 광고하고 송신 측은 그 범위 안에서 아직 확인받지 못한 데이터를 보낸다. `rwnd`는 수신 버퍼의 여유 공간과 연결되어 있다. 버퍼가 가득 차면 윈도우가 작아지고 애플리케이션이 데이터를 읽어 공간이 생기면 다시 커진다.

처음에는 `rwnd`를 전송량을 나타내는 고정 숫자로만 생각했다. 수신 측이 지금 받아들일 수 있는 시퀀스 번호 범위라고 다시 보니 송신 측의 동작도 이어졌다. 송신 측은 이미 확인 응답을 받은 데이터와 아직 확인받지 못한 데이터를 나누어 보고 수신 윈도우 밖으로 새 데이터를 보내지 않는다.

슬라이딩 윈도우를 작은 예로 보면 처음 `rwnd`가 4라서 송신 측이 데이터 1부터 4까지 보낼 수 있다고 하자.

| 상태 | 송신 가능한 범위 | 의미 |
| --- | --- | --- |
| 처음 | `1 ~ 4` | 확인 응답을 기다리는 동안 윈도우 안의 데이터를 보낸다. |
| `1 ~ 2` 확인 후 | `3 ~ 6` | 앞의 데이터가 확인되고 수신 버퍼에 여유가 생기면 윈도우가 오른쪽으로 이동한다. |

앞의 데이터가 확인되었다고 전송이 멈추지는 않는다. 확인 응답을 받은 `1 ~ 2`가 범위에서 빠지면 뒤에 있던 `5 ~ 6`이 새로 들어온다. 송신 측은 이미 보낸 데이터와 새로 보낼 데이터를 함께 관리하면서 윈도우를 오른쪽으로 옮긴다. 이것이 슬라이딩 윈도우의 기본 흐름이다. 실제 TCP에서는 여기에 네트워크 혼잡을 반영한 `cwnd`까지 함께 본다.

## 3. 혼잡 제어와 혼잡 윈도우

`cwnd`는 네트워크 혼잡을 고려해 송신 측이 조절하는 혼잡 윈도우다. ACK를 받기 전까지 송신 측이 네트워크로 보낼 수 있는 데이터 양을 제한한다. `rwnd`가 수신 측의 수용 범위를 알려 준다면 `cwnd`는 네트워크 경로에 한 번에 주입할 양을 정한다.

둘은 이름에 윈도우가 들어간다는 점만 비슷하다. 실제 송신량에는 `rwnd`와 `cwnd` 중 더 작은 제한이 적용된다. 수신 버퍼에 여유가 많아도 경로가 혼잡하면 `cwnd`가 전송량을 줄인다. 반대로 네트워크가 여유로워도 수신 버퍼가 가득 차면 `rwnd`가 전송량을 막는다.

혼잡 제어의 기본 흐름으로 Slow Start와 Congestion Avoidance를 확인했다. Slow Start라는 이름 때문에 처음에는 천천히 증가한다고 생각했지만 실제로는 초기 ACK에 맞춰 `cwnd`가 빠르게 커진다. 이렇게 네트워크가 감당할 양을 탐색한 뒤 혼잡 회피 단계에서는 증가 폭을 완만하게 조절한다. 오늘은 이 두 단계의 흐름만 이해하고 임계값 계산이나 손실 이후의 세부 알고리즘은 다루지 않았다.

![흐름 제어와 혼잡 제어가 보호하는 대상](/assets/images/2026-10-27-tcp-control-udp/flow-congestion-control.svg)

*그림 1. `rwnd`는 수신 버퍼의 여유 공간을 기준으로 수신 측을 보호하고 `cwnd`는 네트워크 경로의 혼잡을 기준으로 전송량을 조절한다.*

## 4. UDP의 데이터그램과 헤더

UDP는 TCP처럼 연결을 사전에 수립하지 않는다. 애플리케이션이 보낸 메시지를 독립된 데이터그램으로 감싸 목적지를 향해 보낸다. IP 주소는 목적지 호스트를 가리키고 포트 번호는 그 호스트 안에서 데이터를 받을 애플리케이션을 구분한다. 두 정보를 함께 사용해 어느 호스트의 어떤 프로그램으로 데이터그램을 보낼지 정한다.

UDP 헤더는 총 8바이트다. 출발지 포트, 목적지 포트, 길이, 체크섬 네 필드가 각각 16비트씩 이어진다.

- 출발지 포트: 데이터를 보낸 애플리케이션의 포트다.
- 목적지 포트: 데이터를 받을 애플리케이션의 포트다.
- 길이: UDP 헤더와 데이터를 합친 전체 길이다. 헤더만 있어도 최소값은 8바이트다.
- 체크섬: 헤더와 데이터 등을 대상으로 오류를 검출하는 값이다. 오류를 검출하지만 전달 자체를 보장하지는 않는다.

![UDP 데이터그램의 8바이트 헤더](/assets/images/2026-10-27-tcp-control-udp/udp-header.svg)

*그림 2. UDP 헤더는 16비트 필드 네 개로 총 8바이트이며 `Length`는 헤더와 데이터 영역을 합친 길이를 가리킨다.*

UDP는 전달 확인이나 순서 보장을 기본으로 제공하지 않는다. 데이터그램이 목적지에 도착했는지 확인하는 일과 중복이나 순서 뒤바뀜을 처리하는 일은 애플리케이션에 맡겨진다.

이 특성은 최신 상태가 중요한 상황에서 의미가 있다. 오래된 데이터를 다시 받는 것보다 새 데이터를 처리하는 편이 낫다면 잃어버린 데이터의 재전송을 기본 동작으로 삼지 않는 UDP가 선택지다. 반대로 모든 데이터가 순서대로 도착해야 하거나 누락된 데이터를 반드시 복구해야 한다면 애플리케이션 계층에 확인 응답과 재전송을 추가하거나 TCP를 선택한다.

UDP가 언제나 TCP보다 빠르다고 단정할 수는 없다. 연결 수립과 전달 확인 같은 기능을 기본으로 포함하지 않으므로 애플리케이션이 필요한 기능을 직접 선택해 구성한다. UDP를 사용하는 애플리케이션은 신뢰성뿐 아니라 네트워크 혼잡에 대한 처리도 필요에 따라 고려해야 한다.

## 학습 과정에서 바뀐 이해

학습 초반에는 흐름 제어와 혼잡 제어를 모두 송신량을 줄이는 방법으로만 보았다. `rwnd`와 `cwnd`를 나란히 적은 뒤 각각의 기준을 확인하니 두 윈도우가 보호하는 대상이 달랐다. `rwnd`는 수신 버퍼의 여유 공간에서 출발하고 `cwnd`는 네트워크 경로의 혼잡에서 출발한다.

UDP도 TCP보다 빠른 프로토콜이라고만 생각하면 설명이 부족했다. UDP는 연결 없이 데이터그램을 전달하고 전달과 순서를 기본 보장하지 않는다. 최신 데이터가 중요한지, 누락된 데이터를 다시 받아야 하는지에 따라 선택 기준이 달라진다. 신뢰성이 필요하면 애플리케이션이 그 책임을 추가로 맡는다는 흐름까지 연결했다.

## 오늘의 정리

- `rwnd`는 수신 측 버퍼를 보호한다.
- `cwnd`는 네트워크 혼잡을 고려한다.
- UDP는 데이터그램을 전달하며 전달·순서 보장을 기본으로 제공하지 않는다.
- 전송 방식은 필요한 신뢰성과 데이터의 최신성에 따라 선택한다.

오늘은 TCP의 흐름 제어와 혼잡 제어가 같은 전송량 조절처럼 보여도 서로 다른 대상을 보호한다는 점을 정리했다. `rwnd`와 `cwnd`를 나누어 보니 수신 버퍼와 네트워크 경로를 별개의 문제로 설명할 수 있었다. UDP는 신뢰성을 기본 제공하지 않는 대신 데이터그램을 독립적으로 전달한다. 데이터의 최신성과 필요한 보장 수준을 함께 보고 전송 방식을 선택해야 한다.
