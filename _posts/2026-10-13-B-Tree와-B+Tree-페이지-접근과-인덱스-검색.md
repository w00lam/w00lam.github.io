이전에 [Trie — 같은 접두사를 공유하면서 단어와 접두사는 어떻게 구분할까?](/posts/trie-prefix-sharing-search/)를 공부하며 자료구조는 데이터의 모양과 필요한 연산에 따라 달라진다는 점을 정리했다. Trie가 문자열의 공통 접두사 경로를 공유한다면 오늘 공부한 B-Tree와 B+Tree는 대량의 데이터를 페이지 단위로 탐색해 검색 비용을 줄이는 데 초점이 맞춰져 있다.

처음에는 B-Tree를 “이진 탐색 트리보다 자식이 많은 트리”라고만 생각했다. 모의면접에서 질문을 따라가 보니 자식 수보다 중요한 것은 디스크나 SSD의 페이지 접근 횟수였다. 한 노드에 여러 키를 담고 모든 리프를 같은 깊이에 두는 규칙도 이 목적에서 이어졌다. 이 글에서는 B-Tree의 분할과 병합, B+Tree의 리프 연결, 페이지 방문과 실제 디스크 I/O의 차이, 데이터베이스 인덱스와 백엔드 개발의 연결을 기록한다.

## 이진 탐색 트리의 한계와 B-Tree가 필요한 이유

이진 탐색 트리는 한 노드가 최대 두 개의 자식을 가진다. 키의 대소 관계에 따라 왼쪽이나 오른쪽으로 이동하는 방식은 간단하다. 다만 삽입 순서가 한쪽으로 치우치면 트리의 높이도 함께 커진다. 균형이 무너지면 루트에서 리프까지 거의 모든 노드를 따라가야 하므로 검색 비용이 `O(log N)`에서 `O(N)` 수준까지 나빠질 수 있다.

데이터베이스 인덱스는 메모리에만 존재하지 않는다. 데이터와 인덱스는 디스크나 SSD에 페이지 단위로 저장되고 필요한 페이지를 메모리나 버퍼에 올리는 일은 메모리 참조보다 큰 비용이 들 수 있다. 키 하나를 찾더라도 페이지 단위로 읽게 되므로 한 번의 페이지 접근에서 더 많은 키를 확인하고 다음 방향을 정하는 편이 유리하다.

B-Tree가 필요한 이유는 다음 흐름으로 이어진다.

> 디스크 I/O 비용이 크다<br>
> → 한 번에 많은 키를 읽는 것이 유리하다<br>
> → 하나의 노드에 여러 키와 자식 포인터를 저장한다<br>
> → 트리 높이가 낮아진다<br>
> → 검색에 필요한 페이지 접근을 줄일 수 있다

B-Tree는 이진 탐색 트리를 다진 탐색 트리로 확장한 구조다. 하나의 노드가 여러 키와 자식 포인터를 가지며, 분할과 병합으로 균형을 유지한다. “자식이 많다”는 특징도 페이지에 정보를 많이 담아 트리 높이를 낮추려는 목적과 함께 봐야 한다.

## B-Tree의 구조와 검색 기준

B-Tree의 한 노드에는 정렬된 여러 키가 들어간다. 키가 `N`개라면 일반적으로 자식 포인터는 `N+1`개다. 키 사이의 빈 공간이 자식 서브트리의 탐색 범위를 나눈다. 내부 노드가 `[30 | 60]`이라면 왼쪽 자식은 30보다 작은 값, 가운데 자식은 30보다 크고 60보다 작은 값, 오른쪽 자식은 60보다 큰 값을 담당한다.

찾는 값이 왼쪽 경계보다 크고 오른쪽 경계보다 작다면 가운데 자식으로 이동한다. 내부 노드의 키는 저장된 값의 목록이 아니라 다음 페이지를 고르는 경계다. 한 페이지에서 여러 키를 비교한 뒤 필요한 서브트리 하나를 고르는 셈이다.

모든 리프 노드는 같은 깊이에 있다. 한 경로만 길어지는 것을 막아 검색 경로의 길이를 일정하게 유지하는 규칙이다. 루트는 트리가 아직 작을 때 다른 내부 노드와 같은 최소 키 개수 조건을 적용받지 않을 수 있다. 차수와 최소 키 개수를 부르는 방식은 구현과 교재마다 다르므로 공식을 사용할 때는 차수의 의미를 정한다. 여기서는 차수 `m`을 한 노드가 가질 수 있는 최대 자식 포인터 수로 부르고, 최대 키 수를 일반적으로 `m-1`로 설명한다. 최소 점유 조건은 구현이 정한 분할·병합 정책에 따라 달라질 수 있다.

B-Tree에서는 실제 데이터나 데이터에 접근하기 위한 정보가 내부 노드에 들어갈 수 있다. 검색 값이 내부 노드의 키와 정확히 일치하면 그 자리에서 데이터에 도달하는 구현도 있다. 이 점이 모든 검색을 리프까지 내려보내는 B+Tree와 갈라지는 기준이다.

처음에는 내부 노드의 키를 정렬된 값의 모음으로만 생각했다. 이제는 그 키가 자식 페이지의 경계를 표시하고 비교 결과가 다음 방문할 페이지를 정하는 인덱스 역할을 한다고 본다. 트리의 모양보다 페이지 탐색 경로가 우선 보이기 시작했다.

## B-Tree 삽입과 분할

새 키를 삽입할 때는 검색과 같은 기준으로 내려가 들어갈 리프 노드를 찾는다. 그 노드 안에서 키가 정렬된 위치에 들어간다. 노드가 허용된 최대 키 수를 초과하면 한 노드에 계속 쌓지 않고 분할한다.

분할은 다음 순서로 진행된다.

1. 새로운 키를 정렬된 위치에 삽입한다.
2. 최대 허용 개수를 초과했는지 확인한다.
3. 가운데 키를 부모 노드로 올린다.
4. 가운데 키보다 작은 나머지 키와 큰 나머지 키를 왼쪽과 오른쪽 노드로 나눈다.
5. 부모도 가득 차면 같은 분할을 부모 방향으로 반복한다.

가운데 키를 부모로 올리는 이유는 왼쪽과 오른쪽의 탐색 범위를 나눌 경계가 필요해서다. 부모에는 분할된 두 자식을 가리키는 포인터가 반영된다. 분할이 리프에서 끝나지 않고 루트까지 올라가면 루트도 둘로 나뉘고 그 위에 새 루트가 만들어진다.

루트만 있던 트리의 높이를 간선 수로 세면 처음 높이는 `0`이다. 루트가 분할되어 새 루트 아래에 두 자식이 생기면 높이는 `1`이 된다. 그 뒤에도 모든 경로가 같은 깊이를 유지하면서 높이가 늘어난다. 높이를 노드 수로 셀지 간선 수로 셀지는 구현이나 교재에 따라 다를 수 있어 여기서는 간선 수를 기준으로 삼았다.

노드가 가득 찰 때마다 전체 트리를 다시 정렬하는 것은 아니다. 문제가 생긴 노드를 쪼개고 부모의 경계를 조정하며 이 분할이 루트 방향으로 전파될 수 있다는 점이 삽입의 핵심이다.

## B-Tree 삭제와 재분배 및 병합

삭제에는 삽입보다 확인할 조건이 많다. 키를 지운 뒤 노드의 키 개수가 최소 조건보다 부족해지면 그대로 둘 수 없어 균형 회복이 필요하다.

형제 노드에 여유 키가 있는지부터 본다. 형제에서 키를 빌릴 수 있다면 부모의 경계 키와 형제의 키를 함께 조정하는 재분배를 수행한다. 형제 키 하나를 현재 노드로 복사하는 일이 아니라 부모가 두 서브트리 사이의 새 경계를 갖도록 바꾸는 과정이다.

형제 노드도 최소 조건에 가까워 빌려줄 키가 없으면 두 노드를 병합한다. 한쪽 노드의 키와 부모의 경계 키, 다른 쪽 노드의 키를 하나로 합친다. 부모의 키와 자식 포인터 하나가 줄어 부모가 최소 조건을 위반할 수 있으므로 병합이 부모 방향으로 이어질 수 있다.

오늘 모의면접에서는 삭제한 노드가 부족해졌으니 항상 형제에게서 하나를 빌리면 된다고 생각했다. 형제 노드에도 재분배할 여유 키가 없다는 조건을 확인한 뒤 병합을 선택했다. 삭제는 “키를 제거하는 작업”보다 “제거 후에도 각 노드의 조건을 유지하는 작업”으로 봐야 했다.

병합이 루트까지 이어져 루트의 키가 모두 아래로 내려가면 루트의 자식 하나가 새 루트가 될 수 있다. 이때 트리의 높이가 감소한다. 삽입의 루트 분할이 높이를 늘리고 삭제의 루트 병합이 높이를 줄이는 관계를 그림으로 확인했다.

## B+Tree의 구조와 리프 연결

B+Tree는 B-Tree에서 내부 노드와 리프 노드의 역할을 더 분리한 변형이다. 내부 노드는 검색 방향을 안내하는 인덱스 키와 자식 포인터를 저장하고 실제 데이터나 데이터에 접근하기 위한 정보는 리프 노드에 모인다.

검색 값이 내부 노드의 키와 같아도 검색을 끝내지 않는다. 그 키는 리프 노드로 내려가기 위한 경계일 수 있으므로 리프에 도달해 실제 항목을 확인한다. B-Tree에서는 내부 노드에 데이터가 있을 수 있지만 B+Tree에서는 일반적으로 리프 노드에 데이터가 모인다.

B+Tree의 리프 노드들은 서로 연결되어 있다. 시작 값이 들어 있는 리프를 찾은 뒤 다음 리프 포인터를 따라가며 정렬된 항목을 이어서 읽을 수 있다. `created_at`이 특정 범위에 들어오는 행을 찾거나 정렬된 순서로 여러 결과를 읽는 범위 검색에 잘 맞는다.

내부 노드에 실제 데이터가 없으면 같은 페이지에 더 많은 인덱스 키를 담을 수 있다. 노드 하나가 더 많은 자식 페이지를 가리키면 트리 높이를 낮추는 데 유리한 경우가 있다. 다만 특정 DBMS의 내부 구현을 확인하지 않은 채 모든 시스템에 그대로 적용할 수는 없다. B+Tree라는 개념과 실제 엔진의 페이지 구성 및 레코드 포인터 방식은 구분해서 본다.

## B-Tree와 B+Tree 비교

| 기준 | B-Tree | B+Tree |
| --- | --- | --- |
| 내부 노드 | 키와 데이터 또는 데이터 접근 정보를 함께 가질 수 있음 | 검색 방향을 정하는 인덱스 키 중심 |
| 실제 데이터 위치 | 내부 노드와 리프 노드에 있을 수 있음 | 일반적으로 리프 노드에 모임 |
| 정확한 일치 검색 | 내부 키에서 데이터에 도달할 수 있음 | 같은 키를 만나도 리프까지 내려가 확인 |
| 리프 연결 | 구현에 따라 다름 | 리프 노드를 연결해 순차 접근을 지원 |
| 범위 검색 | 가능하지만 구조에 따라 추가 이동이 필요함 | 시작 리프를 찾은 뒤 연결된 리프를 따라가기 쉬움 |

처음에는 두 구조의 차이를 “B+Tree는 B-Tree에 연결 리스트를 추가한 것”으로만 외웠다. 이제는 내부 노드에 데이터가 있는지, 모든 데이터가 리프에 모이는지, 리프 사이의 연결로 범위 검색을 이어갈 수 있는지를 기준으로 비교한다.

*그림 2. B-Tree는 내부 노드에서 데이터에 도달할 수 있지만 B+Tree는 내부 키를 따라 리프까지 내려간다. 연결된 리프는 범위 검색을 다음 페이지로 이어가는 통로가 된다.*

## 페이지 방문과 실제 디스크 I/O는 다르다

처음에는 루트와 내부 노드와 리프 노드를 방문하므로 페이지 방문 횟수와 디스크 읽기 횟수가 항상 같다고 생각했다. 실제로는 두 개념을 나눠 봐야 했다.

논리적인 페이지 방문 또는 인덱스 탐색 단계는 검색 경로에서 어떤 페이지를 확인했는지를 나타낸다. 실제 디스크 읽기는 필요한 페이지가 메모리나 데이터베이스 버퍼에 없어 저장장치에서 읽어오는 I/O다.

예를 들어 루트와 내부 노드는 이미 캐시에 있고 리프 페이지만 없다면 여러 페이지를 논리적으로 방문해도 실제 저장장치 읽기는 리프 페이지에서 발생하기도 한다. 필요한 페이지가 모두 캐시에 없으면 루트와 내부 노드와 리프에서 각각 읽기가 발생하기도 한다. 반복 검색에서는 앞선 요청이 올려 둔 페이지가 남아 있는지도 영향을 준다.

MySQL InnoDB의 버퍼 풀처럼 테이블과 인덱스 페이지를 메모리에 캐시하는 영역이 있는 DBMS에서는 캐시 상태가 실제 I/O에 영향을 준다. PostgreSQL의 `EXPLAIN (ANALYZE, BUFFERS)` 결과에서 `Buffers: shared hit=... read=...`처럼 버퍼 적중과 읽기를 구분해 보여주는 이유도 이 차이를 확인하기 위해서다. 트리 높이만큼 항상 디스크를 읽는다거나 페이지를 여러 개 방문했으니 디스크도 같은 횟수만큼 읽는다고 단정하면 안 된다.

B-Tree의 높이를 낮추는 목적과 실제 실행에서 발생하는 I/O를 연결하면서도 논리적인 탐색 비용과 캐시를 반영한 물리적 읽기 비용은 별도 계층으로 설명할 필요가 있다는 점을 교정했다.

## Hash와 B+Tree의 선택 기준

정확한 일치 검색만 필요하다면 Hash 구조를 후보로 고려한다. 해시 인덱스는 키에서 계산한 해시값으로 위치를 찾으므로 정렬된 순서나 범위의 시작과 끝을 따라가는 데에는 맞지 않는다. PostgreSQL 문서도 Hash 인덱스는 단순한 등가 비교를 처리하고 B-tree 인덱스는 정렬 가능한 데이터의 등가·범위 비교와 정렬된 결과에 활용된다고 설명한다.

정확한 검색은 무조건 Hash 인덱스가 더 빠르다고 결론 내리면 안 된다. PostgreSQL에서는 B-tree 인덱스가 기본 인덱스 방식이고 등가 검색도 지원한다. 실제 실행 계획은 DBMS와 스토리지 엔진의 구현, 데이터 분포, 통계 정보, 조건의 선택도, 테이블 크기와 캐시 상태에 따라 달라진다.

Java의 `HashMap`과 데이터베이스의 Hash 인덱스도 같은 것으로 묶지 않아야 한다. 둘 다 해시 원리를 사용할 수 있지만 하나는 애플리케이션 메모리에서 객체를 관리하는 컬렉션이고 다른 하나는 DBMS가 저장장치의 인덱스와 실행 계획을 관리하는 기능이다. 자료구조의 원리는 연결되지만 구현과 비용을 설명할 때는 경계를 둬야 한다.

오늘의 선택 기준은 다음과 같다.

- 키의 정확한 일치 여부만 확인하는 요구라면 Hash 기반 구조를 검토한다.
- 범위 검색이나 정렬된 순차 접근이 필요하다면 B+Tree와 같은 정렬 구조를 검토한다.
- 실제 데이터베이스에서는 인덱스 종류만 보고 결론 내리지 않고 실행 계획과 통계 및 캐시 상태를 함께 확인한다.

## 작은 SQL 예제와 `EXPLAIN`

실제 백엔드 개발에서는 인덱스 구조를 외우기보다 조회 조건과 인덱스 컬럼의 연결을 확인한다. 식당 목록을 생성 시각 순으로 조회하는 상황은 다음처럼 표현한다.

```sql
CREATE INDEX idx_restaurant_created_at
ON restaurant (created_at);

EXPLAIN
SELECT id, name, created_at
FROM restaurant
WHERE created_at BETWEEN '2026-01-01' AND '2026-01-31'
ORDER BY created_at;
```

`created_at`처럼 정렬 가능한 컬럼에 범위 조건을 사용하고 결과도 같은 컬럼으로 정렬하면 B-tree 계열 인덱스의 특성과 연결하기 쉽다. 인덱스를 만들었다고 항상 그 인덱스를 사용하는 것은 아니다. 옵티마이저가 데이터 분포와 조건의 선택도와 테이블 크기와 캐시 상태를 보고 실행 계획을 고르기 때문이다.

위 쿼리에서 실제로 인덱스 스캔이 선택됐다고 가정하지 않았다. 실행 결과를 확인하지 않았으므로 특정 계획이 나왔다고 쓰지 않는다. 실제 사용 여부와 예상 비용은 `EXPLAIN`으로 확인한다. 실행 중의 버퍼 적중과 읽기까지 보려면 DBMS가 지원하는 `EXPLAIN ANALYZE`와 버퍼 옵션을 환경에 맞게 검토한다.

인덱스는 조회를 빠르게 만들 수 있지만 쓰기 작업의 비용도 따른다. 행을 삽입하거나 수정하거나 삭제할 때 관련 인덱스 페이지도 갱신한다. 인덱스를 많이 만들수록 좋은 것이 아니므로 실제 조회 패턴과 읽기·쓰기 비율을 확인해 필요한 인덱스만 유지한다.

Spring Boot 애플리케이션에서 목록 조회 API를 설계할 때도 `WHERE` 조건과 범위 조건과 `ORDER BY`가 어떤 인덱스와 연결되는지 살펴본다. “인덱스가 있으니 빨라질 것”이라고 가정하지 않고 실제 실행 계획으로 검증해 백엔드 성능을 제대로 분석한다.

## 오늘의 정리

B-Tree는 이진 탐색 트리의 높이 문제와 페이지 단위 I/O 비용을 함께 고려한 다진 탐색 트리다. 한 노드에 정렬된 여러 키를 저장하고 키 사이의 경계로 자식 서브트리의 범위를 나눈다. 키가 `N`개면 일반적으로 자식 포인터는 `N+1`개이며 모든 리프 노드는 같은 깊이에 있다. 차수와 최소 키 수의 공식은 표기 방식이 다를 수 있으므로 차수의 의미부터 정의한다.

삽입으로 노드가 가득 차면 정렬된 위치에 키를 넣은 뒤 노드를 분할하고 가운데 키를 부모로 승격한다. 분할이 루트까지 올라가면 새 루트가 생기면서 높이가 증가하기도 한다. 삭제 후 키가 부족하면 형제에게 빌릴 수 있는지 확인하고 여유 키가 없으면 부모의 경계 키를 포함해 병합한다. 병합이 루트까지 이어지면 높이가 줄어들기도 한다.

B+Tree는 내부 노드에 검색 방향을 정하는 인덱스 키를 두고 실제 데이터 또는 접근 정보를 리프에 모으는 구조다. 내부 키와 검색 값이 같아도 리프까지 내려가야 한다. 리프가 서로 연결되어 있으므로 시작 위치를 찾은 뒤 범위와 정렬된 순차 접근을 이어가기 쉽다. 내부 노드에 데이터가 없기 때문에 더 많은 키를 담아 높이를 낮추는 데 유리한 경우가 있지만 실제 DBMS가 어떤 구조와 용어를 사용하는지는 공식 문서와 실행 계획으로 확인할 필요가 있다.

논리적으로 루트·내부·리프 페이지를 방문하는 횟수와 실제 저장장치에서 페이지를 읽는 횟수는 다르다. 필요한 페이지가 버퍼에 있으면 페이지를 방문해도 디스크 읽기 없이 처리되는 경우가 있고 캐시에 없는 페이지가 여러 개면 여러 I/O가 발생할 가능성도 있다. `EXPLAIN`의 버퍼 정보는 이 차이를 관찰하는 데 도움이 된다.

Hash는 정확한 일치 검색을 대상으로 고려하고 B+Tree는 범위 검색과 정렬된 접근에 연결하기 쉽다. 다만 실제 DBMS의 선택은 인덱스 종류 하나로 결정되지 않는다. 데이터 분포와 선택도와 통계와 캐시 상태를 확인해야 하며 Java `HashMap`과 데이터베이스 Hash 인덱스도 같은 구현으로 단정하지 않아야 한다.

오늘 B-Tree와 B+Tree를 공부한 목적은 트리 모양을 외우는 데 있지 않았다. 데이터베이스가 페이지와 인덱스를 이용해 검색 경로를 줄이고 캐시와 실행 계획에 따라 실제 비용을 달리 만든다는 원리를 이해하는 데 있었다. Spring Boot에서 목록 조회와 검색 조건을 설계할 때도 조회 성능만 보지 않고 인덱스 유지 비용까지 함께 판단한다.
