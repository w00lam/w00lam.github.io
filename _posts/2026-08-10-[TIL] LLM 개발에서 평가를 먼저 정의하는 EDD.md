LLM이나 RAG를 처음 개발할 때 자주 하는 말이 있다.

> "프롬프트를 조금 바꿨더니 더 좋아진 것 같다."

그런데 무엇이 좋아졌는지 설명하려고 하면 생각보다 어렵다. 답변이 자연스러워진 것 같기는 한데, 정확성이 좋아진 것인지, 사용자의 의도를 더 잘 반영한 것인지, 아니면 우연히 한두 개의 질문에 잘 답한 것인지 구분하기 어렵다.

이번에 **EDD(Evaluation-Driven Development)**를 처음 공부하면서, AI 기능은 기능을 만드는 것만큼이나 "좋은 결과를 어떻게 판단할 것인가"를 먼저 정하는 일이 중요하다는 점을 알게 됐다. 아직 처음 정리하는 단계인 만큼, 백엔드 개발자가 LLM·RAG·AI Agent를 적용할 때 어떤 식으로 평가를 붙여볼 수 있는지 중심으로 기록해본다.

## 1. 일반적인 테스트 방식만으로는 LLM을 평가하기 어렵다

일반적인 코드 테스트는 입력과 예상 결과를 비교하면 된다.

```text
입력: 1 + 1
예상 결과: 2
실제 결과: 2
→ PASS
```

하지만 LLM에게 같은 질문을 하면 정답이 하나의 문자열로만 나오지 않는다.

```text
A 식당은 조용한 분위기라 데이트 장소로 적합합니다.

A 식당은 소음이 적고 분위기가 차분해서 데이트하기 좋습니다.
```

두 문장은 문자열이 다르지만 의미는 비슷하다. 둘 다 좋은 답변일 수 있다. 반대로 문자열이 예상 답변과 같더라도 사실이 틀렸거나 사용자의 조건을 놓쳤을 수 있다.

그래서 LLM 시스템에서 단순히 `expected == actual`만 비교하면 문제가 생긴다.

- 표현은 다르지만 의미가 맞는 답변을 실패로 판단할 수 있다.
- 문장은 자연스럽지만 사실과 다른 답변을 통과시킬 수 있다.
- 질문의 핵심 조건을 놓쳐도 문체가 좋다는 이유로 높은 평가를 받을 수 있다.

LLM에서는 "정답 문장"보다 **정답이 갖춰야 할 조건**을 정의하는 일이 먼저 필요하다.

## 2. 맛집 추천으로 이해해보는 EDD

예제로 다음 요청을 사용해보자.

```text
강남에서 조용한 데이트 맛집 추천해줘.
```

이 요청에 대한 좋은 답변을 판단하려면 하나의 기준만으로는 부족하다.

```text
[지역 조건]
- 강남에 위치한 식당인가?

[사용자 의도]
- 조용한 분위기인가?
- 데이트 장소로 적합한가?

[사실성]
- 실제 존재하는 식당인가?
- 설명한 정보에 근거가 있는가?

[응답 품질]
- 이해하기 쉽고 자연스러운가?
```

만약 평가 기준이 "답변이 자연스러운가?" 하나뿐이라면 어떻게 될까. AI가 을지로에 있는 식당을 추천해도 설명이 매끄럽다는 이유로 높은 점수를 받을 수 있다. 사용자가 요구한 지역은 지키지 못했는데도 말이다.

즉 **평가 기준을 잘못 정하면 시스템도 잘못된 방향으로 최적화된다.**

EDD는 이런 문제의식에서 출발한다. 기능을 먼저 만들고 결과를 보며 막연히 판단하는 것이 아니라, 어떤 결과를 좋은 결과로 볼지 먼저 정의하고 그 기준을 개발 과정에서 사용한다.

## 3. EDD란 무엇인가

EDD의 개발 흐름을 정리하면 다음과 같다.

```text
좋은 결과 정의
→ 평가 데이터셋 구성
→ 평가 방법 정의
→ 현재 시스템 평가
→ 프롬프트 / RAG / Agent 수정
→ 다시 평가
→ 결과 비교
```

조금 더 풀어 말하면, **개선 여부를 측정할 수 있는 기준을 먼저 만들고 그 결과를 다음 개발 의사결정에 사용하는 방식**이다.

결과가 좋아 보인다는 느낌만으로 프롬프트를 계속 바꾸는 것이 아니라, 평가셋을 기준으로 변경 전후를 비교한다. 어떤 케이스는 좋아졌지만 다른 케이스는 나빠졌는지도 확인한다.

![TDD와 EDD 개발 사이클 비교](/assets/images/2026-08-10-edd/tdd-edd-cycle.png)

이 관점에서 EDD는 단순히 LLM 테스트를 많이 작성하는 방법이라기보다, **평가를 개발 사이클의 중심에 두는 방법**에 가깝다고 이해했다.

## 4. TDD와 EDD의 공통점과 차이

두 방법을 아주 단순하게 그리면 다음과 같다.

```text
TDD
Test → Code → Refactor

EDD
Eval → Build/Change → Evaluate → Improve
```

TDD와 EDD가 완전히 같은 방법론이라는 뜻은 아니다. 다만 둘 다 검증 기준을 개발 사이클의 마지막에 두지 않고 앞부분에 둔다는 사고방식이 비슷하다.

TDD에서는 테스트가 설계하려는 코드의 동작을 비교적 결정적인 형태로 표현한다. 예를 들어 특정 메서드가 `true`를 반환해야 한다거나, 저장 후 조회 결과가 같아야 한다는 식이다.

반면 EDD에서는 LLM 출력의 품질까지 봐야 한다. 출력이 매번 달라질 수 있고, 같은 의미를 여러 문장으로 표현할 수 있으며, 자연스러움이나 적절성처럼 주관적인 기준도 들어온다.

그래서 EDD의 `Eval`은 단순한 PASS/FAIL 테스트만을 뜻하지 않는다. 사실성은 코드로 확인하고, 답변의 관련성은 다른 LLM이나 사람이 평가하는 식으로 여러 평가 방법을 조합해야 한다.

## 5. 좋은 결과를 먼저 정의해야 하는 이유

AI 시스템을 만들 때 가장 먼저 프롬프트부터 작성하고 싶은 마음이 생긴다. 하지만 좋은 결과의 정의가 없으면 프롬프트 수정은 쉽게 감에 의존하게 된다.

예를 들어 맛집 추천 시스템의 목표가 다음과 같이 모호하다고 해보자.

```text
사용자가 좋아할 만한 맛집을 자연스럽게 추천한다.
```

이 문장만으로는 개선 여부를 판단하기 어렵다. 대신 다음처럼 조건을 쪼개볼 수 있다.

| 평가 항목 | 확인할 내용 |
| --- | --- |
| 지역 정확성 | 요청한 지역의 식당을 추천했는가? |
| 의도 반영 | 조용함, 데이트 등 핵심 조건을 반영했는가? |
| 사실성 | 실제 존재하는 식당과 정보를 사용했는가? |
| 근거성 | 추천 이유가 검색 결과나 데이터에 근거하는가? |
| 응답 품질 | 읽기 쉽고 과장 없이 설명하는가? |

이렇게 기준을 나누면 "프롬프트를 바꿔서 좋아졌다"를 조금 더 구체적으로 말할 수 있다. 지역 정확성은 유지됐고, 의도 반영 점수가 올랐는지 확인할 수 있기 때문이다.

이전에 [AI 결과를 어떻게 검증할 것인지 정리하면서](/posts/ai-developer-verification/) AI 시대에는 생산보다 검증의 비중이 커진다고 정리한 적이 있다. EDD는 그 검증 기준을 AI 기능 개발 안으로 더 구체적으로 가져오는 방법처럼 느껴졌다.

## 6. 평가 데이터셋은 정상 케이스만으로 만들지 않는다

평가 데이터셋, 즉 평가셋에는 실제 사용자가 물어볼 법한 질문을 모아둔다. 중요한 점은 정상적인 질문만 넣어서는 안 된다는 것이다.

```text
정상 케이스
- 강남에서 조용한 데이트 맛집 추천해줘.
- 성수에서 파스타 맛집 알려줘.

엣지 케이스
- 조건에 맞는 식당이 하나도 없는 경우
- DB에 해당 지역 데이터가 없는 경우
- 서로 충돌하는 조건을 요청하는 경우

환각 유도 케이스
- 존재하지 않는 식당의 주소를 알려달라고 요청
- 존재하지 않는 유튜버가 방문한 식당을 추천해달라고 요청
```

정상 케이스만 평가하면 시스템이 평소에는 그럴듯하게 답하는지만 확인하게 된다. 실제 서비스에서는 데이터가 비어 있을 수도 있고, 조건이 서로 충돌할 수도 있고, 사용자가 일부러 존재하지 않는 정보를 물어볼 수도 있다.

백엔드 테스트에서 예외 케이스를 빼면 운영 장애를 놓치기 쉬운 것과 비슷하다. LLM 평가셋에서도 실패하기 쉬운 입력을 일부러 넣어야 시스템의 약한 부분이 드러난다.

평가 케이스에는 질문만 저장할 수도 있지만, 가능하면 다음 정보도 함께 관리하는 편이 좋다.

- 기대하는 핵심 조건
- 반드시 포함되어야 하거나 포함되면 안 되는 정보
- 정답 근거가 되는 DB 레코드나 문서
- 평가 방식과 점수 기준
- 실패했을 때의 분류

처음부터 큰 데이터셋을 만들 필요는 없다. 작은 골든셋으로 시작해도 괜찮다. 대신 운영 중 발견한 실패를 계속 추가할 수 있는 구조여야 한다.

## 7. 평가 방법 세 가지

모든 평가를 하나의 방식으로 처리할 필요는 없다. 무엇을 판단할 수 있는지에 따라 평가 방법을 나누는 것이 현실적이다.

### 7.1 Deterministic Eval

코드나 데이터로 명확하게 판별할 수 있는 항목은 deterministic eval로 평가한다.

```text
추천한 식당이 강남에 있는가?
→ DB 주소와 비교

추천한 식당이 실제 존재하는가?
→ 식당 ID / DB 데이터 검증
```

이런 항목은 LLM에게 다시 판단하게 할 필요가 없다. DB 주소와 지역을 비교하면 되고, 식당 ID가 실제 데이터에 존재하는지 확인하면 된다.

객관적으로 검증 가능한 것을 굳이 LLM-as-a-Judge에 맡기면 비용과 비결정성이 추가된다. 따라서 먼저 코드로 판별할 수 있는 항목을 최대한 분리하는 것이 좋다.

### 7.2 LLM-as-a-Judge

코드만으로 판단하기 어려운 주관적인 품질은 다른 LLM에게 평가를 맡길 수 있다. 이를 LLM-as-a-Judge라고 한다.

```text
- 추천 이유가 사용자 의도와 관련 있는가?
- 데이트 장소로 적절한 추천인가?
- 답변이 자연스럽고 이해하기 쉬운가?
```

평가 프롬프트에 기준을 명시하고 1~5점이나 PASS/FAIL 형식으로 결과를 받는다. 예를 들어 지역 정확성과 사실성은 deterministic eval 결과를 전달하고, 추천 이유의 관련성만 Judge가 평가하도록 나눌 수도 있다.

다만 Judge 역시 LLM이다. 평가가 항상 정답이라고 볼 수 없고, 평가 프롬프트가 모호하면 점수가 흔들릴 수 있다. 특정 말투를 좋아하는 Judge를 사용하면 실제 품질보다 문체에 끌려갈 수도 있다.

그래서 Judge를 사용할 때도 평가 기준과 예시를 함께 제공하고, 일부 결과는 사람이 직접 비교해보는 과정이 필요하다.

### 7.3 Human Evaluation

사람이 결과를 직접 읽고 평가하는 방식도 있다. 자동화하기 어렵고 비용이 높지만, 실제 사용자가 느끼는 품질이나 복잡한 주관적 판단을 확인할 때 필요할 수 있다.

예를 들어 다음은 코드나 Judge만으로 완전히 판단하기 어려울 수 있다.

- 추천이 실제로 설득력 있게 느껴지는가?
- 답변이 지나치게 장황하거나 불친절하지 않은가?
- 사용자가 다음 행동을 결정하기에 충분한가?

결국 세 가지 중 하나만 선택하는 것이 아니라 조합하는 것이 현실적이다.

| 평가 대상 | 적합한 방법 |
| --- | --- |
| 지역, ID, 존재 여부 | Deterministic Eval |
| 관련성, 자연스러움 | LLM-as-a-Judge |
| 실제 만족도, 복잡한 UX | Human Evaluation |

## 8. RAG와 AI Agent는 단계별로 평가해야 한다

최종 답변만 보면 실패 원인을 찾기 어렵다. RAG나 AI Agent의 답변은 여러 단계를 거쳐 만들어지기 때문이다.

```text
사용자 질문
→ Retrieval
→ Context 구성
→ Tool Call
→ LLM 추론
→ 최종 답변
```

예를 들어 사용자가 다음과 같이 질문했다고 해보자.

```text
강남에서 조용한 데이트 맛집 추천해줘.
```

그런데 검색 결과가 아래처럼 나왔다고 하자.

```text
검색 결과:
성수 식당 A
마포 식당 B

LLM:
성수 식당 A를 추천
```

최종 답변은 잘못됐지만, LLM의 Generation만 문제라고 단정할 수 없다. 애초에 Retrieval이 강남 식당을 찾지 못한 것이 원인일 수 있다.

![RAG와 AI Agent 단계별 평가](/assets/images/2026-08-10-edd/rag-agent-eval-pipeline.png)

그래서 다음처럼 단계별로 평가할 필요가 있다.

```text
Retrieval Eval
→ 필요한 정보를 제대로 검색했는가?

Tool Eval
→ 올바른 Tool을 선택했는가?
→ 적절한 인자로 호출했는가?

Generation Eval
→ 제공된 Context를 근거로 답변했는가?

End-to-End Eval
→ 최종적으로 사용자 요구를 만족했는가?
```

이렇게 나누면 "AI 성능이 안 좋다"에서 멈추지 않고 실제 개발 작업으로 연결할 수 있다.

```text
Retrieval 문제
→ 검색 / 임베딩 / Chunk / Ranking 개선

Generation 문제
→ Prompt 또는 모델 개선

Tool 문제
→ Tool Selection / Parameter 구성 개선
```

이 부분은 이전에 [RAG의 핵심은 생성이 아니라 검색이라고 정리했던 글](/posts/rag-search-not-generation/)과도 이어진다. RAG에서는 최종 답변보다 먼저 어떤 근거를 가져왔는지가 중요하다. [청킹 전략을 비교하며](/posts/rag-chunking-length-vs-semantic/) 검색 단위를 어떻게 정하느냐가 결과에 영향을 준다고 정리했는데, EDD 관점에서는 청크와 검색 품질도 별도의 평가 대상이 된다.

또 [AI Agent의 실행 구조와 루프를 정리한 글](/posts/ai-agent-architecture-and-loop/)에서 본 것처럼 Agent는 Tool을 선택하고 결과를 다시 다음 판단에 사용한다. 따라서 최종 답변 하나만 평가하기보다 각 단계의 입력과 출력을 남겨야 어느 지점에서 문제가 시작됐는지 추적하기 쉽다.

## 9. 운영에서 발견한 실패를 다시 평가셋에 넣기

EDD는 오프라인 평가 한 번으로 끝나지 않는다. 운영 환경에서 발견한 실패를 평가셋에 추가하고, 수정 이후에도 같은 문제가 재발하지 않는지 확인해야 한다.

```text
운영 중 문제 발견

"마포 맛집을 물었는데
마포구가 아니라 마포역 근처 식당을 추천"

↓

해당 질문을 평가 데이터셋에 추가

↓

수정

↓

이후 변경에서도 동일한 문제가 다시 발생하는지 지속적으로 평가
```

일반 소프트웨어 개발의 회귀 테스트와 비슷하다. 한 번 발견된 버그를 다시 같은 방식으로 놓치지 않기 위해 테스트 케이스로 남기는 것이다.

다만 EDD에서는 평가 데이터셋 자체도 고정된 산출물이 아니다. 새로운 지역이 추가되고, 사용자의 질문 방식이 달라지고, 운영 중 새로운 실패가 발견되면 평가셋도 함께 발전해야 한다.

이 과정이 반복되면 평가셋은 단순한 샘플 모음이 아니라 서비스가 실제로 자주 실패하는 지점을 담은 기록이 된다.

## 10. EDD도 평가셋에 과적합할 수 있다

평가 점수가 올랐다고 실제 사용자 경험이 반드시 좋아지는 것은 아니다. 평가셋에만 맞춰 시스템을 개선하는 과적합이 생길 수 있다.

예를 들어 평가 데이터가 다음 질문에 집중되어 있다고 해보자.

```text
- 강남 데이트 맛집 추천
- 성수 파스타 맛집 추천
- 마포 고깃집 추천
```

이 케이스들에 맞춰 프롬프트와 검색 로직을 계속 조정하면 해당 질문에서는 점수가 좋아질 수 있다. 하지만 실제 사용자가 다음처럼 다르게 질문하면 성능이 떨어질 수 있다.

```text
친구랑 오래 이야기하기 좋고 너무 시끄럽지 않은 곳 있어?
```

또 평가 기준이 아래 세 가지뿐이라면 어떨까.

```text
- 지역 정확성
- 음식 카테고리 정확성
- 사실성
```

기술적으로는 높은 점수를 받더라도 추천 이유가 부족하거나 답변이 불친절해서 사용자가 만족하지 못할 수 있다.

따라서 Eval은 절대적인 정답이 아니라 **실제 품질을 측정하기 위한 근사 지표**라고 이해해야 한다. 평가셋을 넓히고, 실제 사용자 피드백과 비교하고, 사람이 직접 결과를 확인하는 과정이 필요한 이유다.

## 11. 실제 운영 흐름

EDD를 운영 흐름으로 그리면 다음과 같다.

```text
Offline Eval
↓
Prompt / RAG / Agent 개선
↓
배포
↓
실제 사용자 피드백 / 실패 사례 확인
↓
새로운 평가 케이스 추가
↓
Eval 개선
↓
다시 개발
```

![EDD 운영 피드백 루프](/assets/images/2026-08-10-edd/edd-production-feedback-loop.png)

여기서 중요한 점은 AI 시스템만 개선하는 것이 아니라 **평가 체계 자체도 계속 개선한다는 것**이다. 처음 만든 평가 기준이 모든 사용자 경험을 설명해주지는 않는다. 그래서 새로운 실패가 발견되면 시스템을 고치는 동시에, 다음부터 그 실패를 감지할 수 있도록 평가셋과 기준도 보완해야 한다.

## 이번 학습을 통해 느낀 점

처음에는 EDD를 단순히 "LLM 테스트를 많이 작성하는 방법"이라고 생각할 수 있었다. 그런데 실제로는 좋은 결과를 먼저 정의하고, 그 기준을 개발 과정에 사용하는 방식이라는 점이 인상적이었다.

일반적인 백엔드 개발에서는 테스트의 성공과 실패가 비교적 명확했다. 반면 LLM에서는 "좋은 답변" 자체를 정의하는 일이 하나의 개발 작업이 된다. 맛집 추천 예시만 봐도 자연스러운 문장인지뿐 아니라 지역, 의도, 사실성, 근거를 함께 봐야 했다.

특히 RAG나 AI Agent에서는 최종 답변만 평가하면 문제를 실제 개발 작업으로 연결하기 어렵다. Retrieval, Tool Call, Generation을 나누어 평가해야 검색 문제인지, Tool 선택 문제인지, 프롬프트나 모델 문제인지 구분할 수 있다는 점이 중요하게 느껴졌다.

Eval도 완벽한 정답은 아니다. 평가 점수가 올라가도 평가셋에만 맞춘 결과일 수 있고, 실제 사용자가 느끼는 불편을 놓칠 수 있다. 그래서 운영 중 발견한 실패 사례와 사용자 피드백을 계속 반영해야 한다고 이해했다.

앞으로 AI 기능을 구현한다면 프롬프트를 먼저 계속 수정하기보다, 어떤 결과를 좋은 결과라고 볼 것인지와 그것을 어떻게 측정할지부터 고민해보고 싶다. 아직 EDD를 처음 학습한 단계지만, AI 기능도 결국 기준을 세우고 검증하면서 조금씩 개선해가는 개발이라는 점은 분명하게 배웠다.

## 오늘의 정리

- LLM은 정답 문자열이 하나가 아니므로 `expected == actual`만으로 품질을 판단하기 어렵다.
- EDD는 좋은 결과와 평가 기준을 먼저 정의하고, 그 결과를 개발 의사결정에 사용하는 방식이다.
- TDD와 EDD는 검증 기준을 개발 사이클 앞부분에 둔다는 점에서 비슷하지만, EDD는 비결정적이고 주관적인 출력까지 평가해야 한다.
- 평가셋에는 정상 케이스뿐 아니라 엣지 케이스와 환각 유도 케이스도 포함해야 한다.
- 코드로 확인할 수 있는 것은 Deterministic Eval으로, 주관적인 품질은 LLM-as-a-Judge나 Human Evaluation으로 평가한다.
- RAG와 AI Agent는 Retrieval, Tool, Generation, End-to-End를 나누어 평가해야 실패 원인을 실제 개발 작업으로 연결할 수 있다.
- 운영에서 발견한 실패는 평가셋에 다시 추가해야 하며, 평가 체계 자체도 계속 개선해야 한다.
- Eval 점수는 실제 품질의 근사 지표이므로 평가셋 과적합과 지표의 한계를 함께 경계해야 한다.
