## 1. 상속을 다시 공부하게 된 이유

Java에서 상속(Inheritance)은 보통 `extends`를 사용해 부모 클래스의 필드와 메서드를 자식 클래스가 물려받는 문법이라고 배운다. 이 설명은 문법을 이해하는 데는 도움이 되지만, 실제 설계에서 상속을 사용할지 판단하는 기준으로는 부족하다.

클래스 두 개에 비슷한 코드가 있다고 해서 바로 상속을 적용하면 안 된다. 상속은 공통 코드를 재사용하는 방법이면서 동시에 두 클래스 사이에 강한 관계를 만드는 선택이기 때문이다.

오늘은 다음 질문을 중심으로 상속을 정리해 보았다.

> 이 클래스들은 단지 코드가 비슷한가? 아니면 자식 객체가 정말 부모 객체의 한 종류인가?

## 2. 상속이란 무엇인가

`extends`는 자식 클래스가 부모 클래스의 특성을 바탕으로 확장된 타입임을 선언하는 키워드다. 부모 클래스는 공통 상태와 행동을 정의하고, 자식 클래스는 그것을 사용하거나 자신에게 필요한 상태와 행동을 추가할 수 있다.

예를 들어 일반 사용자와 관리자 사용자를 다음처럼 표현할 수 있다.

```java
public class User {

    private final String name;

    public User(String name) {
        this.name = name;
    }

    public String getName() {
        return name;
    }

    public void printName() {
        System.out.println(name);
    }
}
```

```java
public class AdminUser extends User {

    public AdminUser(String name) {
        super(name);
    }

    public void deleteUser(User user) {
        System.out.println(getName() + "이(가) " + user.getName() + "을(를) 삭제합니다.");
    }
}
```

이 관계에서 `AdminUser is a User`가 자연스럽다. 관리자는 사용자이므로 `AdminUser`를 `User`가 필요한 곳에 전달할 수 있고, 사용자에게 공통인 이름 출력 같은 행동도 수행할 수 있다.

```java
User user = new AdminUser("관리자");
user.printName();
```

이처럼 상속은 공통 기능을 물려주는 것뿐 아니라 “자식 타입은 부모 타입으로도 취급할 수 있다”는 관계를 표현한다. 따라서 `extends`를 다음과 같이 이해하면 좋다.

> 자식 클래스는 부모 클래스의 코드를 재사용하는 클래스이면서, 부모 타입의 한 종류로 대체될 수 있는 클래스다.

두 클래스에 `name` 필드나 `print()` 메서드가 공통으로 존재한다는 이유만으로 상속해야 하는 것은 아니다. 공통 코드를 공유하는 목적만 있다면 컴포지션(Composition), 즉 필요한 객체를 필드로 가지고 위임하는 방법이 더 적절할 수도 있다.

## 3. 상속받은 멤버를 자식 클래스에서 사용하는 방법

자식 클래스가 부모 클래스를 상속했다고 해서 부모의 모든 멤버에 직접 접근할 수 있는 것은 아니다. 접근 가능 여부는 멤버에 지정된 접근 제어자와 패키지 위치에 따라 달라진다.

| 접근 제어자 | 같은 클래스 | 같은 패키지 | 다른 패키지의 자식 클래스 | 다른 패키지의 일반 클래스 |
| --- | --- | --- | --- | --- |
| `public` | 가능 | 가능 | 가능 | 가능 |
| `protected` | 가능 | 가능 | 가능 | 불가능 |
| package-private | 가능 | 가능 | 불가능 | 불가능 |
| `private` | 가능 | 불가능 | 불가능 | 불가능 |

### `public`

어디서든 접근할 수 있다. 자식 클래스에서도 당연히 사용할 수 있지만, `public`으로 공개된 멤버는 상속 관계가 없는 외부 코드도 의존할 수 있다는 점을 고려해야 한다.

### `protected`

같은 패키지에서는 일반 클래스도 접근할 수 있고, 다른 패키지에서는 자식 클래스가 상속을 통해 사용할 수 있다. 따라서 `protected`는 자식 클래스의 확장을 염두에 둔 접근 범위다.

다만 다른 패키지의 자식 클래스에서는 아무 부모 객체의 `protected` 멤버를 마음대로 참조할 수 있는 것은 아니다. 상속받은 자신의 인스턴스나 `super`를 통한 접근처럼, 자식 관계를 통한 접근이라는 제약이 있다.

### package-private

접근 제어자를 생략하면 package-private이 된다. 같은 패키지 안에서는 접근할 수 있지만 다른 패키지에서는 접근할 수 없다. 자식 클래스라도 다른 패키지에 있다면 직접 사용할 수 없다.

```java
class User {
    String email; // package-private
}
```

`AdminUser`가 `User`와 같은 패키지에 있다면 `email`을 직접 사용할 수 있지만, 패키지가 다르면 사용할 수 없다. 이 접근 범위는 상속 관계보다 패키지 경계가 우선한다.

### `private`

선언된 `User` 클래스 내부에서만 접근할 수 있다. `private` 필드도 하나의 자식 객체 안에서 부모 클래스가 담당하는 상태로 초기화되지만, 자식 클래스는 그 필드에 직접 접근하거나 이름으로 사용할 수는 없다.

```java
public class User {
    private String password;
}

public class AdminUser extends User {
    public void changePassword() {
        // password = "new-password"; // 컴파일 오류
    }
}
```

부모가 필요한 기능을 `public` 또는 `protected` 메서드로 제공한다면 자식은 그 메서드를 통해 상태를 다룰 수 있다. 예를 들어 비밀번호 검증이나 변경 규칙은 `User` 내부에 두고, 자식 클래스가 필드를 직접 조작하지 않게 만들 수 있다.

결국 “상속받았다”와 “직접 접근할 수 있다”는 같은 말이 아니다. 상속은 타입과 객체 구조의 관계를 만들고, 접근 제어자는 그 관계 안에서 어떤 구현을 직접 사용할 수 있는지를 제한한다.

## 4. 부모 생성자와 자식 생성자의 실행 흐름

다음과 같은 상속 관계를 생각해 보자.

```java
class User {
    User() {
        System.out.println("User");
    }
}

class AdminUser extends User {
    AdminUser() {
        System.out.println("AdminUser");
    }
}

class SuperAdminUser extends AdminUser {
    SuperAdminUser() {
        System.out.println("SuperAdminUser");
    }
}
```

`new SuperAdminUser()`를 실행하면 다음 순서로 출력된다.

```text
User
AdminUser
SuperAdminUser
```

### 자식 생성자의 첫 줄에는 `super()`가 들어갈 수 있다

각 생성자의 첫 줄에 `super()`를 직접 작성하지 않았지만, Java 컴파일러는 자식 생성자의 첫 문장에 부모의 기본 생성자를 호출하는 `super()`를 암묵적으로 삽입할 수 있다.

개념적으로 코드는 다음과 비슷하게 동작한다.

```java
class AdminUser extends User {
    AdminUser() {
        super(); // 생략되어 있음
        System.out.println("AdminUser");
    }
}

class SuperAdminUser extends AdminUser {
    SuperAdminUser() {
        super(); // 생략되어 있음
        System.out.println("SuperAdminUser");
    }
}
```

따라서 `new SuperAdminUser()`는 가장 가까운 부모인 `AdminUser`의 생성자를 먼저 호출하고, `AdminUser` 생성자는 다시 `User`의 생성자를 먼저 호출한다. `User()`가 끝난 뒤 `AdminUser()`가 실행되고, 마지막으로 `SuperAdminUser()`의 본문이 실행된다.

### 생성자는 상속되지 않는다

`User()`가 `AdminUser`에 물려받아 복사되는 것은 아니다. 생성자는 클래스의 인스턴스를 초기화하기 위한 특별한 호출 규칙이며, 일반 메서드처럼 자식 클래스에 상속되지 않는다.

자식 생성자가 부모 생성자를 호출하는 것은 생성자를 상속받아서 사용하는 것이 아니라, 자식 객체가 만들어질 때 부모 클래스가 맡은 초기화 작업도 먼저 수행하도록 요청하는 것이다.

부모에게 기본 생성자가 없으면 암묵적인 `super()`를 사용할 수 없다.

```java
class User {
    User(String name) {
        // 이름 초기화
    }
}

class AdminUser extends User {
    AdminUser(String name) {
        super(name); // 부모 생성자를 명시해야 함
    }
}
```

`User`에 매개변수 없는 생성자가 없는데 `super(name)`까지 생략하면 컴파일 오류가 발생한다. 부모 상태를 어떻게 초기화할지 자식 생성자가 명확히 결정해야 하기 때문이다.

### 부모 객체가 별도로 하나 더 생성되는 것은 아니다

`new SuperAdminUser()`를 실행할 때 `SuperAdminUser` 객체와 별개의 `User` 객체가 각각 생성되는 것은 아니다. 하나의 `SuperAdminUser` 객체가 만들어지고, 그 객체 안에서 부모 클래스가 담당하는 상태와 자식 클래스가 담당하는 상태가 순서대로 초기화된다고 이해하면 된다.

```text
하나의 SuperAdminUser 객체
├─ User가 담당하는 부분 초기화
├─ AdminUser가 담당하는 부분 초기화
└─ SuperAdminUser가 담당하는 부분 초기화
```

실제 메모리 배치는 JVM 구현의 세부 사항이므로 위 구조를 물리적인 메모리 블록으로 단정할 필요는 없다. 중요한 점은 `super()`가 새로운 부모 객체를 만드는 명령이 아니라, 하나의 자식 객체에 포함된 부모 클래스 영역을 초기화하기 위한 생성자 호출이라는 것이다.

부모부터 초기화하는 이유는 자식이 부모의 상태와 기능을 바탕으로 동작하기 때문이다. 부모가 제공하는 필드와 불변식이 준비되지 않은 상태에서 자식의 초기화를 먼저 실행하면 자식 코드가 의존하는 기반이 아직 만들어지지 않을 수 있다. 그래서 Java는 부모 → 자식 순서로 생성자 실행 흐름을 보장한다.

## 5. `super`와 `super()`는 어떻게 다른가

둘은 비슷하게 보이지만 역할이 다르다.

### `super`

`super`는 현재 클래스의 바로 부모 클래스 부분을 가리키는 참조처럼 사용한다. 부모의 필드나 메서드에 접근할 때 쓸 수 있다.

```java
super.name;
super.printName();
```

예를 들어 자식 클래스에서 같은 이름의 필드를 다시 선언했다면 `name`은 자식 필드를 의미하고, `super.name`은 부모 필드를 의미한다. 단, 부모 필드가 `private`이라면 자식 클래스에서 `super.name`으로 접근할 수 없다.

부모 메서드의 구현을 명시적으로 호출할 때도 사용할 수 있다.

```java
class User {
    public void printRole() {
        System.out.println("User");
    }
}

class AdminUser extends User {
    @Override
    public void printRole() {
        super.printRole();
        System.out.println("Admin");
    }
}
```

`super.printRole()`는 현재 객체를 새로 만드는 것이 아니라, 현재 객체에 대해 부모 클래스의 `printRole()` 구현을 호출한다.

### `super()`

`super()`는 부모 클래스의 생성자를 호출하는 생성자 호출문이다. 생성자 안에서 첫 번째 문장으로만 사용할 수 있다.

```java
public AdminUser(String name) {
    super(name);
    // 자식 클래스의 초기화
}
```

괄호 안에 전달하는 값에 따라 부모 생성자 오버로딩 중 하나를 선택한다. `super`가 부모의 멤버를 가리키는 표현이라면, `super()`는 부모 생성자를 실행해 부모 부분의 초기화를 요청하는 표현이다.

## 6. 상속의 장점과 위험성

상속의 가장 분명한 장점은 공통 코드를 한곳에 둘 수 있다는 점이다. `User`의 이름 검증이나 공통 인증 동작을 여러 사용자 타입에서 재사용할 수 있고, 부모 타입을 사용하는 코드에서 자식 타입을 다형적으로 처리할 수도 있다.

```java
public void printUserName(User user) {
    user.printName();
}

printUserName(new User("일반 사용자"));
printUserName(new AdminUser("관리자"));
```

하지만 상속은 자식이 부모의 구현에 의존하게 만드는 구조이기도 하다.

### 부모 클래스 변경이 자식 클래스에 영향을 줄 수 있다

부모 메서드의 동작, 필드의 의미, 생성자 규칙을 바꾸면 이를 상속하던 자식 클래스의 동작이 함께 바뀔 수 있다. 부모의 내부 구현 변경이 자식에게 예상하지 못한 영향을 주는 “취약한 기반 클래스” 문제가 생길 수 있다.

### 부모와 자식 사이의 결합도가 높아진다

자식 클래스는 부모의 메서드 동작과 초기화 순서, 접근 가능한 상태에 의존한다. 부모와 자식은 독립적으로 변경하기 어렵고, 한쪽의 수정이 다른 쪽의 테스트와 배포에도 영향을 줄 수 있다.

### 상속 계층이 깊어질수록 이해하기 어렵다

메서드가 현재 클래스에 있는지, 부모에 있는지, 더 위 부모에 있는지 따라가야 한다. 오버라이딩까지 많아지면 실제 실행되는 구현을 파악하기 어렵고, 생성자 호출 순서와 상태 초기화 책임도 복잡해진다.

### 코드가 비슷하다는 이유만으로 상속하면 안 된다

`Report`와 `Invoice`가 모두 `print()` 메서드를 가진다고 해서 둘 중 하나가 다른 하나의 종류가 되는 것은 아니다. 단순히 필드와 메서드가 겹친다는 이유만으로 상속하면, 재사용은 얻더라도 의미가 맞지 않는 타입 관계를 만들게 된다.

상속을 적용하려면 자식 객체가 부모 객체로 대체되어도 부모를 사용하는 코드의 기대를 깨뜨리지 않는지 함께 확인해야 한다. 이것은 객체지향 설계에서 말하는 치환 가능성(Liskov Substitution Principle)과도 연결된다.

## 7. 상속을 사용할 때의 판단 기준

상속을 고민할 때 다음 질문을 먼저 던져 보려고 한다.

> “공통 코드가 있는가?”보다 “이 객체가 정말 부모 객체의 한 종류인가?”

예를 들어 다음 관계는 비교적 자연스럽다.

```text
AdminUser is a User
```

관리자는 사용자이므로 사용자 목록에 포함될 수 있고, 사용자에게 기대하는 기본 행동을 수행할 수 있다. 이때 관리자의 추가 권한이나 관리자 전용 행동을 `AdminUser`에 확장하는 것은 도메인 관계와 코드 구조가 함께 맞아떨어질 가능성이 있다.

반대로 `User`와 `EmailSender`가 모두 `name`이나 `send()`와 비슷한 메서드를 가진다고 해서 `EmailSender extends User`라고 표현할 수는 없다. 이메일 발송기는 사용자가 아니라 사용자를 도와주는 별도의 기능 객체다.

이 경우에는 컴포지션이 더 자연스럽다.

```java
public class UserService {

    private final EmailSender emailSender;

    public UserService(EmailSender emailSender) {
        this.emailSender = emailSender;
    }

    public void sendWelcomeEmail(User user) {
        emailSender.send(user.getName());
    }
}
```

`UserService`는 `EmailSender`를 상속하지 않고 필요한 객체를 내부에 가지고 사용한다. 이렇게 하면 두 객체가 “같은 종류”라는 관계를 만들지 않으면서도 기능을 재사용할 수 있다. 구성 요소를 교체하거나 각각 독립적으로 테스트하기에도 유리하다.

따라서 상속은 다음 조건을 함께 만족할 때 신중하게 선택할 수 있다.

* 자식이 부모의 한 종류라는 관계가 도메인에서 자연스럽다.
* 자식이 부모 타입을 사용하는 코드에 안전하게 대체될 수 있다.
* 부모의 변경에 함께 영향을 받아도 되는 강한 결합이 존재한다.
* 부모가 제공하는 공통 상태와 행동이 자식의 책임과 실제로 연결된다.

재사용이 유일한 목적이라면 먼저 컴포지션과 위임을 검토하는 편이 좋다.

## 8. 오늘 학습하면서 바로잡은 오해

### 자식 객체를 만들면 부모 객체도 하나 더 만들어진다?

그렇지 않다. `new SuperAdminUser()`는 하나의 객체를 생성한다. 그 객체를 초기화하는 과정에서 부모 생성자와 자식 생성자가 차례로 실행될 뿐, 별도의 `User` 객체가 추가로 만들어지는 것은 아니다.

### 생성자는 자식 클래스에 상속된다?

생성자는 상속되지 않는다. 자식 생성자가 `super()` 또는 `super(arguments)`를 통해 부모 생성자를 명시적으로 호출하거나, 조건이 맞으면 컴파일러가 암묵적인 `super()`를 넣어 부모 초기화를 요청하는 것이다.

### 자식 클래스는 부모의 모든 필드에 직접 접근할 수 있다?

그렇지 않다. `public`은 접근할 수 있지만, `protected`는 패키지와 상속 관계에 따른 조건이 있고 package-private은 같은 패키지에서만 접근할 수 있다. `private`은 부모 클래스 내부에서만 직접 접근할 수 있다.

### 상속은 단순한 코드 재사용 기능이다?

상속은 부모와 자식 사이에 타입 관계와 높은 결합도를 만든다. 공통 코드를 재사용할 수 있다는 장점보다, 그 관계가 도메인에서 자연스럽고 장기적으로 유지할 만한지 먼저 판단해야 한다.

## 9. 오늘의 핵심 정리

* `extends`는 공통 코드를 재사용하는 문법인 동시에 자식이 부모의 한 종류임을 표현하는 타입 관계다.
* 상속받았다고 부모의 모든 멤버에 직접 접근할 수 있는 것은 아니며, 접근 제어자와 패키지 경계가 접근 범위를 결정한다.
* 생성자는 상속되지 않고, 자식 생성자의 `super()` 호출을 통해 부모 → 자식 순서로 하나의 객체가 초기화된다.
* `super`는 부모 멤버를 가리키고, `super()`는 부모 생성자를 호출한다.
* 코드가 비슷하다는 이유만으로 상속하지 말고, `is-a` 관계가 자연스러운지 먼저 판단하며 재사용만 필요하면 컴포지션을 검토한다.

오늘은 상속을 “부모 코드를 물려받는 기능”으로만 보던 관점에서 벗어나, 클래스 사이에 강한 관계를 만드는 설계 선택으로 이해하게 되었다. 앞으로는 `extends`를 작성하기 전에 자식 객체가 정말 부모 객체로 대체될 수 있는지, 그리고 부모와의 결합을 감당할 이유가 있는지 먼저 확인하려고 한다.
