프로세서는 메모리에서 명령어를 가져오고 그 명령어에 따라 연산을 수행한다. 이전에 [컴퓨터 구성 요소와 CPU의 명령어 처리 과정 — 주소와 실제 값은 왜 다를까?](/posts/computer-architecture-cpu-instruction-flow/)를 공부하면서 명령어 인출과 해석의 큰 흐름을 확인했다. 오늘은 그 명령어를 어떤 규칙으로 이해하는지와 이 규칙이 실행 환경의 호환성에 어떻게 이어지는지를 살펴봤다.

전날에는 데이터를 어떻게 표현하고 오류를 어떻게 검출하는지 확인했다. 오늘은 한 단계 더 아래로 내려가 프로세서가 이해하는 명령어의 규칙을 붙잡았다. 처음에는 다음 질문에 답을 한꺼번에 섞어 생각했다.

- x86과 ARM은 무엇이 다른가?
- 같은 ISA를 사용하는 CPU는 내부 구조도 같은가?
- Java는 플랫폼 독립적이라고 하는데 JVM도 어떤 환경에서나 실행되는가?
- x86에서 만든 같은 JAR을 ARM 서버에서 실행할 수 있는가?
- Docker로 묶으면 CPU 아키텍처 차이도 사라지는가?

실제 프로젝트에서 사용하는 ARM 기반 t4g 서버와도 이어지는 주제다. 다만 오늘 서버를 이전하거나 성능을 측정한 것은 아니다. 오늘 확인한 것은 실행 호환성을 판단하는 기준과 앞으로 이전할 때 확인할 항목이다.

## 프로세서가 명령어를 이해하려면 약속이 필요하다

프로세서는 메모리에서 명령어를 가져온다. 제어장치는 명령어를 해석하고 필요한 연산을 ALU 등에 지시한다. 레지스터의 값을 사용해 연산한 뒤 결과를 다시 레지스터나 메모리에 저장한다.

이 흐름만 보면 CPU가 명령어를 해석하는 일은 당연해 보인다. 하지만 소프트웨어가 만든 명령어와 하드웨어가 실행하는 동작 사이에는 공통의 약속이 필요하다.

> CPU가 명령어를 해석하려면 소프트웨어와 하드웨어 사이에 어떤 약속이 필요할까?

이 질문에 대한 답이 ISA다. ISA는 프로세서가 제공하는 명령어와 각 명령어의 동작, 레지스터와 메모리를 다루는 규칙을 정의한다. 컴파일러나 운영체제 같은 소프트웨어는 이 규칙을 전제로 실행할 프로그램을 만든다. CPU는 같은 규칙에 따라 명령어를 해석한다.

즉 프로세서가 명령어를 처리한다는 말은 단순히 전기 신호를 계산한다는 뜻이 아니다. 소프트웨어가 기대하는 명령어 체계와 하드웨어가 실제로 수행하는 동작이 같은 규칙을 공유한다는 뜻도 포함한다.

## ISA가 같아도 CPU의 내부 구현은 다를 수 있다

처음에는 ISA를 CPU의 내부 구조 전체라고 생각했다. ISA가 같으면 레지스터 구성과 연산 속도까지 비슷할 것이라고 예상했다. 다시 나누어 보니 ISA와 CPU 구현은 서로 다른 층위에 있었다.

| 구분 | 확인하는 내용 |
| --- | --- |
| ISA | 어떤 명령어와 동작을 소프트웨어에 제공하는가 |
| CPU 구현 | 그 명령어를 실제 하드웨어에서 어떻게 수행하는가 |

ISA는 소프트웨어와 프로세서 사이의 인터페이스에 가깝다. 같은 ISA를 지원하는 CPU라도 내부 구조와 성능은 다를 수 있다. 어떤 설계는 같은 명령어를 더 적은 전력으로 처리하고 다른 설계는 특정 작업의 처리량에 초점을 둔다.

x86-64와 ARM64는 서로 다른 ISA 계열이다. 따라서 x86-64용 네이티브 실행 파일과 ARM64용 네이티브 실행 파일은 CPU가 이해하는 명령어 체계부터 다르다. 반대로 ISA가 같다는 사실만으로 프로그램 전체의 실행 호환성을 보장할 수도 없다. 운영체제와 실행 파일 형식, 필요한 라이브러리까지 확인해야 한다.

Arm은 아키텍처를 설명하면서 이를 하드웨어와 소프트웨어 사이의 계약으로 표현한다. [Arm Architecture](https://www.arm.com/architecture)에서 말하는 아키텍처의 역할을 이 계약이라는 관점으로 이해하면 ISA와 CPU 구현을 구분하기 쉬워진다.

## RISC와 CISC를 성능 순위로 읽지 않기

RISC와 CISC는 ISA를 이해하는 출발점으로 삼는 설계 방향이다.

- RISC는 비교적 단순하고 규칙적인 명령어 구성을 지향한다.
- CISC는 복잡한 작업을 표현하는 다양한 명령어 구성을 지향한다.

이 설명만 보고 RISC는 무조건 빠르고 CISC는 무조건 느리다고 결론 내리면 안 된다. 명령어 하나가 복잡한지 단순한지만으로 실제 처리 성능을 정할 수도 없다. 현대 CPU는 ISA를 실제로 수행하는 여러 하드웨어 설계를 사용하고 실행하는 작업도 서로 다르다.

ARM과 x86을 비교할 때 RISC와 CISC는 두 계열의 설계 방향을 이해하는 데 도움을 준다. 그러나 실제 성능과 전력 효율은 CPU 구현과 작업의 종류에 따라 확인해야 한다. 오늘은 마이크로 연산이나 파이프라인 내부 동작까지 확장하지 않았다.

## Arm이라는 회사와 ARM 프로세서는 같은 말이 아니다

학습 중에는 Arm이라는 회사를 ARM 프로세서와 같은 의미로 사용했다. 이 표현은 아키텍처와 실제 제품의 관계를 흐리게 만든다.

Arm은 아키텍처와 프로세서 IP를 설계하고 라이선스를 제공한다. 이를 사용하는 기업은 제공받은 IP를 활용하거나 라이선스 범위에 따라 자체 프로세서를 설계하기도 한다. 실제 칩의 설계와 제조는 참여 기업의 역할에 따라 구분된다.

따라서 모든 ARM 프로세서를 Arm이 직접 제조한다고 말하면 안 된다. ARM 아키텍처를 기반으로 한 프로세서는 모바일 기기뿐 아니라 서버에서도 사용된다. 같은 ARM 계열이라는 공통점이 있어도 실제 CPU 제품의 구현과 성능은 별도로 확인해야 한다.

## 실행 파일은 CPU와 운영체제를 함께 확인해야 한다

네이티브 실행 파일을 ARM 환경으로 옮기는 예제를 생각하면서 처음에는 아키텍처만 맞으면 실행된다고 생각했다. 하지만 실행 환경은 CPU 아키텍처 하나로 결정되지 않는다.

### CPU 아키텍처가 다르면 명령어부터 다르다

x86-64용 네이티브 실행 파일이 ARM64 환경에서 그대로 네이티브 실행된다고 생각하면 안 된다. 파일 안에 들어 있는 기계어 명령어를 CPU가 이해해야 하는데 두 환경이 사용하는 명령어 체계가 다르기 때문이다.

### CPU 아키텍처가 같아도 운영체제가 다를 수 있다

이번에는 ARM64라는 조건을 맞춰 보자. macOS ARM64용 실행 파일이 Linux ARM64에서 그대로 실행된다고 보장할 수는 없다. 운영체제가 제공하는 실행 환경과 시스템 호출, 바이너리 형식 등이 다르기 때문이다.

네이티브 실행 파일은 다음 두 축을 함께 확인해야 한다.

| 확인 대상 | 예시 | 판단 |
| --- | --- | --- |
| CPU 아키텍처 | x86-64와 ARM64 | 명령어 체계가 다르면 그대로 실행할 수 없음 |
| 운영체제와 실행 환경 | macOS와 Linux | 같은 ARM64라도 실행 환경이 다를 수 있음 |

에뮬레이션이나 별도 호환 계층을 사용하면 예외가 생길 수 있다. 그러나 일반적인 네이티브 실행을 기준으로 보면 다음 문장으로 정리하는 편이 정확하다.

> 실행 호환성은 CPU 아키텍처 하나만으로 판단할 수 없다. 대상 OS와 필요한 실행 환경도 함께 확인해야 한다.

## 같은 Java 애플리케이션에서 JAR과 JVM을 나누어 보기

Java 애플리케이션을 ARM 서버로 옮기는 질문에서 가장 많이 헷갈린 부분은 JAR과 JVM을 같은 실행 파일처럼 생각한 점이다.

### Java 바이트코드는 CPU가 바로 실행하는 명령어가 아니다

일반적인 Java 클래스는 특정 CPU의 기계어가 아니라 JVM이 이해하는 바이트코드로 컴파일된다. JAR에는 이 클래스 파일과 애플리케이션에 필요한 자원이 담길 수 있다. 이 바이트코드는 x86 CPU나 ARM CPU가 직접 실행하는 네이티브 명령어와 다르다.

Java 21 기준으로 빌드한 애플리케이션을 예로 들어 보자. x86-64 환경에서 빌드했다고 해서 JAR 자체가 x86-64 전용 네이티브 실행 파일이 되는 것은 아니다. JAR 안의 클래스 파일은 JVM 명령어를 담고 있기 때문이다.

### 실제로 설치하는 JVM은 대상 환경에 맞아야 한다

JVM은 하드웨어와 운영체제에 독립적인 추상 머신을 제공하지만 JVM을 실행하는 구현체까지 모든 환경에 동일한 파일로 제공되는 것은 아니다. Linux ARM64 서버에서는 그 환경에서 실행 가능한 JVM이 필요하다.

이 구분은 [Java Virtual Machine Specification, Java SE 21 — Chapter 1](https://docs.oracle.com/javase/specs/jvms/se21/html/jvms-1.html)의 설명과 연결된다. 명세는 특정 호스트 하드웨어나 운영체제를 전제로 하지 않고 클래스 파일을 JVM 명령어와 바이트코드로 설명한다. 그렇다고 설치하는 JVM 실행 파일이 CPU와 운영체제의 영향을 받지 않는다는 뜻은 아니다.

| 항목 | 기존 환경 | 대상 환경 |
| --- | --- | --- |
| OS | Linux | Linux |
| CPU | x86-64 | ARM64 |
| 일반 Java 바이트코드 | 같은 JAR | 같은 JAR 사용 가능 |
| JVM | Linux x86-64용 | Linux ARM64용 |
| 네이티브 라이브러리 | 기존 플랫폼용 | 대상 플랫폼 지원 확인 |

여기서 `같은 JAR 사용 가능`은 조건이 있는 표현이다. 대상 OS와 CPU에서 동작하는 JVM이 있어야 한다. 클래스 파일과 사용하는 API에 호환되는 Java 버전인지 확인해야 한다. 애플리케이션이 기대하는 외부 실행 환경도 맞아야 한다. 네이티브 라이브러리를 포함하고 있다면 그 라이브러리의 호환성도 별도로 확인해야 한다.

Java 21로 빌드했다는 이유만으로 모든 대상 JVM이 실행된다고 단정할 수는 없다. 반대로 버전 숫자가 완전히 같아야만 실행된다고 말하는 것도 정확하지 않다. 클래스 파일 버전과 사용하는 API를 대상 JVM이 지원하는지 확인하고 실제 애플리케이션을 실행해야 한다.

![공통 Java 바이트코드를 담은 JAR과 Linux x86-64·ARM64용 JVM 및 CPU의 관계](/assets/images/2026-10-02-processor-isa-java-arm/bytecode-jvm-platform.svg)

*그림 1. 바이트코드는 재사용할 수 있지만 JVM 구현체는 대상 OS와 CPU에 맞아야 한다. 네이티브 라이브러리는 별도로 호환성을 확인해야 한다.*

## 네이티브 라이브러리가 있으면 JAR만으로 판단할 수 없다

Java 애플리케이션의 모든 의존성이 바이트코드로만 구성되는 것은 아니다. JNI 등으로 네이티브 라이브러리를 사용하는 경우에는 그 라이브러리도 대상 OS와 CPU 아키텍처에 맞아야 한다.

예를 들어 Linux x86-64용 네이티브 라이브러리가 Linux ARM64에서 그대로 사용된다고 보장할 수 없다. macOS ARM64용 라이브러리도 Linux ARM64에서 그대로 사용되지 않는다. CPU 아키텍처가 같아도 운영체제가 다르면 실행 환경이 달라진다.

이때는 대상 환경용 라이브러리를 준비하거나 지원되는 대체 라이브러리를 검토해야 한다. 라이브러리 파일을 교체하는 것으로 확인을 끝내서도 안 된다. 애플리케이션이 그 라이브러리를 실제로 사용하는 기능을 호출해 로딩과 동작이 정상인지 검증해야 한다.

이 부분에서 JAR의 재사용 가능성과 애플리케이션 전체의 실행 가능성을 분리해서 보게 됐다. JAR 안의 일반 클래스가 같은 바이트코드라는 사실과 네이티브 의존성까지 같은 플랫폼에서 실행된다는 사실은 서로 다른 주장이다.

## Docker 이미지는 JAR과 다른 실행 단위다

JAR을 그대로 재사용해도 Docker 이미지 하나만 만들면 된다고 생각하기 쉽다. 하지만 Docker 이미지는 애플리케이션만 담는 파일이 아니다. 이미지에는 JVM과 실행에 필요한 바이너리와 라이브러리가 포함될 수 있다.

Docker에서 자주 보는 플랫폼 표기는 다음과 같다.

| 플랫폼 | 의미 |
| --- | --- |
| `linux/amd64` | Linux 환경의 x86-64 아키텍처 |
| `linux/arm64` | Linux 환경의 ARM64 아키텍처 |

`amd64`는 AMD 회사의 CPU에서만 실행된다는 뜻이 아니다. x86-64 계열을 가리키는 플랫폼 표기다.

그렇다면 JAR은 재사용되는데 왜 `linux/amd64` 이미지를 ARM64 서버에서 그대로 실행할 수 없을까? 이미지 안에 포함된 JVM과 다른 실행 파일도 플랫폼 의존성을 가질 수 있기 때문이다. Docker는 이런 CPU 아키텍처 차이를 이미지로 감싸서 자동으로 없애 주지 않는다.

또한 컨테이너는 호스트 커널을 공유한다. Docker 공식 문서의 [Multi-platform builds](https://docs.docker.com/build/building/multi-platform/)도 컨테이너 안에서 실행되는 코드가 호스트 아키텍처와 호환되어야 하며 `linux/amd64` 컨테이너를 arm64 호스트에서 실행하려면 에뮬레이션 같은 별도 방법이 필요하다고 설명한다.

Windows나 macOS에서 Linux 컨테이너가 실행되는 경우가 있어도 이를 모든 운영체제의 컨테이너가 직접 호환된다는 근거로 사용할 수는 없다. 별도 Linux VM 등 실행 환경을 거치는 경우가 있기 때문이다.

## 멀티 플랫폼 이미지는 플랫폼별 변형을 연결한다

하나의 이미지 이름 아래에 `linux/amd64`용 이미지와 `linux/arm64`용 이미지가 각각 존재한다. 이때 이미지 인덱스 또는 매니페스트 목록이 플랫폼별 이미지를 연결한다.

실행 환경에서 이미지를 가져오면 Docker는 호스트에 맞는 플랫폼 변형을 선택한다. ARM64 환경에서는 지원되는 ARM64 변형을 사용하고 x86-64 환경에서는 `linux/amd64` 변형을 사용한다.

이 구조는 하나의 바이너리가 모든 아키텍처에서 그대로 동작하게 만드는 방식이 아니다. 같은 이미지 이름으로 여러 플랫폼별 구성과 레이어를 묶어 두고 실행 환경에 맞는 변형을 고르는 방식이다.

```text
하나의 이미지 이름
└── 플랫폼별 이미지 변형
    ├── linux/amd64: JVM + 라이브러리 + 애플리케이션
    └── linux/arm64: JVM + 라이브러리 + 애플리케이션
```

![하나의 이미지 이름 아래 매니페스트 목록이 linux/amd64와 linux/arm64 이미지를 연결하고 실행 환경에 맞는 변형을 선택하는 구조](/assets/images/2026-10-02-processor-isa-java-arm/multi-platform-image-selection.svg)

*그림 2. 멀티 플랫폼 이미지는 하나의 범용 실행 파일이 아니라 플랫폼별 이미지를 하나의 이름 아래 연결하는 구조다.*

오늘은 멀티 플랫폼 이미지를 직접 빌드하거나 레지스트리에 배포하지 않았다. 여기서는 이미지 인덱스와 플랫폼별 변형이 어떤 관계인지 이해하는 데까지만 범위를 정했다.

## 처음 이해했던 내용이 어떻게 바뀌었나

오늘은 개념을 각각 외우기보다 같은 JAR과 Docker 이미지를 여러 환경에 놓고 질문을 바꾸어 보았다.

| 처음 이해했던 내용 | 최종적으로 정리한 내용 |
| --- | --- |
| 같은 ISA면 실행 환경도 호환된다 | OS와 필요한 실행 환경도 함께 확인해야 한다 |
| JVM은 어떤 아키텍처에서도 그대로 실행된다 | JVM 명세와 실제 JVM 구현체를 구분해야 한다 |
| x86에서 만든 일반 JAR은 ARM용으로 다시 빌드해야 한다 | 호환되는 JVM과 의존성이 있다면 같은 JAR을 사용할 수 있다 |
| 같은 ARM64 라이브러리면 OS가 달라도 사용할 수 있다 | 네이티브 라이브러리는 대상 OS와 아키텍처를 함께 확인한다 |
| Docker로 묶으면 아키텍처 차이가 해결된다 | 이미지에 포함된 JVM과 바이너리도 플랫폼에 맞아야 한다 |
| ARM이면 항상 더 효율적이다 | 실제 작업의 처리량과 비용을 비교해야 한다 |

처음에는 아키텍처 이름 하나로 실행 가능 여부를 판단하려 했다. 이제는 네이티브 파일인지 JVM 바이트코드인지부터 나눈다. 그다음 JVM과 라이브러리와 운영체제의 조건을 확인한다. 이 순서를 거치면 같은 Java 애플리케이션이라는 말이 어디까지 유효한지도 분명해진다.

## ARM 기반 서버에서 Spring Boot를 실행할 때 확인할 순서

ARM 기반 t4g 서버에서 Spring Boot 애플리케이션을 실행한다고 해 보자. 오늘 서버를 실제로 이전하거나 성능 테스트를 실행한 것은 아니지만 다음 순서로 확인해야 한다.

1. 서버의 OS와 CPU 아키텍처를 확인한다.
2. 해당 환경을 지원하는 JVM과 Java 버전을 확인한다.
3. 컨테이너를 사용한다면 베이스 이미지와 최종 이미지의 플랫폼을 확인한다.
4. 네이티브 의존성이 대상 환경을 지원하는지 확인한다.
5. 애플리케이션 시작 여부만 보지 말고 해당 의존성을 사용하는 기능까지 검증한다.
6. 실제 작업에서 처리량과 비용을 비교한다.

이 순서는 ARM이라는 이름만 보고 서버 선택을 끝내지 않게 해 준다. 일반 Java 바이트코드를 재사용하더라도 JVM과 이미지와 네이티브 라이브러리는 각각 대상 환경을 확인해야 한다. 마지막 판단도 아키텍처의 이미지가 아니라 실제 서비스 작업의 결과를 보고 내려야 한다.

## 오늘의 정리

오늘은 프로세서가 명령어를 실행하는 출발점에 ISA라는 약속이 있다는 사실에서 시작했다. ISA와 CPU 구현을 분리하니 같은 규칙을 지원하는 CPU도 내부 구조와 성능이 다를 수 있다는 점이 보였다. RISC와 CISC도 성능 순위가 아니라 설계 방향으로 읽게 됐다.

실행 환경을 비교할 때는 CPU 아키텍처와 운영체제를 함께 봐야 한다. Java에서는 JAR 안의 바이트코드와 실제로 설치하는 JVM을 나누어야 한다. 일반적인 Java 애플리케이션은 호환되는 JVM과 의존성이 있다면 같은 JAR을 다른 CPU 아키텍처에서도 재사용한다. 네이티브 라이브러리가 들어오면 대상 OS와 CPU를 다시 확인하고 그 기능까지 실행해 봐야 한다.

Docker도 같은 기준으로 읽을 수 있다. 같은 JAR을 재사용한다는 사실과 같은 단일 플랫폼 이미지를 재사용한다는 사실은 다르다. 멀티 플랫폼 이미지는 이 차이를 감추는 마법이 아니라 플랫폼별 JVM과 라이브러리와 애플리케이션을 각각 준비해 하나의 이미지 이름으로 연결하는 구조다.

오늘 배운 내용을 내 말로 정리하면 다음과 같다.

> Java 애플리케이션을 옮길 때는 JAR의 바이트코드와 실제 실행 환경을 분리해서 확인하고, 서버를 선택할 때는 아키텍처뿐 아니라 의존성과 실제 작업의 처리량과 비용까지 함께 비교해야 한다.
