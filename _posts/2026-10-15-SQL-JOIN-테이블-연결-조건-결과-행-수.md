어제 [데이터베이스의 Key — 후보키의 최소성과 제약조건은 어떻게 연결될까?](/posts/database-key-minimality-constraints/)를 공부하면서 기본키와 외래키가 각각 무엇을 보장하는지 정리했다. 기본키는 행을 식별하고 외래키는 참조 대상의 존재를 확인하지만 두 테이블의 데이터를 실제 조회 결과로 묶어 주는 규칙까지 자동으로 만들어 주지는 않는다.

오늘은 이 관계를 SQL JOIN으로 표현하는 방법을 학습했다. 음식점과 방문 기록을 예제로 두 테이블의 행이 어떤 조건에서 연결되는지 직접 계산하고 모의면접에서 처음에 잘못 이해했던 JOIN 조건과 집계 결과도 다시 확인했다.

처음에는 JOIN을 “두 테이블을 합쳐 보는 문법” 정도로 생각했다. 하지만 같은 음식점에 방문 기록이 여러 건 있으면 결과 행도 여러 개가 되고 방문 기록이 없는 음식점을 남길지 여부에 따라 JOIN 종류도 달라졌다. 오늘은 문법의 이름을 외우기보다 어떤 행의 조합이 결과에 들어가는지를 따라가 보는 데 집중했다.

오늘 확인한 질문은 다음과 같다.

- `INNER JOIN`과 `OUTER JOIN`은 어떤 행을 남기는가?
- `LEFT JOIN`은 왼쪽 테이블의 행을 항상 한 번만 반환하는가?
- 외래키가 아닌 컬럼으로 JOIN하면 왜 잘못된 관계가 연결될 수 있는가?
- JOIN 결과의 행 수가 원본 테이블보다 많아지는 이유는 무엇인가?
- 같은 조건을 `ON`과 `WHERE` 중 어디에 작성하느냐에 따라 결과가 달라지는 이유는 무엇인가?
- `COUNT(*)`와 `COUNT(컬럼)`은 왜 다른 값을 세는가?
- `CROSS JOIN`과 `SELF JOIN`은 어떤 상황에서 사용하는가?

## JOIN은 어떤 행을 연결할지 정하는 연산이다

관계형 데이터베이스에서는 성격이 다른 데이터를 테이블로 나누어 저장한다. 음식점의 이름과 주소는 `restaurant`에 두고 방문 기록과 방문한 유튜버는 `visit`에 두는 식이다. 이렇게 나누면 방문 기록이 추가될 때 음식점 이름을 매번 반복해서 저장하지 않아도 된다.

오늘은 다음 데이터를 공통 예제로 사용했다.

`restaurant`

| id | name |
| ---: | :--- |
| 1 | 국밥집 |
| 2 | 초밥집 |
| 3 | 파스타집 |

`visit`

| id | restaurant_id | youtuber |
| ---: | ---: | :--- |
| 1 | 1 | 철수 |
| 2 | 1 | 영희 |
| 3 | 2 | 철수 |
| 4 | 2 | 민수 |

두 테이블에서는 `restaurant.id`와 `visit.restaurant_id`가 음식점과 방문 기록을 연결하는 값이다. 이를 SQL로 표현하면 다음과 같다.

```sql
SELECT r.name, v.youtuber
FROM restaurant r
INNER JOIN visit v
    ON r.id = v.restaurant_id;
```

이 쿼리는 `restaurant`와 `visit`의 행을 단순히 옆으로 붙이지 않는다. `ON r.id = v.restaurant_id`가 참인 행의 조합만 결과로 만든다. `restaurant.id`가 1인 행은 `visit.restaurant_id`가 1인 두 행과 연결되고 2인 행도 두 행과 연결된다. 3인 행에는 연결되는 방문 기록이 없다.

여기서 기본키와 외래키와 JOIN 조건은 서로 다른 개념이다. 기본키와 외래키는 데이터베이스에 데이터 관계를 지키도록 요구하는 제약조건이다. JOIN 조건은 특정 조회에서 어떤 컬럼끼리 비교할지 쿼리가 선택하는 기준이다. 외래키가 선언되어 있지 않아도 JOIN은 실행할 수 있지만 실제 관계를 나타내는 컬럼을 잘못 고르면 결과가 틀어진다.

## INNER JOIN과 OUTER JOIN은 남기는 행이 다르다

`INNER JOIN`은 `ON` 조건을 만족하는 행만 반환한다. 위 예제에서 `restaurant.id = 3`인 파스타집에는 방문 기록이 없으므로 결과에서 빠진다. 국밥집은 방문 기록이 두 건이고 초밥집도 두 건이므로 결과는 네 행이다.

| `r.name` | `v.youtuber` |
| :--- | :--- |
| 국밥집 | 철수 |
| 국밥집 | 영희 |
| 초밥집 | 철수 |
| 초밥집 | 민수 |

`LEFT JOIN`은 왼쪽 테이블의 행을 보존한다.

```sql
SELECT r.name, v.youtuber
FROM restaurant r
LEFT JOIN visit v
    ON r.id = v.restaurant_id;
```

이번에는 방문 기록이 없는 파스타집도 결과에 들어간다. 오른쪽 테이블에서 대응하는 행을 찾지 못했으므로 `v.youtuber`에는 `NULL`이 채워진다.

| `r.name` | `v.youtuber` |
| :--- | :--- |
| 국밥집 | 철수 |
| 국밥집 | 영희 |
| 초밥집 | 철수 |
| 초밥집 | 민수 |
| 파스타집 | `NULL` |

여기서 `LEFT JOIN`을 “왼쪽 행을 한 번씩만 반환하는 JOIN”으로 이해하면 안 된다. 왼쪽의 한 행에 오른쪽의 여러 행이 대응하면 그 조합만큼 결과 행이 생긴다. 왼쪽 행을 보존한다는 말은 대응하는 행이 없을 때도 최소 한 행을 남긴다는 뜻이지 결과에서 중복을 제거한다는 뜻이 아니다.

`RIGHT JOIN`은 오른쪽 테이블의 행을 보존한다. 다음 쿼리에서는 모든 방문 기록을 기준으로 음식점을 붙인다.

```sql
SELECT r.name, v.youtuber
FROM restaurant r
RIGHT JOIN visit v
    ON r.id = v.restaurant_id;
```

현재 예제에서는 모든 방문 기록이 음식점과 연결되므로 네 행이 나온다. 테이블의 위치를 바꿔 같은 의미를 `visit v LEFT JOIN restaurant r`로 표현할 수도 있다. 팀 안에서 기준 테이블이 잘 드러나는 쪽을 선택하면 된다.

`FULL OUTER JOIN`은 양쪽의 행을 모두 보존한다. 현재 데이터에서는 방문 기록이 없는 파스타집이 남기 때문에 다섯 행이 나온다. 만약 외래키 없이 `restaurant_id = 99`인 방문 기록이 추가되었다면 음식점 쪽 컬럼이 `NULL`인 행도 함께 생긴다.

![restaurant와 visit의 INNER JOIN·LEFT JOIN 결과 비교. 한 음식점에 여러 방문 기록이 있으면 결과 행이 늘고 방문 기록이 없는 파스타집은 LEFT JOIN에서 NULL로 남는다.](/assets/images/2026-10-15-sql-join/join-type-result.svg)

*그림 1. JOIN 종류는 어떤 행을 보존할지 결정하고 실제 결과 행 수는 매칭되는 행의 조합으로 결정된다.*

## JOIN 결과의 행 수는 매칭 조합으로 계산한다

오늘 모의면접에서 가장 오래 생각한 부분은 JOIN 결과의 행 수였다. 처음에는 왼쪽 테이블이 세 행이면 `LEFT JOIN` 결과도 세 행일 것이라고 예상했다. 하지만 국밥집에 방문 기록이 두 건 있으므로 국밥집 행은 두 번 나타난다.

한쪽 행마다 반대쪽에서 조건에 맞는 행의 개수를 세면 결과 행 수를 계산할 수 있다. 이번 `LEFT JOIN`은 다음처럼 정리된다.

| 음식점 | 일치하는 방문 기록 수 | 결과에 생기는 행 수 |
| :--- | ---: | ---: |
| 국밥집 | 2 | 2 |
| 초밥집 | 2 | 2 |
| 파스타집 | 0 | 1 (`NULL` 행) |
| 합계 | 4 | 5 |

`INNER JOIN`에서는 일치하는 행이 0개인 파스타집이 결과에 들어오지 않으므로 `2 + 2 = 4`행이다. `LEFT JOIN`에서는 일치하는 행이 0개인 경우에도 왼쪽 행을 보존해야 하므로 그 음식점에 대해 `NULL`이 들어간 한 행이 추가된다.

따라서 JOIN 결과에서 같은 음식점 이름이 반복된다고 해서 바로 중복 데이터라고 결론 내리면 안 된다. 국밥집의 두 행은 방문 기록의 `id`가 1과 2로 다르다. 조회 목적이 방문 기록이라면 서로 다른 결과이고 음식점 목록만 필요하다면 `DISTINCT`나 그룹화처럼 별도의 결과 기준을 정해야 한다.

이 차이를 구분하지 않으면 API 응답의 음식점 개수와 JOIN 결과의 행 개수를 같은 값으로 다루게 된다. “음식점이 몇 개인가?”와 “방문 기록이 몇 건 연결되었는가?”는 SQL에서도 서로 다른 질문이다.

## JOIN 조건을 잘못 쓰면 관계가 틀어진다

오늘 모의면접에서 처음에는 두 테이블의 `id` 컬럼을 비교해도 된다고 생각했다. 두 컬럼의 이름이 같고 값의 범위도 비슷해 보였기 때문이다. 하지만 `restaurant.id`는 음식점을 식별하고 `visit.id`는 방문 기록 자체를 식별한다.

다음 쿼리는 실행될 수 있지만 음식점과 방문 기록의 관계를 비교하는 조건이 아니다.

```sql
SELECT r.name, v.youtuber
FROM restaurant r
JOIN visit v
    ON r.id = v.id;
```

같은 데이터를 넣으면 결과는 다음처럼 나온다.

| `r.name` | `v.id` | `v.restaurant_id` | `v.youtuber` |
| :--- | ---: | ---: | :--- |
| 국밥집 | 1 | 1 | 철수 |
| 초밥집 | 2 | 1 | 영희 |
| 파스타집 | 3 | 2 | 철수 |

`id` 값이 우연히 같아서 세 행이 연결되었지만 초밥집과 영희의 방문 기록이 연결된 것은 잘못된 결과다. 방문 기록 `id = 2`의 음식점은 `restaurant_id = 1`인 국밥집이다. `id = 3`인 방문 기록도 파스타집이 아니라 초밥집에 속한다.

올바른 조건은 방문 기록이 가리키는 음식점 컬럼을 비교하는 것이다.

```sql
SELECT r.name, v.youtuber
FROM restaurant r
JOIN visit v
    ON r.id = v.restaurant_id;
```

어제 [데이터베이스의 Key](/posts/database-key-minimality-constraints/)를 공부하면서 외래키는 참조 대상의 존재를 확인할 뿐 관계의 조회 결과를 대신 만들어 주지 않는다고 정리했다. 오늘은 그 내용을 실제 쿼리에 적용했다. 어떤 컬럼이 기본키인지보다 더 직접적인 질문은 “이 행이 다른 테이블의 어느 행을 가리키는가?”였다.

## `ON`과 `WHERE`는 필터가 적용되는 위치가 다르다

`ON`은 JOIN 과정에서 어떤 두 행을 매칭할지 정한다. `WHERE`는 JOIN으로 만들어진 결과에서 어떤 행을 최종적으로 남길지 정한다. 이 차이는 `INNER JOIN`에서는 비슷하게 보일 수 있지만 `OUTER JOIN`에서는 결과를 바꾼다.

방문한 유튜버가 철수인 기록만 음식점에 붙이고 싶다고 하자. 철수의 방문 기록이 없는 음식점도 목록에 남기려면 조건을 `ON`에 둔다.

```sql
SELECT r.name, v.youtuber
FROM restaurant r
LEFT JOIN visit v
    ON r.id = v.restaurant_id
   AND v.youtuber = '철수';
```

JOIN할 때부터 철수인 방문 기록만 오른쪽 후보로 남기므로 결과는 다음과 같다.

| `r.name` | `v.youtuber` |
| :--- | :--- |
| 국밥집 | 철수 |
| 초밥집 | 철수 |
| 파스타집 | `NULL` |

같은 조건을 `WHERE`에 작성하면 의미가 달라진다.

```sql
SELECT r.name, v.youtuber
FROM restaurant r
LEFT JOIN visit v
    ON r.id = v.restaurant_id
WHERE v.youtuber = '철수';
```

이 쿼리는 먼저 일반적인 `LEFT JOIN`을 수행한다. 그 결과에는 국밥집의 영희 행과 초밥집의 민수 행과 파스타집의 `NULL` 행이 모두 있다. 그 다음 `WHERE v.youtuber = '철수'`를 적용하므로 철수가 아닌 행과 `NULL`인 행이 제거된다.

| `r.name` | `v.youtuber` |
| :--- | :--- |
| 국밥집 | 철수 |
| 초밥집 | 철수 |

처음에는 `LEFT JOIN`이면 왼쪽 테이블의 모든 행이 어떤 조건에서도 남는다고 생각했다. 하지만 오른쪽 컬럼을 `WHERE`에서 검사하면 JOIN 이후의 결과를 다시 걸러내므로 `NULL` 행도 남지 않을 수 있다. JOIN 자체의 보존 규칙과 그 뒤의 필터를 분리해서 읽어야 이 차이를 놓치지 않는다.

![LEFT JOIN에서 철수 조건을 ON에 둘 때와 WHERE에 둘 때의 처리 순서와 결과 비교](/assets/images/2026-10-15-sql-join/on-where-filter-order.svg)

*그림 2. `ON`의 조건은 매칭 대상을 줄이고 왼쪽 행 보존은 유지하지만 `WHERE`의 조건은 JOIN 결과에서 행을 제거한다.*

## `COUNT(*)`와 `COUNT(컬럼)`은 세는 대상이 다르다

JOIN 결과의 행 수를 확인한 뒤에는 집계 함수가 무엇을 세는지도 구분해야 했다. 음식점별 방문 수를 구하는 쿼리를 생각해 보자.

```sql
SELECT r.name, COUNT(*) AS row_count
FROM restaurant r
LEFT JOIN visit v
    ON r.id = v.restaurant_id
GROUP BY r.id, r.name;
```

`COUNT(*)`는 `LEFT JOIN`으로 만들어진 결과 행 자체를 센다. 방문 기록이 없는 파스타집도 오른쪽 컬럼이 `NULL`인 한 행으로 존재하므로 결과가 1로 나온다.

```sql
SELECT r.name, COUNT(v.id) AS visit_count
FROM restaurant r
LEFT JOIN visit v
    ON r.id = v.restaurant_id
GROUP BY r.id, r.name;
```

`COUNT(v.id)`는 `v.id`가 `NULL`이 아닌 행만 센다. 따라서 실제 방문 기록이 없는 파스타집은 0이 된다.

| 음식점 | `COUNT(*)` | `COUNT(v.id)` |
| :--- | ---: | ---: |
| 국밥집 | 2 | 2 |
| 초밥집 | 2 | 2 |
| 파스타집 | 1 | 0 |

`GROUP BY r.id, r.name`은 음식점별로 JOIN 결과를 묶기 위한 구문이다. 전체 JOIN 결과가 다섯 행이라는 사실과 음식점별 집계 결과가 세 행이라는 사실도 서로 다르다.

방문 횟수가 아니라 고유한 유튜버 수를 구하려면 집계 대상도 바뀐다.

```sql
SELECT r.name, COUNT(DISTINCT v.youtuber) AS unique_youtuber_count
FROM restaurant r
LEFT JOIN visit v
    ON r.id = v.restaurant_id
GROUP BY r.id, r.name;
```

`COUNT(v.id)`는 방문 기록을 세고 `COUNT(DISTINCT v.youtuber)`는 같은 음식점을 방문한 유튜버의 중복을 제외한다. 어떤 숫자가 필요한지 먼저 정한 뒤 COUNT의 대상을 선택해야 한다.

## `CROSS JOIN`과 `SELF JOIN`은 목적이 다르다

`CROSS JOIN`은 두 테이블의 모든 행 조합을 만든다. `restaurant`가 3행이고 `visit`가 4행이면 다음 결과는 12행이다.

```sql
SELECT r.name, v.id AS visit_id
FROM restaurant r
CROSS JOIN visit v;
```

이 쿼리에는 음식점과 방문 기록 사이의 일치 조건이 없다. 국밥집과 네 방문 기록을 조합하고 초밥집과 네 방문 기록을 조합하며 파스타집과 네 방문 기록을 조합하는 식으로 모든 경우를 만든다. 일반적인 관계 조회에서 JOIN 조건을 빠뜨린 결과와 비슷해 보일 수 있으므로 의도한 카티션 곱인지 확인해야 한다.

`SELF JOIN`은 하나의 테이블을 두 개의 역할로 나누어 참조하는 방식이다. 예를 들어 직원과 상사를 같은 `employee` 테이블에 저장했다면 다음처럼 조회할 수 있다.

```sql
SELECT e.name AS employee_name, m.name AS manager_name
FROM employee e
LEFT JOIN employee m
    ON e.manager_id = m.id;
```

`e`는 직원 역할이고 `m`은 상사 역할이다. 상사가 없는 대표 직원도 보고 싶기 때문에 `LEFT JOIN`을 선택했다. `SELF JOIN`이라고 해서 항상 `INNER JOIN`만 사용하는 것은 아니다. 같은 테이블을 어떤 두 역할로 비교할지와 대응하지 않는 행을 보존할지에 따라 JOIN 종류를 선택한다.

## 명시적인 JOIN 조건과 인덱스는 구분한다

두 테이블에 같은 이름의 컬럼이 있고 그 컬럼을 그대로 연결할 때는 `USING`을 사용할 수 있다.

```sql
SELECT *
FROM restaurant r
JOIN restaurant_snapshot s
USING (id);
```

`USING (id)`는 양쪽의 `id`가 같다는 조건을 짧게 표현하고 출력에서 같은 이름의 컬럼을 하나로 합친다. 하지만 `restaurant.id`와 `visit.restaurant_id`처럼 컬럼 이름이 다르면 `ON`으로 관계를 명시해야 한다.

`NATURAL JOIN`은 양쪽 테이블에 같은 이름을 가진 모든 컬럼을 자동으로 JOIN 조건에 넣는다. 지금은 같은 이름이 아니던 컬럼이 나중에 추가되면서 JOIN 조건에 포함될 수도 있으므로 비즈니스 관계를 쿼리에 남겨야 하는 경우에는 명시적인 `ON`이 더 읽기 쉽고 안전하다.

JOIN 조건을 정확하게 작성하는 일과 그 쿼리가 빠르게 실행되는 일도 같은 문제는 아니다. [B-Tree와 B+Tree — 페이지 접근을 줄이면서 인덱스 검색은 어떻게 이루어질까?](/posts/b-tree-b-plus-tree-index-search/)에서 정리한 것처럼 인덱스는 검색 경로와 페이지 접근을 줄이는 구조다. 인덱스가 있다고 해서 잘못된 JOIN 조건이 올바른 관계로 바뀌지는 않는다. 오늘은 JOIN 알고리즘이나 실행 계획을 비교하거나 성능을 측정한 것이 아니라 결과 행의 정확성을 확인했다.

이전에 [이진 탐색 트리와 Hash — 값을 찾는 기준과 탐색 비용은 어떻게 달라질까?](/posts/binary-search-tree-hash-search-cost/)에서 HashMap의 키 조회와 데이터의 관계를 표현하는 자료구조를 구분했다. SQL JOIN도 비슷하게 “값을 찾는 비용”과 “어떤 행이 같은 관계인지”를 나누어 보아야 한다. HashMap에서 키가 같다는 판단과 SQL에서 두 컬럼의 관계가 같다는 판단은 서로 다른 계층의 문제다.

실제 백엔드 API에서 음식점 목록과 방문 기록을 함께 반환해야 한다면 어떤 음식점을 기준으로 조회할지 먼저 결정해야 한다. 방문 기록이 없는 음식점도 보여줘야 한다면 `LEFT JOIN`을 고려하고 음식점별 방문 횟수를 보여준다면 JOIN 결과의 행 수와 `COUNT(v.id)`의 값을 분리해 확인해야 한다. 오늘은 이를 프로젝트 코드에 구현하거나 성능을 검증한 것이 아니라 SQL 결과를 계산하고 조건의 의미를 비교하는 연습을 했다.

## 오늘의 정리

처음에는 JOIN을 두 테이블을 이어 붙이는 문법으로 이해했다. 직접 결과 행을 계산해 보니 JOIN은 `ON` 조건을 만족하는 행의 조합을 만들고 JOIN 종류에 따라 일치하지 않는 행을 보존하는 연산이었다. 한 음식점에 방문 기록이 여러 건이면 `LEFT JOIN`에서도 왼쪽 테이블의 행 수보다 결과가 많아질 수 있다.

두 테이블의 `id` 값이 우연히 같다고 해서 올바른 관계가 연결되는 것은 아니다. 음식점의 기본키와 방문 기록이 가리키는 외래키를 비교해야 하며 어떤 컬럼이 실제 관계를 표현하는지 먼저 확인해야 한다. 이 부분에서 어제 학습한 Key 개념이 오늘 SQL 조건으로 이어졌다.

`ON`은 매칭할 행을 정하고 `WHERE`는 JOIN 이후 결과를 필터링한다. 특히 `LEFT JOIN`에서 오른쪽 컬럼을 `WHERE`로 검사하면 `NULL` 행이 제거될 수 있다. `COUNT(*)`는 결과 행을 세고 `COUNT(v.id)`는 실제 방문 기록이 있는 행을 세므로 방문 기록이 없는 음식점의 수를 0으로 표현하려면 집계 대상을 확인해야 한다.

`CROSS JOIN`은 모든 행의 조합을 만들고 `SELF JOIN`은 같은 테이블을 서로 다른 역할로 참조한다. 결국 SQL 문법을 맞게 작성하는 것만으로는 충분하지 않다. 어떤 관계를 연결하고 몇 개의 결과 행을 남겨야 하는지까지 예상한 뒤 쿼리를 작성해야 백엔드 API의 응답도 의도와 맞아진다.
