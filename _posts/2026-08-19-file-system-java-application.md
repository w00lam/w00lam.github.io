파일을 저장한다는 말은 꽤 단순하게 들린다. Java에서는 `Files.writeString()`을 호출하고, 읽을 때는 `Files.readString()`을 호출하면 된다. 개발자는 파일 경로와 내용을 넘기면 작업이 끝난 것처럼 보인다.

하지만 애플리케이션이 실제 디스크의 어느 위치에 어떤 방식으로 데이터를 기록하는지까지 직접 관리해야 한다면 이야기가 달라진다.

> **애플리케이션은 왜 디스크를 직접 다루지 않고 File System(파일 시스템)이라는 추상화를 사용하는가?**

이번 글에서는 이 질문을 중심으로 파일 시스템의 역할과 파일 접근 방식, 디렉터리 구조를 정리해 보려고 한다. 마지막에는 Java/Spring 애플리케이션에서 파일을 읽고 쓸 때 어떤 계층을 거치는지도 연결해 보겠다.

## 1. 파일을 저장한다는 것은 생각보다 복잡하다

파일 시스템이 없다면 애플리케이션은 저장장치에 데이터를 기록할 때 다음 정보를 직접 관리해야 할 수 있다.

- 데이터가 저장된 물리적 위치
- 데이터의 크기와 현재 사용 중인 공간
- 파일 이름과 파일을 찾는 방법
- 파일이 어느 사용자에게 속하는지
- 파일과 디렉터리 사이의 구조
- 저장 공간을 언제 할당하고 회수할지

SSD나 HDD는 데이터를 물리적인 블록 단위로 저장한다. 애플리케이션이 모든 블록의 위치를 직접 기록하고, 파일이 커질 때 새로운 블록을 할당하고, 삭제된 공간을 다시 관리한다고 생각하면 프로그램의 핵심 로직과 저장장치 관리 로직이 뒤섞이게 된다.

파일 시스템은 이 복잡성을 숨기고 다음과 같은 논리 구조를 제공한다.

```text
물리적인 저장 공간
        ↓
파일 / 디렉터리
```

애플리케이션은 `report.txt`라는 이름과 경로를 사용하지만, 실제 데이터가 저장되는 블록의 위치를 직접 알 필요가 없다. 운영체제와 파일 시스템이 경로를 해석하고, 필요한 저장 공간을 찾고, 권한과 메타데이터를 확인한 뒤 저장장치에 작업을 요청한다.

따라서 파일 시스템은 단순히 “파일을 저장하는 기능”이라기보다 **저장장치의 물리적 구조를 파일과 디렉터리라는 논리적 단위로 바꿔 제공하는 관리 계층**이라고 이해하는 편이 더 정확하다.

## 2. File System은 왜 필요한가

파일 시스템이 제공하는 가장 중요한 가치는 추상화와 관리다.

### 물리적인 위치를 논리적인 이름으로 바꾼다

애플리케이션은 “몇 번째 블록에 기록할까?” 대신 `/logs/app.log`라는 경로를 사용한다. 경로와 파일 이름을 기준으로 파일을 찾는 일은 파일 시스템의 책임이다.

### 저장 공간을 할당하고 회수한다

새 파일을 만들거나 기존 파일의 크기가 커지면 파일 시스템은 저장장치에서 필요한 공간을 할당한다. 파일을 삭제하면 더 이상 사용하지 않는 공간을 회수해 다른 파일이 사용할 수 있도록 관리한다.

### 접근 권한과 소유자를 관리한다

파일은 아무 프로그램이나 읽고 쓸 수 있는 대상이 아니다. 파일 시스템은 파일의 소유자와 권한 같은 정보를 바탕으로 접근 가능 여부를 판단하는 데 필요한 기반을 제공한다. 실제 권한 검사는 운영체제가 수행하지만, 파일과 관련된 관리 정보는 파일 시스템에 함께 기록된다.

### 여러 프로그램의 접근을 조정한다

여러 프로세스가 같은 파일을 읽거나 쓰려고 할 때 운영체제는 파일 디스크립터, 잠금, 버퍼링 같은 기능을 통해 접근을 조정한다. 애플리케이션이 저장장치의 전기적·물리적 동작을 직접 제어하지 않아도 되는 이유도 여기에 있다.

파일 시스템이 없다면 프로그램마다 이런 기능을 따로 구현해야 한다. 파일 시스템은 공통으로 사용할 수 있는 저장장치 관리 규칙을 운영체제 수준에서 제공한다.

![Java 애플리케이션에서 저장장치까지의 계층 흐름](/assets/images/2026-08-19-filesystem/java-to-storage.png)

위 그림처럼 애플리케이션이 바라보는 파일과 실제 저장장치 사이에는 여러 계층이 있다. 각 계층이 책임을 나누기 때문에 Java 코드는 물리 블록의 배치 방식과 무관하게 파일을 사용할 수 있다.

## 3. File과 Metadata

파일 시스템이 관리하는 정보는 크게 **Data(데이터)**와 **Metadata(메타데이터)**로 나누어 생각할 수 있다.

### Data: 실제로 저장하려는 내용

Data는 사용자가 파일에 담고 싶은 실제 내용이다.

- 이미지 파일의 픽셀 데이터
- 로그 파일의 로그 내용
- 문서의 텍스트
- Java 프로그램의 소스 코드나 컴파일 결과

예를 들어 `app.log` 파일 안에 기록된 `Request completed`라는 문자열은 파일의 Data에 해당한다.

### Metadata: 파일을 찾고 관리하기 위한 정보

Metadata는 파일 자체를 관리하기 위한 정보다.

- 파일 이름
- 파일 크기
- 생성 시간과 수정 시간
- 파일 권한
- 파일 소유자
- 데이터가 저장된 위치를 찾기 위한 정보

`app.log`라는 이름, 파일의 크기, 마지막 수정 시각은 로그 내용 자체가 아니다. 하지만 이 정보가 있어야 파일 시스템이 파일을 찾고, 접근을 허용하고, 데이터를 어디까지 읽어야 하는지 판단할 수 있다.

> **파일 시스템은 파일의 내용만 저장하는 것이 아니라 파일을 찾고 관리하기 위한 정보까지 함께 관리한다.**

Data와 Metadata를 구분하면 파일 크기를 변경하는 작업과 파일 내용 자체를 변경하는 작업이 왜 서로 다른 관리 대상처럼 보일 수 있는지도 이해하기 쉬워진다. 애플리케이션이 파일에 내용을 쓰면 Data가 바뀌지만, 그 결과 파일 크기와 수정 시간 같은 Metadata도 함께 갱신될 수 있다.

## 4. 파일에 접근하는 세 가지 방법

파일을 저장하는 방식만큼이나 중요한 것이 저장된 데이터를 어떻게 읽을지다. 대표적인 접근 방식은 Sequential Access(순차 접근), Direct Access(직접 접근), Indexed Access(인덱스 접근)로 설명할 수 있다.

### Sequential Access(순차 접근)

현재 위치를 기준으로 데이터를 앞에서부터 순서대로 읽는 방식이다.

```text
Block 1 → Block 2 → Block 3 → Block 4
```

로그 파일을 처음부터 끝까지 읽어 특정 패턴을 찾거나, 전체 파일을 다른 저장소로 복사할 때 자연스럽다. 이미 읽은 위치에서 다음 데이터를 이어서 처리하는 흐름이기 때문에 전체 데이터를 한 번 훑는 작업에 잘 맞는다.

반대로 파일 중간에 있는 작은 데이터 하나만 확인하려면 앞부분을 모두 읽어야 할 수 있어 비효율적이다.

### Direct Access(직접 접근)

원하는 데이터의 위치를 알고 있을 때 해당 위치를 직접 지정해 접근하는 방식이다. 전체 데이터를 앞에서부터 읽지 않아도 특정 위치로 이동할 수 있다는 점이 특징이다.

예를 들어 고정된 크기의 레코드가 있고 100번째 레코드가 필요하다면, 레코드 크기와 번호를 이용해 접근 위치를 계산할 수 있다. 대용량 파일에서 특정 위치의 데이터를 수정하거나, 파일을 여러 구간으로 나누어 처리할 때 이런 방식이 자연스럽다.

다만 “직접 접근”이 물리 디스크의 블록 번호를 애플리케이션이 직접 지정한다는 뜻은 아니다. 애플리케이션은 파일 내부의 논리적인 오프셋을 지정하고, 실제 물리 위치로 변환하는 일은 운영체제와 파일 시스템이 담당한다.

### Indexed Access(인덱스 접근)

별도의 Index(인덱스)에서 원하는 데이터의 위치를 먼저 찾은 후 실제 데이터에 접근하는 방식이다.

```text
Index
  ↓
Data Location
  ↓
Data
```

많은 데이터 중 특정 항목을 반복해서 찾는 상황에 적합하다. 파일 이름에서 실제 데이터 위치를 찾는 파일 시스템의 관리 정보도 넓은 의미의 위치 탐색 구조로 볼 수 있고, 데이터베이스의 인덱스처럼 별도의 탐색 구조를 두어 접근 범위를 줄이는 경우도 있다.

다만 모든 파일 시스템의 파일 접근이 데이터베이스 인덱스와 같은 방식으로 동작한다고 단정하면 안 된다. Indexed Access는 “위치를 찾기 위한 별도의 구조를 먼저 사용한다”는 접근 방식의 관점에서 이해하는 것이 좋다.

세 방식을 상황별로 비교하면 다음과 같다.

| 접근 방식 | 자연스러운 상황 | 상대적으로 불리한 상황 |
| --- | --- | --- |
| Sequential Access | 로그 전체 분석, 전체 파일 복사 | 중간의 한 데이터만 자주 조회 |
| Direct Access | 오프셋을 알고 있는 대용량 파일 접근 | 위치를 계산할 수 없는 가변 데이터 탐색 |
| Indexed Access | 특정 데이터를 반복 탐색, 빠른 위치 검색 | 인덱스 생성·갱신 비용이 필요한 경우 |

어떤 방식이 항상 가장 빠른 것은 아니다. 처음부터 끝까지 읽는 작업에는 순차 접근이 오히려 단순하고 효율적이며, 반복적인 특정 항목 검색에는 인덱스 접근이 더 적합할 수 있다.

## 5. Directory 구조는 왜 발전했을까

Directory(디렉터리)는 단순히 화면에서 파일을 모아 보여주는 폴더가 아니다. 파일 시스템이 파일을 조직하고 탐색하기 위한 논리적인 관리 구조다. 파일이 많아지면 파일 이름만으로는 원하는 파일을 구분하기 어려워지므로, 디렉터리와 경로가 필요해진다.

### Single-Level Directory

Single-Level Directory(단일 레벨 디렉터리)는 모든 파일을 하나의 디렉터리에서 관리하는 구조다.

```text
Directory
 ├─ report.txt
 ├─ image.png
 └─ app.log
```

구조가 단순하다는 장점이 있지만 파일 이름이 전체 공간에서 유일해야 한다. 사용자 수가 늘어나거나 파일 종류가 많아지면 이름 충돌이 발생하고, 파일을 찾고 관리하기도 어려워진다.

### Two-Level Directory

Two-Level Directory(2단계 디렉터리)는 사용자별로 별도의 디렉터리를 둔다.

```text
MFD
 ├─ User A UFD
 ├─ User B UFD
 └─ User C UFD
```

MFD(Master File Directory)는 사용자별 디렉터리를 가리키는 상위 디렉터리다. UFD(User File Directory)는 각 사용자의 파일을 관리하는 디렉터리다.

이 구조에서는 User A와 User B가 각각 `report.txt`라는 이름을 사용해도 사용자별 UFD가 다르기 때문에 이름 충돌을 줄일 수 있다. 하지만 사용자 외의 기준으로 파일을 더 세분화하거나, 디렉터리를 자유롭게 중첩하기에는 한계가 있다.

### Tree-Structured Directory

Tree-Structured Directory(트리 구조 디렉터리)는 현재 우리가 가장 익숙하게 사용하는 구조다. 하나의 루트에서 여러 디렉터리가 가지처럼 뻗고, 각 디렉터리 안에 다시 하위 디렉터리와 파일을 둘 수 있다.

```text
/
├── home
│   └── user
│       └── file.txt
└── var
    └── log
```

이 구조에서는 경로(Path)를 통해 파일을 탐색할 수 있다. `/home/user/file.txt`처럼 루트부터 내려가는 절대 경로를 사용할 수도 있고, 현재 디렉터리를 기준으로 한 상대 경로를 사용할 수도 있다.

### Graph Directory

Graph Directory(그래프 디렉터리)는 파일이나 디렉터리를 여러 위치에서 공유하거나 서로 참조할 수 있는 구조다. 트리에서는 하나의 부모 아래로만 내려가는 흐름이 기본이지만, 그래프에서는 링크를 통해 다른 위치의 파일을 가리킬 수 있다.

공유가 자유로워지는 대신 순환 참조가 생길 수 있다.

```text
A → B → C → A
```

재귀적으로 디렉터리를 탐색하는 프로그램이 방문한 경로를 기록하지 않는다면 위 구조를 계속 따라가며 종료되지 않을 수 있다. 따라서 그래프 구조를 다룰 때는 방문 여부를 기록하거나 링크를 따라갈지 여부를 제한하는 등 순환 참조를 관리하는 전략이 필요하다.

실제 파일 시스템에서도 하드 링크나 심볼릭 링크처럼 공유와 참조를 지원하는 기능을 볼 수 있다. 그래서 겉으로 보이는 경로 구조는 트리처럼 보이더라도, 링크까지 따라가면 그래프처럼 동작할 수 있다는 점을 기억할 필요가 있다.

## 6. File System과 Database는 무엇이 다른가

파일 시스템과 데이터베이스는 모두 데이터를 저장하지만, 관리하는 단위와 제공하는 기능이 다르다.

### File System이 관리하는 것

파일 시스템의 주요 관리 대상은 다음과 같다.

```text
File
Directory
```

파일 시스템은 운영체제가 저장장치를 사용하기 위한 기반 계층이다. 파일 이름, 경로, 권한, 소유자, 저장 공간 같은 파일 단위의 정보를 관리하고, 애플리케이션이 파일을 읽고 쓸 수 있도록 인터페이스를 제공한다.

### Database가 관리하는 것

데이터베이스의 주요 관리 대상은 다음과 같다.

```text
Table
Row
Record
Index
Transaction
```

데이터베이스는 애플리케이션이 데이터를 구조적으로 저장하고 조회하기 위한 시스템이다. 조건에 맞는 행을 검색하고, 여러 작업을 하나의 트랜잭션으로 묶고, 인덱스를 이용해 조회를 최적화하는 등 파일 시스템보다 애플리케이션 데이터 관리에 가까운 기능을 제공한다.

둘의 차이를 “하나는 저장하고 하나는 조회한다”라고 지나치게 단순화하면 안 된다. 파일 시스템도 파일을 찾고 권한을 검사하며 공간을 관리한다. 핵심 차이는 **파일 시스템은 저장장치와 파일·디렉터리를 관리하는 기반 계층이고, 데이터베이스는 그 위에서 애플리케이션 데이터를 구조화하고 질의하는 시스템**이라는 점이다.

```text
Application
    ↓
Database
    ↓
Operating System
    ↓
File System
    ↓
Storage Device
```

Database 역시 결국 운영체제가 제공하는 파일 시스템 위에 데이터를 저장한다. 데이터베이스가 자체적인 테이블, 인덱스, 트랜잭션 개념을 제공하더라도 저장장치에 데이터를 기록하는 가장 아래의 기반까지 직접 대체하는 것은 아니다.

## 7. Java 애플리케이션에서 파일이 저장되기까지

Java 코드에서 다음 API를 호출한다고 해서 Java가 SSD나 HDD를 직접 제어하는 것은 아니다.

```java
Path path = Path.of("logs/app.log");

Files.writeString(path, "Request completed\n");
String content = Files.readString(path);
```

개념적인 흐름은 다음과 같다.

```text
Spring / Java Application
        ↓
Java File I/O API
        ↓
JVM / Native Interface
        ↓
System Call
        ↓
Operating System Kernel
        ↓
File System
        ↓
Disk / SSD
```

`Files.readString()`이나 `Files.writeString()`은 개발자가 파일을 다루기 쉽게 만든 Java API다. 내부적으로 JVM과 운영체제 사이의 구현 계층을 거쳐 운영체제에 파일 작업을 요청하고, 운영체제 커널은 경로와 권한을 확인한 뒤 파일 시스템을 통해 저장장치와 상호작용한다.

이때 `InputStream`, `OutputStream`, `FileChannel` 같은 API도 같은 관점에서 볼 수 있다. Java 개발자는 스트림이나 채널이라는 추상화로 데이터를 읽고 쓰지만, 실제 저장장치의 블록을 어떻게 배치하고 읽을지는 운영체제와 파일 시스템이 맡는다.

이 흐름은 이전에 [System Call을 공부하면서 정리했던 사용자 애플리케이션과 운영체제의 경계](/posts/system-call-fork-exec-wait/)와 연결된다. 사용자 애플리케이션은 운영체제가 관리하는 자원을 임의로 직접 조작하지 않고, System Call을 통해 필요한 기능을 요청한다. 파일 I/O도 그중 하나다.

앞서 [Paging과 Page Replacement를 정리하면서](/posts/paging-page-replacement/) 메모리 주소와 실제 메모리 사이에 운영체제의 관리 계층이 있다는 점을 살펴봤다. 파일 시스템도 비슷한 관점에서 이해할 수 있다. 애플리케이션이 사용하는 경로와 파일이라는 논리적 단위 뒤에 운영체제가 관리하는 실제 저장 위치가 존재한다.

다만 메모리의 가상 주소와 파일 시스템의 경로는 같은 개념이 아니다. 둘 다 복잡한 물리 자원을 추상화하지만, 메모리 접근과 영속적인 파일 저장을 담당하는 서로 다른 관리 영역이다.

## 8. 오늘 학습하며 이해한 점

처음에는 파일 시스템을 단순히 파일을 저장하는 기능이라고 생각했다. Java에서 파일 경로를 넘기고 읽기·쓰기 API를 호출하면 결과를 얻을 수 있으니, 그 아래에서 어떤 일이 일어나는지 깊게 생각하지 않았다.

하지만 파일 시스템은 저장장치의 물리적인 구조를 애플리케이션으로부터 숨기는 추상화 계층에 가까웠다. Metadata가 없다면 프로그램이 파일의 위치, 크기, 소유자, 권한 같은 관리 정보를 직접 알고 있어야 한다는 점에서 파일 시스템의 역할이 더 명확하게 느껴졌다.

Java에서 `Files`, `InputStream`, `OutputStream` 같은 API를 사용할 때도 결국 운영체제의 파일 시스템을 거쳐 저장장치에 접근한다. API가 편리하다는 이유로 파일 저장이 단순한 메서드 호출 하나로 끝난다고 생각했지만, 실제로는 각 계층이 서로 다른 책임을 나눠 가진 결과였다.

이전에 System Call을 공부하면서 사용자 애플리케이션이 운영체제 기능을 직접 사용할 수 없고, 정해진 인터페이스를 통해 요청해야 한다는 점을 정리했다. 이번에 파일 시스템을 함께 보면서 그 System Call이 파일 접근에서도 같은 경계 역할을 한다는 것을 연결해서 이해할 수 있었다.

이번 학습을 통해 파일 시스템을 다음과 같이 정리할 수 있게 되었다.

> **File System은 저장장치의 물리적인 복잡성을 파일과 디렉터리라는 논리적인 구조로 추상화하고, 운영체제가 파일의 데이터와 메타데이터를 안전하게 관리하도록 돕는 계층이다.**

그리고 Java 애플리케이션에서 파일을 읽고 쓰는 흐름은 다음 한 줄로 요약할 수 있다.

```text
Java API → System Call → OS Kernel → File System → Storage Device
```

파일을 저장한다는 말 뒤에 있는 계층 구조를 이해하고 나니, 파일 권한 오류나 경로 문제, I/O 지연 같은 현상을 만났을 때 애플리케이션 코드만 보는 것이 아니라 운영체제와 파일 시스템까지 함께 생각해야 한다는 점도 알게 되었다.

## 한 줄 정리

> 애플리케이션은 디스크의 물리 블록을 직접 관리하지 않는다. Java File I/O API를 통해 운영체제에 요청하고, 파일 시스템이 파일·디렉터리·메타데이터와 저장 공간을 관리한다.
