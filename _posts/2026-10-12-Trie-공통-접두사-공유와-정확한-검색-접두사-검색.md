오늘은 문자열을 문자 단위로 따라가며 저장하는 Trie를 학습했다. 단어 전체를 각각 저장하는 대신 같은 접두사에 해당하는 경로를 공유한다는 점이 핵심이었다. 문자열의 모양에 맞춰 탐색 경로가 만들어지지만 경로가 있다는 사실만으로 단어가 저장됐다고 말할 수는 없었다.

처음에는 `car`와 `care`가 같은 문자를 사용한다는 정도로만 생각했다. 하지만 모의면접 질문을 따라가면서 다음 내용을 따로 확인해야 했다.

- `car`와 `care`는 어느 부분을 함께 사용하는가?
- `ca` 경로가 있다는 사실만으로 `ca`라는 단어가 저장됐다고 할 수 있는가?
- 단어를 삭제할 때 다른 단어가 사용하는 경로는 어떻게 남기는가?
- 접두사 존재 여부와 자동완성 후보 전체 조회는 같은 비용인가?
- 정확한 존재 여부만 필요할 때도 Trie를 선택해야 하는가?

오늘은 개념과 작은 코드의 동작을 학습했다. Trie를 실제 서비스에 적용하거나 성능을 측정한 경험을 정리한 글은 아니다. 질문에 처음 답했던 방식이 예제를 통해 어떻게 바뀌었는지 중심으로 기록한다.

## Trie는 공통 접두사 경로를 공유한다

Trie는 문자열을 한 글자씩 따라가며 노드를 연결한다. 루트는 빈 문자열에서 시작하는 별도의 시작점이다. 루트 자체가 첫 글자를 담은 노드는 아니다. 첫 글자를 담은 노드는 루트의 자식으로 만들어진다.

예를 들어 `car`와 `cat`을 넣으면 두 단어는 `c → a`까지 같은 경로를 사용한다. 그 다음에는 `r`과 `t`에서 갈라진다.

```text
root → c → a → r
             └→ t
```

`car`와 `care`도 `c → a → r`까지 공유한다. `care`를 추가할 때 이미 있는 `r`을 다시 만들지 않고 `r` 아래에 `e`를 이어 붙인다.

이 구조는 자식 수가 최대 두 개로 제한되는 이진 트리와 구분해야 한다. 이진 트리에서는 왼쪽과 오른쪽 자식을 각각 하나씩 둘 수 있지만 Trie의 한 노드는 문자 종류에 따라 여러 자식을 가질 수 있다. `a` 다음에 `b`와 `c`와 `r`이 이어질 수 있는 식이다. 트리라는 모양은 비슷하지만 자식 수를 제한하는 규칙과 노드가 표현하는 정보가 다르다.

### `pen`과 `pet`을 넣으며 경로를 따라가다

`pen`을 처음 넣으면 루트에서 `p`와 `e`와 `n`을 차례로 만든다. `n`에 단어 종료 표시를 설정하면 `pen`이라는 문자열이 끝났다는 상태가 된다.

이후 `pet`을 넣을 때는 루트에서 `p`로 가고 `e`로 가는 경로를 재사용한다. `e` 아래에 없던 `t`만 새로 만들고 `t`에도 종료 표시를 설정한다.

여기서 `pe` 노드는 두 단어가 지나가는 공통 경로다. 하지만 `pe` 자체를 넣으면서 종료 표시를 설정한 것은 아니다. 이 차이를 그림으로 먼저 확인했다.

<img src="/assets/images/2026-10-12-trie/trie-prefix-end.png" alt="루트에서 p와 e를 공유한 뒤 n과 t로 갈라지는 pen과 pet Trie 경로. n과 t에는 종료 표시가 있고 e에는 종료 표시가 없다." loading="eager">

*그림 1. `pen`과 `pet`은 `p → e`를 공유하지만 `e`에 종료 표시가 없으므로 `pe`라는 단어가 저장된 것은 아니다.*

`pen`을 다시 넣는 경우도 구현 정책을 확인해야 한다. 오늘 학습한 Set 형태의 Trie처럼 중복 횟수를 세지 않는 구현이라면 기존 경로와 `n`의 종료 표시를 그대로 사용한다. 구조도 늘지 않고 저장 단어 수도 늘지 않는다. 모든 Trie가 중복을 반드시 같은 방식으로 처리한다고 일반화할 수는 없다. 중복을 허용하거나 횟수를 별도 필드에 저장하는 구현도 가능하기 때문이다.

## 경로 존재와 단어 존재는 다르다

처음에는 `pe`까지 이동할 수 있으면 `search("pe")`도 성공할 것이라고 생각했다. 하지만 `pen`과 `pet`만 저장한 상태에서는 `pe`가 두 단어의 경로라는 사실과 `pe`가 하나의 저장 단어라는 사실이 다르다.

| 연산 | 결과 | 이유 |
| --- | --- | --- |
| `search("pe")` | `false` | 경로는 있지만 마지막 노드에 종료 표시가 없음 |
| `startsWith("pe")` | `true` | 해당 접두사까지 이어지는 경로가 있음 |
| `search("pen")` | `true` | 경로가 있고 마지막 `n` 노드에 종료 표시가 있음 |
| `startsWith("pea")` | `false` | `a`로 이어지는 자식 경로가 없음 |

정확한 검색은 모든 문자를 따라간 뒤 마지막 노드의 종료 표시까지 확인한다. 접두사 검색은 접두사에 해당하는 경로가 존재하는지만 확인한다. 그래서 같은 `pe` 경로를 사용해도 두 연산의 마지막 판단이 달라진다.

사용자는 처음에 마지막 판정을 `node != word.end`처럼 표현했다. 이 표현을 다시 보면서 단어 문자열과 노드를 비교하는 것이 아니라는 점을 알게 됐다. `end`는 노드에 저장된 상태다. 마지막으로 도달한 노드가 단어의 끝인지 확인해야 한다. 정확한 검색의 마지막 반환은 `return node.end;`로 표현할 수 있다.

### 공통 경로를 찾는 코드

아래 코드는 오늘 확인한 핵심 동작만 남긴 발췌 예제다. `root`는 검색을 시작하는 루트 노드다. 루트에서 문자를 하나씩 읽고 해당 자식이 없으면 경로가 없다고 판단한다.

```java
class Node {
    Map<Character, Node> children = new HashMap<>();
    boolean end;
}

private Node findNode(String text) {
    Node node = root;

    for (int i = 0; i < text.length(); i++) {
        node = node.children.get(text.charAt(i));

        if (node == null) {
            return null;
        }
    }

    return node;
}
```

정확한 검색은 `findNode`가 반환한 노드의 `end`를 확인한다. 접두사 검색은 노드가 반환됐는지만 확인한다.

```java
boolean search(String word) {
    Node node = findNode(word);

    if (node == null) {
        return false;
    }

    return node.end;
}

boolean startsWith(String prefix) {
    return findNode(prefix) != null;
}
```

따라서 `pen`과 `pet`을 저장한 뒤 `search("pe")`는 `e.end`가 `false`이므로 `false`다. 같은 `e` 노드를 `startsWith("pe")`로 확인하면 경로 자체는 존재하므로 `true`다. 이 작은 차이를 분리하고 나서야 경로와 단어를 같은 것으로 취급했던 이유가 보였다.

위 코드는 검색 차이를 보여 주기 위한 발췌다. 완전한 클래스나 운영용 입력 검증을 포함한 구현으로 소개하는 코드는 아니다. 오늘 따로 학습하지 않은 빈 문자열과 `null` 입력 정책은 확장하지 않는다.

## 삭제는 공유 경로를 보존해야 한다

삭제를 처음에는 마지막 노드를 바로 제거하는 일로 생각했다. 하지만 Trie에서는 한 노드가 여러 단어의 경로일 수 있다. 그래서 삭제는 종료 표시를 해제하는 일과 더 이상 필요하지 않은 노드 연결을 제거하는 일을 나누어 봐야 한다.

### `car`와 `care`에서 `car` 삭제

`car`의 마지막 `r`은 `care`에서도 사용한다. `car`를 삭제할 때는 `r`의 종료 표시만 해제한다. `r` 아래의 `e` 연결은 `care`를 위해 남겨야 한다.

삭제 후의 판단은 다음과 같다.

- `search("car")`는 `false`다. `r`의 종료 표시가 해제됐기 때문이다.
- `startsWith("car")`는 `true`다. `c → a → r` 경로가 여전히 있기 때문이다.
- `search("care")`는 `true`다. `e`의 종료 표시와 전체 경로가 남아 있기 때문이다.

그림 2의 가운데 패널은 이 상태를 보여 준다. `car`의 종료 표시만 사라졌고 `care`로 가는 경로는 끊기지 않았다.

### `car`와 `card`에서 `card` 삭제

이번에는 `d`가 다른 단어에서 사용되지 않는다. `card`의 종료 표시를 해제한 뒤 `d`로 이어지는 연결도 제거할 수 있다. 하지만 `r`은 `car`의 종료 지점이므로 남겨야 한다. `r`까지 지우면 `car`도 함께 사라진다.

### `car`와 `care`에서 `care` 삭제

`care`를 삭제할 때는 `e`가 다른 단어에서 필요하지 않으므로 `e` 연결을 제거할 수 있다. `r`은 `car`를 위해 보존해야 한다. 같은 초기 Trie에서 출발해도 삭제하는 단어가 어느 쪽인지에 따라 종료 표시만 바꾸거나 연결까지 정리하는 결과가 달라진다.

<img src="/assets/images/2026-10-12-trie/trie-delete-shared-path.png" alt="car와 care의 초기 Trie를 기준으로 car 삭제 후 종료 표시만 해제한 상태와 care 삭제 후 e 연결을 제거한 상태를 비교한 세 패널" loading="eager">

*그림 2. 공유 경로를 가진 단어를 삭제할 때는 종료 표시 해제와 불필요한 연결 제거를 구분해야 한다. 세 패널은 동일한 초기 상태에서 출발한 별도 삭제 사례다.*

정리할 기준은 다음과 같다.

> 해당 노드가 다른 단어의 종료 지점인지 확인한다.
> 다른 단어로 이어지는 자식이 있는지도 확인한다.
> 어느 쪽에도 필요하지 않을 때만 부모와의 연결을 제거한다.

여기서 부모의 참조를 제거하는 동작과 Java 객체의 메모리를 직접 해제하는 동작도 구분해야 한다. Trie 코드에서 `parent.children.remove('e')` 같은 연결을 끊으면 더 이상 해당 객체를 참조하지 않게 될 수 있다. Java의 객체 메모리를 개발자가 직접 해제한다는 뜻은 아니다. 가비지 컬렉터가 회수할 수 있는 상태가 되는 것과 참조를 끊는 코드는 같은 말이 아니다.

## 접두사 충돌 검증에서 확인한 `end`와 `pass`

오늘 모의면접에서는 전화번호처럼 한 문자열이 다른 문자열의 접두사가 되면 안 되는 삽입 코드도 확인했다. 처음에는 `pass`가 무엇을 세는 값인지 설명하지 못했다. 변수 이름만 보고 일반적인 Trie의 의미를 추측하면 안 된다는 점부터 다시 확인했다.

오늘 확인한 특정 구현에서는 다음 의미로 사용됐다.

- `end`: 현재 경로에서 저장된 문자열이 끝났다는 표시
- `pass`: 현재 노드 아래에 자식이 생성됐다는 표시

이 예제의 `pass`는 지금까지 통과한 단어 수를 세는 카운터가 아니다. 다른 Trie 구현에서는 같은 이름을 통과한 문자열 수로 사용할 수도 있지만 오늘의 코드에 그런 의미를 가져오면 안 된다. `end`와 `pass`의 정확한 의미는 변수 이름이 아니라 해당 구현에서 상태를 바꾸고 읽는 방식을 기준으로 확인해야 한다.

### 기존 문자열이 새 문자열의 접두사인 경우

먼저 `911`을 저장한 뒤 `9112`를 넣는 경우를 생각했다. 새 문자열의 문자를 처리하는 중 `9 → 1 → 1` 노드에 도달하면 아직 처리할 문자 `2`가 남아 있다. 그런데 현재 노드의 `end`가 이미 켜져 있다. 기존 문자열 `911`이 새 문자열의 앞부분에서 끝난다는 뜻이다.

즉 기존 문자열이 새 문자열의 접두사다. 반복문 안에서 현재 노드의 `end`를 확인해야 이 상황을 발견할 수 있다.

### 새 문자열이 기존 문자열의 접두사인 경우

반대 방향도 확인했다. `9112`를 먼저 저장한 뒤 `911`을 넣으면 새 문자열의 문자를 모두 처리한 지점에서 반복문이 끝난다. 이때 마지막 `1` 노드 아래에는 기존 문자열 `9112`로 이어지는 자식 `2`가 남아 있다.

이번에는 반복문 안에서 남은 문자를 처리하다가 `end`를 만나는 방식으로는 충분하지 않다. 반복문을 마친 뒤 현재 노드 아래에 기존 경로가 이어지는지 확인해야 한다. 오늘의 특정 구현에서는 `pass`가 그 아래에 자식이 생성됐는지를 나타내는 상태였기 때문에 이 지점의 충돌 판단에 연결됐다.

두 방향을 나란히 그리면 어느 위치에서 검사해야 하는지가 분명해진다.

<img src="/assets/images/2026-10-12-trie/trie-prefix-conflict.png" alt="911 저장 후 9112 삽입과 9112 저장 후 911 삽입에서 각각 기존 종료 지점과 마지막 노드 아래 자식 경로를 확인하는 접두사 충돌 비교" loading="eager">

*그림 3. 접두사 충돌은 새 문자열을 따라가는 중간 지점과 모든 문자를 처리한 마지막 지점에서 각각 확인해야 한다.*

오늘 확인한 코드에서는 마지막 노드의 `end`를 변경한 뒤 실패를 반환하는 흐름도 있었다. 실패를 반환한다고 해서 앞에서 변경한 상태가 자동으로 되돌아가지는 않는다. 삽입 전에 충돌을 모두 검증하거나 실패 시 상태를 명시적으로 복구하는 설계가 별도로 필요하다. 다만 오늘은 원본 코드 전체를 가지고 있지 않으므로 구현을 복원하거나 이 사례를 모든 Trie의 기본 삽입 규칙으로 일반화하지 않는다.

## 시간 복잡도는 문자열 길이와 결과 생성 비용을 구분한다

기호를 먼저 정했다.

- `L`: 검색하거나 삽입하는 문자열의 길이
- `P`: 확인할 접두사의 길이

문자 하나에 해당하는 자식 접근이 `O(1)`이라고 가정하면 삽입과 정확한 검색은 문자열을 한 글자씩 따라가므로 `O(L)`이다. 자식을 배열로 관리하면 문자에서 인덱스를 계산해 접근하는 비용을 `O(1)`으로 볼 수 있다. `HashMap`으로 자식을 관리한다면 이 설명은 평균적인 자식 접근 비용을 전제로 한다.

여기서 기준은 저장한 단어 수가 아니라 이번 연산에서 따라가는 문자열의 길이다. 단어가 많이 저장돼 있어도 탐색 경로에서 문자를 `L`개 처리하는 연산이라면 기본 경로 탐색 비용은 `L`에 비례해 설명한다.

접두사 존재 여부만 확인하는 `startsWith(prefix)`는 `O(P)`로 볼 수 있다. 접두사 경로를 찾은 뒤 더 내려가서 후보를 수집하지 않기 때문이다.

반면 자동완성 후보를 모두 반환하는 작업은 `O(P)`에서 끝나지 않는다. 다음 작업이 이어진다.

1. 접두사 경로를 `P`만큼 찾는다.
2. 접두사 노드 아래의 자손 경로를 탐색한다.
3. 종료 표시가 있는 단어를 수집한다.
4. 각 결과 문자열을 만들고 반환한다.

이때 접두사 노드 아래에서 방문한 자손 노드 수를 `N_sub`라고 하자. 반환하는 후보 수를 `R`이라고 하고 실제로 만들어 반환한 문자열 전체의 문자 수를 `T_out`이라고 하면 자동완성 비용은 대략 `O(P + N_sub + T_out)`처럼 나누어 설명할 수 있다. 구현이 결과를 어떤 자료형으로 만들고 기존 문자열을 어떻게 복사하는지에 따라 세부 비용은 달라지지만 접두사 경로만 찾는 비용과 후보 전체를 만드는 비용이 같지는 않다.

처음에는 하위 노드를 모두 탐색하므로 자동완성이 `O(n)`이라고 답했다. 방향은 맞았지만 전체 단어 수인지 하위 노드 수인지 정의하지 않은 `n` 하나로 뭉뚱그린 설명이었다. 이제는 `startsWith`의 `O(P)`와 하위 경로 탐색 및 결과 생성 비용을 나누어 말해야 한다. Princeton의 [TrieSET API 문서](https://algs4.cs.princeton.edu/code/javadoc/edu/princeton/cs/algs4/TrieSET.html)에서 `keysWithPrefix`가 접두사에 해당하는 키들을 반환하는 연산이라는 점도 이 구분을 확인하는 데 참고했다. 문서의 API와 오늘의 `Node` 구현은 같은 코드가 아니다.

## 자료구조를 선택할 때 필요한 연산을 먼저 본다

### 상품 ID의 정확한 존재 여부만 확인한다면

상품 ID가 있는지만 정확히 확인하고 접두사 검색이나 자동완성이 없다면 HashSet처럼 더 단순한 구조를 먼저 고려할 수 있다. 이미 데이터베이스에서 ID를 조회하고 있다면 서버 메모리에 별도 Trie를 만들어야 하는지도 따로 판단해야 한다. Trie를 추가하면 데이터베이스와 메모리 자료구조 사이의 동기화와 서버 메모리 관리 부담이 생길 수 있다.

이때 HashSet 조회를 문자열 처리 비용까지 포함해 무조건 상수 시간이라고 단정하지도 않아야 한다. 평균적인 해시 기반 조회를 설명할 수는 있지만 키의 해시 계산과 충돌 조건 그리고 자료구조에 넣고 꺼내는 비용을 함께 봐야 한다. 오늘 이전 Hash 학습에서 확인한 것처럼 자료구조 이름 하나만으로 모든 조건의 비용을 결정할 수는 없다.

### 상품명이나 검색어의 접두사 후보를 찾아야 한다면

입력 문자열로 시작하는 후보들을 찾아야 한다면 공통 접두사 경로를 저장하는 Trie가 자연스럽게 연결된다. 다만 오늘 Trie를 서비스에 구현하거나 운영 환경에서 검증한 것은 아니다. 실제 선택에서는 후보 수와 갱신 빈도와 저장 위치를 함께 확인해야 한다.

접두사를 공유한다고 항상 전체 메모리 사용량이 작아지는 것도 아니다. 같은 경로를 재사용해 중복 문자를 줄일 수 있지만 노드 객체와 자식 참조와 종료 상태를 관리하는 공간도 필요하다. 데이터가 작거나 정확한 존재 여부만 필요한 경우에는 이 구조가 문제를 해결하는 데 필요한 복잡도보다 클 수 있다.

결국 자료구조 이름보다 필요한 연산을 먼저 봐야 한다. 정확한 존재 확인과 접두사 탐색은 서로 다른 요구사항이다. 기능에 필요한 구조를 선택하면서 구현 비용과 데이터 동기화와 메모리 관리 비용도 함께 고려해야 한다.

## 오늘의 정리

Trie는 문자열의 공통 접두사 경로를 공유한다. `car`와 `care`는 `c → a → r`을 함께 사용하고 `care`를 추가할 때 `r` 아래에 `e`만 이어진다. `pen`과 `pet`도 `p → e`를 공유하지만 공유 경로가 곧 저장된 단어를 의미하지는 않는다.

경로가 있다는 사실과 단어가 저장됐다는 사실은 다르다. 정확한 검색은 모든 문자를 따라간 뒤 마지막 노드의 종료 표시를 확인한다. 접두사 검색은 해당 경로가 있는지만 확인한다. 그래서 `pen`과 `pet`이 저장된 상태에서 `search("pe")`는 `false`이고 `startsWith("pe")`는 `true`다.

삭제할 때는 종료 표시를 해제하는 일과 불필요한 연결을 제거하는 일을 나누어야 한다. 다른 단어가 사용하는 공유 경로는 보존해야 한다. 접두사 존재 확인은 `O(P)`로 설명할 수 있지만 후보 전체를 반환하는 자동완성은 하위 경로 탐색과 결과 생성 비용이 추가된다.

정확한 존재 여부만 필요하다면 더 간단한 자료구조가 적절할 수 있다. 반대로 접두사 후보를 찾아야 한다면 Trie를 검토할 수 있다. 어느 경우든 자료구조 이름을 먼저 고르기보다 필요한 연산과 구현 및 운영 비용을 함께 확인해야 한다.
