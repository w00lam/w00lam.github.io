처음에는 배열은 인덱스로 빠르게 접근하고 연결 리스트는 중간 삽입·삭제에 유리하다는 문장으로 두 구조를 나누려 했다. 이 정도면 면접 답변으로 충분하다고 생각했다. 그런데 실제로 설명해 보니 두 문장 모두 비용이 생기는 지점을 생략하고 있었다. 배열은 무엇을 옮기는지, 연결 리스트는 무엇을 찾는지까지 말해야 비교가 완성된다.

- 배열은 왜 인덱스로 바로 접근할 수 있을까?
- 인덱스 접근과 원하는 값의 탐색은 어떻게 다를까?
- 배열 중간에 값을 넣으면 왜 다른 요소를 옮겨야 할까?
- 연결 리스트에도 인덱스 API가 있는데 왜 접근 비용은 다를까?
- 연결 리스트의 삽입·삭제는 정말 항상 `O(1)`일까?
- Java의 참조를 실제 메모리 주소라고 설명해도 될까?

오늘 자료구조를 교체하거나 성능을 측정한 것은 아니다. 개념을 확인한 뒤 모의면접에서 직접 설명해 보면서, 연산의 이름 뒤에 어떤 조건을 붙여야 하는지 정리한 하루다.

## 배열은 위치를 계산해 접근한다

배열은 같은 타입의 요소를 정해진 길이만큼 저장하는 구조다. 길이가 `n`이면 유효한 인덱스는 `0`부터 `n - 1`까지다. 한 번 만든 배열 객체의 길이는 나중에 늘리거나 줄이지 못한다.

배열의 인덱스 접근을 설명할 때는 일반적인 배열 모델을 사용한다. 시작 위치에서 요소 하나의 크기와 인덱스를 이용해 원하는 위치를 계산하는 방식이다.

```text
시작 위치 + 인덱스 × 요소 크기
```

요소가 일정한 크기로 배치되어 있다고 보면 `arr[3]`을 읽기 위해 `arr[0]`, `arr[1]`, `arr[2]`를 거칠 필요가 없다. 앞의 요소를 하나씩 방문하지 않고 목표 위치를 바로 계산하므로 인덱스 접근은 `O(1)`로 설명한다.

이 식을 Java 배열의 실제 물리 메모리 배치에 대한 명세처럼 읽으면 안 된다. Java 코드에서 배열의 실제 주소를 직접 확인하거나 주소 연산을 하는 것도 아니다. 배열이 인덱스를 위치로 바꾸는 접근 방식을 이해하기 위한 모델일 뿐이다.

### 인덱스 접근과 값 탐색은 다르다

`arr[3]`은 읽을 위치를 이미 알고 있는 작업이다. 어떤 값이 어느 위치에 있는지 찾는 일은 별도의 탐색이다.

정렬되지 않은 배열에서 원하는 값을 찾는다면 첫 요소부터 비교한다. 값이 중간에 있으면 그 자리에서 멈추지만 마지막에 있거나 아예 없다면 모든 요소를 확인한다. 그래서 최악의 시간 복잡도는 `O(n)`이다.

이진 탐색은 정렬된 배열에서만 사용한다. 가운데 값과 찾는 값을 비교했을 때 어느 쪽을 버릴지 판단하려면 배열의 정렬 순서를 알고 있어야 한다. 정렬되지 않은 배열을 단순히 절반씩 줄이면 찾는 값이 있는 구간을 잘못 제외하게 된다. 정렬이라는 전제가 있을 때 이진 탐색의 탐색 비용을 `O(log n)`으로 말한다. 배열을 정렬하는 비용까지 포함한 전체 작업을 `O(log n)`이라고 말하는 것은 아니다.

## 배열 중간 삽입·삭제에는 요소 이동이 따른다

배열은 중간에 요소를 삽입하거나 삭제하는 API를 기본으로 제공하지 않는다. 배열의 길이도 그대로 유지된다. 직접 자료구조를 구현한다면 배열이 가진 전체 공간과 그중 실제로 사용하는 요소의 수를 따로 기록해야 한다.

예를 들어 길이가 5인 배열에서 현재 요소 4개를 사용하고 있다고 하자.

```java
int[] values = new int[5];
values[0] = 10;
values[1] = 20;
values[2] = 30;
values[3] = 40;
int size = 4;
```

이 상태에서 인덱스 1에 `99`를 넣으려면 결과가 다음처럼 바뀌어야 한다.

```text
사용 전: [10, 20, 30, 40,  _]
결과:    [10, 99, 20, 30, 40]
```

인덱스 1 뒤의 요소를 오른쪽으로 한 칸씩 밀어야 한다. 이동 순서는 `40`, `30`, `20`이다. 가장 뒤의 값부터 비워 둔 칸으로 옮기고 그다음 앞의 값을 옮겨야 원래 순서가 보존된다.

```java
for (int i = size; i > 1; i--) {
    values[i] = values[i - 1];
}
values[1] = 99;
size++;
```

뒤쪽부터 옮기는 이유는 아직 읽지 않은 값을 덮어쓰지 않기 위해서다. 앞에서부터 이동하면 `values[1]`을 `values[2]`에 복사하는 순간 원래 `values[2]`의 값이 사라진다. 이후 `values[2]`에서 읽어야 할 값이 이미 바뀌는 셈이다. 뒤에서 시작하면 각 원본을 읽기 전에 덮어쓰는 일이 생기지 않는다.

삭제는 반대 방향으로 진행한다. 인덱스 1의 값을 지웠다면 `20`을 `10` 다음으로 당기고 `30`, `40`도 한 칸씩 왼쪽으로 옮긴다. 이렇게 삭제한 자리 뒤의 요소가 논리적인 빈자리를 메운다.

```text
삭제 전: [10, 99, 20, 30, 40]
결과:    [10, 20, 30, 40,  _]
```

여기서 `int[]` 배열 객체의 길이가 5에서 4로 줄어드는 것은 아니다. 실제 배열 길이는 계속 5이고 `size`만 4가 된다. 마지막 칸에 이전 값이 남아 있어도 논리적으로 사용하는 범위에서 제외하면 된다.

이동하는 요소 수는 삽입·삭제 위치에 따라 달라진다. 앞쪽에 넣거나 지우는 최악의 경우에는 `n - 1`개에 가까운 요소를 옮긴다. 그래서 시간 복잡도를 `O(n)`으로 정리했다. 오늘은 실제 이동 횟수를 `n - 1`번까지 세어 보면서 이 표기가 단순한 암기가 아니라는 점을 확인했다.

이미 있는 위치의 값을 덮어쓰는 작업은 다르다.

```java
values[1] = 77;
```

이 작업은 다른 요소를 이동하지 않고 한 위치의 값만 바꾸므로 `O(1)`이다. 중간 삽입과 위치 덮어쓰기를 같은 배열 대입으로 묶어 설명하면 안 된다.

## 배열을 확장하면 새 배열과 복사가 필요하다

배열의 길이는 배열 객체에 정해져 있다. 용량이 부족해지면 기존 배열 객체의 길이만 바꿀 수 없다. 더 큰 배열을 새로 만들고 기존 요소를 복사한 뒤 변수가 새 배열을 참조하도록 바꾼다.

참조 대입과 배열 복사는 결과가 다르다.

```java
int[] original = {10, 20, 30};
int[] shared = original;
int[] copied = java.util.Arrays.copyOf(original, 5);

shared[0] = 99;

System.out.println(original[0]);      // 99
System.out.println(copied[0]);        // 10
System.out.println(original.length);  // 3
System.out.println(copied.length);    // 5
```

`shared = original`은 배열을 복사하지 않는다. 두 변수가 같은 배열 객체를 가리키게 할 뿐이다. `shared[0]`을 바꾸면 같은 배열을 읽는 `original[0]`도 바뀐다.

`Arrays.copyOf()`는 새 배열을 만들고 요소를 복사한다. `copied`는 `original`과 다른 배열을 가리키므로 이후 변경이 서로에게 전달되지 않는다. 용량을 늘리는 순간에는 새 배열 생성과 기존 요소 복사라는 비용이 생긴다.

`ArrayList`도 내부적으로 배열을 이용해 요소를 관리하지만 오늘은 내부 성장 비율이나 세부 구현까지 확장하지 않았다. 배열의 길이가 고정되어 있고 용량 변경은 새 배열과 복사로 처리된다는 원리만 연결했다.

## Java 배열의 기본값과 참조 대상

배열을 생성하면 각 요소는 타입에 따른 기본값으로 초기화된다.

| 요소 타입 | 기본값 |
| --- | --- |
| 정수형 | `0` |
| `boolean` | `false` |
| `char` | `\u0000` |
| 참조형 | `null` |

`char`의 기본값인 `\u0000`은 문자 `'0'`이나 `'A'`가 아니다. 줄바꿈 문자도 아니다. 화면에 눈에 보이는 글자가 없는 문자 값으로 이해해야 한다.

참조형 배열의 각 칸에는 객체 자체가 아니라 객체를 가리키는 참조가 들어간다.

```java
String[] names = new String[2];

System.out.println(names[0]); // null
System.out.println(names[2]); // ArrayIndexOutOfBoundsException
```

`new String[2]`를 실행했다고 `String` 객체 두 개가 자동으로 만들어지는 것도 아니다. 길이 2인 배열 객체가 만들어지고 각 요소가 `null`로 초기화된다. 실제 `String` 객체를 사용하려면 별도로 생성해 해당 요소에 넣어야 한다.

배열이 담은 참조와 그 참조가 가리키는 객체는 나누어 봐야 한다. 객체들이 물리 메모리에 연속적으로 배치된다고 단정할 필요도 없다. 배열 슬롯과 참조 대상은 서로 다른 개념이기 때문이다.

![기본형 배열의 값 슬롯과 참조형 배열의 참조 슬롯 및 별도 객체를 비교한 개념도](/assets/images/2026-10-06-array-linked-list/array-values-and-references.svg)

*그림 1. 배열 슬롯에는 값이 들어갈 수도 있고 객체를 가리키는 참조가 들어갈 수도 있다. 물리 주소와 실제 배치를 나타내는 그림이 아닌 개념도다.*

## 연결 리스트는 노드의 참조로 순서를 만든다

배열이 인덱스와 위치 계산으로 접근한다면 연결 리스트는 노드 사이의 연결로 순서를 만든다. 노드 하나는 저장할 데이터와 다음 노드를 가리키는 참조를 묶어 가진다. 값이 들어 있는 칸과 다음 노드로 이어지는 연결이 한 단위가 된다.

```text
head → [data | next] → [data | next] → [data | null]
```

이 구조가 단일 연결 리스트다. 각 노드는 다음 노드만 알고 이전 노드를 직접 가리키지 않는다. 이중 연결 리스트는 이전 노드와 다음 노드를 모두 참조한다.

```text
null ← [prev | data | next] ⇄ [prev | data | next] ⇄ [prev | data | next] → null
```

`head`는 첫 노드를 가리킨다. `tail`을 함께 관리하는 구현이라면 마지막 노드에 바로 접근한다. 일반적인 비순환 단일 연결 리스트에서 마지막 노드의 `next`는 `null`이다.

새 요소를 넣을 때는 새 노드를 만들고 기존 노드의 참조 관계를 바꾼다. 노드들이 물리적으로 서로 인접한 위치에 있을 필요는 없다. 각 노드의 `next` 또는 `prev`를 따라가며 떨어져 있는 노드 사이에 논리적인 순서를 만든다.

여기서 일반적인 단일 연결 리스트의 원리와 Java `LinkedList`의 구현을 구분해야 한다. Java의 `LinkedList`는 이중 연결 구조를 사용하므로 노드에 `prev`와 `next`가 함께 있다고 설명한다. 그렇다고 `head`와 `tail`이 있다는 이유만으로 모든 위치에 `O(1)`로 접근하는 것은 아니다. 단일 연결 리스트에서 `tail`만 알고 있어도 마지막 노드의 이전 노드를 바로 알 수는 없다.

## 인덱스 API가 있어도 노드를 따라가야 한다

처음에는 연결 리스트에 인덱스가 없어서 위치 접근을 할 수 없다고 생각했다. Java API를 확인하면서 이 생각을 고쳤다. `LinkedList`에도 `get(index)`가 있다. 하지만 메서드에 인덱스를 전달할 수 있다는 사실과 배열처럼 위치를 계산한다는 사실은 다르다.

Java `LinkedList`는 목표 인덱스에 가까운 앞쪽 또는 뒤쪽에서 시작해 노드를 따라간다. 요소가 10개이고 인덱스가 `0`부터 `9`까지라면 인덱스 7을 찾을 때 뒤에서 출발한다.

```text
tail: 9 → 8 → 7
```

이 경우 `9`에서 `8`로 한 번, `8`에서 `7`로 한 번 이동하므로 총 두 번이다. 뒤에서 시작하는 경우의 이동 횟수는 다음과 같다.

```text
n - 1 - index = 10 - 1 - 7 = 2
```

가까운 끝을 고르는 최적화가 있어도 일반적인 인덱스 접근의 최악 시간 복잡도는 `O(n)`이다. `get(index)`는 배열로 캐스팅해야 쓰는 기능이 아니다. 연결 리스트가 내부 노드를 따라가 목표 위치의 요소를 반환하는 API다.

![head와 tail을 가진 이중 연결 리스트에서 인덱스 7을 찾기 위해 tail에서 9, 8, 7로 이동하는 경로](/assets/images/2026-10-06-array-linked-list/linked-list-index-traversal.svg)

*그림 3. `LinkedList.get(7)`은 인덱스를 주소로 계산하지 않는다. 가까운 끝인 `tail`에서 노드를 두 번 따라간다.*

## 위치 탐색과 연결 변경의 비용을 나눈다

연결 리스트의 삽입·삭제를 설명할 때 가장 먼저 확인할 조건은 연결을 바꾸기 전에 필요한 노드를 이미 알고 있는지다.

단일 연결 리스트에서 `A` 다음에 `B`가 있고 그 사이에 `X`를 넣는 상황을 보자.

```java
x.next = a.next;
a.next = x;
```

`X`가 먼저 `B`를 참조하게 해야 한다. 그다음 `A`가 `X`를 참조하도록 바꾼다. 순서를 반대로 바꾸면 `A`가 원래 가리키던 `B`와의 연결을 잃을 수 있다.

이 두 줄은 사용자 정의 노드로 연결 리스트의 원리를 설명한 코드다. Java `LinkedList`의 내부 노드를 외부에서 직접 수정하는 공개 API를 보여주는 예제는 아니다.

이중 연결 리스트에서는 앞뒤 참조를 함께 갱신해야 한다. `A`, `B` 사이에 `X`를 넣는다면 `X.prev`와 `X.next`를 설정하고 `A.next`, `B.prev`도 `X`를 가리키게 만들어야 한다. 바뀌어야 할 연결이 더 많지만 필요한 노드 참조를 확보한 뒤의 연결 변경 자체는 `O(1)`로 볼 수 있다.

인덱스나 값만 알고 있다면 먼저 해당 위치나 노드를 찾아야 한다. 연결 리스트를 앞이나 뒤에서 따라가는 탐색 비용은 `O(n)`이 된다. 위치를 찾은 뒤 연결을 바꾸는 작업이 `O(1)`이라는 설명과 인덱스로 중간 요소를 삽입·삭제하는 전체 비용은 구분해야 한다. 일반적인 인덱스 기반 중간 삽입·삭제는 탐색 비용 때문에 전체적으로 `O(n)`이다.

처음에는 중간 삽입·삭제가 많으면 연결 리스트가 배열보다 항상 유리하다고 생각했다. 지금은 비용의 위치를 나누어 본다. 배열은 요소를 옮기는 데 시간이 들고 연결 리스트는 목표 위치를 찾는 데 시간이 든다. 어느 구조가 더 나은지는 변경 위치를 이미 알고 있는지와 실제 접근 패턴에 달려 있다.

삭제도 같은 조건을 확인해야 한다. 단일 연결 리스트에서는 삭제할 노드만 알고 있어도 이전 노드의 `next`를 항상 바꿀 수 있는 것은 아니다. 이전 노드의 참조가 필요하기 때문이다. 이중 연결 리스트에서 필요한 내부 노드에 접근할 수 있는 경우 `prev`와 `next`를 이용해 연결을 바꾼다.

그래서 “노드를 알면 삭제가 `O(1)`”이라는 문장에는 연결 변경에 필요한 참조를 이미 확보했다는 조건을 붙여야 한다. Java `LinkedList`의 공개 API가 내부 노드를 직접 제공한다는 뜻으로 받아들이면 안 된다.

![배열은 뒤 요소를 옮기고 단일 연결 리스트는 A와 B 사이에 X를 연결하는 과정을 비교한 개념도](/assets/images/2026-10-06-array-linked-list/array-vs-linked-list-insertion.svg)

*그림 2. 배열의 중간 삽입은 뒤 요소 이동에 비용이 생기고 연결 리스트의 삽입은 위치 탐색과 연결 변경을 나누어 봐야 한다.*

## Java 참조와 실제 주소를 구분한다

연결 리스트를 설명하면서 참조를 논리 주소나 가상 주소처럼 표현했던 부분도 고쳤다. Java의 참조는 객체를 가리키는 값으로 이해하는 편이 정확하다. 이를 물리 메모리 주소나 가상 주소 숫자와 동일시하면 안 된다.

참조로 객체의 필드와 메서드에 접근한다. 하지만 일반 Java 코드에서 포인터 산술처럼 주소에 숫자를 더해 다음 객체를 찾지는 않는다. 연결 리스트에서 `next`에 저장된 참조를 읽고 그 참조가 가리키는 다음 노드로 이동하는 방식이다.

데이터 값이 같아도 서로 다른 노드가 존재한다.

```java
Node first = new Node(10);
Node second = new Node(10);
Node alias = first;

System.out.println(first != second); // true: 데이터가 같아도 다른 노드
System.out.println(first == alias);  // true: 같은 노드를 함께 참조
```

여기서 데이터 중복과 같은 객체를 참조하는 일은 다르다. `first`와 `second`는 같은 값 `10`을 담지만 서로 다른 노드다. `alias`는 `first`와 같은 노드를 가리키는 다른 참조 변수다.

[JVM 메모리 영역 — 변수와 객체의 생명주기는 왜 다를까?](/posts/java-jvm-memory-lifecycle/)에서 정리한 것처럼 참조 변수와 실제 객체를 나누어 봐야 한다. 오늘은 JVM 내부의 참조 표현이나 메모리 주소 구현까지 확장하지 않고 자료구조의 연결을 따라가는 개념에 집중했다.

## 작업 전체 비용으로 자료구조를 선택한다

배열과 연결 리스트를 비교할 때는 연산 이름 하나만 보지 않고 비용이 생기는 조건까지 함께 적어야 한다.

| 비교 항목 | 배열 | 연결 리스트 |
| --- | --- | --- |
| 인덱스 접근 | 위치를 계산하므로 `O(1)` | 노드를 따라가므로 최악 `O(n)` |
| 정렬되지 않은 데이터의 값 탐색 | 최악 `O(n)` | 최악 `O(n)` |
| 중간 삽입·삭제 | 요소 이동 때문에 최악 `O(n)` | 위치를 이미 알고 연결만 바꾸면 `O(1)`, 위치 탐색까지 포함하면 `O(n)` |
| 크기 변경 방식 | 새 배열 생성과 복사 | 새 노드 생성과 연결 변경 |
| 연결 정보 관리 | 인덱스와 배열 길이로 관리 | 노드의 `next`, 필요하면 `prev`로 관리 |

정렬되지 않은 데이터의 값 탐색은 두 구조 모두 앞에서부터 확인해야 한다. 연결 리스트라고 값 탐색이 자동으로 빨라지는 것은 아니다. 중간 삽입·삭제도 연결 리스트가 무조건 `O(1)`인 것은 아니다. 목표 위치를 찾는 시간이 포함되는지 확인해야 한다.

### 하루 24시간별 데이터라면 배열을 고른다

0시부터 23시까지 시간대별 데이터를 저장한다면 시간 자체를 인덱스에 대응시킬 수 있다. 데이터 개수가 24개로 고정되어 있고 특정 시간의 값을 바로 읽을 수 있다. 중간에 요소를 넣거나 삭제할 일도 거의 없다.

이 상황에서는 배열이 자연스럽다.

```java
int[] hourlyCount = new int[24];
int countAtNine = hourlyCount[9];
```

인덱스가 곧 시간대라는 점이 코드에 드러나고 배열의 고정 길이도 문제가 되지 않는다. 시간대별 집계처럼 백엔드에서 고정된 범위의 값을 메모리에서 관리하는 상황을 생각할 때 적용할 수 있는 판단 기준이다.

### 계속 늘어나는 목록은 조회 방식까지 본다

요소 수가 계속 늘어나는 목록에서는 배열 용량을 초과할 때 새 배열 생성과 복사가 필요하다. 그렇다고 가변 데이터라는 이유만으로 연결 리스트를 고르면 안 된다.

목록을 주로 인덱스로 읽는지, 값을 순서대로 순회하는지, 삽입 위치를 이미 알고 있는지, 위치를 찾는 탐색이 더 자주 일어나는지 함께 확인해야 한다. 배열은 이동과 확장 비용을 부담하는 대신 위치 접근이 단순하다. 연결 리스트는 노드 연결을 바꾸는 대신 위치를 찾는 비용을 부담한다.

## 오늘의 정리

오늘은 배열과 연결 리스트를 연산 이름으로만 비교하지 않으려고 했다. 배열은 인덱스를 위치로 바꾸는 접근이 빠르지만 중간 변경에는 요소 이동이 필요하다. 배열을 확장할 때도 기존 배열의 길이를 바꾸는 것이 아니라 새 배열을 만들고 요소를 복사한다.

연결 리스트는 노드의 참조로 순서를 만든다. 위치를 이미 알고 필요한 참조를 확보했다면 연결 변경은 `O(1)`로 처리한다. 인덱스나 값으로 목표 위치를 찾아야 한다면 탐색 비용이 발생한다. 같은 `O(n)`이라도 배열은 요소 이동 때문에, 연결 리스트는 위치 탐색 때문에 시간이 든다.

Java의 참조는 객체를 가리키는 값이지 코드에서 다루는 실제 메모리 주소 숫자가 아니다. 배열의 참조형 요소와 연결 리스트의 `next`를 이해할 때도 참조 변수와 대상 객체를 분리해서 봐야 한다.

자료구조는 “배열이 빠른가, 연결 리스트가 빠른가”만으로 고르는 것이 아니다. 인덱스 접근과 값 탐색의 비율, 변경 위치를 찾는 방식, 크기 변화와 연결 관리 비용을 한 작업 흐름으로 보고 선택해야 한다.

> 배열은 위치 계산을 활용하고 연결 리스트는 연결 관계를 활용한다. 선택 기준은 자료구조의 이름이 아니라 전체 작업 흐름에 있다.
