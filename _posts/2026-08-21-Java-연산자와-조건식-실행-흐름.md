## 연산자를 다시 보게 된 계기

Java 코드를 읽으면서 연산자를 `+`, `==`, `&&` 같은 기호의 모음으로만 알고 있었다. 값을 더하거나 비교할 때 사용하는 문법이라는 정도로 이해하고 있었던 것이다.

그런데 조건문을 따라가다 보니 연산자는 단순히 결과를 계산하는 기호가 아니었다. 어떤 조건을 먼저 확인하는지, 오른쪽 표현식이 실제로 실행되는지, 실패한 요청이 핵심 로직까지 도달하는지를 결정하고 있었다.

오늘은 연산자의 종류를 전부 외우기보다 다음 관점으로 정리했다.

> 연산자는 단순한 기호가 아니라 프로그램의 실행 흐름과 조건 평가 방식을 결정한다.

이전에 [Java 변수와 타입: 값의 저장부터 도메인 모델링까지](/posts/java-variable-type/)를 공부하면서 타입이 연산과 비교 방식에도 영향을 준다는 점을 정리했다. 이번에는 그 연산이 실제 조건식 안에서 어떤 순서로 평가되는지에 초점을 맞춰 보았다.

## 1. 연산자는 값을 계산하고 상태를 판단하는 문법이다

Java에서 연산자(Operator)는 값을 계산하거나 비교하고, 변수에 값을 대입할 때 사용한다. 자주 만나는 연산자는 다음과 같다.

| 종류 | 대표 연산자 | 주로 하는 일 |
| --- | --- | --- |
| 산술 연산자 | `+`, `-`, `*`, `/`, `%` | 숫자 계산 |
| 비교 연산자 | `==`, `!=`, `>`, `<`, `>=`, `<=` | 두 값을 비교해 `boolean` 결과 생성 |
| 논리 연산자 | `&&`, `||`, `!` | 조건을 결합하거나 반전 |
| 대입 연산자 | `=`, `+=`, `-=`, `*=`, `/=` | 변수에 값을 저장하거나 계산 결과 반영 |
| 증감 연산자 | `++`, `--` | 값을 1씩 증가 또는 감소 |

예를 들어 아래 코드는 산술 연산과 대입 연산을 함께 사용한다.

```java
int total = 10 + 5;
```

`10 + 5`를 먼저 계산한 뒤 그 결과인 `15`를 `total`에 대입한다. 여기서 중요한 점은 연산자를 단독으로 보는 것이 아니라, 하나의 표현식(Expression)이 어떤 순서로 계산되는지 함께 읽는 것이다.

## 2. Operator Precedence(연산자 우선순위)와 괄호

연산자가 여러 개 등장하면 모든 연산이 왼쪽에서 오른쪽으로 단순하게 실행되지는 않는다. 연산자마다 우선순위가 있기 때문이다.

```java
int result = 1 + 3 * 2;
```

실행 결과는 다음과 같다.

```text
7
```

곱셈이 덧셈보다 우선순위가 높아서 `3 * 2`가 먼저 계산되고, 그 다음 `1 + 6`이 계산된다.

괄호를 사용하면 평가 순서를 명시적으로 바꿀 수 있다.

```java
int result = (1 + 3) * 2;
```

실행 결과는 다음과 같다.

```text
8
```

이번에는 괄호 안의 `1 + 3`이 먼저 계산되기 때문이다.

우선순위를 알고 있는 것은 필요하지만, 실무 코드에서 복잡한 우선순위를 개발자가 계속 암기해서 사용하는 것이 항상 좋은 방법은 아닌 것 같다. 다음처럼 각 조건을 괄호로 감싸면 코드가 전달하려는 의도가 더 분명해진다.

```java
boolean valid = (age >= 20) && (status == ACTIVE);
```

괄호가 없어도 Java가 같은 방식으로 해석할 수 있지만, 괄호를 사용하면 읽는 사람이 `age >= 20`과 `status == ACTIVE`라는 두 조건을 결합했다는 사실을 바로 파악할 수 있다. 코드에서는 짧음보다 의도가 먼저 읽히는 것이 더 중요할 때가 많다.

## 3. `&&`와 `&`의 차이는 오른쪽을 실행하는지에 있다

오늘 가장 중요하게 느낀 부분은 `&&`와 `&`가 모두 AND처럼 보이지만, 오른쪽 표현식을 평가하는 방식은 다르다는 점이었다.

```java
if (user != null && user.isActive()) {
    // 사용자 처리
}
```

`&&`는 Logical AND(논리 AND) 연산자다. 왼쪽 조건인 `user != null`이 `false`라면 전체 결과도 이미 `false`로 결정된다. 따라서 오른쪽의 `user.isActive()`는 평가하지 않는다. 이런 방식을 Short-Circuit Evaluation(단락 평가)이라고 한다.

![Java &&와 &의 단락 평가 비교 다이어그램](/assets/images/2026-08-21-java-operators/short-circuit-evaluation.png)

반면 `&`를 `boolean` 식에 사용하면 양쪽 식을 모두 평가한다.

```java
if (user != null & user.isActive()) {
    // 사용자 처리
}
```

만약 `user`가 `null`이라면 `user != null`은 `false`가 된다. 하지만 `&`는 오른쪽도 평가하므로 `user.isActive()`까지 실행하려고 한다. 그 결과 `NullPointerException`이 발생할 수 있다.

따라서 두 연산자의 차이를 단순히 “AND 연산자가 두 개 있다”라고 외우기보다 다음처럼 이해하는 편이 더 정확했다.

* `&&`: 왼쪽 결과로 전체 결과가 결정되면 오른쪽을 평가하지 않는다.
* `&`: `boolean` 식에서 양쪽을 모두 평가한다. 숫자에서는 비트 AND 연산자로도 사용된다.

`||`도 같은 원리로 동작한다. 왼쪽 조건이 `true`라면 전체 결과가 이미 `true`이므로 오른쪽 조건을 평가하지 않는다.

```java
boolean allowed = isAdmin() || hasPermission();
```

`isAdmin()`이 `true`라면 `hasPermission()`은 실행되지 않는다. 결국 논리 연산자는 결과만 만드는 것이 아니라, 뒤에 있는 표현식의 실행 여부도 결정한다.

## 4. 단락 평가가 Spring 백엔드 코드에서 중요한 이유

단락 평가를 처음에는 불필요한 계산을 줄이는 성능 최적화 정도로 생각했다. 하지만 백엔드 코드를 떠올려 보니 `null` 접근을 막거나, 외부 메서드 호출을 막고, 조건 평가 순서를 통제하는 데도 사용할 수 있었다.

```java
if (request != null && request.isValid()) {
    process(request);
}
```

이 코드는 `request`가 존재할 때만 `request.isValid()`를 호출한다. 요청 객체가 없는 상황에서 객체의 메서드를 호출하지 않으므로 `null` 접근을 피할 수 있다.

또 다른 예시는 실패 조건을 앞에 두는 방식이다.

```java
if (user == null || !user.isActive()) {
    return;
}
```

`user == null`이 `true`라면 `||`의 오른쪽인 `!user.isActive()`는 평가되지 않는다. 그리고 사용자가 없거나 비활성 상태라면 뒤의 처리로 넘어가지 않는다.

이처럼 단락 평가는 다음과 같은 목적으로 활용될 수 있다.

* 불필요한 연산을 방지한다.
* `null`인 객체에 접근하는 것을 피한다.
* 비용이 있거나 외부 상태에 영향을 주는 메서드 호출을 건너뛸 수 있다.
* 조건식 안에서 어떤 검사를 먼저 할지 표현한다.

다만 오른쪽 조건에 상태 변경 같은 Side Effect(부수 효과)를 넣으면 주의해야 한다.

```java
if (isValid() && saveLog()) {
    // 다음 처리
}
```

`isValid()`가 `false`이면 `saveLog()`는 실행되지 않는다. 따라서 로그 저장이 조건 평가에 따라 실행되거나 생략된다. 결과만 보면 짧은 코드지만, 실행 흐름을 이해하려면 `isValid()`의 결과가 `saveLog()` 호출 여부까지 결정한다는 사실을 알아야 한다. 조건식은 가능하면 판단을 표현하는 역할에 집중시키고, 중요한 상태 변경은 별도의 문장으로 분리하는 편이 읽기 쉬울 수 있다.

## 5. 대입 연산자와 복합 대입 연산자

대입 연산자(Assignment Operator)는 오른쪽의 값을 왼쪽 변수에 저장한다.

```java
int a = 10;
a += 5;
```

실행이 끝난 뒤 `a`의 값은 다음과 같다.

```text
15
```

`a += 5`는 개념적으로 다음과 비슷하다.

```java
a = a + 5;
```

그래서 `+=`, `-=`, `*=`, `/=` 같은 복합 대입 연산자(Compound Assignment Operator)는 기존 값을 기준으로 계산한 뒤 다시 대입하는 코드를 짧게 표현할 때 사용한다.

다만 Java에서는 두 표현식이 형변환 측면에서 완전히 동일하지 않을 수 있다.

```java
short value = 10;
value += 1;       // 가능
```

`value += 1`은 복합 대입 연산자에 포함된 변환 때문에 대입이 가능하다. 반면 다음 코드는 컴파일되지 않는다.

```java
short value = 10;
value = value + 1; // 컴파일 오류
```

`value + 1`을 계산하는 과정에서 `short`가 `int`로 타입 승격(Type Promotion)되기 때문이다. 따라서 `int` 결과를 `short`에 넣으려면 명시적인 형변환이 필요하다.

```java
short value = 10;
value = (short) (value + 1); // 가능
```

숫자 연산에서는 변수의 타입 그대로 계산되지 않고 더 넓은 타입으로 승격될 수 있다는 점을 기억해 두면, 복합 대입과 일반 대입 사이의 차이를 만났을 때 원인을 추적하기 쉬울 것 같다.

## 6. 전위 증가와 후위 증가

증감 연산자(Increment and Decrement Operator)는 변수의 값을 1 증가시키거나 감소시킨다. 단독 문장으로 쓰면 전위와 후위의 최종 결과는 같다.

```java
a++;
++a;
```

두 문장 모두 실행 후 `a`를 1 증가시킨다. 하지만 다른 연산과 함께 사용하면 값을 반환하는 시점이 달라진다.

```java
int a = 10;
int b = a++;
```

실행 결과는 다음과 같다.

```text
a = 11
b = 10
```

후위 증가(`a++`)는 현재 값을 먼저 사용한 뒤 `a`를 증가시킨다.

이번에는 전위 증가를 사용한다.

```java
int a = 10;
int b = ++a;
```

실행 결과는 다음과 같다.

```text
a = 11
b = 11
```

전위 증가(`++a`)는 `a`를 먼저 증가시킨 뒤 증가한 값을 사용한다.

이 차이를 알면 코드를 해석할 수 있지만, 하나의 복잡한 표현식 안에 증감 연산자를 여러 개 넣으면 읽는 사람이 평가 순서를 계속 추적해야 한다. 그래서 `a++`와 `++a`는 필요한 곳에 사용하되, 복잡한 표현식에서는 증가와 값 사용을 별도의 문장으로 나누는 편이 의도를 전달하기 쉬울 것 같다.

## 7. 연산자에서 조건문 설계로

연산자를 공부하면서 결국 중요한 것은 연산자 자체보다 조건식을 어떻게 구성하느냐라는 생각이 들었다. 같은 조건을 검사하더라도 중첩된 코드와 실패 조건을 먼저 제거하는 코드는 읽는 흐름이 다르다.

다음 코드는 조건이 안쪽으로 계속 중첩되어 있다.

```java
if (user != null) {
    if (user.isActive()) {
        if (user.hasPermission()) {
            process(user);
        }
    }
}
```

조건이 많아질수록 핵심 로직인 `process(user)`가 어디에 있는지 찾기 위해 여러 단계의 들여쓰기를 따라가야 한다.

같은 조건을 Early Return(조기 반환) 또는 Guard Clause(가드 절) 형태로 표현하면 실패 조건을 먼저 제거할 수 있다.

```java
if (user == null) {
    return;
}

if (!user.isActive()) {
    return;
}

if (!user.hasPermission()) {
    return;
}

process(user);
```

이 코드에서는 위에서부터 사용자가 없는 경우, 비활성 상태인 경우, 권한이 없는 경우를 빠르게 반환한다. 그 결과 마지막의 `process(user)`는 앞의 조건을 모두 통과한 경우에만 실행된다는 사실이 자연스럽게 드러난다.

Early Return이 항상 좋은 것은 아니다. 반환 지점이 지나치게 많아지거나 하나의 메서드 안에서 조건 분기가 복잡해지면 오히려 실행 흐름을 추적하기 어려울 수 있다.

그래서 오늘 정리한 핵심은 Early Return이라는 형식을 무조건 사용하는 것이 아니다.

> 실패 조건이나 실행할 필요가 없는 조건을 앞에서 제거해 핵심 비즈니스 로직을 단순하게 만든다.

조건문은 결과만 맞으면 끝나는 문법이 아니라, 어떤 상태에서 어디까지 실행할지를 설계하는 코드이기 때문이다.

## 8. 오늘 학습하며 바뀐 생각

처음에는 연산자를 값을 계산하거나 비교하는 기호 정도로 생각했다. 하지만 `&&`의 단락 평가를 따라가 보면서 연산자가 실제로는 오른쪽 표현식의 실행 여부까지 결정할 수 있다는 점을 알게 됐다. `||`도 같은 방식으로 조건의 순서와 호출 여부에 영향을 주고, `+=`나 증감 연산자도 값을 언제 계산하고 사용하는지가 결과에 연결되어 있었다.

오늘 학습한 내용을 정리하면 다음과 같다.

* Operator Precedence(연산자 우선순위)는 표현식이 계산되는 순서를 결정한다.
* `&&`와 `||`는 결과가 이미 결정되면 오른쪽 조건을 평가하지 않는다.
* `&`는 `boolean` 식에서 양쪽을 모두 평가하므로 `&&`와 실행 흐름이 다르다.
* 복합 대입 연산자는 일반 대입과 비슷해 보여도 숫자 타입 승격과 형변환에서 차이가 날 수 있다.
* 전위와 후위 증감 연산자는 값을 사용하는 시점이 다르다.
* 조건식을 어떻게 배치하느냐에 따라 핵심 로직이 읽히는 방식이 달라진다.

결국 중요한 것은 복잡한 표현식을 짧게 만드는 것이 아니라, 어떤 조건부터 평가되고 어떤 코드는 실행되지 않는지가 코드에서 자연스럽게 드러나도록 작성하는 것이다. 앞으로 Spring 백엔드 코드를 읽거나 작성할 때도 조건식의 결과만 확인하지 않고, 각 표현식의 평가 순서와 호출 여부까지 함께 살펴봐야겠다고 정리했다.
