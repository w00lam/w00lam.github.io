## 비슷해 보였던 두 가지 추상화

상속과 오버라이딩, 다형성을 공부한 뒤 추상 클래스와 인터페이스를 이어서 살펴봤다. 그런데 두 개념의 차이가 바로 보이지 않았다.

둘 다 직접 객체를 만들기보다 자식 클래스나 구현 클래스가 실제 동작을 완성하는 구조처럼 느껴졌기 때문이다.

```java
interface PaymentService {

    void pay();
}
```

```java
abstract class BasePaymentService {

    public abstract void pay();
}
```

두 구조 모두 결제 방식에 따라 `pay()`를 구현한다. 처음에는 `abstract`와 `interface`의 문법 차이만 외우면 되는 줄 알았다.

설계에 적용하려 하니 문법보다 먼저 답해야 할 질문이 생겼다.

> **둘 다 추상화를 제공하는데, 실제 설계에서는 무엇을 기준으로 선택해야 할까?**

이번 글에서는 이 질문을 따라가며 두 추상화가 설계에서 맡는 역할을 정리해 보았다.

## 인터페이스는 구현 객체가 지켜야 할 계약이다

결제 서비스가 제공해야 할 기능부터 인터페이스로 정의해 보았다.

```java
public interface PaymentService {

    void pay();
}
```

이 인터페이스에는 결제 기능이 있어야 한다는 사실만 적혀 있다. 실제 결제 방식은 구현 클래스가 결정한다.

```java
public class CardPaymentService implements PaymentService {

    @Override
    public void pay() {
        System.out.println("카드 결제");
    }
}
```

```java
public class AccountPaymentService implements PaymentService {

    @Override
    public void pay() {
        System.out.println("계좌 결제");
    }
}
```

여기서 중요한 것은 인터페이스가 구현체마다 같은 코드를 나눠 주는 구조가 아니라는 점이다.

> **`PaymentService`를 구현한다면 `pay()`라는 기능을 제공해야 한다는 계약을 정의한다.**

호출부는 구현체가 아니라 이 계약을 기준으로 작성한다.

```java
public class PaymentController {

    // 실제 구현체가 아니라 계약에 의존한다.
    private final PaymentService paymentService;

    public PaymentController(PaymentService paymentService) {
        this.paymentService = paymentService;
    }

    public void pay() {
        paymentService.pay();
    }
}
```

`PaymentController`는 주입된 객체가 `CardPaymentService`인지 `AccountPaymentService`인지 알 필요가 없다. 두 객체 모두 `PaymentService`라는 계약을 지키므로 컨트롤러는 같은 방식으로 `pay()`를 호출한다.

이 부분은 이전에 공부한 다형성과 이어진다. `PaymentService` 타입으로 바라봐도 실제 객체의 `pay()` 구현이 호출된다. 호출부가 계약만 사용하면 구현체를 바꿀 때 수정 범위도 줄어든다.

Spring에서는 생성자 주입으로 이 구조가 자연스럽게 드러난다. 컨트롤러나 서비스가 구체 클래스 대신 인터페이스 타입을 주입받으면 구현의 세부 내용과 호출부가 분리된다.

## 추상 클래스는 상태와 행동을 공유하는 상속 구조다

인터페이스만으로는 부족한 경우도 있다. 여러 결제 서비스가 같은 결제사 정보와 검증 절차를 공유한다면 공통 상태와 행동을 한곳에 모은다.

```java
public abstract class BasePaymentService {

    protected final String provider;

    protected BasePaymentService(String provider) {
        this.provider = provider;
    }

    public void validate() {
        System.out.println("결제 검증");
    }

    public abstract void pay();
}
```

```java
public class CardPaymentService extends BasePaymentService {

    public CardPaymentService() {
        // 부모가 가진 provider 상태를 초기화한다.
        super("CARD");
    }

    @Override
    public void pay() {
        System.out.println("카드 결제");
    }
}
```

`CardPaymentService`는 `BasePaymentService`를 `extends`하면서 `provider`라는 공통 상태와 `validate()`라는 공통 행동을 물려받는다. 생성자에서는 `super("CARD")`를 호출해 부모가 맡은 상태를 초기화한다.

이 흐름은 이전에 공부한 상속과 연결된다. 자식 생성자가 실행되기 전에 부모 생성자가 호출되고 부모는 전달받은 값으로 자신의 상태를 초기화한다. 이후 `pay()`는 자식 클래스가 구체적인 결제 방식에 맞게 오버라이딩한다.

그래서 추상 클래스를 “구현하지 않은 메서드를 가진 클래스”라고만 설명하면 부족하다고 느꼈다.

> **추상 클래스는 같은 계열의 클래스가 공통 상태와 행동을 공유하는 상속 구조에 사용한다.**

추상 메서드는 이 구조의 한 부분일 뿐이다. 부모가 공통 상태와 행동을 제공하고 결제 방식마다 달라지는 `pay()`의 구현은 자식에게 맡긴다는 점이 더 중요하다.

## 코드 재사용만으로 상속을 선택하면 안 되는 이유

이번에 특히 조심해야겠다고 느낀 부분은 “코드가 겹치면 부모 클래스를 만들자”는 접근이었다.

상속을 사용하면 부모 클래스의 변경이 자식 클래스에 영향을 준다. 공통 코드를 한곳에서 관리하는 대신 두 클래스 사이에 강한 관계가 생긴다.

추상 클래스를 만들기 전에는 이 질문부터 확인한다.

> **자식 클래스가 부모 클래스의 한 종류인가?**

`CardPaymentService`가 `BasePaymentService`의 한 종류이고 부모의 상태와 행동을 자연스럽게 물려받는다면 상속 관계가 성립한다. 이것이 흔히 말하는 `IS-A` 관계다.

반대로 여러 클래스에서 `validate()` 코드가 반복된다는 이유만으로 상속시키면 관계가 어색해진다. 나중에 부모 클래스의 필드나 생성자 규칙이 바뀌면 자식도 그 변경을 함께 감당하게 된다.

재사용할 기능이 있어도 `IS-A` 관계가 자연스럽지 않다면 인터페이스를 사용하거나 필요한 객체를 내부에 두고 위임하는 Composition을 고려한다. 중복을 줄이기 전에 클래스 사이에 의미 있는 관계가 있는지 확인하는 것이 우선이다.

## 인터페이스와 추상 클래스를 함께 사용하는 구조

인터페이스와 추상 클래스 중 하나만 골라야 한다고 생각했지만 둘을 함께 사용하는 구조도 가능했다.

```java
public interface PaymentService {

    // 외부 호출부가 바라보는 결제 기능의 계약
    void pay();
}
```

```java
public abstract class BasePaymentService {

    protected final String provider;

    protected BasePaymentService(String provider) {
        this.provider = provider;
    }

    // 여러 결제 방식이 함께 사용하는 공통 행동
    public void validate() {
        System.out.println("결제 검증");
    }
}
```

```java
public class CardPaymentService
        extends BasePaymentService
        implements PaymentService {

    public CardPaymentService() {
        super("CARD");
    }

    @Override
    public void pay() {
        System.out.println("카드 결제");
    }
}
```

이 구조에서 각 타입의 역할은 다음처럼 나뉜다.

```text
PaymentService
→ 외부에서 바라보는 기능의 계약

BasePaymentService
→ 실제 구현 클래스들이 공유하는 상태와 행동

CardPaymentService
→ 계약을 구현하면서 공통 구조도 상속받는 실제 구현체
```

호출부는 여전히 다음처럼 인터페이스 타입만 사용한다.

```java
private final PaymentService paymentService;
```

호출부는 `BasePaymentService`나 `CardPaymentService`의 내부 구조를 알지 못해도 된다. 외부에는 `PaymentService`로 기능의 계약을 제공하고 내부에서는 `BasePaymentService`로 공통 상태와 행동을 공유한다.

이렇게 정리하니 둘은 경쟁 관계가 아니라 서로 다른 책임을 맡는 도구였다. 인터페이스는 “무엇을 제공하는가”를 보여주고 추상 클래스는 “같은 계열의 구현체가 어떤 구조를 공유하는가”를 표현한다.

## 선택할 때 스스로 던질 질문

실제 코드에 적용할 때는 문법보다 다음 질문을 먼저 떠올리려고 한다.

### 기능의 계약을 정의하고 싶은가?

구현체와 관계없이 외부에서 바라볼 기능을 정하고 싶다면 인터페이스를 먼저 고려한다.

```java
interface PaymentService {
    void pay();
}
```

### 공통 상태와 행동을 공유해야 하는가?

여러 구현 클래스가 같은 상태와 공통 행동을 가져야 하며 클래스 사이에 자연스러운 상속 관계까지 있다면 추상 클래스를 고려한다.

```java
abstract class BasePaymentService {
    protected String provider;
}
```

### 단순히 코드 중복을 줄이려는 것인가?

그 이유만으로 상속을 선택하지 않는다. 부모의 변경이 자식에게 전파되어도 괜찮은지, 자식이 정말 부모의 한 종류인지 확인한다.

## 오늘 배운 점

처음에는 추상 클래스와 인터페이스가 모두 구현 클래스에서 메서드를 완성하게 만든다는 점 때문에 비슷한 기능이라고 생각했다. `abstract`와 `interface`의 문법 차이를 외우는 것이 먼저라고 봤다.

하지만 코드를 나란히 놓고 호출부와 구현부를 살펴보니 역할이 달랐다. 인터페이스는 **구현 객체가 제공해야 하는 기능의 계약**이고 추상 클래스는 **관련 클래스들이 상태와 행동을 공유하는 상속 구조**였다.

특히 공통 코드가 있다는 이유만으로 상속을 적용하면 안 된다는 점을 알게 되었다. `IS-A` 관계가 자연스러운지 먼저 판단해야 하고 단순 재사용이라면 다른 구조가 더 적절하다.

또 하나 기억해 둘 내용은 둘 중 하나만 선택하지 않아도 된다는 점이다. 외부에는 인터페이스로 계약을 제공하고 내부 구현에서는 추상 클래스로 공통 구조를 공유한다.

이제 `extends`나 `implements`를 작성하기 전에 스스로 묻는 질문이 남았다.

> **지금 필요한 것은 기능의 계약인가, 공통 상태와 행동을 가진 상속 구조인가?**

이 질문을 기준으로 보면 추상 클래스와 인터페이스의 선택은 단순한 문법 문제가 아니다. 클래스 사이의 관계와 책임을 정하는 설계 문제다.
