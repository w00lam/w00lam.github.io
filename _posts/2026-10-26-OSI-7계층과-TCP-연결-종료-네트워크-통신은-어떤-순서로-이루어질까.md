오늘은 네트워크 통신을 OSI 계층 이름만 외우는 데서 멈추지 않았다. Java/Spring 백엔드 개발을 준비하며 요청이 각 계층을 어떻게 지나고 TCP 연결이 어떤 순서로 열리고 닫히는지 연결해 보았다. 순서는 알고 있었지만 역할과 데이터 단위를 설명하려니 막혔다. TCP도 처음에는 시작 번호를 알려 주는 절차로만 이해했는데 양쪽의 초기 순서 번호를 주고받고 응답을 확인하는 과정이었다. 종료도 한 번에 끊는 것이 아니라 양쪽 송신 방향을 각각 닫는다.

오늘 글에서는 다음 질문에 답해 본다.

- OSI 7계층은 어떤 순서로 구성되며 계층마다 무엇을 담당하는가?
- 각 계층에서 데이터를 부르는 단위는 어떻게 달라지는가?
- TCP 연결을 시작할 때 왜 세 번의 메시지를 주고받는가?
- TCP 연결을 종료할 때는 왜 종료 방향을 나누어 확인하는가?
- FIN 재전송과 마지막 ACK는 TIME-WAIT와 어떻게 연결되는가?

## OSI 7계층은 역할을 나누어 본 통신 모델이다

처음에는 계층 이름을 아래에서 위로 **물리 → 데이터 링크 → 네트워크 → 전송 → 세션 → 표현 → 응용** 순서로 기억하고 있었다. 순서는 알고 있었지만 이름을 말하는 것과 각 계층이 맡은 일을 설명하는 것은 달랐다. 계층을 나눈 이유는 통신 과정을 역할별로 나누어 볼 수 있고 문제가 생겼을 때 어느 범위를 확인할지 정하기 쉽기 때문이다.

역할과 데이터 단위를 나란히 놓으니 외워 둔 순서가 통신 흐름으로 이어졌다.

| 계층 | 핵심 역할 | 데이터 단위 |
| --- | --- | --- |
| 물리 계층 | 데이터를 전송할 수 있는 신호로 전달한다. | 비트 |
| 데이터 링크 계층 | 데이터를 프레임으로 묶어 정해진 전달 단위로 다룬다. | 프레임 |
| 네트워크 계층 | 목적지까지 이동하는 경로를 기준으로 데이터를 전달한다. | 패킷 |
| 전송 계층 | 양 끝의 프로그램 사이에서 데이터를 전달하고 TCP·UDP 방식의 전송을 담당한다. | TCP 세그먼트, UDP 데이터그램 |
| 세션 계층 | 통신 대화를 시작하고 유지하고 종료하는 흐름을 관리한다. | 데이터 |
| 표현 계층 | 서로 다른 표현 형식의 데이터를 해석할 수 있도록 맞춘다. | 데이터 |
| 응용 계층 | 응용 프로그램이 사용하는 서비스를 제공한다. | 데이터 |

송신 측에서 응용 데이터가 아래로 내려가면 전송 계층에서는 TCP 세그먼트나 UDP 데이터그램이 되고 네트워크 계층에서는 패킷이 된다. 데이터 링크 계층에서는 프레임으로, 물리 계층에서는 비트로 다루어진다. 수신 측은 이 흐름을 반대로 따라 올라가며 데이터를 전달한다.

세션 계층은 단순한 연결보다 통신 대화를 관리하는 역할로 이해하는 편이 분명했다. 표현 계층도 데이터를 새로 만드는 곳이 아니라 표현 형식을 맞추는 계층이다. 응용 계층은 화면만 뜻하지 않고 응용 프로그램이 사용하는 서비스를 담당한다. 이름보다 각 계층의 책임을 한 문장으로 연결해야 전체 흐름이 보였다.

![OSI 7계층의 순서와 데이터 단위](/assets/images/2026-10-26-osi-tcp/osi-seven-layers.svg)

*그림 1. 위에서 아래로 내려갈수록 데이터 단위가 데이터에서 비트로 바뀌고 수신 측에서는 반대 방향으로 해석한다.*

## TCP 연결은 3-Way Handshake로 시작한다

처음에는 TCP 연결을 시작 번호를 상대에게 알려 주는 과정이라고 생각했다. 실제로는 한쪽의 번호만 전달하는 것이 아니라 양쪽이 각자의 초기 순서 번호를 알리고 상대의 요청과 응답을 확인한다.

메시지 순서는 `SYN → SYN-ACK → ACK`다.

| 단계 | 송신자 → 수신자 | 확인하는 내용 |
| --- | --- | --- |
| 1 | 클라이언트 → 서버: `SYN` | 클라이언트가 연결을 시작하겠다는 뜻과 자신의 초기 순서 번호를 보낸다. |
| 2 | 서버 → 클라이언트: `SYN-ACK` | 서버가 클라이언트의 `SYN`을 받았다고 확인하고 자신의 초기 순서 번호를 함께 보낸다. |
| 3 | 클라이언트 → 서버: `ACK` | 클라이언트가 서버의 `SYN`을 받았다고 확인한다. |

세 번의 메시지가 필요한 이유는 양쪽의 확인을 모두 끝내야 하기 때문이다. 첫 번째 메시지만으로는 서버가 요청을 받았는지 알 수 없다. 두 번째 메시지에서 서버는 클라이언트의 요청을 확인하며 자신의 요청도 보낸다. 세 번째 메시지는 클라이언트가 서버의 요청을 받았다는 응답이다. 따라서 3-Way Handshake는 시작 번호 전달과 연결 가능성 확인을 함께 수행한다.

## TCP 연결 종료는 4-Way Handshake로 진행된다

TCP 연결은 전체를 한 번에 닫지 않는다. 양방향으로 데이터를 주고받으므로 한쪽이 더 보낼 데이터가 없다는 사실과 반대쪽도 같은 상태라는 사실을 따로 확인한다. 그래서 종료는 두 방향의 송신을 차례로 닫는다.

정상적인 종료 순서는 `FIN → ACK → FIN → ACK`다.

| 단계 | 송신자 → 수신자 | 확인하는 내용 |
| --- | --- | --- |
| 1 | 종료를 먼저 시작한 쪽 → 상대방: `FIN` | 이 방향으로는 더 보낼 데이터가 없다고 알린다. |
| 2 | 상대방 → 종료를 먼저 시작한 쪽: `ACK` | 첫 번째 `FIN`을 받았다고 확인한다. 상대방은 아직 자신의 데이터를 보낼 수 있다. |
| 3 | 상대방 → 종료를 먼저 시작한 쪽: `FIN` | 상대방도 자신의 방향으로 더 보낼 데이터가 없다고 알린다. |
| 4 | 종료를 먼저 시작한 쪽 → 상대방: `ACK` | 두 번째 `FIN`을 받았다고 확인한다. 정상 종료에서 이쪽은 `TIME-WAIT`로 들어간다. |

첫 번째 `FIN`을 받았다고 양쪽 방향이 동시에 닫히지는 않는다. 상대방은 첫 번째 `ACK`를 보낸 뒤 남은 데이터를 처리하고 자신의 `FIN`을 보낼 수 있다. `FIN`은 연결 전체를 끊는 신호가 아니라 한쪽 송신 방향을 닫겠다는 신호다.

마지막 `ACK`가 전달되지 않으면 `FIN`을 보낸 쪽은 종료 확인을 받지 못한다. 상대방이 `FIN`을 다시 보내면 `TIME-WAIT`에 있는 쪽은 마지막 `ACK`를 다시 보낼 수 있다. `TIME-WAIT`는 종료를 시작한 쪽이 재전송된 `FIN`에 응답할 수 있도록 남아 있는 구간이다. 네 개의 이름만 외우면 놓치기 쉬운 관계였다.

![TCP 연결 수립과 정상 종료 메시지 흐름](/assets/images/2026-10-26-osi-tcp/tcp-handshake-flow.svg)

*그림 2. 연결 수립은 양쪽의 요청과 응답을 확인하고 종료는 각 송신 방향을 차례로 닫는다. 점선은 `FIN` 재전송과 이에 대한 마지막 `ACK` 재전송을 나타낸다.*

## 학습 과정에서 바뀐 이해

학습 초반에는 OSI 계층을 아래에서 위로 외우는 데 집중했다. 이름과 순서를 맞히는 것만으로는 각 계층의 책임을 설명하기 어려웠다. 데이터가 아래로 내려가며 비트·프레임·패킷·세그먼트로 다르게 불리고 수신 측에서 다시 올라간다는 흐름을 적고 나니 계층의 순서가 암기 목록으로 보이지 않았다.

TCP 연결 수립에서는 시작 번호 전달과 상대의 응답 확인을 나누어 보았다. 연결 종료에서는 `FIN`을 받은 뒤에도 반대 방향의 송신이 남을 수 있다는 점을 기준으로 `FIN → ACK → FIN → ACK`를 이해했다. 마지막 `ACK`가 유실되었을 때 `TIME-WAIT` 중인 쪽이 재전송된 `FIN`에 다시 응답할 수 있다는 관계도 정리했다.

## 오늘의 정리

- OSI 계층은 이름과 순서만 외우지 않고 각 계층의 역할과 데이터 단위를 함께 봐야 한다.
- TCP 연결 수립은 양쪽의 초기 순서 번호와 연결 가능성을 확인하는 과정이다.
- TCP 연결 종료는 양방향을 각각 종료하며 재전송에 대비하는 흐름까지 고려해야 한다.

오늘은 OSI 계층의 기본 역할과 데이터 단위, TCP의 연결 수립·정상 종료 메시지 흐름을 확인했다. 세부 상태 전이까지 모두 숙달했다고 말하기는 어렵지만 오늘 학습 범위에서는 어떤 메시지가 어느 방향으로 가고 무엇을 확인하는지 구분할 수 있게 됐다. 다음에 다시 볼 때도 계층 이름을 먼저 외우기보다 역할과 데이터 단위를 연결하고, TCP는 메시지의 방향과 확인 대상을 순서대로 적어 보려고 한다.
