Java/Spring 백엔드 신입 기술면접을 준비하면서 Database 개념을 공부하고 모의면접으로 다시 확인했다. 이전에는 정규화를 통해 데이터를 어떤 테이블에 나누어 저장할지 살펴봤고 [데이터베이스 이상과 인덱스 — 설계 문제와 조회 비용은 어떻게 구분할까?](https://w00lam.github.io/posts/database-anomalies-indexes/)에서는 분리한 데이터에서 이상 현상과 조회 비용을 구분했다.

오늘은 여기서 한 단계 더 나아가 “정규화로 데이터를 나누어 저장했다면 여러 테이블의 변경을 언제 하나의 성공으로 확정해야 할까?”라는 질문을 공부했다. 음식점 정보를 저장하는 작업과 음식점·영상 연결을 저장하는 작업을 예로 들어 트랜잭션의 경계를 정했다. 단순히 여러 SQL을 한 번에 실행하는 문법을 외우는 데서 끝내지 않고 업무의 성공 조건과 커밋의 의미와 장애 복구까지 이어서 살펴봤다.

처음에는 영상 연결에 음식점 정보가 필요하다는 선행 관계를 근거로 두 작업을 묶어야 한다고 설명했다. 이후에는 선행 관계만으로 판단할 수 없고 두 작업 중 일부만 성공한 상태를 허용할 수 있는지와 사용자가 요청한 기능의 성공 조건이 무엇인지를 먼저 물어야 한다는 점을 확인했다. 오늘 다룬 음식점과 영상은 트랜잭션 원리를 설명하기 위한 학습용 사례다.

## 함께 성공해야 하는 작업부터 정한다

### 음식점 저장과 영상 연결 저장을 하나의 기능으로 본다면

음식점 정보를 저장한 뒤 음식점과 영상을 연결하는 기능을 생각해 보자. 두 작업이 모두 성공해야 “음식점 등록과 대표 영상 연결”이 완료되는 기능이라면 다음 두 SQL은 하나의 업무 단위로 볼 수 있다.

~~~sql
INSERT INTO restaurant (id, name)
VALUES (101, '달빛국수');

INSERT INTO restaurant_video (restaurant_id, video_id)
VALUES (101, 999);
~~~

이 예제는 개념 설명을 위해 단순화했다. 음식점 101은 아직 존재하지 않고 영상 999도 존재하지 않는다. restaurant_video에는 video_id를 참조하는 외래키 제약이 있으며 예제에 필요한 최소 컬럼만 표시했다. 따라서 첫 번째 INSERT는 성공하지만 두 번째 INSERT는 존재하지 않는 영상 999를 참조하려고 하므로 실패한다.

이때 각 SQL을 하나의 트랜잭션으로 묶지 않고 애플리케이션의 자동 커밋 모드에서 실행하면 첫 번째 INSERT가 먼저 커밋되어 음식점 101만 남을 수 있다. 두 번째 INSERT가 실패했다는 사실이 이미 완료된 첫 번째 작업까지 자동으로 되돌리지는 않는다. PostgreSQL에서 명시적인 BEGIN이 없다고 트랜잭션이 전혀 없는 것은 아니다. 각 SQL 문장이 별도의 트랜잭션 안에서 실행되는 상황과 여러 SQL을 하나의 트랜잭션으로 묶은 상황을 구분해야 한다.

음식점 등록과 영상 연결을 반드시 함께 성공시켜야 한다면 두 문장을 명시적인 트랜잭션으로 묶는다.

~~~sql
BEGIN;

INSERT INTO restaurant (id, name)
VALUES (101, '달빛국수');

INSERT INTO restaurant_video (restaurant_id, video_id)
VALUES (101, 999);

-- 외래키 제약 위반으로 두 번째 INSERT 실패
ROLLBACK;
~~~

두 번째 INSERT에서 오류가 나면 PostgreSQL의 현재 트랜잭션은 계속 정상적인 명령을 받을 수 있는 상태가 아니다. 앞선 INSERT를 포함해 해당 트랜잭션에서 수행한 변경을 취소하려면 ROLLBACK으로 경계를 닫아야 한다. 그러면 음식점 101을 저장한 변경도 함께 확정되지 않는다.

반대로 영상 999가 실제로 존재하고 두 INSERT가 모두 성공했다면 마지막에 COMMIT을 실행한다.

~~~sql
BEGIN;

INSERT INTO restaurant (id, name)
VALUES (101, '달빛국수');

INSERT INTO restaurant_video (restaurant_id, video_id)
VALUES (101, 999);

COMMIT;
~~~

COMMIT은 이 트랜잭션에서 수행한 변경을 성공한 작업으로 확정한다. 오류가 난 경로에서 ROLLBACK을 실행하는 것과 모든 작업이 끝난 경로에서 COMMIT을 실행하는 것이 업무 단위를 보장하는 기본 흐름이다.

![자동 커밋과 명시적 트랜잭션에서 일부 저장과 전체 롤백이 달라지는 흐름도](/assets/images/2026-10-21-database-transactions/transaction-rollback-boundary.svg)

*그림 1. 두 번째 저장이 실패했을 때 자동 커밋은 먼저 저장한 음식점을 남길 수 있지만 하나의 트랜잭션에서는 앞선 변경까지 ROLLBACK할 수 있다.*

### 트랜잭션 경계는 SQL의 개수가 아니라 업무의 성공 조건으로 정한다

처음에는 “영상 연결이 음식점 정보를 필요로 하므로 두 작업을 묶는다”고 설명했다. 이 말은 실행 순서를 이해하는 데는 도움이 되지만 트랜잭션의 경계를 정하는 기준으로는 충분하지 않았다. 음식점을 먼저 저장해야 영상 연결을 저장할 수 있다는 사실과 두 작업이 반드시 하나의 성공으로 확정되어야 한다는 사실은 다른 질문이다.

음식점만 먼저 등록해도 사용자에게 유효한 상태라면 음식점 등록과 영상 연결은 서로 다른 성공 단위가 될 수 있다. 음식점 등록은 성공시키고 영상 연결은 영상이 준비된 뒤 별도로 처리하는 흐름이 업무 규칙에 맞을 수 있다. 반대로 음식점 상세 페이지가 영상 연결까지 있어야만 완성된 것으로 간주된다면 둘 중 하나만 남는 상태를 허용하면 안 된다.

따라서 트랜잭션을 정할 때는 SQL이 몇 개인지보다 중간 상태가 사용자에게 허용되는지와 일부만 성공했을 때 시스템이 유효한 상태인지부터 확인해야 한다. 여러 SQL을 무조건 하나로 묶는 것이 좋은 설계는 아니다. 원자적으로 성공시켜야 하는 업무 단위를 먼저 정하고 그 안에 필요한 변경을 포함해야 한다.

## ACID를 원자성과 동시성 문제로 나누어 본다

트랜잭션을 공부할 때 ACID를 한 줄씩 외우는 것보다 앞의 음식점 예제에 대입해 보는 편이 이해하기 쉬웠다.

- 원자성(Atomicity)은 함께 처리하기로 한 변경을 모두 반영하거나 모두 취소하는 성질이다. 음식점 저장과 영상 연결을 한 기능으로 정했다면 두 작업이 모두 성공하거나 둘 다 확정되지 않아야 한다.
- 일관성(Consistency)은 트랜잭션 전후의 데이터가 데이터베이스 제약과 업무 규칙을 만족해야 한다는 뜻이다. 존재하지 않는 영상 999를 연결하지 못하게 하는 외래키는 이런 규칙 중 하나다. 트랜잭션으로 묶었다는 사실만으로 잘못 작성한 업무 로직까지 올바르게 바뀌지는 않는다.
- 격리성(Isolation)은 동시에 실행되는 작업이 서로의 미완료 변경을 어떻게 볼지와 어떤 간섭을 허용할지를 다룬다. 한 트랜잭션의 중간 결과가 다른 트랜잭션에 그대로 노출되지 않도록 하는 문제다.
- 지속성(Durability)은 COMMIT으로 성공을 확인한 변경이 장애가 발생한 뒤에도 보존되어야 한다는 성질이다. 이 성질은 커밋 순간 모든 데이터 페이지를 디스크에 쓰는가와는 구분해서 이해해야 한다.

### 원자적으로 묶었다고 동시성 문제가 사라지지는 않는다

오늘은 트랜잭션의 원자성과 동시성 제어를 같은 의미로 설명하지 않으려고 했다. 여러 변경을 함께 커밋하거나 함께 롤백하는 문제와 두 작업이 같은 값을 읽은 뒤 서로의 결과를 덮어쓰는 문제는 서로 다르다.

예를 들어 재고가 20개인 상품을 두 요청이 동시에 읽고 각각 1개를 차감한다고 하자. 요청 A와 요청 B가 모두 20을 읽은 뒤 각각 19를 저장하면 최종 값이 18이 아니라 19가 될 수 있다. 두 요청이 각자 하나의 트랜잭션이었다고 해도 각 트랜잭션의 원자성이 다른 트랜잭션의 읽기와 쓰기 순서를 자동으로 조정해 주지는 않는다.

이 문제는 어제 [데이터베이스 이상과 인덱스 — 설계 문제와 조회 비용은 어떻게 구분할까?](https://w00lam.github.io/posts/database-anomalies-indexes/)에서 구분한 Lost Update와 연결된다. 이전 글에서 갱신 이상은 중복된 사실을 여러 행에 저장한 설계 문제이고 Lost Update는 여러 작업이 같은 값을 읽고 저장하는 동시성 문제라고 정리했다. 오늘은 여기에 트랜잭션의 원자성을 더해 본다. 함께 취소되는 범위와 동시에 실행되는 작업 사이의 간섭은 서로 다른 축이다.

동시성 문제를 다룰 때는 락과 원자적 UPDATE와 격리 수준 같은 별도 제어 수단을 검토해야 한다. [낙관적 락·비관적 락·아토믹 업데이트, 무엇을 선택해야 할까](https://w00lam.github.io/posts/lock-selection-criteria/)에서 각 방식이 어떤 충돌을 다루는지 살펴본 것처럼 트랜잭션을 사용한다는 한 문장만으로 해결 방법을 정할 수 없다.

PostgreSQL에서 다른 트랜잭션의 미커밋 변경을 볼 수 없다는 설명도 “모든 트랜잭션이 순서대로 하나씩 실행된다”는 뜻이 아니다. 여러 트랜잭션은 동시에 실행될 수 있고 각 문장은 자신의 스냅샷과 동시성 제어 규칙에 따라 데이터를 본다. PostgreSQL의 MVCC가 읽기 가시성을 관리한다는 내용은 뒤에서 WAL과 구분해 다시 정리한다.

### 트랜잭션 범위와 행 단위 충돌 범위도 다르다

한 트랜잭션 안에 여러 테이블의 INSERT와 UPDATE를 넣을 수 있다. 하지만 그것이 모든 행에 대한 독점 권한을 얻는다는 뜻은 아니다. 트랜잭션의 범위는 어떤 변경을 함께 확정하거나 취소할지에 관한 업무 범위이고 락의 범위는 동시에 접근하는 작업 사이에서 어떤 충돌을 조정할지에 관한 실행 범위다.

이 구분은 이전에 [데이터베이스의 안전성과 일관성 — SQL Injection부터 복제 지연까지](https://w00lam.github.io/posts/database-security-consistency-replication/)에서 여러 행과 테이블을 포함하는 일관성 범위와 특정 행의 동시 변경을 구분했던 내용과도 이어진다. 둘을 모두 “안전하게 처리한다”는 표현으로 묶으면 어떤 문제가 해결된 것인지 설명하기 어렵다.

## COMMIT과 데이터 페이지의 디스크 반영을 구분한다

트랜잭션의 지속성을 생각하다 보니 다음 질문으로 넘어갔다. “메모리에서 바뀐 데이터가 언제 디스크에 기록되는가?”

SQL을 입력하면 Query Processor가 구문을 해석하고 실행 계획을 세워 필요한 작업을 수행한다. Storage System은 테이블과 인덱스 같은 데이터를 저장하고 접근하는 역할을 맡는다. DBMS는 데이터를 행 하나씩 디스크에 바로 쓰는 대신 페이지라는 고정 크기의 저장 단위를 읽고 쓴다. 한 페이지에는 여러 행이 들어갈 수 있으므로 페이지와 행을 같은 단위로 보면 안 된다.

메모리와 저장 장치 사이에는 Buffer Manager가 있다. 자주 사용하는 페이지를 메모리 버퍼에 유지하고 필요한 페이지를 읽어 오며 변경된 페이지를 나중에 데이터 파일에 기록한다. 따라서 다음 세 가지 상태를 분리해서 보아야 한다.

- SQL 실행 결과가 메모리의 버퍼 페이지에 반영되었다.
- 트랜잭션이 COMMIT으로 성공 처리되었다.
- 변경된 데이터 페이지가 테이블 데이터 파일에 기록되었다.

이 세 사건은 항상 같은 순간에 일어나지 않는다. PostgreSQL 공식 문서의 [Database Page Layout](https://www.postgresql.org/docs/18/storage-page-layout.html)에서도 테이블과 인덱스가 페이지 배열로 저장되고 테이블의 한 항목이 특정 페이지에 저장된다고 설명한다. 오늘은 페이지 내부의 헤더와 행 레이아웃을 자세히 분석하지 않고 여러 행이 들어가는 저장 단위라는 점만 확인했다.

### COMMIT은 모든 변경 페이지를 그 순간 디스크에 쓰는 명령이 아니다

COMMIT을 “바뀐 모든 데이터 페이지를 그 순간 디스크에 쓰는 작업”으로 이해하면 커밋과 장애 복구의 관계가 꼬인다. 커밋 시점에 데이터 파일의 모든 변경 페이지를 즉시 반영하도록 강제하지 않는 DBMS에서는 버퍼에 변경 페이지가 남아 있을 수 있다.

그렇다고 성공한 트랜잭션의 변경이 휘발성 메모리에만 있다는 뜻은 아니다. 일반적인 로그 기반 복구 모델에서는 커밋을 보장하기 위한 로그가 먼저 영속 저장소에 기록된다. 데이터 페이지가 나중에 기록되더라도 장애가 발생하면 로그를 사용해 필요한 변경을 다시 반영할 수 있다. PostgreSQL에서는 이 역할을 WAL이 담당한다.

이 차이를 이해하면 “커밋은 완료됐는데 데이터 파일의 페이지가 아직 최신이 아닐 수 있다”는 상황이 모순이 아니라는 것을 알 수 있다. 커밋은 업무 변경을 성공으로 확정하는 사건이고 데이터 페이지 쓰기는 버퍼 관리와 저장 정책에 따라 나중에 일어날 수 있는 물리적 반영이다.

## 일반적인 UNDO·REDO 모델을 버퍼 정책과 연결한다

여기서 설명하는 UNDO·REDO는 특정 제품의 내부 구현을 그대로 옮긴 것이 아니라 일반적인 DBMS의 로그 기반 복구 모델이다. 버퍼에 있는 변경과 데이터 파일에 있는 변경의 시점이 다를 수 있기 때문에 장애 뒤에 무엇을 되돌리고 무엇을 다시 반영할지 설명하는 틀로 사용한다.

두 가지 장애 상황을 먼저 생각해 보자.

1. 커밋하지 않은 변경이 포함된 데이터 페이지가 데이터 파일에 기록된 뒤 작업이 실패했다. 장애가 복구되면 아직 성공으로 확정되지 않은 변경은 제거해야 한다. 이것이 UNDO와 연결된다.
2. 커밋은 완료됐지만 변경된 데이터 페이지가 디스크에 기록되기 전에 메모리를 잃었다. 데이터 파일만 보면 성공한 변경이 빠져 있으므로 로그에서 변경 내용을 찾아 다시 적용해야 한다. 이것이 REDO와 연결된다.

UNDO는 미커밋 변경을 되돌리는 복구이고 REDO는 커밋된 변경 중 데이터 파일에 남지 않은 내용을 다시 반영하는 복구다. 어느 작업이 필요한지는 버퍼 정책과 디스크 기록 정책에 따라 달라진다.

| 정책 | 데이터 페이지 기록 기준 | 일반 복구 모델에서의 의미 |
| --- | --- | --- |
| STEAL | 미커밋 변경이 포함된 페이지도 디스크에 기록할 수 있음 | 미커밋 변경을 되돌리는 UNDO가 필요할 수 있음 |
| NO-STEAL | 미커밋 변경 페이지의 디스크 기록을 제한함 | 이 정책 때문에 생기는 디스크상의 미커밋 변경 UNDO를 피함 |
| FORCE | 커밋할 때 변경 페이지를 모두 디스크에 반영함 | 해당 변경을 다시 적용하는 REDO 필요를 피할 수 있음 |
| NO-FORCE | 커밋할 때 모든 변경 페이지의 반영을 강제하지 않음 | 커밋된 변경을 다시 반영하는 REDO가 필요할 수 있음 |

STEAL과 NO-STEAL은 “커밋 전 변경 페이지를 데이터 파일에 써도 되는가?”를 묻는다. FORCE와 NO-FORCE는 “커밋할 때 변경 페이지를 모두 데이터 파일에 써야 하는가?”를 묻는다. 서로 다른 질문이므로 두 축을 섞어 외우면 안 된다.

NO-FORCE는 커밋할 때 데이터 페이지를 절대로 쓰지 않는다는 뜻이 아니다. 커밋 시 모든 변경 페이지를 반드시 디스크에 반영하도록 강제하지 않는다는 뜻이다. 일부 페이지는 커밋 전에 이미 기록될 수도 있고 커밋 시점에 기록될 수도 있다. 다만 모든 페이지의 기록이 완료될 때까지 커밋을 기다리도록 강제하지 않으므로 REDO가 필요할 수 있다.

반대로 어떤 정책에서 특정 복구 작업이 필요하지 않다고 해서 트랜잭션을 취소할 필요가 없거나 로그 자체가 필요 없다는 뜻은 아니다. 표는 장애가 난 뒤 데이터 파일과 로그를 어떤 상태로 맞춰야 하는지 읽는 기준이다. 실제 DBMS는 로그 순서와 체크포인트와 동시 실행을 포함한 더 많은 조건을 함께 다루지만 오늘은 그 내부 구현으로 확장하지 않았다.

## PostgreSQL의 MVCC와 WAL은 역할을 구분한다

일반적인 UNDO·REDO 표를 PostgreSQL에 그대로 대입하면 혼동하기 쉽다. PostgreSQL을 이해할 때는 MVCC와 WAL을 같은 기능으로 묶지 않고 각각의 질문에 답하게 해야 한다.

MVCC는 여러 행 버전과 스냅샷을 사용해 어떤 트랜잭션이 어떤 행을 볼 수 있는지 관리한다. 다른 트랜잭션이 아직 커밋하지 않은 변경을 읽지 못하게 하고 각 SQL 문장이 자신에게 허용된 데이터 가시성을 기준으로 결과를 만들도록 한다. PostgreSQL 공식 문서의 [Concurrency Control: Introduction](https://www.postgresql.org/docs/18/mvcc-intro.html)은 MVCC를 여러 버전의 데이터와 스냅샷으로 동시 접근을 관리하는 모델로 설명한다.

WAL은 Write-Ahead Logging의 약자로 데이터 파일을 변경하기 전에 변경 내용을 로그에 기록하고 그 로그를 영속 저장소에 반영하는 원칙이다. PostgreSQL의 [Write-Ahead Logging](https://www.postgresql.org/docs/18/wal-intro.html)은 데이터 파일보다 WAL 기록이 먼저 영속화되어야 하며 데이터 페이지에 아직 반영되지 않은 변경은 장애 뒤 WAL을 이용해 다시 적용할 수 있다고 설명한다. 기본적인 내구성 설정에서는 커밋을 확인하기 위해 WAL이 먼저 안전한 저장소에 반영되고 데이터 페이지 쓰기는 그 뒤에 진행될 수 있다.

두 개념의 질문을 나누면 다음과 같다.

| 개념 | 주로 답하는 질문 |
| --- | --- |
| MVCC | 이 트랜잭션이 어떤 행 버전을 볼 수 있는가? |
| WAL | 장애 뒤 데이터 파일을 어떤 변경 기록으로 복구할 것인가? |

MVCC가 있다고 해서 모든 동시성 문제가 해결되는 것은 아니다. 읽기 가시성을 관리해도 애플리케이션이 같은 값을 읽고 덮어쓰는 로직을 작성하면 Lost Update 같은 문제는 별도 제어가 필요할 수 있다. 행 수준 락과 원자적 UPDATE와 격리 수준은 업무 충돌에 맞춰 따로 검토해야 한다.

또 PostgreSQL이 ROLLBACK할 때 항상 UNDO 로그로 기존 행을 덮어쓴다고 설명해서도 안 된다. PostgreSQL의 MVCC에서는 변경 전후의 행 버전과 트랜잭션 가시성 정보가 함께 사용된다. 커밋되지 않았거나 중단된 트랜잭션의 버전이 변경 직후 모두 사라지는 것도 아니다. 더 이상 어떤 트랜잭션에도 필요하지 않은 이전 행 버전은 VACUUM을 통해 회수된다. [Routine Vacuuming](https://www.postgresql.org/docs/18/routine-vacuuming.html)은 UPDATE나 DELETE 뒤의 이전 행 버전이 즉시 제거되지 않고 다른 트랜잭션에 보일 가능성이 사라진 뒤 회수된다고 설명한다.

WAL도 커밋된 트랜잭션의 기록만 담는다고 단정할 수 없다. WAL은 데이터 파일의 변경을 복구할 수 있도록 변경 기록을 남기는 층위이고 트랜잭션이 최종적으로 커밋되었는지와 어떤 버전을 조회에 노출할지는 다른 정보와 절차로 판단한다. 학습 중에는 “행 버전과 스냅샷”이라는 MVCC의 역할과 “데이터 파일보다 먼저 남기는 로그”라는 WAL의 역할이 자꾸 섞였다. 일반 UNDO·REDO 모델을 배운 뒤 PostgreSQL 구현에 연결할 때는 두 질문을 분리해야 한다는 점을 교정했다.

![메모리의 변경 페이지와 영속 WAL과 데이터 파일의 기록 시점을 구분한 복구 흐름도](/assets/images/2026-10-21-database-transactions/wal-data-page-recovery.svg)

*그림 2. WAL은 데이터 페이지보다 먼저 영속화되어 장애 뒤 REDO에 사용될 수 있고 MVCC는 별도의 축에서 행 버전과 조회 가시성을 관리한다.*

이 그림에서 MVCC를 WAL 기록 순서의 한 단계로 그리지 않았다. 메모리의 버퍼 페이지와 WAL과 데이터 파일은 장애 복구의 흐름을 표현하고 MVCC는 어떤 버전을 읽을지 판단하는 가시성의 흐름이다. 이 둘을 한 줄의 저장 순서로 합치지 않는 것이 오늘의 중요한 구분이었다.

## 오늘의 정리

오늘은 트랜잭션을 여러 SQL을 묶는 문법으로만 보지 않았다. 음식점 저장과 음식점·영상 연결 저장을 예로 들면서 두 작업이 모두 성공해야 하는 기능인지부터 확인했다. 처음에는 영상 연결에 음식점 정보가 필요하다는 선행 관계를 기준으로 생각했지만 이후에는 일부만 성공한 상태를 업무에서 허용할 수 있는지와 사용자가 요청한 기능의 성공 조건이 무엇인지로 판단 기준을 바꿨다. 트랜잭션의 경계는 SQL의 개수나 실행 순서보다 업무의 성공 조건을 기준으로 정한다.

ACID를 통해 원자성은 변경을 함께 확정하거나 취소하는 성질이고 격리성은 동시에 실행되는 작업 사이의 가시성과 간섭을 다루는 성질이라는 점도 나누어 보았다. 트랜잭션으로 묶었다는 사실만으로 Lost Update 같은 동시성 문제가 모두 사라지지는 않는다. 이전에 공부한 락과 원자적 UPDATE와 별도의 동시성 제어가 왜 필요한지 연결할 수 있었다.

COMMIT은 바뀐 모든 데이터 페이지를 그 순간 디스크에 쓰는 사건과 같지 않다. Query Processor와 Storage System의 역할을 나누고 DBMS가 페이지 단위로 데이터를 읽고 쓰며 Buffer Manager가 메모리의 변경 페이지를 관리한다는 흐름을 확인했다. 메모리의 변경과 데이터 파일의 기록 사이에 시간이 생길 수 있기 때문에 로그 기반 복구가 필요하다.

일반적인 UNDO·REDO 모델에서는 STEAL과 NO-STEAL이 커밋 전 변경 페이지의 기록을 다루고 FORCE와 NO-FORCE가 커밋 시 데이터 페이지 기록을 강제하는지를 다룬다. 두 축은 서로 다른 질문이다. PostgreSQL에서는 MVCC가 행 버전과 데이터 가시성을 관리하고 WAL이 데이터 파일보다 먼저 남는 변경 기록과 장애 복구를 담당한다. 두 개념을 같은 기능으로 설명하지 않으려고 했다.

오늘 내용을 완전히 숙달했다고 말하기는 어렵다. 다만 어떤 변경을 함께 성공시킬지와 어떤 데이터를 언제 볼지와 장애 뒤 어떤 기록으로 복구할지를 서로 다른 질문으로 나누어 생각할 수 있게 됐다. 교과서의 용어를 외운 결과보다 실제 상황에서 구분해야 할 경계가 무엇인지 확인한 학습이었다.
