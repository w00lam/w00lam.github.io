신입 Java/Spring 백엔드 개발자로 기술 면접을 준비하면서 Java의 기초 문법을 다시 보고 있다. 처음에는 이미 익숙한 내용이라고 생각했지만, 코드를 읽다 보면 `null` 처리, 형변환, 객체 비교처럼 변수와 타입에 대한 이해가 필요한 순간이 계속 나타난다.

오늘은 문법을 나열하기보다 다음 질문을 중심으로 정리했다.

> Java에서 변수는 무엇을 저장하며, 타입에 따라 값이 어떻게 저장·변환·비교·전달되는가?

## 1. 변수, 타입, 리터럴은 무엇인가

다음 코드는 매일 보지만, 세 요소를 정확히 나누어 보면 변수와 타입의 역할이 조금 더 분명해진다.

```java
double price = 12.5;
```

* `double` → 타입(Type)
* `price` → 변수명(Variable Name)
* `12.5` → 리터럴(Literal)

`double`은 `price`가 어떤 종류의 값을 다룰 수 있는지 결정한다. `price`는 그 값을 코드에서 이름으로 다루기 위한 식별자이고, `12.5`는 소스 코드에 직접 작성한 값인 리터럴이다.

따라서 변수는 단순히 “값 그 자체”라기보다 **특정 타입의 값을 저장하기 위한 공간을 이름으로 다루는 것**에 가깝다. 타입은 저장할 수 있는 값의 범위뿐 아니라 연산 방식, 비교 방식, 다른 타입으로 변환할 수 있는 방법에도 영향을 준다.

예를 들어 `12.5`를 `int` 변수에 그대로 대입할 수 없는 이유도 타입이 허용하는 표현 방식이 다르기 때문이다.

```java
double price = 12.5;
// int truncatedPrice = price; // 컴파일 오류
int truncatedPrice = (int) price; // 12
```

## 2. 기본 타입과 참조 타입

Java의 타입은 크게 기본 타입(Primitive Type)과 참조 타입(Reference Type)으로 나눌 수 있다.

### 기본 타입(Primitive Type)

```java
int count = 10;
double price = 12.5;
boolean active = true;
char grade = 'A';
```

기본 타입 변수는 값 자체를 저장한다. 대표적으로 `byte`, `short`, `int`, `long`, `float`, `double`, `char`, `boolean`이 있다.

기본 타입에는 `null`을 대입할 수 없다.

```java
int count = null; // 컴파일 오류
```

값이 없다는 상태를 표현해야 한다면 뒤에서 살펴볼 Wrapper Type이나 별도의 상태 모델이 필요하다.

### 참조 타입(Reference Type)

```java
String name = "Java";
Member member = new Member();
int[] scores = {90, 80};
```

참조 타입 변수에는 객체 자체가 아니라 **객체를 가리키기 위한 참조값(reference value)** 이 저장된다. 이 참조값을 실제 JVM의 물리적인 메모리 주소라고 단정할 필요는 없다. 중요한 점은 변수가 객체의 내용을 직접 담는 것이 아니라, 객체를 찾아갈 수 있는 참조 관계를 가진다는 것이다.

참조 타입에는 클래스, 배열, 인터페이스, `String` 등이 포함되며 `null`을 사용할 수 있다.

```java
String name = null;
Member member = null;
```

개념적으로 두 타입의 차이를 그려 보면 다음과 같다.

![기본 타입과 참조 타입의 개념적 저장 방식](/assets/images/2026-08-20-java-variable-type/primitive-vs-reference.svg)

여기서 `Member member`가 객체의 주소를 그대로 보관한다고 이해하면 구현 세부사항과 개념을 혼동하기 쉽다. Java 코드에서 중요한 것은 `member`를 통해 특정 객체를 참조할 수 있다는 사실이다.

## 3. Primitive와 Wrapper Type, 그리고 `null`

```java
int count = 0;
Integer nullableCount = null;
```

`Integer`는 `int`를 객체로 감싼 Wrapper Type이다. 기본 타입과 달리 `Integer`는 참조 타입이므로 `null`을 표현할 수 있다.

Wrapper Type이 필요한 대표적인 이유는 다음과 같다.

* 값이 없음을 `null`로 표현해야 할 때
* Collection과 Generic을 사용할 때
* 객체로서의 동작이나 API가 필요할 때

Collection과 Generic에는 기본 타입을 직접 사용할 수 없기 때문에 `Integer`를 사용한다.

```java
List<Integer> numbers = new ArrayList<>();
numbers.add(10);
```

다만 Wrapper Type을 선택할 때는 자동 박싱과 언박싱만 생각하면 안 된다. `Integer`가 `null`인 상태에서 기본 타입으로 자동 언박싱되면 `NullPointerException`이 발생할 수 있다.

```java
Integer count = null;
// int value = count; // 자동 언박싱 중 NullPointerException
```

결국 다음 두 선언의 차이는 단순히 객체냐 아니냐의 문제가 아니다.

```java
int quantity;
Integer quantity;
```

상품 수량처럼 `0` 자체가 의미 있는 값이고 “아직 값이 없음”을 별도로 표현할 필요가 없다면 `int`가 더 자연스러울 수 있다. 반대로 DB 컬럼이 nullable이거나 “아직 계산되지 않음”이라는 상태가 필요하다면 `Integer`가 적합할 수 있다.

## 4. 필드와 지역 변수의 초기화 차이

### 필드(Field)

```java
class Member {
    int age;
    boolean active;
    String name;
}
```

필드에는 타입별 기본값이 자동으로 할당된다.

| 타입 | 기본값 |
| :--- | :--- |
| `int` | `0` |
| `boolean` | `false` |
| 참조 타입 | `null` |

이는 객체가 생성될 때 필드가 관리되는 방식과 관련이 있다. 인스턴스 필드는 객체의 생명주기와 함께 관리되고, 클래스의 필드는 클래스 생명주기와 함께 관리된다.

### 지역 변수(Local Variable)

```java
void test() {
    int age;
    System.out.println(age); // 컴파일 오류
}
```

지역 변수는 필드처럼 자동으로 사용할 수 있는 기본값이 할당되지 않는다. 사용하기 전에 반드시 명시적으로 초기화해야 한다.

```java
void test() {
    int age = 0;
    System.out.println(age);
}
```

지역 변수는 메서드 호출과 실행 흐름에 맞춰 짧게 사용되므로 Java 컴파일러가 “초기화되지 않은 값을 읽는 코드”를 컴파일 단계에서 막는다. 필드와 지역 변수의 초기화 차이는 단순한 문법 차이가 아니라, 둘의 생명주기와 관리 방식이 다르기 때문에 생긴다.

## 5. 형변환(Type Casting): 넓어지는 변환과 좁아지는 변환

타입이 다른 값을 대입하거나 연산하려면 형변환이 필요할 수 있다. 변환 방향에 따라 넓은 타입 변환(Widening Conversion)과 좁은 타입 변환(Narrowing Conversion)으로 나눌 수 있다.

### 넓은 타입 변환(Widening Conversion)

```java
int number = 10;
long value = number;
```

`int`의 값을 더 넓은 범위를 표현할 수 있는 `long`으로 옮기는 경우다. 일반적으로 값이 손실될 가능성이 낮기 때문에 명시적인 캐스팅 없이 대입할 수 있다.

### 좁은 타입 변환(Narrowing Conversion)

```java
double value = 12.5;
int number = (int) value;
System.out.println(number); // 12
```

더 좁은 범위의 타입으로 변환할 때는 명시적인 캐스팅이 필요하다. 위 예제에서는 소수 부분이 사라질 수 있다.

하지만 Narrowing Conversion이라고 해서 항상 실제 값 손실이 발생하는 것은 아니다.

```java
long value = 10L;
int number = (int) value;
System.out.println(number); // 10
```

변환 방향 자체는 `long`에서 `int`로 좁아지는 변환이지만, `10`은 `int`가 표현할 수 있는 범위 안에 있으므로 실제 값 손실은 발생하지 않는다.

따라서 다음처럼 정리하는 편이 정확하다.

> Narrowing Conversion은 **값 손실 가능성이 있는 변환**이지 항상 손실이 발생하는 변환은 아니다.

## 6. Overflow와 타입 변환에서 주의할 점

```java
int number = Integer.MAX_VALUE;
number++;

System.out.println(number); // -2147483648
```

`int`가 표현할 수 있는 최댓값에서 1을 더하면 Java의 일반적인 정수 연산에서는 자동으로 예외가 발생하지 않는다. 표현 범위를 넘어간 결과가 같은 타입의 범위 안에서 순환해 최솟값처럼 보이게 된다. 이를 오버플로우(Overflow)라고 한다.

따라서 캐스팅을 사용한다고 해서 값 손실이나 오버플로우가 자동으로 방지되는 것은 아니다.

> Casting은 개발자가 타입 변환을 명시하는 것이지, 값 손실이나 Overflow를 자동으로 방지해주는 기능은 아니다.

덧셈이나 곱셈에서 오버플로우를 예외로 감지하고 싶다면 `Math.addExact()` 같은 메서드를 사용할 수 있다.

```java
int result = Math.addExact(Integer.MAX_VALUE, 1); // ArithmeticException
```

실제 서비스 코드에서는 금액, 개수, 시간처럼 범위를 넘을 가능성이 있는 값을 다룰 때 타입의 범위와 연산 결과를 함께 고려해야 한다.

## 7. `==`와 `equals()`는 무엇을 비교하는가

### 기본 타입에서의 `==`

```java
int a = 10;
int b = 10;

System.out.println(a == b); // true
```

기본 타입에서 `==`는 두 변수의 실제 값을 비교한다.

### 참조 타입에서의 `==`와 `equals()`

```java
String a = new String("Java");
String b = new String("Java");

System.out.println(a == b);      // false
System.out.println(a.equals(b)); // true
```

참조 타입에서 `==`는 두 변수가 **같은 객체를 참조하고 있는지**를 비교한다. 위 코드의 `a`와 `b`는 내용은 같지만 서로 다른 객체를 참조하므로 `==`의 결과가 `false`다.

`equals()`는 객체가 정의한 **논리적 동등성(Logical Equality)** 을 비교하는 메서드다. `String`은 문자열의 내용을 기준으로 `equals()`를 재정의했기 때문에 `true`가 나온다.

다만 `equals()`가 무조건 객체의 실제 내부 값을 비교한다고 외우면 안 된다. 어떤 기준을 논리적 동등성으로 삼을지는 클래스가 `equals()`를 어떻게 구현했는지에 따라 결정된다. 직접 만든 엔티티나 값 객체에서 `equals()`와 `hashCode()`를 재정의할 때도 이 기준을 명확히 해야 한다.

## 8. Java는 Pass by Value로 값을 전달한다

### 기본 타입의 전달

```java
int a = 10;

change(a);

System.out.println(a); // 10

static void change(int value) {
    value = 22;
}
```

메서드를 호출할 때 `a`의 값인 `10`이 복사되어 매개변수 `value`에 전달된다. 메서드 내부에서 `value`를 `22`로 바꾸어도 `a`가 가진 값에는 영향을 주지 않는다.

### 참조 타입도 Pass by Value

참조 타입을 전달할 때도 Java는 Pass by Reference가 아니라 값에 의한 전달(Pass by Value)을 사용한다. 다만 전달되는 값이 객체 그 자체가 아니라 **객체를 참조하는 값의 복사본**이라는 점이 다르다.

```java
class Member {
    private String name;

    Member(String name) {
        this.name = name;
    }

    void changeName(String name) {
        this.name = name;
    }

    String getName() {
        return name;
    }
}

Member member = new Member("before");
change(member);

System.out.println(member.getName()); // changed

static void change(Member value) {
    value.changeName("changed");
    value = new Member("new object");
}
```

`value`에는 `member`가 가진 참조값의 복사본이 들어간다. 그래서 `value.changeName()`처럼 같은 객체의 필드를 수정하면 호출자도 변경된 객체를 보게 된다.

하지만 `value = new Member("new object")`는 메서드 안의 매개변수 `value`가 다른 객체를 참조하도록 바꾸는 것일 뿐이다. 호출자 변수 `member` 자체가 다른 객체를 가리키도록 바뀌지는 않는다.

## 9. 타입 선택도 설계의 일부다

타입 선택을 “작은 값이면 `int`, 큰 값이면 `long`” 정도로만 이해하면 실제 백엔드 코드에서 중요한 부분을 놓치기 쉽다.

예를 들어 데이터 개수가 커질 가능성이 있다면 다음처럼 더 큰 범위를 표현할 수 있는 `long`을 고려한다.

```java
long count;
```

그런데 다음 두 선언의 차이는 단순한 저장 크기의 차이가 아니다.

```java
long count;
Long count;
```

더 중요한 질문은 다음이다.

> 값이 없는 상태와 `0`을 구분해야 하는가?

* 조회 결과가 반드시 존재하고 `0`도 정상적인 값이라면 `long`이 자연스러울 수 있다.
* DB의 nullable 컬럼, 아직 집계되지 않은 값, 요청에서 생략된 값처럼 “없음”이 별도의 상태라면 `Long`이 필요할 수 있다.

이 판단은 Entity뿐 아니라 DTO, API 요청·응답, DB 스키마에도 영향을 준다. 예를 들어 API에서 `null`과 `0`을 다르게 해석한다면 Java 필드 타입만 바꾸는 것으로 끝나지 않고 validation, JSON 직렬화, DB 매핑 정책까지 함께 확인해야 한다.

결국 타입 선택은 단순한 Java 문법 문제가 아니라 **도메인의 상태를 어떻게 표현할 것인가에 대한 설계 결정**이다.

## 10. 오늘 학습하며 정리된 생각

`double price = 12.5`처럼 익숙하게 사용하던 코드에서도 이제 타입, 변수, 리터럴을 정확히 구분해서 볼 수 있게 됐다. 특히 타입은 저장 범위만 정하는 것이 아니라 변환, 비교, 전달 방식까지 함께 결정한다는 점이 연결되어 보였다.

오늘 다시 정리한 핵심은 다음과 같다.

* Narrowing은 항상 값 손실이 발생하는 것이 아니라 **값 손실 가능성이 있는 변환**이다.
* Wrapper Type은 단순히 Primitive의 객체 버전이 아니라, `null`이라는 상태를 표현해야 하는 설계와 연결된다.
* Java의 Pass by Value에서는 참조 타입도 결국 참조값의 복사본을 전달한다.
* `==`와 `equals()`는 “주소 비교 / 값 비교”로 외우기보다 참조 동일성과 논리적 동등성이라는 기준으로 이해하는 편이 정확하다.
* 변수와 타입은 기초 문법이지만 실제 백엔드 코드에서는 데이터 모델링과 API·DB의 nullable 설계까지 연결된다.

Java의 변수와 객체가 JVM에서 어떻게 관리되는지 더 깊게 이해하고 싶다면 이전에 정리한 [JDK, JVM과 플랫폼 독립성](/posts/java-jdk-jvm-platform/) 및 [JVM 구성 요소와 Garbage Collection](/posts/java-jvm-gc/) 글과 함께 보면 좋다. 이번 글에서 다룬 변수와 참조값이 실행 환경에서 어떤 영역과 생명주기로 이어지는지 연결해서 볼 수 있다.

기초 문법을 다시 공부하는 일은 이미 아는 내용을 반복하는 것처럼 보이지만, 실제로는 코드의 선택에 이유를 붙이는 과정에 가깝다. 앞으로 Spring 코드를 작성할 때도 필드 타입 하나를 정할 때 그 값의 범위뿐 아니라 `null`의 의미와 도메인의 상태까지 함께 생각해 보려 한다.
