앞서 트랜잭션과 격리 수준을 공부하면서 함께 확정할 변경과 다른 트랜잭션에서 보이는 데이터를 구분해 보았다. 여러 변경을 하나의 업무 단위로 묶는 문제와 동시에 실행되는 작업 사이의 읽기 문제는 비슷해 보여도 서로 다른 기준으로 판단해야 했다. [트랜잭션 격리 수준 — 같은 트랜잭션에서 다시 읽으면 같은 값이 보일까?](https://w00lam.github.io/posts/transaction-isolation-levels/)에서 T1과 T2의 실행 순서를 따라가며 이 차이를 정리했던 것도 같은 흐름이었다.

오늘은 Database의 저장 프로시저와 Redis를 공부했다. 처음에는 둘 다 애플리케이션의 부담을 줄이는 기술이라고만 생각했다. 살펴보니 저장 프로시저는 DB에 정의한 작업의 실행 위치를 정하는 문제였다. Redis는 어떤 데이터를 어떤 연산으로 얼마나 보관할지 정하는 문제였다. 둘을 한 기능으로 엮지 않고 다음 두 질문을 따로 살펴봤다.

1. 여러 SQL과 절차적 처리를 DB에 저장해 두면 호출과 실행은 어떻게 이루어질까?
2. 반복 조회 데이터를 Redis에 저장하면 어떤 자료형과 만료·복구 기준이 필요할까?

## 저장 프로시저는 호출할 때 무엇을 전달할까

여러 SQL과 조건에 따른 처리를 데이터베이스 안에 정의해 두면 애플리케이션은 작업 본문을 매번 전송하지 않고 이름으로 호출한다. 반복되는 DB 작업을 한곳에서 관리하고 애플리케이션과 DB 사이의 왕복 횟수도 줄인다. 그렇다고 모든 업무 로직을 DB로 옮기는 것이 정답은 아니다.

처음에는 “절차적 쿼리문의 묶음을 보내고 실제 작업은 DB에서 실행한다”고 생각했다. 실행 장소는 맞게 이해했지만 정의 시점과 호출 시점을 뒤섞었다. PostgreSQL에서는 다음 두 단계를 나누어 보아야 한다.

- 정의: `CREATE PROCEDURE`로 프로시저 본문을 DB에 저장한다.
- 호출: `CALL`로 저장된 프로시저의 이름과 인수를 넘긴다.

호출할 때마다 프로시저 본문 전체를 다시 보내는 것으로 설명하면 안 된다. 본문은 DB에 남아 있고 호출자는 이름과 입력값만 넘긴다. 다음 도식처럼 실행 위치와 전달 범위를 나누어 보면 이 차이를 더 쉽게 구분할 수 있다.

![DB에 저장된 프로시저를 이름과 인수로 호출하는 흐름](/assets/images/2026-10-23-stored-procedure-redis/procedure-definition-call.svg)

*그림 1. 프로시저 본문은 DB에 정의해 두고 호출 시에는 이름과 인수를 전달한다.*

## IN·OUT·INOUT은 값의 전달 방향으로 이해한다

프로시저의 매개변수를 볼 때 `IN`, `OUT`, `INOUT`을 입력과 출력이라는 이름만 외우면 호출 예제를 읽기 어려웠다. 호출자에서 프로시저로 값이 들어가는지, 실행 뒤 결과가 나오는지를 기준으로 정리하니 다음처럼 나눌 수 있었다.

| 모드 | 입력과 출력 | 이해할 기준 |
| --- | --- | --- |
| `IN` | 호출자 → 프로시저 | 실행에 필요한 입력값 |
| `OUT` | 프로시저 → 호출자 | 실행 후 전달할 결과값 |
| `INOUT` | 호출자 → 프로시저 → 호출자 | 초기값을 받아 변경한 결과를 전달 |

PostgreSQL 18을 기준으로 작은 예제를 적어 보았다. 이 코드는 실제 실행 기록이 아니라 값의 방향을 설명하기 위한 예제다.

```sql
CREATE OR REPLACE PROCEDURE add_amount(
    IN p_amount integer,
    INOUT p_total integer,
    OUT p_added integer
)
LANGUAGE plpgsql
AS $$
BEGIN
    p_total := p_total + p_amount;
    p_added := p_amount;
END;
$$;

CALL add_amount(5, 10, NULL);
```

이 호출에서 `p_amount`는 `5`를 입력으로 받는다. `p_total`은 호출자가 전달한 초기값 `10`에서 본문 실행 뒤 `15`가 된다. `p_added`에는 프로시저가 `5`를 출력한다. 이 예제에서 예상하는 결과 행은 `p_total = 15`, `p_added = 5`다. `CALL`은 출력 매개변수가 있으면 그 값을 담은 결과 행을 반환한다.

여기서 마지막 `NULL`을 계산에 사용하는 입력값으로 이해하면 안 된다. 기본값이 없는 `OUT` 매개변수도 일반 SQL의 `CALL`에서는 인수 자리를 써야 한다. `OUT`에 대응하는 인수 표현식은 평가하지 않으므로 관례적으로 `NULL`을 넣는다. 호출 문법에서 자리를 채우는 일과 프로시저 안으로 값이 들어가는 일은 별개다. Java 메서드의 `return`이나 참조 변수 변경과 완전히 같은 방식이라고 단순화할 수도 없다.

## 프로시저와 함수는 호출 방식과 트랜잭션 제어가 다르다

PostgreSQL 18의 함수와 프로시저는 모두 DB에 저장된 루틴이다. 다만 호출 방식과 트랜잭션 제어가 다르다.

| 구분 | 함수 | 프로시저 |
| --- | --- | --- |
| 정의 | `CREATE FUNCTION` | `CREATE PROCEDURE` |
| 호출 | `SELECT` 등 SQL 표현식 안에서 호출 | `CALL`로 별도로 호출 |
| 반환 | 함수 반환값을 SQL 안에서 사용 | 함수 반환값 대신 `OUT`·`INOUT`으로 전달 가능 |
| 트랜잭션 제어 | 내부에서 `COMMIT`·`ROLLBACK` 불가 | 호출 문맥에 따라 내부 트랜잭션 제어 가능 |

여러 조회 결과나 반환값을 SQL 안에서 조합하려는 상황이라면 함수가 자연스럽다. DB 안에서 여러 작업을 절차적으로 처리하고 호출 결과를 `OUT`이나 `INOUT`으로 돌려줘야 한다면 프로시저를 검토한다. 함수는 조회만 가능하고 프로시저는 결과를 돌려줄 수 없다는 식으로 나누면 정확하지 않다.

트랜잭션 제어를 판단할 때는 호출 문맥을 함께 확인한다. 독립된 트랜잭션으로 실행되는 `CALL`에서는 조건에 따라 프로시저 내부에서 `COMMIT`이나 `ROLLBACK`을 실행한다. 명시적인 트랜잭션 블록 안에서 `CALL`을 실행하면 호출된 프로시저는 내부에서 트랜잭션을 제어할 수 없다. 프로시저 호출 자체가 새로운 독립 트랜잭션을 만드는 것도 아니다.

이 차이는 Spring의 `@Transactional`을 볼 때도 이어졌다. 애플리케이션이 이미 트랜잭션을 시작한 상태에서 `CALL`을 실행하면 DB 입장에서는 트랜잭션 블록 안에서 호출된다. 이전에 [트랜잭션 — 함께 성공할 작업과 커밋의 의미는 무엇일까?](https://w00lam.github.io/posts/database-transactions/)에서 커밋과 롤백의 경계를 업무 단위로 나누었다. 프로시저의 트랜잭션 제어도 호출자가 만든 경계를 먼저 확인한다. Spring의 다른 전파 옵션이나 실제 프로젝트의 트랜잭션 구조까지 넓히지 않고 호출 문맥이 중요하다는 기준만 정리했다.

## 프로시저를 선택해도 보안과 유지보수 판단은 남는다

프로시저가 DB 안에서 실행되어도 SQL Injection 위험이 저절로 사라지지는 않는다. 프로시저 안에서 사용자 입력을 SQL 문자열에 그대로 이어 붙이면 그 입력이 쿼리문 일부로 해석될 수 있다. [데이터베이스의 안전성과 일관성 — SQL Injection부터 복제 지연까지](https://w00lam.github.io/posts/database-security-consistency-replication/)에서 정리했던 값 바인딩 원칙을 프로시저의 동적 SQL에도 연결해 보았다.

- 값은 파라미터로 전달한다.
- PL/pgSQL 동적 SQL에서는 `EXECUTE ... USING`으로 값을 넘긴다.
- 테이블명과 컬럼명 같은 식별자는 일반적인 값 바인딩 대상이 아니므로 허용 범위를 제한한다.

프로시저의 장단점도 같이 살폈다. DB 중심의 반복 작업을 한곳에 모으고 호출 횟수를 줄이는 장점이 있다. 반대로 DB에 로직이 모이면 변경과 배포와 테스트를 애플리케이션 코드와 함께 관리한다. DBMS별 문법 차이와 DB 안에서 로직을 추적하는 디버깅 비용도 따져야 한다. 외부 API 호출과 여러 애플리케이션 작업을 조율하는 흐름은 Spring 서비스에 두는 편이 자연스러울 수 있다.

프로시저가 늘 빠르거나 안전하다고 결론 내리면 안 된다. 실행 계획 재사용 같은 설명도 DBMS와 실행 방식에 따라 달라진다. 저장 프로시저를 고를 때는 DB에 두는 편이 자연스러운 반복 작업인지, 호출자가 어떤 결과와 트랜잭션 경계를 필요로 하는지 확인한다.

## Redis는 저장할 값보다 필요한 연산을 먼저 본다

저장 프로시저 다음에는 반복 조회 결과를 Redis에 저장하는 학습용 상황으로 넘어갔다. 관계형 DB가 원본을 담당하고 Redis가 반복 조회 비용을 줄이는 캐시 역할을 맡는다. Redis는 메모리에 데이터를 두고 다양한 자료구조 연산을 제공한다. 이 구성을 모든 서비스에 적용할 고정 역할로 단정하지 않고 오늘의 캐시 상황에 한정해 이해했다.

자료형 이름부터 외우기보다 저장한 뒤 어떤 연산을 할지 물었다. 오늘 살펴본 다섯 자료형은 다음과 같다. Redis가 지원하는 전체 자료형이 다섯 개뿐이라는 뜻은 아니다.

| 자료형 | 오늘 연결한 용도 | 먼저 물어볼 질문 |
| --- | --- | --- |
| `String` | 직렬화한 조회 결과 전체와 정수 카운터 | 값을 통째로 읽거나 숫자를 증가시키는가? |
| `Hash` | 하나의 객체에 속한 필드별 조회·수정 | 객체 일부 필드만 바꾸는가? |
| `List` | 순서를 가진 값과 큐 형태의 처리 | 들어온 순서를 유지하며 처리하는가? |
| `Set` | 중복 없는 값과 포함 여부 확인 | 같은 값을 한 번만 두고 포함 여부를 확인하는가? |
| `Sorted Set` | 중복 없는 항목을 점수 기준으로 정렬 | 항목마다 점수를 두고 순위를 조회하는가? |

JSON 문자열 전체를 저장하는 경우와 객체의 일부 필드만 수정하는 경우를 나란히 놓으면 `String`과 `Hash`의 차이가 보인다. 음식점 검색 결과 전체를 직렬화해 통째로 교체한다면 `String`이 단순하다. 음식점의 일부 속성만 읽거나 바꿀 때는 `Hash`의 필드 단위 연산을 검토한다.

중복을 막는 자료형을 생각하다가 UUID를 떠올리기도 했다. 하지만 UUID는 식별자의 형식일 뿐 중복 없는 집합이나 포함 여부 확인을 제공하는 자료형은 아니다. 값의 모양과 필요한 연산을 구분해야 하므로 이때는 `Set`을 선택한다.

최근 본 항목처럼 중복을 없애면서 마지막 조회 순서를 남길 때는 `Sorted Set`을 검토한다. 항목 ID를 member로, 마지막 조회 시각을 score로 두면 같은 항목을 다시 보았을 때 score를 갱신하고 시간순으로 조회한다. `List`는 순서가 있는 값을 저장하고 큐처럼 활용한다는 기본 동작까지 정리했다.

자료형 선택은 Redis에 무엇을 저장할지에서 끝나지 않는다. 값을 전체 교체하는지 일부만 수정하는지, 중복을 허용하는지, 순서와 점수가 필요한지를 확인한 뒤 선택해야 했다.

## TTL과 캐시 무효화는 서로 다른 문제를 다룬다

TTL은 키가 일정 시간 뒤 만료되도록 설정하는 기능이다. DB 변경을 감지하거나 캐시를 즉시 최신 상태로 만드는 기능은 아니다. 두 기능을 같은 문제로 보면 캐시의 오래된 값을 언제 제거할지 설명하기 어려워진다.

음식점 주소를 DB에서 수정했는데 Redis에 이전 조회 결과가 남아 있는 상황을 떠올려 보자. TTL이 아직 남아 있다면 다음 요청은 만료 전의 오래된 결과를 받는다. DB 변경을 커밋한 뒤 관련 캐시를 삭제하거나 갱신한다. 삭제한 캐시는 다음 조회에서 DB를 읽어 다시 채운다. 이 순서만으로 모든 동시 실행 상황에서 최신성이 완전히 보장된다고 단정하지는 않았다.

그림처럼 TTL과 무효화는 담당하는 시점이 다르다. TTL은 시간이 지나면 키를 없애는 장치이고 캐시 무효화는 원본 변경으로 더 이상 사용할 수 없는 결과를 제거하는 대응이다.

![DB 변경 뒤 Redis 캐시를 무효화하고 다시 채우는 흐름](/assets/images/2026-10-23-stored-procedure-redis/cache-invalidation-flow.svg)

*그림 2. TTL은 만료 시간을 정하고 캐시 무효화는 원본 변경으로 오래된 조회 결과를 제거한다.*

Hash 필드를 수정할 때 TTL이 어떻게 되는지도 확인했다. 다음 명령은 실제 실행 기록이 아니라 동작을 설명하기 위한 예제다.

```text
HSET user:1 name "우람"
EXPIRE user:1 60
HSET user:1 name "이우람"
TTL user:1
```

마지막 `TTL`은 명령이 실행된 뒤 남아 있는 만료 시간이다. `HSET`으로 필드를 수정해도 만료 시간이 다시 60초로 설정되거나 사라지지 않는다. 반면 일반적인 `SET`으로 키의 값을 덮어쓰면 기존 TTL이 제거되므로 명령이 키를 수정하는지 통째로 교체하는지 구분한다.

키 설계도 같은 기준으로 보았다. 필터와 정렬 조건과 페이지 정보가 다른 검색 결과를 같은 키에 저장하면 결과가 서로 덮어써진다. `음식점 검색`이라는 키 하나만 두기보다 다음처럼 검색 조건과 페이지를 키에 포함한다.

```text
restaurant:search:region=마포:sort=rating:page=1
```

실제 키 이름과 인코딩 방식은 시스템에 맞춰 정한다. 검색 조건과 결과를 같은 키로 뭉뚱그리지 않는 것이 중요했다.

## RDB와 AOF는 복구할 데이터와 허용할 손실로 선택한다

Redis는 메모리를 중심으로 동작한다. 프로세스가 재시작되거나 장애가 나면 데이터가 사라질 수 있다. 반복 조회로 다시 만들 수 있는 캐시라면 다시 채우면 되지만 세션이나 쉽게 만들 수 없는 상태를 Redis에 둔다면 손실의 의미가 달라진다. 영속성은 빠른 서비스를 위한 스위치가 아니라 장애 뒤 무엇을 어느 범위까지 복구할지 정하는 기준으로 보아야 한다.

| 방식 | 남기는 내용 | 복구와 비용을 판단할 기준 |
| --- | --- | --- |
| `RDB` | 특정 시점의 데이터 스냅샷 | 마지막 스냅샷 이후 변경은 유실될 수 있음 |
| `AOF` | 데이터를 변경하는 쓰기 작업 기록 | 기록을 재적용하며 디스크 동기화 정책에 따라 손실 범위와 비용이 달라짐 |

처음에는 빠른 서비스를 위해 영속성을 켜겠다고 생각했다. 하지만 영속성은 장애 후 복구와 데이터 손실 허용 범위를 위한 선택에 가깝다. 영속성을 켠다고 무조건 빨라지는 기능은 아니다. AOF도 오류 기록이 아니었다. 오류를 모으는 로그가 아니라 데이터를 복원하는 데 사용할 쓰기 작업 기록이다.

AOF의 디스크 동기화를 자주 수행하면 데이터를 더 잘 보호할 수 있지만 쓰기 비용과 지연도 커질 수 있다. RDB는 한 시점의 스냅샷이어서 그 이후 변경이 복구되지 않을 수 있다. AOF는 쓰기 기록을 어느 시점까지 디스크에 동기화했는지에 따라 장애 시 손실 범위가 달라진다.

관계형 DB에서 다시 만들 수 있는 캐시라면 Redis의 영속성을 끄는 선택도 가능하다. 그래도 재시작 뒤 캐시를 다시 만드는 시간과 그동안 DB에 몰리는 조회 부하를 함께 확인한다. 쉽게 재생성할 수 없는 데이터를 Redis에 둔다면 RDB와 AOF 중 무엇을 어떤 동기화 정책으로 사용할지, 일부 손실을 허용할 수 있는지를 먼저 정한다. Redis라서 영속성을 반드시 끄거나 중요한 데이터라서 AOF만 켜면 손실이 없다고 결론 내리면 안 된다.

## 세션 공유와 요청 제한에서도 운영 기준이 필요하다

Redis 활용을 캐시에만 한정하지 않고 오늘 본 사례를 짧게 묶었다.

세션 공유에서는 여러 애플리케이션 서버가 공통 Redis의 세션 데이터를 조회하도록 구성한다. 어느 서버로 요청이 들어와도 동일한 세션 상태를 읽어야 할 때 유용하다. 세션 만료와 Redis 장애 시 동작까지 함께 정한다.

조회수와 요청 제한은 정수 카운터와 만료 개념으로 연결된다. `INCR`는 키의 정수 값을 1 증가시키고 키가 없으면 0을 기준으로 시작한다. 일정 시간 동안 한 사용자의 요청 횟수를 세어 제한하는 데 활용한다. 이는 일정 시간의 요청 빈도를 제한하는 문제이며 현재 동시에 접속한 사용자 수를 제한하는 문제와 같은 뜻은 아니다. 단일 `INCR` 명령의 원자성과 여러 명령을 묶은 전체 흐름의 원자성도 구분한다.

메모리도 운영 기준으로 봐야 한다. 모든 데이터를 무제한으로 캐시할 수 없으므로 키 수와 값 크기와 보관 기간을 정한다. Redis 조회가 실패한 요청이 모두 DB로 몰리면 DB 부하와 응답 지연이 커질 수 있다. 캐시를 사용하면 빨라진다는 설명에서 멈추지 않고 캐시가 없거나 실패했을 때 원본 DB가 떠안게 될 작업까지 생각한다.

오늘은 완성된 요청 제한 구현이나 Lua 스크립트까지 확장하지 않았다. 자료형과 만료와 장애 시 부하를 하나의 운영 문제로 바라보는 기준을 얻었다.

## 오늘의 정리

오늘은 DB 안에 저장할 작업과 메모리에 보관할 데이터를 어떤 기준으로 정할지 공부했다. 저장 프로시저에서는 정의와 호출을 나누어 보았다. `CREATE PROCEDURE`로 본문을 DB에 저장하고 `CALL`에서는 이름과 인수를 전달한다. `IN`·`OUT`·`INOUT`은 입력과 출력이라는 이름보다 값의 전달 방향으로 이해하는 편이 명확했다.

함수와 프로시저는 호출 방식과 트랜잭션 제어 조건이 다르다. `CALL`이 독립적으로 실행되는지 이미 시작된 트랜잭션 안에서 실행되는지에 따라 프로시저 내부의 `COMMIT`·`ROLLBACK` 가능 여부가 달라진다. DB에서 실행한다고 SQL Injection과 유지보수 문제가 저절로 사라지는 것도 아니었다.

Redis에서는 자료형 이름보다 필요한 연산을 먼저 보게 됐다. 전체 값을 교체하는지 일부 필드를 수정하는지, 중복을 허용하는지, 순서나 점수가 필요한지에 따라 `String`, `Hash`, `List`, `Set`, `Sorted Set`을 선택한다. TTL은 만료 시간을 정할 뿐 DB 변경 직후 캐시를 최신 상태로 만드는 기능이 아니다. 원본이 바뀌면 별도의 무효화나 갱신이 필요하다.

영속성은 빠르기를 위한 선택이 아니라 복구할 데이터와 허용할 손실을 정하는 기준이다. RDB와 AOF의 차이도 스냅샷과 쓰기 기록 중 무엇을 남기는지로 구분했다. 캐시의 효과를 말하려면 메모리 한계와 Redis 장애 때 DB에 몰릴 부하까지 함께 살펴야 한다.

오늘 배운 내용을 완전히 숙달했다고 말하기는 어렵다. 그래도 저장 프로시저에서는 호출자와 DB 사이의 실행 경계를 확인하고 Redis에서는 데이터의 형태보다 필요한 연산과 운영 기준을 먼저 묻는 쪽으로 질문을 바꾸게 됐다.
