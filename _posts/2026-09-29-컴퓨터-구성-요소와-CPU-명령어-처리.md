Spring에서 Controller와 Service를 작성할 때는 보통 “서버가 요청을 처리한다”고 설명한다. 그런데 이 말을 조금 더 아래로 내려가 보면 질문이 남는다.

> 프로그램은 어디에 저장되어 있다가 실행되고, CPU는 명령어와 데이터를 어떤 순서로 읽는가?

CPU가 계산한다는 사실은 알고 있었다. 하지만 실행 파일이 SSD에 있는 상태와 실행 중인 프로그램이 RAM을 사용하는 상태를 구분하지 못했고, CPU와 RAM 사이에서 주소와 실제 값이 어느 방향으로 이동하는지도 섞어 이해했다. ALU가 계산한 결과와 서버가 만드는 HTTP 응답의 관계도 한 흐름으로 뭉뚱그렸다.

오늘은 이 질문을 따라 컴퓨터 구성 요소부터 버스, 레지스터, 명령어 인출·해독·실행까지 여러 차례 학습하고 모의면접을 진행했다. 용어를 외우는 데서 끝내지 않고 작은 주소와 값을 직접 추적하면서 처음의 설명을 계속 수정했다.

## 컴퓨터 구성 요소를 실행 흐름으로 나누어 보기

### SSD에 있는 프로그램과 RAM에서 실행되는 프로그램

처음에는 RAM과 SSD를 모두 데이터를 저장하는 곳이라고 생각했다. 프로그램의 실행 파일도 데이터이고 로그도 데이터이니 저장 장치라는 큰 범주에서는 틀린 말이 아니었다. 하지만 프로그램을 실행하는 흐름을 따라가 보니 두 장치의 역할이 달랐다.

SSD에는 전원이 꺼져도 남아 있어야 하는 프로그램의 실행 파일과 이미 기록된 로그 같은 정보가 저장된다. 전원이 꺼져도 내용을 유지하는 지속적인 보존이 SSD의 역할이다.

프로그램을 실행하면 운영체제가 실행에 필요한 명령어와 데이터를 SSD에서 읽어 RAM에 올린다. CPU는 실행 중인 프로그램의 명령어와 데이터를 RAM에서 읽고 처리한다. RAM은 실행 중인 상태를 빠르게 다루는 작업 공간이지만 휘발성이므로 전원이 끊기면 그 안에 있던 실행 상태를 유지하지 못한다.

로그도 같은 기준으로 나눠 봐야 한다. 이미 SSD에 기록된 로그는 전원이 꺼져도 남는 정보다. 반면 프로그램이 로그를 만들었지만 아직 파일에 기록하지 않은 데이터는 실행 중인 메모리나 운영체제의 버퍼에 머물 수 있다. “로그가 있다”는 말만으로 곧바로 SSD에 보존되었다고 단정하면 안 된다.

```text
SSD
→ 실행 파일과 이미 기록된 로그를 지속적으로 보존

프로그램 실행
→ 필요한 명령어와 데이터를 RAM에 적재

RAM
→ 실행 중인 프로그램의 상태와 데이터를 임시로 관리

CPU
→ RAM에서 명령어와 데이터를 읽고 명령어를 실행
```

여기서 JVM의 힙도 짧게 연결할 수 있다. 실행 중인 JVM 프로세스가 Java 객체를 만들면 JVM은 힙이라는 논리적 메모리 영역에서 그 객체를 관리한다. 이 힙을 물리 RAM 전체와 같은 개념으로 보면 안 된다. JVM 힙은 Java 프로그램이 사용하는 메모리 모델이고 물리 RAM은 여러 프로세스가 사용하는 하드웨어 자원이다. JVM의 실행 상태도 결국 운영체제가 관리하는 프로세스의 메모리를 사용하지만 두 용어가 가리키는 층위는 다르다.

이 차이는 [JVM 메모리 영역 — 변수와 객체의 생명주기는 왜 다를까?](/posts/java-jvm-memory-lifecycle/)에서 정리한 참조 변수와 Heap 객체의 관계를 컴퓨터 구조의 실행 흐름에 이어 붙일 때도 도움이 됐다. 그 글에서 다룬 Heap은 Java 프로그램 안의 논리적 영역이고 오늘 보는 RAM은 CPU가 실행 중인 명령어와 데이터를 주고받는 물리 메모리 자원이다.

## CPU와 메모리 사이에서 버스가 옮기는 것

CPU와 RAM이 데이터를 주고받는다고만 말하면 어느 방향으로 무엇이 움직이는지 다시 헷갈렸다. 버스는 값을 저장하거나 계산하는 장치가 아니라 CPU와 메모리 사이에서 신호와 값을 전달하는 경로다. 어떤 내용을 전달하는지에 따라 세 가지 버스로 나누어 생각했다.

- 주소 버스는 접근할 위치를 전달한다. CPU가 RAM의 몇 번 주소를 볼지 알려 주는 경로다.
- 데이터 버스는 그 위치에 있는 실제 값이나 메모리에 저장할 값을 전달한다.
- 제어 버스는 읽기·쓰기처럼 어떤 동작을 할지 나타내는 제어 신호를 전달한다.

메모리 읽기와 쓰기를 나누면 방향이 분명해진다.

```text
읽기
CPU ── 주소 버스: 읽을 위치 ──→ RAM
CPU ── 제어 버스: 읽기 신호 ──→ RAM
RAM ── 데이터 버스: 해당 위치의 실제 값 ──→ CPU

쓰기
CPU ── 주소 버스: 저장할 위치 ──→ RAM
CPU ── 제어 버스: 쓰기 신호 ──→ RAM
CPU ── 데이터 버스: 저장할 실제 값 ──→ RAM
```

예를 들어 CPU가 `RAM[500]`의 값을 읽는다면 `500`이라는 주소와 읽기 신호는 CPU에서 RAM으로 간다. RAM은 그 위치에 저장된 실제 값을 CPU 쪽으로 보낸다. 반대로 CPU가 `13`을 `RAM[502]`에 저장한다면 주소 `502`, 쓰기 신호, 값 `13`이 모두 CPU에서 RAM으로 향한다.

![CPU 내부 레지스터와 제어장치·ALU가 RAM과 주소·제어 신호·실제 값을 주고받는 흐름](/assets/images/2026-09-29-computer-architecture-cpu-instruction-flow/cpu-memory-bus-flow.svg)

그림의 세 방향을 뒤에서 사용할 명령어 추적 예시와 연결해 보자. 명령어를 인출할 때는 CPU가 명령어가 있는 주소를 RAM으로 보내고 RAM이 그 주소의 명령어를 CPU로 돌려준다. `ADD`에 필요한 값을 읽을 때도 주소와 읽기 신호가 먼저 RAM으로 향하고 실제 값이 CPU로 돌아온다. `STORE`에서는 AC의 실제 값이 데이터 버스를 타고 RAM으로 이동한다.

## 제어장치와 ALU의 역할을 나누어 보기

CPU 안에는 명령어를 해석하고 실행 순서를 조정하는 제어장치와 실제 산술·논리 연산을 수행하는 ALU가 있다. 제어장치는 현재 명령어가 무엇을 요구하는지 해석하고 레지스터와 메모리가 어떤 순서로 움직일지 조정한다. 연산이 필요하면 ALU가 레지스터에 담긴 값을 사용해 덧셈이나 비교 같은 연산을 수행한다.

처음에는 ALU가 비교 연산을 수행한 뒤 클라이언트에게 HTTP 응답을 보내는 일까지 하나의 흐름이라고 설명했다. 이 설명은 CPU 내부의 연산과 서버 애플리케이션의 역할을 섞은 것이다.

실제 흐름은 다음처럼 나누어야 한다.

```text
CPU
→ 서버 프로그램의 명령어를 실행
→ 필요한 산술·논리 연산을 수행

서버 프로그램
→ CPU가 실행한 명령어를 이용해 요청 처리 결과를 계산
→ HTTP 응답에 넣을 내용을 구성

운영체제와 네트워크 기능
→ 프로그램이 요청한 전송 작업을 처리
→ 네트워크를 통해 응답을 전달
```

ALU가 `4 + 9`를 계산할 수는 있지만 ALU가 Spring의 비즈니스 로직을 이해하거나 HTTP 응답 문장을 직접 작성하는 것은 아니다. 서버 프로그램이 실행되면서 CPU의 연산을 이용해 응답 내용을 만들고 운영체제의 네트워크 기능을 통해 전송 작업이 이어진다.

## PC와 IR로 실행할 명령어를 구분하기

모의면접에서 PC와 IR을 설명하면서 명령어의 주소와 명령어 자체를 한동안 혼동했다. 작은 메모리 예시로 둘을 분리해 보니 역할이 단순해졌다.

```text
주소 100: LOAD 501
주소 101: ADD 503
주소 102: STORE 502
```

PC(Program Counter)는 다음에 인출할 명령어의 주소를 담는다. PC가 `100`이면 CPU는 주소 `100`에서 명령어를 읽는다. RAM의 `100`번 위치에 들어 있는 `LOAD 501` 자체가 PC에 들어가는 것은 아니다.

CPU가 주소 `100`에서 `LOAD 501`을 인출하면 그 명령어는 IR(Instruction Register)에 들어간다. IR은 지금 해석하고 실행하는 명령어를 담는다. 이때 PC는 다음 인출을 위해 `101`을 가리키도록 갱신될 수 있다.

```text
PC = 100
→ RAM[100]에서 명령어 인출
→ IR = LOAD 501
→ PC는 다음 명령어 주소인 101을 가리킴
```

명령어는 수행할 동작을 나타내는 연산 코드와 연산에 사용할 값 또는 주소를 나타내는 부분으로 나누어 볼 수 있다. `LOAD 501`에서 `LOAD`는 수행할 동작이고 `501`은 값을 읽을 메모리 주소다. 따라서 명령어 안에 적힌 `501`과 `RAM[501]`에 저장된 값은 같은 것이 아니다.

## MAR, MBR, AC에서 주소와 실제 값을 구별하기

오늘 사용한 CPU 모형에서는 메모리에 접근하는 주소와 메모리에서 오가는 실제 값을 각각 다른 레지스터에 담아 추적했다.

- MAR(Memory Address Register)은 접근할 메모리 주소를 담는다.
- MBR(Memory Buffer Register)은 메모리에서 읽거나 메모리에 쓸 값을 담는다.
- AC(Accumulator)는 연산에 사용하는 값이나 연산 결과를 담는 누산기다.

`500`과 `RAM[500]`을 다시 구분해 보자.

```text
MAR = 500
→ 500번 메모리 위치에 접근한다는 뜻

RAM[500] = 27
→ 500번 위치에 실제로 저장된 값이 27이라는 뜻

MBR = 27
→ RAM에서 읽은 실제 값 27을 CPU 쪽에서 들고 있는 상태
```

명령어 인출과 데이터 읽기도 다른 접근이다. PC가 `100`을 가리킬 때 CPU는 `MAR = 100`으로 두고 `RAM[100]`에 저장된 명령어를 MBR로 읽은 뒤 IR에 담는다. 그 명령어가 `LOAD 500`이라면 해독 후에는 다시 `MAR = 500`으로 두고 `RAM[500]`의 값을 읽어 AC에 넣는다.

즉 주소 `100`에서 명령어를 인출하는 과정과 명령어에 적힌 주소 `500`에서 데이터를 읽는 과정은 메모리 접근이 두 번 일어나는 별개의 단계다. `500`이라는 숫자를 읽었다고 해서 곧바로 값 `RAM[500]`을 읽은 것도 아니다.

이 글에서 사용하는 MAR, MBR, AC와 단계별 흐름은 학습을 위한 단순화된 CPU 모형에 따른 것이다. 실제 CPU는 다른 이름과 더 복잡한 구조를 사용할 수 있으므로 모든 CPU가 같은 레지스터 이름과 동일한 순서로 동작한다고 일반화하지 않는다. Cornell University의 자료에서는 오늘의 MBR과 비슷한 역할을 하는 이름으로 MDR(Memory Data Register)을 사용하기도 한다. 여기서는 학습 중 사용한 MBR 명칭을 유지했다.

## 명령어를 인출하고 해독하고 실행하기

명령어 처리의 큰 흐름은 인출(Fetch), 해독(Decode), 실행(Execute)으로 이어진다. Cornell University의 [The 5 Classic CPU Stages](https://www.cs.cornell.edu/courses/cs3410/2025fa/notes/cpu_stages.html)에서 설명하는 큰 단계를 확인하되 오늘은 파이프라인 최적화나 세부 단계까지 확장하지 않았다. [A5: CPU Simulation](https://www.cs.cornell.edu/courses/cs3410/2025fa/assignments/cpusim/instructions.html)에서는 PC가 인출할 명령어의 주소를 담고 명령어를 해독한 뒤 필요한 피연산자를 사용하는 흐름을 확인했다.

오늘의 단순한 CPU 모형으로 정리하면 다음과 같다.

```text
1. PC가 가리키는 주소를 MAR에 넣는다.
2. 해당 주소의 명령어를 메모리에서 읽어 MBR을 거쳐 IR에 넣는다.
3. 다음 명령어를 준비하도록 PC를 갱신한다.
4. 제어장치가 IR의 연산 코드와 피연산자 주소를 해독한다.
5. 필요한 데이터를 메모리에서 읽거나 레지스터 값을 사용한다.
6. ALU가 연산하거나 AC의 값을 메모리에 저장한다.
```

세 명령어의 차이도 이 흐름에서 보면 분명하다.

```text
LOAD 501
→ RAM[501]의 값을 읽어 AC에 적재

ADD 503
→ RAM[503]의 값을 읽어 AC의 값과 더함
→ 결과를 AC에 저장

STORE 502
→ AC의 값을 RAM[502]에 저장
```

`STORE`는 메모리의 값을 AC로 읽어 오는 명령어가 아니다. CPU에서 RAM으로 실제 값을 보내는 쓰기 동작이다. 반대로 `LOAD`는 RAM의 값을 CPU 쪽으로 읽어 AC에 담는 동작이다.

## 주소와 실제 값을 직접 추적해 보기

지금부터는 학습을 위해 다음 초기값을 설정하고 `AC = 13`이라는 연산 결과가 만들어지는 과정을 추적한다. `RAM[501] = 4`를 따로 기억하는 것보다 각 단계에서 어느 주소에 접근했고 어떤 값이 이동했는지 확인하는 것이 목적이다.

```text
초기 PC = 100
초기 AC = 0

RAM[100] = LOAD 501
RAM[101] = ADD 503
RAM[102] = STORE 502

RAM[501] = 4
RAM[503] = 9        ← 설명을 위해 설정한 초기 데이터
RAM[502] = 0
```

이 모형에서는 명령어 한 개를 인출한 뒤 실행하고 PC가 다음 주소로 이동한다고 단순화한다.

| 단계 | PC | MAR | MBR | IR | AC | 관련 RAM 변화 |
| --- | ---: | ---: | --- | --- | ---: | --- |
| `LOAD 501` 인출 | 100 → 101 | 100 | `LOAD 501` | `LOAD 501` | 0 | `RAM[100]`의 명령어를 읽음 |
| `LOAD 501` 실행 | 101 | 501 | 4 | `LOAD 501` | 4 | `RAM[501] = 4`를 AC로 읽음 |
| `ADD 503` 인출 | 101 → 102 | 101 | `ADD 503` | `ADD 503` | 4 | `RAM[101]`의 명령어를 읽음 |
| `ADD 503` 실행 | 102 | 503 | 9 | `ADD 503` | 13 | `RAM[503] = 9`를 읽어 `4 + 9` 수행 |
| `STORE 502` 인출 | 102 → 103 | 102 | `STORE 502` | `STORE 502` | 13 | `RAM[102]`의 명령어를 읽음 |
| `STORE 502` 실행 | 103 | 502 | 13 | `STORE 502` | 13 | AC의 `13`을 써서 `RAM[502] = 13` |

첫 번째 인출에서는 주소 `100`이 MAR로 이동하고 RAM은 그 위치의 명령어 `LOAD 501`을 MBR로 돌려준다. 이후 IR이 이 명령어를 담는다. `LOAD`를 실행할 때는 명령어에 적힌 주소 `501`이 MAR로 들어가고 `RAM[501]`의 실제 값 `4`가 MBR을 거쳐 AC로 이동한다.

두 번째 명령어를 인출한 뒤 `ADD 503`을 실행하면 접근 주소는 `503`이다. `RAM[503]`의 값 `9`를 읽어 AC의 `4`와 더하므로 연산 결과는 `AC = 13`이 된다. 여기서 ALU가 더한 대상은 주소 `503` 자체가 아니라 그 주소에서 읽은 실제 값 `9`다.

마지막 `STORE 502`에서는 `502`가 읽을 주소가 아니라 쓸 주소다. AC에 있던 실제 값 `13`이 MBR에 담긴 뒤 주소 `502`와 쓰기 신호를 따라 RAM으로 이동한다. 그래서 실행 후 `RAM[502] = 13`이 된다. 레지스터 값을 한 단계씩 적어 보니 명령어 인출, 데이터 읽기, 연산, 결과 저장을 같은 동작으로 취급하지 않게 됐다.

## 순차 실행과 분기를 나누어 보기

순차 실행에서는 현재 명령어가 끝난 뒤 PC가 다음 명령어 주소를 가리킨다. 예를 들어 `103`번 주소의 명령어를 실행한 뒤 다음 주소로 이어지면 PC는 `104`를 본다.

```text
주소 103: 어떤 명령어
순차 실행
→ 다음 PC = 104
```

분기 명령어가 실행되면 순서상 다음 주소 대신 분기 대상 주소를 PC에 넣을 수 있다.

```text
주소 103: 조건이 참이면 110으로 분기
분기 실행
→ 다음 PC = 110
```

여기서 메모리에 값을 저장하는 동작과 다음 명령어의 위치를 바꾸는 동작을 구분해야 한다. `STORE`는 AC의 값을 RAM에 저장하지만 다음에 실행할 명령어의 위치를 바꾸는 명령어가 아니다. 분기 명령어는 조건에 따라 PC를 `110`처럼 다른 주소로 바꾸지만 그 자체가 메모리에 값을 저장하는 동작은 아니다.

오늘 모의면접에서 `STORE`와 분기를 함께 설명하려다 둘을 같은 제어 흐름으로 묶었다. 지금은 “어떤 값을 RAM에 쓰는가”와 “다음에 어느 주소의 명령어를 인출하는가”를 서로 다른 질문으로 확인한다.

## 기존에 공부한 JVM과 서버 요청 흐름에 연결하기

오늘의 RAM과 CPU 흐름은 앞서 공부한 Java와 Spring 글의 아래 단계와 연결된다.

먼저 실행 중인 JVM 프로세스가 사용하는 메모리와 Java 객체의 생명주기는 [JVM 메모리 영역 — 변수와 객체의 생명주기는 왜 다를까?](/posts/java-jvm-memory-lifecycle/)에서 다뤘다. 오늘은 그 JVM 프로그램 자체도 CPU가 읽고 실행하는 명령어들의 흐름 위에서 동작한다는 점을 덧붙였다. 다만 JVM Heap을 물리 RAM과 동일시하지 않고 논리적 메모리 영역과 하드웨어 자원을 분리해서 봤다.

서버에 여러 요청이 들어왔을 때 각 Thread가 공유 객체의 상태를 어떻게 다루는지는 [Java Thread와 동시성 — 공유 상태는 왜 문제가 되고 어떻게 제어할까?](/posts/java-thread-concurrency-shared-state/)에서 정리했다. 오늘의 내용은 Thread가 실행하는 서버 코드도 결국 CPU가 명령어를 인출하고 데이터를 읽고 연산하는 과정을 거친다는 더 낮은 층위의 설명이 된다.

요청이 Controller에 도착하고 응답이 만들어지는 Spring MVC 흐름은 [Spring MVC HTTP 요청 처리 흐름 — DispatcherServlet부터 Jackson까지](/posts/spring-mvc-http-request-flow/)에서 다뤘다. 오늘은 그 흐름 안에서 CPU가 Spring이라는 이름을 이해한다고 생각하지 않도록 경계를 다시 그었다. CPU는 프로그램의 명령어를 실행하고 서버 프로그램이 처리 결과를 구성한다. HTTP 응답을 네트워크로 내보내는 일에는 운영체제의 네트워크 기능이 관여한다.

## 실제 백엔드 개발에서 이어지는 흐름

Spring 서버가 요청을 처리하는 과정을 오늘 배운 컴퓨터 구조에 맞춰 짧게 이어 보면 다음과 같다.

```text
SSD에 서버 실행 파일과 관련 데이터가 보존되어 있다.
        ↓
서버를 시작하면 운영체제가 필요한 프로그램과 데이터를 메모리에 올린다.
        ↓
실행 중인 JVM과 객체가 메모리를 사용한다.
        ↓
CPU가 JVM과 서버 프로그램의 명령어를 인출·해독·실행한다.
        ↓
서버 프로그램이 요청을 처리하고 HTTP 응답 내용을 구성한다.
        ↓
운영체제의 네트워크 기능을 거쳐 응답이 전송된다.
        ↓
로그 기록 작업이 완료되어야 로그가 SSD에 지속적으로 남는다.
```

이 흐름은 각 층위의 책임을 섞지 않을 때 더 정확해진다. SSD는 실행 파일과 기록된 로그를 보존한다. RAM은 실행 중인 프로그램이 사용하는 작업 공간이다. CPU는 명령어를 실행하고 필요한 연산을 한다. 서버 프로그램은 그 연산을 이용해 요청 처리와 응답 구성을 수행한다. 운영체제는 프로그램과 장치 사이의 작업을 조정하고 네트워크 전송과 파일 기록을 지원한다.

그래서 CPU가 Spring의 비즈니스 로직을 직접 이해하거나 ALU가 HTTP 응답을 직접 전송한다고 말하면 안 된다. “서버가 요청을 처리한다”는 설명 아래에서 CPU의 명령어 실행, JVM 프로세스의 메모리 사용, 운영체제의 장치 접근이 이어진다고 구체화하는 편이 맞다.

## 학습 중 헷갈렸던 차이를 다시 정리하기

RAM과 SSD는 모두 정보를 다루지만 실행 중 사용하는 공간과 전원이 꺼져도 보존하는 공간이라는 역할이 다르다. RAM에서 사용한 데이터가 아직 SSD에 기록되지 않았다면 지속적으로 남았다고 볼 수 없다.

메모리를 읽을 때는 주소와 읽기 신호가 CPU에서 메모리로 가고 실제 값이 메모리에서 CPU로 온다. 메모리에 쓸 때는 주소와 쓰기 신호뿐 아니라 저장할 실제 값도 CPU에서 메모리로 간다.

PC는 다음 명령어의 주소를 가리키고 IR은 인출한 명령어 자체를 담는다. MAR는 이번에 접근할 주소를 담고 MBR은 메모리에서 읽거나 메모리에 쓸 실제 값을 담는다. 명령어의 `500`과 `RAM[500]`의 값도 주소와 값이라는 서로 다른 대상이다.

ALU의 내부 연산은 서버 프로그램이 요청 처리 결과를 만드는 데 사용되는 낮은 단계의 작업이다. 응답 내용을 구성하는 일은 서버 프로그램의 책임이고 네트워크를 통해 전송하는 과정에는 운영체제의 네트워크 기능이 관여한다.

`STORE`는 AC의 값을 메모리에 저장하고 분기 명령어는 다음에 인출할 명령어의 주소를 바꾼다. 하나는 데이터의 위치를 바꾸는 일이고 다른 하나는 실행 순서를 바꾸는 일이다.

## 오늘 이해한 내용

오늘 처음에는 “프로그램은 SSD에 있고 CPU가 데이터를 처리한다” 정도로만 설명했다. 여러 번 질문을 받고 주소와 실제 값의 차이, 명령어 인출과 데이터 읽기의 차이, 그리고 CPU 내부 연산과 서버 응답의 역할을 하나씩 분리했다.

이제는 `PC = 100`이라는 상태를 봤을 때 주소 `100`의 명령어를 인출한다는 뜻으로 이해한다. `MAR = 501`이면 접근할 위치가 `501`이라는 뜻이고 `RAM[501] = 4`라면 그 위치의 실제 값이 `4`라는 뜻이다. `AC = 13`은 연산 결과를 CPU 내부에서 들고 있는 상태이며 `STORE 502`를 실행해야 비로소 그 값이 `RAM[502]`에 저장된다.

용어를 외운 것보다 중요한 변화는 이동 방향을 확인할 수 있게 된 점이다. CPU가 RAM에서 명령어와 값을 읽는 경우와 CPU가 RAM에 결과를 쓰는 경우를 구분하고, 그 사이에서 제어장치와 ALU와 레지스터가 어떤 역할을 맡는지 설명할 수 있게 됐다.

오늘 공부를 한 문장으로 묶으면 다음과 같다.

> 컴퓨터가 서버 요청을 처리한다는 말은 SSD에 보존된 프로그램이 메모리에 올라오고, CPU가 주소와 제어 신호를 사용해 명령어와 실제 값을 주고받으며, 서버 프로그램이 그 실행 결과로 응답을 구성하는 과정을 짧게 표현한 말이다.

다음에는 오늘 사용한 단순한 CPU 모형과 실제 JVM 바이트코드·기계어 실행 사이의 차이를 더 확인해 볼 수 있겠다. 다만 이번 학습에서 가장 먼저 남겨야 할 기준은 주소와 값을 섞지 않는 것, 읽기와 쓰기의 방향을 나누는 것, CPU의 연산과 서버의 응답 전송을 서로 다른 책임으로 보는 것이다.
