어제 [배열과 연결 리스트 — 접근과 삽입·삭제 비용은 어디에서 생길까?](/posts/array-linked-list-access-insert-delete-cost/)를 공부하면서 자료구조의 이름보다 비용이 생기는 위치를 봐야 한다고 정리했다. 배열은 요소를 옮기는 데 비용이 들고 연결 리스트는 원하는 위치를 찾는 데 비용이 든다는 내용이었다. 오늘은 그 차이를 Java 컬렉션의 동작과 처리 순서까지 확장했다.

처음에는 `ArrayList`의 초기 용량을 정하면 그만큼 요소가 미리 만들어진다고 생각했다. 배열을 확장하는 순간에는 `O(n)` 복사가 발생하는데 맨 뒤 추가를 왜 분할 상환 `O(1)`이라고 부르는지도 바로 연결하지 못했다. `LinkedList`는 인덱스가 있으니 반복문으로 읽어도 배열과 비슷할 것이라고 생각했다.

모의면접에서는 처리 순서도 헷갈렸다. 먼저 들어온 작업을 처리하는 `Queue`와 나중에 들어온 작업을 먼저 꺼내는 `Stack`을 섞어 설명했고 `Heap`은 전체 데이터가 정렬된 구조라고 답했다. 오늘은 다음 질문을 따라가며 이 부분을 다시 나누어 보았다.

- `ArrayList`의 초기 용량을 지정하면 요소도 만들어질까?
- 배열 확장에 복사가 필요하다면 추가는 왜 분할 상환 `O(1)`일까?
- 같은 `LinkedList`도 순회 방법에 따라 전체 비용이 달라질까?
- 먼저 들어온 작업과 우선순위가 높은 작업은 같은 방식으로 처리할까?
- `Heap`은 전체 데이터가 정렬된 구조일까?

오늘 실제 서비스를 수정하거나 성능을 측정한 것은 아니다. 개념을 학습하고 모의면접에서 설명하면서 자료구조를 선택하는 기준을 고친 날이다.

## `ArrayList`의 `size`와 `capacity`는 서로 다르다

`ArrayList`를 설명할 때 먼저 나누어야 하는 값은 `size`와 `capacity`다.

- `size`는 현재 실제로 저장된 요소의 수다.
- `capacity`는 내부 배열이 확보한 저장 공간이다.

초기 용량을 지정해도 요소가 만들어지지는 않는다. 저장 공간을 먼저 확보할 뿐이다. 초기 용량은 최대 저장 개수를 제한하는 값도 아니다. 공간이 부족해지면 `ArrayList`는 더 큰 배열을 만들고 기존 요소를 새 배열로 복사한 뒤 내부 배열을 바꾼다.

다음 코드에서 `new ArrayList<>(3)`은 요소 세 개가 들어 있는 리스트를 만드는 코드가 아니다.

```java
List<Integer> values = new ArrayList<>(3);

System.out.println(values.size()); // 0

values.add(10);
values.add(20);
values.add(30);
values.add(40);

System.out.println(values.size()); // 4
```

네 번째 `add`가 성공하는 이유는 초기 용량이 최대 크기 제한이 아니기 때문이다. `size`는 요소를 추가할 때마다 늘어난다. 내부 배열의 길이가 기존 배열 객체에서 바로 변하는 것도 아니다. 공간이 부족해진 시점에 더 큰 배열 객체를 만들고 요소를 복사하는 방식이다.

Java API는 `ArrayList`의 정확한 성장 비율을 보장하지 않는다. 그래서 여기서 `capacity`를 직접 출력할 수 있는 공개 메서드가 있다고 가정하거나 특정 배수로 늘어난다고 단정하면 안 된다. 오늘 필요한 내용은 공간이 부족할 때 새 배열과 복사가 필요하다는 원리다.

![capacity가 6인 내부 배열에서 실제 요소 3개와 여유 슬롯을 구분하고 공간이 부족할 때 더 큰 배열로 복사하는 개념도](/assets/images/2026-10-07-data-structure-cost/arraylist-size-capacity.svg)

*그림 1. `size`는 실제 요소 수이고 `capacity`는 내부 배열의 저장 공간이다. 오른쪽 배열은 특정 성장 비율을 뜻하지 않는 설명용 예시다.*

## `set`과 `add`는 빈 공간이 아니라 유효한 위치를 다룬다

`size`와 `capacity`를 구분하지 못하면 `set`과 `add`도 헷갈린다. 다음 리스트에는 요소가 세 개 있다.

```java
List<Integer> values = new ArrayList<>(3);
values.add(10);
values.add(20);
values.add(30);

// values.set(3, 40); // IndexOutOfBoundsException
values.add(3, 40);    // 맨 뒤에 새 요소 추가
```

`size`가 3이면 기존 요소의 인덱스는 `0`, `1`, `2`다. `set(index, value)`는 이미 존재하는 위치의 요소를 교체한다. 인덱스 3에는 교체할 요소가 없어서 실패한다.

반면 `add(index, value)`는 새 요소를 삽입한다. 삽입 위치로 `size`를 허용하므로 `add(3, 40)`은 맨 뒤에 새 요소를 추가한다. 삽입 후 `size`는 4가 되고 인덱스 3에 `40`이 존재한다.

내부 배열에 빈 슬롯이 있다는 사실과 그 위치에 리스트 요소가 있다는 사실은 다르다. `capacity`가 6이라고 해서 인덱스 3부터 5까지를 `set`으로 사용할 수 있는 것은 아니다. 리스트가 관리하는 유효한 요소 범위는 `size`로 결정된다.

메서드 이름을 외우는 것보다 다음 관계를 먼저 확인하는 편이 정확하다.

| 작업 | 의미 | 허용되는 인덱스 범위 |
| --- | --- | --- |
| `set(index, value)` | 기존 요소 교체 | `0 <= index < size` |
| `add(index, value)` | 새 요소 삽입 | `0 <= index <= size` |

## 확장 한 번의 `O(n)`과 추가의 분할 상환 `O(1)`은 모순이 아니다

처음에는 배열 확장에 기존 요소 복사가 필요하다는 사실과 맨 뒤 추가의 분할 상환 `O(1)`이 서로 충돌한다고 생각했다. 복사하는 순간에는 분명 요소 수만큼 확인해야 하므로 `O(n)`이기 때문이다. 두 표현은 한 번의 비용과 여러 번의 작업에 대한 평균 비용을 각각 말한다.

맨 뒤에 공간이 남아 있을 때 요소를 추가하는 비용은 `O(1)`이다. 용량이 가득 차서 확장이 발생하는 추가는 기존 요소를 새 배열로 복사하므로 `O(n)`이다. 하지만 모든 추가에서 전체 복사가 일어나는 것은 아니다.

설명을 위해 용량이 두 배씩 늘어나는 모델을 사용해 보자. 이 모델을 실제 `ArrayList`나 `ArrayDeque`의 정확한 성장 정책이라고 말하는 것은 아니다. 여러 번의 추가에서 복사량이 어떻게 누적되는지 보기 위한 단순한 모델이다.

확장할 때 복사하는 요소 수가 다음처럼 늘어난다고 하자.

```text
2 + 4 + 8 + ... + 2^k
```

마지막 배열의 크기를 `n`이라고 보면 이 합은 마지막 항의 일정한 배수보다 크지 않다. 여러 번의 추가에 걸친 총복사량은 `O(n)`으로 묶인다. 요소 `n`개를 추가하는 동안 일반 추가에 드는 비용 `O(n)`과 확장 복사에 드는 총비용 `O(n)`을 합치면 전체 비용은 `O(n)`이다.

그래서 추가 `n`회의 평균 비용을 나누면 한 번의 추가에 대한 분할 상환 비용은 `O(1)`이다. 특정 한 번의 확장 비용이 `O(n)`이라는 사실을 없애는 표현이 아니다. 비싼 복사가 드물게 발생하고 그 사이의 저렴한 추가가 비용을 나누어 부담한다는 뜻이다.

반대로 매번 배열의 길이를 1씩만 늘린다고 가정하면 복사량은 다음처럼 된다.

```text
0 + 1 + 2 + ... + (n - 1)
```

이 합은 `n(n - 1) / 2`이므로 총복사 비용은 `O(n²)`이다. 핵심은 배열을 몇 번 만들었는지가 아니다. 확장할 때마다 점점 더 많은 요소를 복사한다는 점이다.

## `LinkedList`는 순회 방식에 따라 전체 비용이 달라진다

어제 `LinkedList`의 인덱스 접근이 배열처럼 위치를 계산하지 않는다는 점을 배웠다. 오늘은 이 차이가 반복문 전체의 비용까지 바꾼다는 것을 확인했다.

```java
List<Integer> values = new LinkedList<>();
values.add(10);
values.add(20);
values.add(30);

for (int i = 0; i < values.size(); i++) {
    System.out.println(values.get(i));
}

for (Integer value : values) {
    System.out.println(value);
}
```

`LinkedList`의 `get(index)`는 가까운 끝에서 시작해 노드를 따라간다. 인덱스를 전달할 수는 있지만 배열처럼 주소를 바로 계산하는 것은 아니다. 첫 번째 반복문은 `get(i)`를 호출할 때마다 해당 위치를 다시 찾는다.

요소가 `n`개라면 위치를 찾는 작업이 반복된다. 앞에서 가까운 인덱스는 앞에서 탐색하고 뒤에서 가까운 인덱스는 뒤에서 탐색하지만 최악의 경우 탐색 길이는 `O(n)`이다. 이 작업을 `n`번 반복하므로 인덱스 기반 전체 순회는 `O(n²)`이 된다.

두 번째 반복문은 `Iterator`를 사용한다. 현재 노드에서 다음 노드로 이동하면서 각 요소를 한 번씩 처리한다. 그 결과 전체 순회 비용은 `O(n)`이다. 같은 `LinkedList`라도 순회 방법이 다르면 전체 비용이 달라진다. 반면 `ArrayList`는 인덱스 접근이 `O(1)`이므로 인덱스 기반 전체 순회도 `O(n)`이다.

### 삽입·삭제는 위치 탐색과 실제 변경을 나누어 본다

중간 삽입·삭제도 자료구조 이름만 보고 판단하면 안 된다.

- `ArrayList`는 삽입·삭제 위치 뒤의 요소를 이동하는 데 비용이 생긴다.
- `LinkedList`는 목표 위치의 노드를 찾는 데 비용이 생긴다.
- `LinkedList`에서 필요한 위치와 앞뒤 노드 참조를 `Iterator` 등으로 이미 확보했다면 연결 변경 자체는 `O(1)`이다.
- `Iterator`를 목표 위치까지 이동시키는 비용은 별도로 계산한다.

학습 중에는 `LinkedList`의 중간 삽입도 배열처럼 뒤 요소를 복사한다고 혼동했다. 최종적으로는 노드를 새로 만들고 앞뒤 참조를 바꾸는 작업으로 정리했다. Java `LinkedList`는 이중 연결 구조이므로 삽입 위치의 앞 노드와 뒤 노드가 새 노드를 가리키도록 연결을 바꾼다.

“중간 삽입·삭제는 `LinkedList`가 빠르다”는 문장만으로는 부족하다. 위치를 인덱스로 찾는 전체 연산인지, 연결 변경에 필요한 위치를 이미 확보한 연산인지에 따라 비용이 달라진다. 중간 변경이 있다는 이유만으로 `LinkedList`를 항상 선택할 수는 없다.

## `Stack`·`Queue`·`Deque`는 처리 순서를 표현한다

세 구조를 구분할 때는 데이터를 어떤 방식으로 저장하는지보다 다음에 어떤 요소를 꺼내는지를 먼저 본다.

| 구조 | 삽입·제거 규칙 | 처리 순서 |
| --- | --- | --- |
| Stack | 같은 끝에 넣고 같은 끝에서 꺼냄 | LIFO. 나중에 넣은 요소를 먼저 꺼냄 |
| FIFO Queue | 뒤에 넣고 앞에서 꺼냄 | FIFO. 먼저 넣은 요소를 먼저 꺼냄 |
| Deque | 앞과 뒤 양쪽에서 넣고 꺼냄 | 사용하는 끝에 따라 Stack 또는 Queue처럼 표현 |

오늘 답변에서 `Stack`의 순서를 FIFO와 혼동했지만 최종적으로 `Stack`은 LIFO로 교정했다. `A`, `B`, `C`를 순서대로 넣으면 Stack에서는 `C`, `B`, `A` 순서로 꺼낸다. FIFO Queue에서는 `A`, `B`, `C` 순서로 꺼낸다.

개념으로서의 Stack과 Java의 `Stack` 클래스도 구분한다. Java의 `Stack`은 인터페이스가 아니라 클래스다. 오늘 예제에서는 양 끝 연산을 제공하는 `Deque` 인터페이스와 구현 클래스 `ArrayDeque`를 사용한다. `Queue`와 `Deque`는 인터페이스이고 `ArrayDeque`와 `LinkedList`는 구현 클래스다.

모든 Queue 구현이 FIFO인 것도 아니다. `PriorityQueue`처럼 우선순위 기준으로 head를 정해 반환하는 구현도 있다. `Queue`라는 타입 이름보다 실제 구현이 어떤 처리 규칙을 사용하는지 확인한다.

```java
Deque<String> stack = new ArrayDeque<>();
stack.push("A");
stack.push("B");

System.out.println(stack.pop()); // B

Queue<String> queue = new ArrayDeque<>();
queue.offer("A");
queue.offer("B");

System.out.println(queue.poll()); // A
```

같은 `ArrayDeque`라도 `push`와 `pop`을 사용하면 Stack처럼 동작하고 `offer`와 `poll`을 사용하면 FIFO Queue처럼 동작한다. 저장 구조와 처리 규칙을 분리해서 보아야 하는 이유다.

*그림 2. Stack은 같은 끝에서 LIFO로 처리하고 FIFO Queue는 뒤에 넣어 앞에서 꺼낸다. Deque는 양쪽 끝을 모두 사용할 수 있다.*

## 반환값과 예외는 쌍으로 비교한다

Queue와 Deque의 메서드는 같은 종류의 작업이라도 실패했을 때 예외를 던지는지 특수한 값을 반환하는지에 따라 나뉜다.

| 작업 | 예외를 사용하는 메서드 | 특수 반환값을 사용하는 메서드 |
| --- | --- | --- |
| 추가 | `add` | `offer` |
| 제거 | `remove` | `poll` |
| 조회 | `element` | `peek` |
| Deque 앞쪽 추가 | `addFirst` | `offerFirst` |
| Deque 앞쪽 제거 | `removeFirst` | `pollFirst` |
| Deque 앞쪽 조회 | `getFirst` | `peekFirst` |

빈 구조에서 `remove`와 `element`는 `NoSuchElementException`을 발생시킨다. `poll`과 `peek`는 `null`을 반환한다. `push`는 Deque의 앞쪽에 추가하는 작업이고 `pop`은 앞쪽에서 제거하는 작업이다. 이름에 `push`가 들어가지만 제거가 아니라 추가라는 점을 다시 확인했다.

용량이 제한된 Queue에서는 추가할 수 없을 때 `offer`가 `false`를 반환하고 `add`가 `IllegalStateException`을 발생시킬 수 있다. 다만 `new ArrayDeque<>(2)`의 `2`는 고정된 최대 저장 개수가 아니다. 세 번째 요소를 넣었다고 곧바로 `offer`가 `false`를 반환하는 구조로 이해하면 안 된다. `ArrayDeque`는 필요하면 내부 저장 공간을 늘린다.

`ArrayDeque`는 `null`을 허용하지 않는다. 그래서 빈 상태에서 반환되는 `null`과 저장된 요소를 구분할 수 있다. `null`을 실제 요소로 허용하는 Queue라면 `poll`이나 `peek`의 `null`이 빈 상태를 뜻하는지 별도로 확인할 필요가 있다.

변수의 선언 타입도 사용할 수 있는 메서드에 영향을 준다.

```java
Queue<String> queue = new ArrayDeque<>();
queue.offer("A");
// queue.addFirst("B"); // Queue 타입에는 Deque 전용 메서드가 없음
```

실제 객체가 `ArrayDeque`여도 변수 타입이 `Queue`이면 그 타입이 노출하는 메서드만 바로 호출할 수 있다. 양쪽 끝 연산이 필요할 때는 `Deque` 타입으로 선언한다.

## `ArrayDeque`와 연결 구조는 같은 `O(1)`이어도 다르게 움직인다

`ArrayDeque`는 배열의 양 끝 위치를 관리하면서 동작한다. 앞에서 요소를 제거할 때 남은 모든 요소를 매번 한 칸씩 옮기는 구조가 아니다. 앞쪽 위치를 다음 칸으로 이동시키고 뒤쪽 위치도 별도로 관리한다. 공간이 부족해 확장할 때는 새 배열과 복사 비용이 발생할 수 있다.

그래서 양 끝의 추가·제거는 일반적으로 분할 상환 `O(1)`로 설명한다. 한 번의 확장에는 `O(n)` 비용이 생길 수 있지만 여러 연산 전체에서 나누어 보는 비용은 `O(1)`이다.

`LinkedList`는 양 끝의 `head`와 `tail` 및 관련 참조를 바꾸어 양 끝 연산을 수행한다. 요소를 추가할 때 새 노드 객체도 만든다. 두 구현 모두 양 끝 연산을 `O(1)`로 표현할 수 있지만 객체 생성과 연결 정보 관리 그리고 메모리 접근 방식은 다르다.

연결 구조로 Stack의 `pop`을 설명한다면 맨 끝까지 탐색한다고 말하면 안 된다. Stack의 top을 `head`로 사용한다고 가정하면 다음 세 단계로 충분하다.

1. 현재 `head`의 값을 확보한다.
2. `head`를 다음 노드로 변경한다.
3. 확보한 값을 반환한다.

어느 쪽을 Stack의 top으로 사용할지는 구현의 선택이다. `head`를 top으로 정하면 `pop`은 `head`에서 바로 처리할 수 있다. 이런 이유로 일반적인 메모리 내 Stack이나 FIFO Queue를 구현할 때는 양 끝 연산이 단순한 `ArrayDeque`가 자연스러운 선택이 될 수 있다.

## `Heap`은 우선순위를 유지하기 위한 부분 순서다

입력 순서와 우선순위는 서로 다른 처리 기준이다. 먼저 들어온 작업은 FIFO Queue로 처리한다. 소요 시간이 짧은 작업은 작업의 길이 같은 기준으로 우선순위를 정한다. 매번 모든 데이터를 정렬하지 않고 우선 요소를 반복해서 꺼낼 수 있는 구조가 필요하다.

이때 사용하는 구조가 Heap이다. 여기서 Heap은 JVM의 객체 저장 영역인 Heap 메모리와 다른 개념이다. 오늘의 Heap은 우선순위를 빠르게 꺼내기 위한 자료구조다.

이진 Heap은 완전 이진 트리 형태다. 마지막 레벨은 왼쪽부터 채운다. `Min Heap`에서는 부모가 자식보다 작거나 같고 `Max Heap`에서는 부모가 자식보다 크거나 같다. 이 조건은 부모와 자식 사이의 부분 순서만 보장한다.

이 조건에서는 형제끼리도 정렬되어 있을 필요가 없고 전체 배열이 오름차순이나 내림차순으로 정렬되어 있을 필요도 없다. 같은 값도 여러 개 저장할 수 있다. Heap은 전체 데이터를 정렬된 상태로 보관하는 구조가 아니다.

### 트리와 배열의 인덱스를 대응시킨다

이진 Heap은 완전 이진 트리라서 배열로 표현하기 좋다. 0번 인덱스를 루트로 사용하면 인덱스 `i`의 관계는 다음처럼 계산한다.

- 부모: `(i - 1) / 2` — 루트 제외
- 왼쪽 자식: `2 * i + 1`
- 오른쪽 자식: `2 * i + 2`

예를 들어 Min Heap `[2, 4, 7, 9, 8]`에서 0번 요소 `2`는 루트다. 1번 인덱스의 `4`와 2번 인덱스의 `7`이 자식이 된다. 1번 요소 `4`의 자식은 3번 `9`와 4번 `8`이다. 부모가 자식보다 작거나 같다는 조건은 지키지만 `[2, 4, 7, 9, 8]` 전체가 정렬된 배열은 아니다.

![Min Heap 2 4 7 9 8을 완전 이진 트리와 0번 인덱스 배열로 대응하고 부모·자식 관계를 표시한 개념도](/assets/images/2026-10-07-data-structure-cost/heap-tree-array-mapping.svg)

*그림 3. Heap 배열의 인덱스는 완전 이진 트리의 부모·자식 관계를 계산하기 위한 값이다. 배열 전체의 정렬 순서를 나타내지 않는다.*

## `Heap`은 삽입과 제거 방향이 다르다

Min Heap이 `[2, 4, 7, 9, 8]`인 상태에서 `1`을 삽입해 보자. 새 요소는 완전 이진 트리의 빈자리를 유지하기 위해 먼저 마지막에 들어간다.

```text
[2, 4, 7, 9, 8, 1]
```

`1`의 부모는 `7`이다. Min Heap에서 부모보다 작으므로 둘을 바꾸며 위로 올라간다.

```text
[2, 4, 1, 9, 8, 7]
→ [1, 4, 2, 9, 8, 7]
```

삽입은 마지막 위치에서 부모 방향으로 조정한다. 부모가 자식보다 작거나 같아지는 순간 멈춘다.

이번에는 루트 `1`을 제거해 보자. 루트를 바로 지우면 트리의 빈자리가 생기므로 마지막 요소 `7`을 루트로 옮긴다.

```text
[7, 4, 2, 9, 8]
```

이제 `7`의 자식은 `4`와 `2`다. Min Heap에서는 두 자식 중 더 작은 `2`와 비교한다. `7`이 더 크므로 `2`와 바꾼다.

```text
[2, 4, 7, 9, 8]
```

루트 제거는 마지막 요소를 루트로 옮긴 뒤 자식 방향으로 조정한다. 모든 요소를 왼쪽으로 한 칸씩 이동하는 작업이 아니다. 완전 이진 트리의 높이가 `O(log n)`이므로 삽입과 루트 제거의 조정 경로도 `O(log n)`이다.

![Min Heap에 1을 삽입할 때 부모 방향으로 올라가고 루트 제거 후 7이 작은 자식 2를 따라 내려가는 과정](/assets/images/2026-10-07-data-structure-cost/heap-sift-up-down.svg)

*그림 4. 삽입은 부모 방향으로 올라가고 루트 제거는 더 작은 자식을 따라 내려간다. 두 작업 모두 전체 배열을 정렬하지 않는다.*

## Heap 연산 비용은 조건별로 나누어 본다

Heap의 연산 비용은 “정렬되어 있다”는 말로 설명할 수 없다. 실제로 보장되는 구조 조건을 기준으로 나누어야 한다.

| 연산 | 비용 | 이유 |
| --- | --- | --- |
| 루트 조회 | `O(1)` | 우선 요소가 루트에 있음 |
| 삽입 | `O(log n)` | 마지막에 넣은 뒤 부모 방향 조정 |
| 루트 제거 | `O(log n)` | 마지막 요소를 올린 뒤 자식 방향 조정 |
| 임의 값 탐색 | `O(n)` | 어느 가지에 값이 있는지 부모·자식 조건만으로 결정하기 어려움 |
| bottom-up Heap 구성 | `O(n)` | 하단 노드는 짧게 이동하고 상단의 긴 이동은 적음 |
| 하나씩 삽입해 구성 | `O(n log n)` | `n`개 삽입 각각에 조정 비용이 생김 |
| `n`개 요소를 반복 제거 | `O(n log n)` | 매번 루트 제거와 조정을 수행함 |

처음에는 Heap의 부모·자식 관계를 보고 임의의 값을 `O(log n)`에 찾을 수 있다고 답했다. 이진 탐색 트리처럼 비교 결과에 따라 탐색하지 않아도 되는 한쪽 가지를 항상 결정할 수 있는 구조가 아니므로 이 답은 틀렸다. 원하는 값이 여러 가지 중 어디에 있는지 알 수 없어서 최악의 경우 전체를 확인할 필요가 있다.

bottom-up 방식의 Heap 구성도 모든 노드가 `log n`만큼 이동하는 작업이 아니다. 마지막 레벨에 가까운 노드가 많지만 이 노드들은 이동할 수 있는 높이가 짧다. 반대로 긴 거리를 이동할 수 있는 상단 노드는 적다. 이 이동 거리와 노드 수를 함께 보면 전체 비용을 `O(n)`으로 정리할 수 있다.

## `PriorityQueue`는 비교 기준에 따라 head를 정한다

Java의 `PriorityQueue`는 Heap을 이용해 우선순위가 가장 앞서는 요소를 head에 둔다. 숫자를 저장한다고 해서 자료구조가 본질적으로 작은 수를 먼저 반환하는 것은 아니다. 기본 비교 기준이 자연 순서이기 때문에 결과가 그렇게 보이는 것이다.

```java
Queue<Integer> minQueue = new PriorityQueue<>();
minQueue.offer(4);
minQueue.offer(1);
minQueue.offer(7);

while (!minQueue.isEmpty()) {
    System.out.println(minQueue.poll());
}
// 1, 4, 7
```

Comparator를 바꾸면 같은 숫자도 반환 기준이 달라진다.

```java
Queue<Integer> maxQueue =
        new PriorityQueue<>(Comparator.reverseOrder());

maxQueue.offer(4);
maxQueue.offer(1);
maxQueue.offer(7);

while (!maxQueue.isEmpty()) {
    System.out.println(maxQueue.poll());
}
// 7, 4, 1
```

두 예제에서 Queue의 head는 지정된 비교 기준에서 가장 앞서는 요소다. `PriorityQueue`의 초기 용량도 최대 저장 개수 제한이 아니다. 중복값은 허용하지만 `null`을 추가하면 `NullPointerException`이 발생한다.

빈 Queue에서 `poll`과 `peek`는 `null`을 반환한다. `remove`와 `element`는 `NoSuchElementException`을 발생시킨다. `ArrayDeque`와 마찬가지로 빈 상태의 `null`을 실제 요소와 구분해야 하지만 `PriorityQueue`는 애초에 `null`을 저장하지 않는다.

주의할 점은 Iterator나 향상된 `for`문으로 순회할 때 우선순위 순서가 보장되지 않는다는 것이다. 우선순위 순서로 하나씩 처리할 때는 반복적으로 `poll`한다. 동일한 우선순위를 가진 요소의 입력 순서도 보장되지 않는다. 그 순서를 보장하려면 비교 기준에 별도의 순서 조건을 포함한다.

## 백엔드에서 자료구조를 고르는 기준

오늘 배운 내용을 실제 판단 기준으로 줄이면 다음과 같다.

| 상황 | 먼저 고려할 구조 | 이유와 조건 |
| --- | --- | --- |
| 인덱스로 자주 조회하고 중간 변경이 적은 목록 | `ArrayList` | 인덱스 접근이 단순하고 순회 비용을 예측하기 쉬움 |
| 완료한 작업을 역순으로 꺼내는 처리 | Stack의 LIFO | 마지막 작업을 먼저 꺼내는 순서가 필요함 |
| 입력된 순서대로 처리할 작업 목록 | FIFO Queue | 먼저 들어온 작업부터 꺼냄 |
| 소요 시간이 짧은 작업을 먼저 고르는 처리 | `PriorityQueue` | 작업 시간 등 비교 기준에 따른 우선순위를 사용함 |

완료한 작업을 역순으로 꺼낸다고 해서 모든 부작용이 자동으로 복구되는 것은 아니다. LIFO는 꺼내는 순서를 정할 뿐이고 실제 복구 작업은 별도로 구현한다.

메모리 내 Queue에 작업을 저장했다고 요청 스레드의 실행 순서나 작업 완료 순서까지 보장되는 것도 아니다. Queue는 저장된 작업의 처리 규칙을 표현한다. 스레드의 실행과 완료는 별도의 동시성 조건을 확인한다.

`ArrayDeque`와 `PriorityQueue`는 스레드 안전한 컬렉션이 아니다. 여러 요청이 같은 인스턴스를 수정한다면 그 공유 방식에 맞는 동시성 대책이 필요하다. 오늘은 락 구현이나 분산 메시지 처리 설계까지 확장하지 않고 자료구조의 선택 기준만 정리했다.

## 오늘의 정리

오늘은 `ArrayList`의 초기 용량과 실제 요소 수가 다르다는 점에서 시작했다. `size`는 요소의 수이고 `capacity`는 내부 배열이 확보한 공간이다. 공간이 부족하면 새 배열을 만들어 복사하지만 모든 추가에서 복사가 발생하는 것은 아니므로 확장 한 번의 `O(n)`과 여러 추가의 분할 상환 `O(1)`은 모순이 아니다.

`LinkedList`는 인덱스 API가 있어도 배열처럼 위치에 바로 접근하지 않는다. `get(i)`를 반복하면 위치를 매번 다시 찾아 전체 `O(n²)`이 되고 Iterator 기반 순회는 `O(n)`이 된다. 삽입·삭제도 위치를 찾는 비용과 노드 연결을 바꾸는 비용을 분리해서 봐야 한다.

Stack·FIFO Queue·`PriorityQueue`는 저장 방식보다 다음에 꺼낼 요소를 고르는 기준이 다르다. Deque는 양쪽 끝을 사용할 수 있어 같은 구현으로 Stack과 Queue를 표현할 수 있다. `add`·`remove`·`element`와 `offer`·`poll`·`peek`는 실패 시 예외와 반환값이 다르므로 함께 비교한다.

Heap은 전체 정렬이 아니라 부모와 자식 사이의 부분 순서를 유지한다. 그래서 루트 조회와 조정은 빠르지만 임의 값 탐색은 `O(n)`이다. `PriorityQueue`도 반복적인 `poll`과 Iterator 순회의 순서가 다르다.

오늘은 자료구조를 완벽히 외웠다고 정리하기보다 설명이 막혔던 지점을 고쳤다. 연산 이름만 보지 않고 실제 접근 방식과 처리 규칙 그리고 위치 탐색 비용까지 확인해야 선택 기준을 설명할 수 있다.
