동시성 문제를 공부하면서 가장 먼저 떠올린 해결책은 락이었다. 여러 요청이 같은 데이터를 수정한다면 한 번에 하나씩 실행시키면 안전할 것 같았다.

그런데 실제로 구현하려고 보니 질문은 조금 달랐다.

> **이 문제에 정말 락이 필요한가? 필요하다면 충돌을 나중에 감지할 것인가, 처음부터 기다리게 할 것인가?**

이번 글에서는 낙관적 락, 비관적 락, 아토믹 업데이트를 정의만 나열하지 않고, 어떤 상황에서 무엇을 선택할지 판단하는 기준을 정리해 본다. 이전에 [동시성 문제를 이해하면서 정리한 생각](/posts/concurrency-control-strategy/)에서 동시성 제어의 종류를 넓게 살펴봤다면, 이번에는 선택 과정에 초점을 맞춘다.

## 1. 왜 DB 동시성 제어가 필요할까

재고가 1개 남은 상품에 두 요청이 동시에 들어온다고 가정해 보자. 애플리케이션 코드가 다음처럼 되어 있다면 겉보기에는 문제가 없어 보인다.

```java
if (stock > 0) {
    stock--;
}
```

하지만 여러 요청이 거의 동시에 실행되면 다음과 같은 흐름이 가능하다.

1. 요청 A가 `stock = 1`을 읽는다.
2. 요청 B도 `stock = 1`을 읽는다.
3. A와 B가 모두 `stock > 0` 조건을 통과한다.
4. 두 요청이 모두 주문을 생성하거나 재고 차감 결과를 저장한다.

결과적으로 실제 재고보다 많은 주문이 처리될 수 있다. 두 실행 흐름이 같은 값을 읽고 각자의 결과를 덮어쓰는 **Race Condition** 또는 **Lost Update** 문제다.

이때 `synchronized`나 `ReentrantLock`을 떠올릴 수 있다. 이런 JVM 락은 같은 프로세스 안의 스레드 순서를 제어하는 데는 유용하다. 하지만 서버가 두 대라면 서버 A의 JVM 락과 서버 B의 JVM 락은 서로 다른 객체다.

```text
서버 A (JVM 1) ── synchronized ── 요청 A
서버 B (JVM 2) ── synchronized ── 요청 B
                         │
                         └── 같은 DB 행을 동시에 수정할 수 있음
```

따라서 애플리케이션 인스턴스가 여러 대인 환경에서는 공유 자원인 DB 레코드에 대한 제어가 필요하다. 다만 여기서 바로 “DB 락을 걸자”로 결론 내리기보다, 변경을 DB 연산 하나로 안전하게 표현할 수 있는지부터 확인하는 것이 순서라고 느꼈다.

## 2. 먼저 락 없이 해결할 수 있는가: 아토믹 업데이트

재고 1개 감소처럼 조건과 변경을 SQL 하나로 표현할 수 있다면 아토믹 업데이트가 가장 단순한 선택일 수 있다.

```sql
UPDATE product
SET stock = stock - 1
WHERE id = ?
  AND stock > 0;
```

이 쿼리의 핵심은 애플리케이션에서 먼저 조회하고 나중에 저장하지 않는다는 점이다. DB가 하나의 `UPDATE` 문 안에서 `stock > 0`을 검사하고, 조건을 만족할 때만 감소시킨다.

Spring Data JPA에서는 변경된 행의 수를 확인해 성공 여부를 판단할 수 있다.

```java
@Modifying
@Query("""
    UPDATE Product p
       SET p.stock = p.stock - 1
     WHERE p.id = :productId
       AND p.stock > 0
    """)
int decreaseStock(@Param("productId") Long productId);
```

반환값이 `1`이면 차감에 성공한 것이고, `0`이면 상품이 없거나 재고가 이미 소진된 것으로 처리할 수 있다. 구현에 따라 상품 존재 여부와 재고 부족을 별도 메시지로 구분해야 한다면 추가 조회가 필요할 수 있지만, 적어도 차감 자체를 위해 객체를 먼저 읽고 다시 저장할 필요는 없다.

아토믹 업데이트의 장점은 분명하다.

- 별도의 락 관리 코드가 거의 필요 없다.
- 조회 후 변경 사이의 애플리케이션 구간을 줄일 수 있다.
- 단순한 증가·감소 연산을 적은 DB 요청으로 처리할 수 있다.
- 동시 요청이 많아도 한 행에 대한 조건부 연산을 DB가 처리한다.

반대로 다음과 같은 경우에는 쿼리 하나로 표현하기 어려워진다.

- 여러 비즈니스 조건을 읽고 판단해야 하는 경우
- 여러 테이블이나 여러 엔티티를 함께 변경해야 하는 경우
- 변경 전 상태를 바탕으로 복잡한 도메인 로직을 실행해야 하는 경우

예를 들어 “재고가 있고, 회원 등급이 조건을 만족하며, 특정 쿠폰이 아직 사용되지 않았을 때 주문을 생성한다”는 흐름은 단순한 숫자 감소보다 훨씬 많은 상태를 함께 다룬다. 이때는 아토믹 업데이트 하나에 모든 규칙을 욱여넣기보다 트랜잭션과 적절한 동시성 제어를 함께 설계해야 한다.

> **단순한 상태 변경이라면 모든 문제를 락으로 해결하려 하지 말고, DB 연산 하나로 원자적으로 표현할 수 있는지 먼저 확인한다.**

## 3. 충돌을 나중에 감지하기: 낙관적 락

### 동작 방식

낙관적 락은 “대부분의 요청은 충돌하지 않을 것”이라고 가정한다. 그래서 데이터를 읽을 때부터 락을 점유하지 않고, 수정할 때 다른 트랜잭션이 먼저 변경했는지를 확인한다.

JPA에서는 보통 `@Version`으로 구현한다.

```java
@Entity
public class Product {

    @Id
    private Long id;

    private int stock;

    @Version
    private Long version;
}
```

JPA는 대략 다음과 같은 SQL을 실행한다.

```sql
UPDATE product
SET stock = ?,
    version = version + 1
WHERE id = ?
  AND version = ?;
```

두 트랜잭션이 모두 `version = 1`을 읽었다고 하자. A가 먼저 수정하면 해당 행의 버전은 `2`가 된다. 그다음 B가 자신이 읽었던 `version = 1`을 조건으로 UPDATE를 실행하면 조건에 맞는 행이 없으므로 변경 행 수가 0이 된다. JPA는 이를 낙관적 락 충돌로 감지하고 예외를 발생시킨다.

![낙관적 락의 버전 비교와 재시도 흐름](/assets/images/2026-08-11-lock-selection-criteria/optimistic-lock-flow.svg)

여기서 중요한 점은 낙관적 락이 **충돌을 막는 방식이 아니라 충돌을 감지하는 방식**이라는 것이다. 따라서 충돌이 발생했을 때 어떻게 응답할지까지 설계해야 한다.

### 충돌이 발생하면 어떻게 할까

게시글 수정처럼 사용자가 최신 내용을 다시 확인해야 하는 기능이라면 충돌 사실을 알리고 다시 입력하게 할 수 있다. 반면 재고 차감처럼 최신 값을 기준으로 같은 연산을 반복해도 되는 작업이라면 제한된 횟수만큼 재시도할 수 있다.

재시도할 때 특히 조심할 부분은 **기존 트랜잭션 안에서 그대로 반복하지 않는 것**이다. 낙관적 락 예외가 발생한 트랜잭션은 이미 롤백 대상으로 표시되거나, 해당 트랜잭션 안에서 읽은 엔티티가 오래된 상태일 수 있다. 같은 영속성 컨텍스트에서 다시 저장한다고 최신 데이터를 읽었다고 볼 수 없다.

안전한 재시도 흐름은 다음과 같다.

1. 한 번의 시도를 별도 트랜잭션으로 실행한다.
2. 충돌이 발생하면 해당 트랜잭션을 종료한다.
3. 새로운 트랜잭션에서 최신 데이터를 다시 조회한다.
4. 비즈니스 로직을 다시 수행하고 수정한다.
5. 정해진 횟수를 넘기면 실패로 처리한다.

Spring에서는 트랜잭션을 담당하는 메서드와 재시도를 조정하는 메서드를 분리하는 방식이 이해하기 쉽다. 같은 클래스 안에서 자기 메서드를 호출하면 Spring 프록시를 통과하지 않아 새 트랜잭션이 만들어지지 않을 수 있다는 점도 함께 확인해야 한다. 이 주제는 [낙관적 락 테스트가 실패하던 이유](/posts/optimistic-lock-failure/)를 다시 읽으면서 더 구체적으로 확인할 수 있다.

## 4. 충돌을 미리 직렬화하기: 비관적 락

### 동작 방식

비관적 락은 “충돌이 발생할 가능성이 높다”고 보고, 데이터를 수정하기 전에 다른 트랜잭션이 접근하지 못하도록 락을 획득한다.

SQL로는 보통 다음과 같이 표현한다.

```sql
SELECT *
FROM product
WHERE id = ?
FOR UPDATE;
```

JPA에서는 조회 메서드에 `PESSIMISTIC_WRITE` 락 모드를 지정할 수 있다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select p from Product p where p.id = :id")
Optional<Product> findByIdForUpdate(@Param("id") Long id);
```

트랜잭션 A가 이 조회를 실행하면 해당 행에 Row Lock을 획득한다. 그동안 트랜잭션 B가 같은 행을 수정하거나 같은 방식으로 잠그려 하면 A가 커밋 또는 롤백하여 락을 반환할 때까지 기다린다.

![비관적 락의 Row Lock 대기 흐름](/assets/images/2026-08-11-lock-selection-criteria/pessimistic-lock-flow.svg)

비관적 락은 충돌 후 실패하고 재시도하는 대신, 처음부터 같은 데이터에 대한 접근을 순서대로 처리한다. 따라서 충돌이 매우 잦고 재시도해도 대부분 다시 충돌하는 상황에서는 오히려 예측 가능한 선택이 될 수 있다.

다만 락은 트랜잭션이 끝날 때까지 유지되므로 다음 비용이 생긴다.

- 다른 트랜잭션의 대기 시간이 길어진다.
- 동시에 처리할 수 있는 요청 수가 줄어든다.
- 트랜잭션이 길어질수록 락 점유 시간도 길어진다.
- 여러 행을 서로 다른 순서로 잠그면 Deadlock이 발생할 수 있다.

따라서 `SELECT ... FOR UPDATE`를 실행한 뒤 외부 API를 호출하거나, 긴 계산을 하거나, 사용자 입력을 기다리는 식으로 트랜잭션을 길게 유지하면 안 된다. [락과 트랜잭션 경계 분리](/posts/lock-transaction-boundary/) 글에서 정리했듯이 락의 범위와 트랜잭션의 범위를 함께 관리해야 한다.

## 5. 세 가지 방식은 무엇이 다를까

세 방식의 차이를 “락의 종류”로만 외우면 선택할 때 다시 막힌다. 실제로는 요청을 처리하는 방식과 실패 비용이 다르다고 보는 편이 이해하기 쉬웠다.

### 아토믹 업데이트

> **복잡한 객체 상태를 읽고 판단하지 않고 DB 연산 하나로 끝낼 수 있는가?**

그렇다면 아토믹 업데이트를 먼저 검토한다. 단순한 증가·감소, 조건부 상태 변경에 특히 잘 맞는다. 실패를 예외와 재시도로 처리하기보다 UPDATE 결과 행 수로 성공 여부를 판단할 수 있다는 점도 장점이다.

### 낙관적 락

> **충돌 가능성이 낮고, 대부분의 요청이 한 번에 성공하는가?**

그렇다면 락을 미리 점유하지 않고 충돌할 때만 실패시키는 편이 효율적일 수 있다. 읽기 요청이 많고 수정 충돌이 드문 게시글 편집이 대표적인 예다.

### 비관적 락

> **동시에 같은 데이터를 수정하는 요청이 많아 충돌이 자주 발생하는가?**

그렇다면 계속 실패하고 재시도하는 것보다, 처음부터 락을 획득해 순차적으로 처리하는 편이 나을 수 있다. 단, 처리 시간이 짧고 락을 오래 잡지 않는다는 전제가 필요하다.

## 6. 가장 중요한 판단 기준: 충돌 비용과 대기 비용

### 충돌 비용

낙관적 락에서는 충돌이 발생하면 실패한 작업을 다시 수행해야 한다. 재시도 한 번이 단순한 UPDATE 한 번으로 끝나지 않을 수도 있다.

- 최신 데이터 재조회
- 비즈니스 로직 재실행
- UPDATE 재시도
- 그 과정에서 발생하는 DB 요청 증가

충돌률이 낮을 때는 이 비용이 거의 드러나지 않는다. 하지만 같은 행에 요청이 몰리면 여러 요청이 계속 실패하고 다시 읽는 작업을 반복하게 된다.

> **충돌이 많을수록 낙관적 락의 재시도 비용이 커진다.**

### 대기 비용

비관적 락에서는 충돌을 실패로 돌리지 않는 대신, 다른 트랜잭션이 락을 가진 동안 기다린다. 특히 트랜잭션 안에 다음 작업이 들어가면 대기 비용이 커진다.

- 외부 API 호출
- 긴 계산이나 파일 작업
- 여러 테이블 수정
- 인덱스를 타지 못하는 느린 쿼리

락을 잡은 트랜잭션이 길어지면 뒤의 요청은 그만큼 오래 기다린다. 처리량이 떨어지고 커넥션 풀의 대기까지 이어질 수 있다.

> **트랜잭션이 길수록 비관적 락의 대기 비용이 커진다.**

결국 비교해야 할 것은 “낙관적 락과 비관적 락 중 무엇이 더 좋은가”가 아니다. 해당 기능에서 충돌로 재실행하는 비용과 락을 기다리는 비용 중 어느 쪽이 더 작은지다.

## 7. 상황별로 적용해 보기

### 단순 재고 1개 감소

재고가 0보다 클 때 1을 감소시키는 것뿐이고, 다른 상태를 함께 판단하지 않는다면 아토믹 업데이트가 우선순위가 높다.

```sql
UPDATE product
SET stock = stock - 1
WHERE id = ?
  AND stock > 0;
```

업데이트 결과가 성공이면 주문 흐름을 이어가고, 실패면 품절 응답을 반환하면 된다. 이 경우 `@Version`을 붙이거나 Row Lock을 오래 유지하는 것보다 조건부 UPDATE가 코드와 실행 흐름 모두 단순하다.

### 게시글 수정

동일한 게시글을 여러 사용자가 동시에 수정하는 일은 보통 재고 차감보다 드물다. 이때 낙관적 락을 적용하면 먼저 저장한 사용자의 수정은 반영하고, 뒤늦게 저장한 사용자는 “다른 사람이 먼저 수정했다”는 안내를 받을 수 있다.

무조건 마지막 저장으로 덮어쓰는 것보다 데이터 손실을 감지할 수 있다는 점이 중요하다. 충돌 시 사용자에게 최신 내용을 보여줄지, 수정 내용을 병합할지는 별도의 제품 정책이다.

### 선착순 상품이나 인기 상품 재고

같은 상품 행을 동시에 수정하는 요청이 매우 많다면 낙관적 락은 지속적인 충돌과 재시도를 만들 수 있다. 이 경우 짧은 트랜잭션 안에서 비관적 락으로 순차 처리하거나, 조건부 UPDATE로 재고 차감 자체를 원자화하는 방법을 검토할 수 있다.

다만 “선착순이면 무조건 비관적 락”이라고 정할 수는 없다. 트래픽 규모와 허용 가능한 대기 시간에 따라 Redis 분산 락, 대기열, 재고를 미리 나누는 방식, 비동기 처리 같은 다른 전략이 더 적합할 수 있다. [포인트 결제 동시성 설계](/posts/point-payment-concurrency-design/)에서 조건부 UPDATE와 분산 락을 함께 비교한 것도 같은 이유였다.

## 8. 선택 전 체크리스트

새로운 동시성 문제를 만났을 때는 다음 순서로 질문해 보려고 한다.

1. 변경을 조건부 UPDATE 하나로 표현할 수 있는가?
2. 변경 전 데이터를 읽어 복잡한 비즈니스 판단을 해야 하는가?
3. 같은 데이터를 수정하는 충돌은 얼마나 자주 발생하는가?
4. 충돌이 났을 때 재조회와 재실행을 감당할 수 있는가?
5. 락을 사용한다면 트랜잭션은 얼마나 오래 유지되는가?
6. 여러 행을 잠근다면 모든 코드가 같은 순서로 락을 획득하는가?
7. 실패를 사용자에게 알릴지, 자동으로 제한된 횟수만큼 재시도할지 정했는가?

정리하면 다음과 같은 방향으로 시작할 수 있다.

| 상황 | 우선 검토할 방식 | 이유 |
| --- | --- | --- |
| 단순 조건부 증가·감소 | 아토믹 업데이트 | DB 연산 하나로 정합성을 지키기 쉬움 |
| 충돌이 드문 객체 수정 | 낙관적 락 | 락 대기 없이 성공 요청을 빠르게 처리 |
| 충돌이 잦고 재시도 비용이 큼 | 비관적 락 고려 | 충돌을 사후 처리하지 않고 순차화 |
| 트래픽이 매우 크거나 처리 흐름이 김 | Redis·Queue 등 별도 전략 검토 | DB 한 행의 락만으로 해결하기 어려울 수 있음 |

## 마무리: 락보다 먼저 문제를 고르기

처음에는 동시성 문제가 발생하면 락을 사용하면 된다고 생각하기 쉽다. 하지만 실제로는 어떤 락을 사용할지를 결정하기 전에 먼저 “이 문제에 정말 락이 필요한가?”를 판단해야 한다.

단순한 상태 변경이라면 아토믹 업데이트가 더 단순할 수 있다. 충돌이 드물다면 낙관적 락으로 필요한 순간에만 충돌을 감지하는 편이 유리할 수 있다. 반대로 충돌이 빈번하고 재시도 비용이 크다면 비관적 락으로 접근을 직렬화하는 편이 나을 수 있다.

이번에 정리하면서 선택 기준은 기술 이름이 아니라 다음 항목이라는 생각이 들었다.

- 충돌 빈도
- 재시도 비용
- 락 대기 시간
- 트랜잭션 길이
- 비즈니스 로직의 복잡도

> **충돌이 많으면 낙관적 락의 재시도 비용이 커지고, 트랜잭션이 길면 비관적 락의 대기 비용이 커진다.**

결국 좋은 동시성 제어는 가장 강한 락을 고르는 것이 아니라, 데이터 변경의 모양과 실패 비용에 맞는 가장 작은 제어 수단을 고르는 데서 시작한다.
