## 1. 왜 캡슐화를 다시 공부하게 되었는가

Java를 처음 배울 때 캡슐화(Encapsulation)는 보통 이렇게 설명했다.

> 필드를 `private`으로 만들고 getter/setter를 사용한다.

문법을 익히는 단계에서는 충분히 이해할 수 있는 설명이었다. 실제로 필드를 `private`으로 바꾸면 외부에서 직접 접근할 수 없고, getter와 setter를 추가하면 필요한 값을 읽고 수정할 수 있다.

그런데 객체지향 코드를 다시 공부하면서 이 설명만으로는 캡슐화의 목적을 충분히 설명하기 어렵다는 생각이 들었다. 모든 필드에 getter와 setter를 만들어 두면 외부에서 필드를 직접 건드리는 것과 크게 다르지 않은 코드가 되기 때문이다.

오늘은 접근을 막는 문법보다 다음 질문을 중심으로 캡슐화를 정리해 보았다.

> 왜 객체의 상태를 숨겨야 하는가?

이 질문에 대한 답은 객체가 자신의 상태를 책임지게 만들기 위해서라고 이해했다. 외부가 객체의 필드를 마음대로 바꾸게 두는 대신, 객체가 수행해야 하는 의미 있는 행동을 공개하면 상태 변경 규칙을 객체 안에 모아둘 수 있다.

## 2. Encapsulation이란 무엇인가

캡슐화는 객체의 내부 상태와 내부 구현을 감추고, 외부에는 필요한 인터페이스만 공개하는 설계 방식이다. 여기서 말하는 내부에는 단순한 필드 값뿐 아니라 그 값을 변경하는 세부 방법과 검증 규칙도 포함된다.

예를 들어 다음과 같은 `User`가 있다고 해 보자.

`BT`java
public class User {

    public String status;
}
`BT`

이 객체는 외부 코드에서 아무 제약 없이 수정할 수 있다.

`BT`java
user.status = "ACTIVE";
`BT`

처음에는 간단해 보이지만, `status`가 가질 수 있는 값이 늘어나면 문제가 생긴다. 어떤 코드는 `"ACTIVE"`를 넣고, 어떤 코드는 `"ACTIVATED"`를 넣고, 다른 코드는 아직 가입하지 않은 사용자를 곧바로 활성화할 수도 있다. 상태 변경이 여러 서비스와 컨트롤러에 흩어지면 `User`가 어떤 상태로 바뀔 수 있는지 한곳에서 확인하기 어려워진다.

![Java 캡슐화 전후 비교 다이어그램](/assets/images/2026-08-24-posting/encapsulation-before-after.png)

상태를 직접 노출하는 대신 변경 방법을 객체 안에 둘 수 있다.

`BT`java
public class User {

    private UserStatus status;

    public void activate() {
        this.status = UserStatus.ACTIVE;
    }
}
`BT`

이제 외부에서는 `status`에 어떤 값을 넣을지 결정하지 않고 객체의 행동을 호출한다.

`BT`java
user.activate();
`BT`

핵심은 단순히 `private`을 사용했다는 사실이 아니다.

> 상태 변경 방법을 객체 내부에 두고, 외부에는 의미 있는 행동만 공개했다는 점이 캡슐화의 핵심이다.

나중에 활성화 전에 이메일 인증 여부를 확인하거나 활성화 시각을 기록해야 하더라도 변경할 위치가 `activate()` 안으로 모인다. 외부 코드는 `User`의 내부 구현을 알 필요 없이 “이 사용자를 활성화한다”는 의도만 표현하면 된다.

## 3. Getter/Setter가 있다고 캡슐화된 것은 아니다

필드를 `private`으로 선언하고 setter를 제공하면 외부에서 필드에 바로 접근할 수는 없다. 하지만 다음과 같은 setter는 사실상 내부 상태를 그대로 공개하는 통로가 될 수 있다.

`BT`java
public void setStatus(UserStatus status) {
    this.status = status;
}
`BT`

호출하는 코드는 다음과 같다.

`BT`java
user.setStatus(UserStatus.ACTIVE);
`BT`

setter가 무조건 나쁜 것은 아니다. 단순한 설정 객체나 외부 입력을 담는 객체에서는 값을 주입하는 용도로 자연스럽게 사용할 수 있다. 문제는 도메인 객체의 중요한 상태 변경까지 모두 setter로 열어 두는 경우다.

`setStatus(UserStatus.ACTIVE)`와 `activate()`를 비교해 보면 차이가 더 분명해진다.

| 관점 | `setStatus(...)` | `activate()` |
| --- | --- | --- |
| 상태 변경 규칙 | 호출하는 쪽에 흩어질 가능성이 있다 | `User` 내부에서 관리할 수 있다 |
| 코드의 의도 | 어떤 값을 넣는지 드러난다 | 어떤 행동을 하는지 드러난다 |
| 변경 영향 범위 | 상태 변경 절차가 바뀌면 여러 호출부를 확인할 수 있다 | 객체 내부 메서드 중심으로 수정할 수 있다 |
| 잘못된 상태 변경 | 호출부에서 실수할 여지가 있다 | 객체가 허용 여부를 검사할 수 있다 |

예를 들어 활성화에 조건이 필요해지면 setter 방식에서는 호출하는 곳마다 조건을 알고 있어야 한다.

`BT`java
if (user.isEmailVerified()) {
    user.setStatus(UserStatus.ACTIVE);
}
`BT`

반면 행동을 공개하면 조건과 상태 변경을 객체 안에 둘 수 있다.

`BT`java
user.activate();
`BT`

물론 `activate()`라는 메서드가 있다고 자동으로 캡슐화가 완성되는 것은 아니다. 메서드 안에 규칙이 있고, 객체가 자신의 상태를 일관되게 관리해야 한다. 중요한 기준은 getter/setter의 개수가 아니라 상태 변경에 대한 책임이 어디에 모여 있는가이다.

## 4. 생성자와 캡슐화의 관계

이전에는 생성자(Constructor)를 객체를 만드는 특별한 메서드 정도로만 생각했다. 다시 정리해 보니 생성자는 객체가 생성되는 순간의 초기 상태를 관리하는 역할과 연결되어 있었다.

> 생성자는 객체가 어떤 상태로 태어날 것인지 관리한다.

그렇다면 캡슐화는 객체가 생성된 이후의 상태 변화와 연결된다.

> 캡슐화는 객체가 생성된 이후 어떻게 상태를 변경할 수 있는지 관리한다.

다음 `Account`를 예로 들어 보자.

`BT`java
public enum AccountStatus {
    PENDING,
    ACTIVE,
    SUSPENDED
}
`BT`

`BT`java
public class Account {

    private AccountStatus status;

    public Account() {
        this.status = AccountStatus.PENDING;
    }

    public void activate() {
        if (status != AccountStatus.PENDING) {
            throw new IllegalStateException("대기 중인 계정만 활성화할 수 있습니다.");
        }

        this.status = AccountStatus.ACTIVE;
    }
}
`BT`

`Account`는 생성될 때 항상 `PENDING` 상태로 시작한다. 그리고 생성된 이후에는 `activate()`를 통해서만 활성화할 수 있으며, 이미 활성화되었거나 정지된 계정은 다시 활성화할 수 없다.

이 코드에서는 생성 시점의 규칙과 이후 상태 전이 규칙이 모두 `Account` 안에 있다. 외부에서 `status`를 직접 변경할 수 없기 때문에 다음과 같은 잘못된 변경도 막을 수 있다.

`BT`java
// Account 외부에서는 status에 직접 접근할 수 없다.
account.status = AccountStatus.ACTIVE;
`BT`

![Constructor와 객체 행동에 따른 상태 관리 흐름](/assets/images/2026-08-24-posting/constructor-state-management.png)

생성자가 초기 상태를 정해 준다고 해서 그 이후의 객체가 자동으로 안전해지는 것은 아니다. 객체가 살아 있는 동안 어떤 상태 변경을 허용할지까지 관리해야 객체의 일관성을 유지할 수 있다.

## 5. Access Modifier는 접근 범위보다 설계 의도를 보여준다

Java의 접근 제어자(Access Modifier)는 클래스, 필드, 메서드 등에 접근할 수 있는 범위를 제한한다. 기본적인 범위는 다음과 같다.

| 접근 제어자 | 같은 클래스 | 같은 패키지 | 다른 패키지의 자식 클래스 | 다른 패키지의 일반 클래스 |
| --- | --- | --- | --- | --- |
| `public` | 가능 | 가능 | 가능 | 가능 |
| `protected` | 가능 | 가능 | 가능 | 불가능 |
| default (package-private) | 가능 | 가능 | 불가능 | 불가능 |
| `private` | 가능 | 불가능 | 불가능 | 불가능 |

`protected`는 다른 패키지의 자식 클래스에서도 접근할 수 있지만, 상속 관계가 있다고 해서 아무 객체 참조를 통해서나 접근할 수 있는 것은 아니다. 실제 코드에서는 이 특성 때문에 정말 상속을 통해 확장해야 하는 멤버인지 함께 판단해야 한다.

각 접근 제어자는 단순한 문법 이상의 의도를 나타낼 수 있다.

### `public`

어디서든 사용할 수 있도록 공개한다는 의미다. 클래스의 외부 사용자가 알아야 하는 기능이나, 객체가 제공할 공식 인터페이스를 `public`으로 만들 수 있다.

`BT`java
public void activate() {
    // 외부에 공개할 객체의 행동
}
`BT`

다만 `public`으로 열었다는 것은 다른 코드가 그 메서드에 의존할 수 있다는 뜻이기도 하다. 따라서 내부 구현을 공개하기보다 외부 사용자가 이해할 수 있는 행동을 공개하는 편이 변경에 유리할 때가 많다.

### `protected`

같은 패키지에서 사용하거나 자식 클래스가 확장할 수 있도록 열어 둔다. 상속을 전제로 한 확장 지점이 될 수 있지만, 단순히 “`private`보다 넓은 범위”라는 이유로 사용하는 것은 조심해야 한다.

### default(package-private)

접근 제어자를 생략하면 같은 패키지 안에서만 접근할 수 있다.

`BT`java
class PackageHelper {
    // 같은 패키지 내부에서만 사용
}
`BT`

패키지 내부의 협력 객체만 사용해야 하는 구현이나 공개 API로 만들 필요가 없는 클래스에 활용할 수 있다. 패키지를 하나의 협력 범위처럼 구성하고 싶을 때 의도를 드러내는 선택이 될 수 있다.

### `private`

선언된 클래스 내부에서만 접근할 수 있다. 필드나 구현 메서드를 숨길 때 많이 사용하지만, 의미는 단순히 “남이 못 보게 한다”에 그치지 않는다.

> `private`은 이 상태나 구현을 이 객체가 책임진다는 뜻으로 해석할 수 있다.

외부에서 직접 바꾸지 못하게 해야 객체가 자신의 상태를 검증하고 보호할 수 있다. 그래서 `private`은 캡슐화를 구현하기 위한 도구인 동시에 책임의 경계를 표시하는 방법이기도 하다.

## 6. `private constructor`는 왜 사용하는가

생성자에도 접근 제어자를 지정할 수 있다. 생성자를 `private`으로 만들면 클래스 외부에서 `new`를 직접 호출할 수 없다.

`BT`java
public class User {

    private final String name;

    private User(String name) {
        this.name = name;
    }

    public static User create(String name) {
        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException("이름은 비어 있을 수 없습니다.");
        }

        return new User(name);
    }
}
`BT`

이제 객체는 다음처럼 생성해야 한다.

`BT`java
User user = User.create("홍길동");
`BT`

`new User("홍길동")`은 클래스 외부에서 호출할 수 없다. 생성 경로를 `create()`로 제한했기 때문에 이름 검증이나 기본값 설정 같은 생성 규칙을 한곳에서 통제할 수 있다.

정적 팩터리 메서드(Static Factory Method)를 사용하는 이유는 여러 가지가 있지만, 여기서는 객체 생성 방법을 클래스 내부에 두고 외부의 생성 방식을 제한한다는 캡슐화 관점으로 이해했다. 생성자 자체를 숨기고 싶을 만큼 생성 과정에 규칙이 있거나, 생성 시점에 의미 있는 이름을 부여하고 싶을 때 선택할 수 있다.

다만 모든 클래스가 `private constructor`를 사용해야 하는 것은 아니다. 단순한 값 전달 객체처럼 공개 생성자가 더 자연스러운 경우도 있다. 중요한 것은 객체 생성 방식까지 클래스가 책임져야 하는지 판단하는 것이다.

## 7. Spring Service와 Domain Object

Spring 백엔드에서 캡슐화는 Service와 Domain Object의 책임을 나누는 과정에서도 드러날 수 있다.

사용자를 활성화하는 Service가 다음처럼 작성되어 있다고 해 보자.

`BT`java
user.setStatus(UserStatus.ACTIVE);
user.setActivatedAt(LocalDateTime.now());
`BT`

이 코드는 당장 동작할 수 있다. 하지만 Service가 사용자의 상태를 바꾸는 순서를 알아야 하고, 다른 곳에서 같은 활성화 로직을 실행하려면 같은 코드를 다시 작성할 가능성이 있다. 활성화 조건이 추가되면 여러 호출부를 찾아 수정해야 한다.

조금 더 객체에 책임을 두면 Service는 다음처럼 비즈니스 흐름을 표현할 수 있다.

`BT`java
user.activate();
`BT`

`User` 내부에서는 상태와 관련된 규칙을 함께 처리한다.

`BT`java
public class User {

    private UserStatus status;
    private LocalDateTime activatedAt;

    public void activate() {
        if (status != UserStatus.PENDING) {
            throw new IllegalStateException("활성화할 수 없는 상태입니다.");
        }

        this.status = UserStatus.ACTIVE;
        this.activatedAt = LocalDateTime.now();
    }
}
`BT`

이렇게 하면 Service는 다음과 같은 흐름에 집중할 수 있다.

`BT`java
@Service
public class UserService {

    public void activateUser(Long userId) {
        User user = userRepository.findById(userId)
            .orElseThrow(UserNotFoundException::new);

        user.activate();
        userRepository.save(user);
    }
}
`BT`

Service는 “사용자를 조회하고 활성화한다”는 비즈니스 흐름을 표현하고, `User`는 “어떤 조건에서 활성화할 수 있는가”와 “활성화할 때 어떤 필드를 바꿔야 하는가”를 책임진다.

그렇다고 모든 로직을 무조건 Entity나 Domain Object에 넣어야 한다는 뜻은 아니다. 외부 API 호출, 여러 객체를 조합하는 작업, 트랜잭션 흐름처럼 객체 하나의 상태 규칙을 넘어서는 책임은 Service나 다른 협력 객체에 남을 수 있다.

> 객체가 책임져야 할 상태와 그 상태의 변경 규칙은 객체에 배치하고, 애플리케이션의 전체 흐름은 Service가 조정한다.

이 기준으로 보면 캡슐화는 Service를 없애는 기술이 아니라, Service가 객체 내부의 필드 조작 방법까지 알지 않도록 책임을 나누는 설계에 가깝다.

이전에 [테스트 때문에 엔티티에 setter를 추가하면 안 되는 이유](/posts/entity-setter-test/)를 정리하면서도 비슷한 문제를 다룬 적이 있다. 테스트를 편하게 만들기 위해 상태 setter를 열면 도메인 규칙을 우회하는 통로가 생길 수 있다는 내용이었다. 이번에는 그 이유를 접근 제어자와 객체의 행동이라는 관점에서 다시 이해할 수 있었다.

## 8. DTO와 Domain Object

DTO(Data Transfer Object)와 Domain Object는 모두 데이터를 가지고 있지만, 중심 역할은 다를 수 있다.

요청 DTO는 계층 사이에서 데이터를 전달하는 목적이 강하다.

`BT`java
public record CreateUserRequest(
    String name,
    String email
) {}
`BT`

컨트롤러가 받은 입력을 Service로 전달하거나, 조회 결과를 응답 형태로 바꾸는 것이 DTO의 주된 역할이다. record처럼 값을 담고 전달하는 데 적합한 형태를 사용할 수 있다.

반면 Domain Object는 자신의 상태와 행동, 상태 변경 규칙을 함께 가질 수 있다.

`BT`java
public class User {

    private String name;
    private UserStatus status;

    public void activate() {
        if (status != UserStatus.PENDING) {
            throw new IllegalStateException("활성화할 수 없는 상태입니다.");
        }

        this.status = UserStatus.ACTIVE;
    }
}
`BT`

DTO에 반드시 모든 접근을 제한해야 한다거나, Domain Object는 무조건 모든 필드를 숨겨야 한다고 단정할 필요는 없다. 중요한 것은 그 객체가 어떤 역할과 책임을 맡고 있는가이다.

외부 입력을 전달하는 DTO는 전달 과정에서 필요한 형태로 데이터를 노출할 수 있다. 반면 상태의 일관성을 유지해야 하는 Domain Object는 외부가 내부 상태를 임의로 변경하지 못하도록 행동 중심의 인터페이스를 제공하는 편이 자연스러울 수 있다.

## 9. 학습하면서 바뀐 생각

처음에는 `private` 필드에 getter/setter를 붙이면 캡슐화가 된다고 생각하기 쉬웠다. 실제로 접근 제어는 제한되지만, 모든 상태를 setter로 변경할 수 있다면 객체가 자신의 상태를 관리한다고 말하기는 어려웠다.

이번에 학습하면서 캡슐화를 이렇게 이해하게 되었다.

> 캡슐화는 접근을 막는 것보다 객체가 자신의 상태 변경에 대한 책임을 가지도록 만드는 설계에 가깝다.

외부에서 객체의 필드를 직접 조작하기 시작하면 상태 변경 규칙이 여러 곳에 흩어질 수 있다. 반대로 객체가 `activate()`, `changeName()`, `cancel()`처럼 자신의 행동을 제공하면 변경 규칙을 한곳에 모을 수 있다. 외부 코드는 객체가 내부에서 어떤 필드를 어떤 순서로 바꾸는지보다 객체가 무엇을 하는지만 알면 된다.

물론 메서드 이름을 행동처럼 바꾼다고 항상 좋은 설계가 되는 것은 아니다. `activate()` 내부에 필요한 규칙이 없거나, 여전히 외부에서 여러 setter를 조합해야 한다면 책임이 실제로 이동한 것은 아니다. 객체가 자신의 상태를 검사하고, 필요한 값을 함께 변경하며, 허용되지 않는 전이를 막는지가 더 중요하다.

## 10. 마무리

오늘 학습한 내용을 정리하면 다음과 같다.

* 캡슐화는 단순히 `private`을 사용하는 것이 아니다.
* 객체의 상태와 상태 변경 규칙을 객체가 관리하도록 만드는 것이 핵심이다.
* 접근 제어자는 객체의 책임 범위와 외부에 공개할 인터페이스를 설계하기 위한 도구다.
* 생성자가 초기 상태를 관리한다면, 캡슐화는 객체가 생성된 이후의 상태 변경까지 이어진다.
* `setter`보다 의미 있는 행동을 공개하면 객체의 역할과 코드의 의도가 더 잘 드러날 수 있다.
* DTO와 Domain Object는 데이터를 가진다는 공통점보다 역할과 책임의 차이를 기준으로 바라봐야 한다.

캡슐화를 공부하면서 `private`이라는 키워드를 단순한 접근 제한 문법으로만 볼 수 없게 되었다. 이제 코드를 볼 때는 “이 필드가 private인가?”에서 멈추지 않고, “이 상태를 변경할 책임은 어디에 있는가?”, “외부에는 어떤 행동을 공개해야 하는가?”를 함께 확인하려고 한다.

다음에는 객체가 책임을 나누고 서로 협력하는 방식까지 이어서 Java 객체지향 개념을 더 공부해 보려고 한다.
