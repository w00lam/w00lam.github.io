앞서 트랜잭션을 공부하면서 여러 작업을 함께 커밋하거나 롤백하는 이유를 정리했다. 여러 변경을 하나의 업무 단위로 묶으면 전부 성공하거나 전부 취소할 수 있지만 그 사실만으로 동시에 실행되는 작업 사이의 읽기 문제까지 사라지는 것은 아니었다. 이전에 [데이터베이스 이상과 인덱스 — 설계 문제와 조회 비용은 어떻게 구분할까?](https://w00lam.github.io/posts/database-anomalies-indexes/)에서 테이블 설계에서 생기는 이상 현상과 동시 실행에서 생기는 문제를 구분했던 것도 같은 맥락이었다.

오늘은 Database의 “9. Transaction Isolation Level”을 공부했다. 다음 질문에서 시작했다.

> 하나의 트랜잭션 안에서 같은 데이터를 다시 읽으면 같은 값이 보일까?

원자성은 작업을 전부 반영하거나 전부 취소하는 성질이다. 다른 트랜잭션이 변경한 데이터를 언제 볼 수 있는지는 격리 수준과 관련된다. 트랜잭션으로 묶었다는 사실만으로 동시 실행에서 발생하는 문제가 모두 해결되는 것은 아니다. 오늘은 읽기 이상 현상의 이름을 외우기보다 T1과 T2의 실행 순서와 커밋 시점과 스냅샷 기준을 따라가며 확인했다.

## READ COMMITTED에서도 같은 행의 값이 달라질 수 있었다

음식점 이름을 변경하는 예제를 생각해 보자. 초기 상태는 다음과 같다.

| 항목 | 값 |
| --- | --- |
| `restaurant.id` | `17` |
| `restaurant.name` | `'달빛국수'` |
| T1의 격리 수준 | `READ COMMITTED` |
| 조회 방식 | 잠금 구문이 없는 일반 `SELECT` |

T1의 첫 조회는 다음과 같다.

```sql
SELECT name
FROM restaurant
WHERE id = 17;
```

이 조회의 결과는 `'달빛국수'`다. 그 뒤 T2가 이름을 변경하고 커밋한다.

```sql
UPDATE restaurant
SET name = '달빛면옥'
WHERE id = 17;
```

실행 순서를 나누면 다음과 같다.

1. T1이 `id = 17`인 음식점의 이름을 조회한다.
2. T2가 이름을 `'달빛면옥'`으로 변경한다.
3. T2가 `COMMIT`한다.
4. T1이 같은 `SELECT`를 다시 실행한다.

T1의 두 번째 조회 결과는 `'달빛면옥'`이다. PostgreSQL의 `READ COMMITTED`는 각 문장이 시작할 때의 스냅샷을 사용하므로 같은 트랜잭션 안의 두 `SELECT`라도 서로 다른 시점을 볼 수 있다. T1의 첫 조회 뒤에 T2가 변경을 커밋했고 T1의 재조회가 그 이후에 시작했기 때문이다.

처음에는 “T1이 같은 트랜잭션 안에 있으니 같은 행은 같은 값으로 읽을 것”이라고 생각했다. 하지만 T1의 첫 조회와 T2의 변경 및 커밋과 T1의 재조회를 순서대로 적으니 결과가 달라지는 이유를 구분할 수 있었다. 이미 읽었던 행을 다시 읽었는데 다른 트랜잭션이 커밋한 변경 때문에 값이 달라진 현상이 `Non-repeatable Read`다.

## 커밋 전 변경과 커밋 후 변경을 구분해야 했다

앞의 예제와 별개로 초기 상태를 다시 `'달빛국수'`로 둔다. 이번에는 T2가 이름을 변경했지만 아직 커밋하지 않은 상황을 생각해 보자.

```sql
-- T2
BEGIN;

UPDATE restaurant
SET name = '달빛면옥'
WHERE id = 17;

-- 아직 COMMIT하지 않음
```

이때 T1이 같은 행을 조회한다.

```sql
-- T1
SELECT name
FROM restaurant
WHERE id = 17;
```

처음에는 T2가 이미 `UPDATE`를 실행했으니 커밋되지 않은 `'달빛면옥'`도 읽을 수 있다고 생각했다. PostgreSQL의 `READ COMMITTED`에서는 그렇게 읽지 않는다. T1은 T2의 미커밋 변경을 볼 수 없고 기존에 커밋된 `'달빛국수'`를 읽는다.

이때 일반 `SELECT`가 T2의 `COMMIT`까지 반드시 기다린다고 설명하면 정확하지 않다. PostgreSQL은 MVCC를 바탕으로 조회 시점에 보이는 행 버전을 판단한다. 커밋되지 않은 변경을 읽지 않는다는 결과와 다른 트랜잭션의 커밋을 기다린다는 동작을 같은 문장으로 묶으면 안 된다.

두 현상은 다음처럼 나누어야 했다.

- `Dirty Read`: 다른 트랜잭션의 미커밋 변경을 읽는 현상이다.
- `Non-repeatable Read`: 다른 트랜잭션이 커밋한 변경 때문에 같은 행을 다시 읽었을 때 값이 달라지는 현상이다.

둘 다 “다른 트랜잭션 때문에 읽기 결과가 달라진다”는 인상만 보면 헷갈린다. 다른 트랜잭션의 변경이 커밋됐는지와 T1이 그 행을 처음 읽었는지 다시 읽었는지를 함께 확인해야 한다.

## 값이 바뀌는 것과 조건에 맞는 행이 늘어나는 것도 달랐다

이번에는 한 행의 이름이 아니라 조건에 맞는 음식점 목록을 조회한다. 초기 상태에서 `마포`에 있는 음식점은 `id = 17`인 `'달빛국수'` 하나라고 하자.

```sql
SELECT id, name
FROM restaurant
WHERE region = '마포';
```

T1의 첫 조회 결과는 `[17]`이다. 그 뒤 T2가 같은 조건에 맞는 음식점을 추가하고 커밋한다.

```sql
INSERT INTO restaurant (id, name, region)
VALUES (23, '연남만두', '마포');
```

T1이 같은 조건으로 다시 조회하면 결과는 `[17, 23]`이 된다. 이미 읽었던 `id = 17`의 이름이 바뀐 것이 아니다. 처음에는 조건에 맞지 않았던 `id = 23` 행이 T2의 커밋 뒤에 결과 집합에 들어왔다.

`Non-repeatable Read`에서는 이미 읽었던 행의 값이 달라졌다. `Phantom Read`에서는 같은 조건으로 조회한 결과의 행 집합이 달라졌다. 따라서 조회 결과를 비교할 때는 값과 커밋 시점뿐 아니라 새 행이 `WHERE` 조건에 맞는지도 확인해야 했다. PostgreSQL 문서도 `Phantom Read`를 검색 조건을 만족하는 행의 집합이 다른 트랜잭션의 커밋으로 달라지는 현상으로 설명한다.

## REPEATABLE READ는 스냅샷을 유지하지만 기준 시점을 정확히 봐야 했다

`READ COMMITTED`와 `REPEATABLE READ`의 차이는 재조회가 어떤 스냅샷을 사용하는지에 있다. `READ COMMITTED`는 각 문장 시작 시점의 스냅샷을 사용한다. `REPEATABLE READ`는 트랜잭션의 첫 조회나 데이터 변경 문장에서 정해진 스냅샷을 이후의 일반 조회에서도 사용한다. PostgreSQL의 [SET TRANSACTION 문서](https://www.postgresql.org/docs/18/sql-set-transaction.html)도 `REPEATABLE READ`에서 첫 query 또는 data-modification statement 전에 커밋된 행만 이후 문장들이 볼 수 있다고 설명한다.

여기서 `BEGIN`을 실행하는 순간 스냅샷이 무조건 확정된다고 단순화하면 안 된다. T1이 `BEGIN`만 실행한 뒤 T2가 변경을 커밋하고 T1이 첫 일반 `SELECT`를 실행했다면 T1의 첫 문장은 T2의 커밋 이후에 시작한다. 이때 T1은 T2의 커밋을 볼 수 있다.

반대로 T1의 첫 조회가 먼저 실행되어 스냅샷이 정해졌다면 그 뒤 T2가 커밋한 변경은 T1의 일반 `SELECT`에 새로 반영되지 않는다. 흐름을 나누면 다음과 같다.

```text
T1: BEGIN
T2: UPDATE ...
T2: COMMIT
T1: 첫 SELECT        → T2의 커밋을 볼 수 있음
```

```text
T1: BEGIN
T1: 첫 SELECT        → 이 시점의 스냅샷이 정해짐
T2: UPDATE ...
T2: COMMIT
T1: 두 번째 SELECT   → 첫 스냅샷을 계속 사용
```

처음에는 `REPEATABLE READ`라는 이름만 보고 트랜잭션이 시작되는 순간부터 모든 값이 고정된다고 생각했다. 실제로는 스냅샷을 정한 시점을 찾아야 했다. 격리 수준의 이름을 외우는 것보다 첫 조회나 첫 데이터 변경이 언제 시작됐는지를 확인하는 편이 결과를 판단하는 데 더 중요했다.

![READ COMMITTED와 REPEATABLE READ의 스냅샷 기준을 비교한 실행 순서 도식](/assets/images/2026-10-22-transaction-isolation/snapshot-timing.svg)

*그림 1. `BEGIN`과 첫 조회 시점을 구분하고 T1의 재조회가 어떤 스냅샷을 참조하는지 비교했다.*

## SQL 표준의 표를 PostgreSQL에 그대로 적용하면 안 됐다

학습의 출발점에서는 SQL 표준이 네 가지 격리 수준을 어떤 읽기 이상 현상과 연결하는지 확인했다. 표에서 “허용”은 해당 현상이 반드시 발생한다는 뜻이 아니다. 그 격리 수준이 해당 현상의 발생을 방지한다고 보장하지 않는다는 의미다.

| 격리 수준 | Dirty Read | Non-repeatable Read | Phantom Read |
| --- | --- | --- | --- |
| READ UNCOMMITTED | 허용 | 허용 | 허용 |
| READ COMMITTED | 방지 | 허용 | 허용 |
| REPEATABLE READ | 방지 | 방지 | 허용 |
| SERIALIZABLE | 방지 | 방지 | 방지 |

이 표는 [gyoogle의 트랜잭션 격리 수준 정리](https://github.com/gyoogle/tech-interview-for-developer/blob/master/Computer%20Science/Database/Transaction%20Isolation%20Level.md)에서 처음 접한 기준이다. 다만 gyoogle 원문의 Lock 중심 설명을 PostgreSQL의 일반 `SELECT` 동작에 그대로 옮기면 안 된다. 같은 격리 수준 이름이라도 DBMS가 구현하는 방식과 추가로 보장하는 범위가 다를 수 있기 때문이다.

PostgreSQL 18에서는 두 가지 차이를 확인해야 한다. `READ UNCOMMITTED`를 요청해도 내부적으로는 `READ COMMITTED`처럼 동작한다. PostgreSQL이 MVCC 구조에 맞춰 네 표준 수준을 세 가지 구현 수준으로 처리하기 때문이다. 또 PostgreSQL의 `REPEATABLE READ`는 SQL 표준 표에서 허용하는 `Phantom Read`도 방지한다. 더 높은 보장을 제공하는 것은 표준에 어긋나지 않는다.

따라서 SQL 표준이 특정 격리 수준에서 방지하지 않는다고 적은 현상과 PostgreSQL 18에서 실제로 허용되는 현상을 구분해야 한다. 격리 수준 표를 볼 때는 표준의 최소 보장인지 특정 DBMS의 실제 동작인지부터 확인해야 했다. 이 차이는 [PostgreSQL 18의 Transaction Isolation 문서](https://www.postgresql.org/docs/18/transaction-iso.html)에 정리되어 있다.

## 조회 결과가 안정적이어도 모든 업무 규칙이 보장되지는 않았다

읽기 결과가 반복해서 같다는 보장이 업무 규칙까지 지켜 준다고 생각하기 쉬웠다. “활성 운영자는 최소 한 명 남아야 한다”는 규칙을 예로 들어 보자. 처음에는 운영자 A와 운영자 B가 모두 활성 상태다.

T1과 T2가 각각 `REPEATABLE READ`로 실행되고 두 트랜잭션이 같은 초기 상태를 읽는다고 하자. T1은 활성 운영자가 두 명임을 확인한 뒤 운영자 A를 비활성화한다. T2도 활성 운영자가 두 명이라고 확인한 뒤 운영자 B를 비활성화한다. 서로 다른 행을 변경하면 두 트랜잭션이 모두 커밋하는 결과를 생각할 수 있다. 그 결과 활성 운영자가 한 명도 남지 않는다.

각 트랜잭션은 자신의 스냅샷 안에서 같은 값을 안정적으로 읽었다. 하지만 두 트랜잭션이 함께 만든 결과가 업무 규칙을 만족하는지는 별도의 문제였다. “같은 트랜잭션에서 다시 읽어도 같은 값이 보인다”와 “동시에 실행한 결과가 어떤 직렬 실행 순서의 결과와 같다”는 서로 다른 보장이다.

`SERIALIZABLE`은 성공적으로 커밋한 트랜잭션들의 결과가 어떤 순서로 하나씩 실행한 결과와 같도록 보장한다. 모든 트랜잭션을 실제로 한 줄에 세워 실행한다는 뜻은 아니다. 예제처럼 어떤 직렬 실행 순서로도 설명할 수 없는 결과가 만들어지지 않도록 동시 실행을 조정하고 필요하면 트랜잭션을 실패시킨다. 어느 트랜잭션이 반드시 실패한다고 미리 단정할 수는 없지만 두 작업이 모두 커밋해 업무 규칙을 깨는 결과를 허용하지 않는다는 점이 중요하다.

![활성 운영자 확인과 SERIALIZABLE의 결과 보장을 비교한 실행 순서 도식](/assets/images/2026-10-22-transaction-isolation/serializable-operator-rule.svg)

*그림 2. 두 트랜잭션이 같은 초기 상태를 읽고 서로 다른 운영자를 비활성화할 때 `REPEATABLE READ`와 `SERIALIZABLE`의 결과 보장을 비교했다.*

## 직렬화 실패에서는 마지막 SQL만 다시 실행하면 부족했다

`SERIALIZABLE`은 모든 요청을 성공시켜 주는 설정이 아니다. 동시 실행의 결과가 어떤 직렬 실행 순서와도 같지 않다고 판단되면 직렬화 실패가 발생할 수 있다. PostgreSQL에서 이 오류의 SQLSTATE는 `40001`이다. `REPEATABLE READ`에서도 직렬화 이상을 막기 위한 오류가 발생할 수 있다는 점을 함께 확인했다.

처음에는 실패한 `UPDATE`만 다시 실행하면 된다고 생각했다. 그러나 `UPDATE`에 사용한 값은 앞에서 읽고 판단한 결과다. 그 판단이 더 이상 유효하지 않다면 마지막 SQL만 반복해도 같은 충돌을 다시 만들 수 있다.

재시도 범위는 처음의 조회와 업무 판단을 포함한 전체 트랜잭션이어야 한다.

```text
새 트랜잭션 시작
→ 필요한 데이터 다시 조회
→ 업무 규칙 다시 판단
→ 변경 수행
→ COMMIT
```

PostgreSQL 공식 문서의 [Serialization Failure Handling](https://www.postgresql.org/docs/18/mvcc-serialization-failure-handling.html)도 SQL을 발행할지와 어떤 값을 사용할지를 결정하는 로직까지 포함해 전체 트랜잭션을 재시도해야 한다고 설명한다. 데이터베이스가 업무 로직까지 자동으로 재시도해 주는 것은 아니며 `SERIALIZABLE`이라고 해서 항상 첫 시도에 성공하는 것도 아니다. 학습 중에는 “처음부터 다시 시작한다”고 정리했던 이유가 이제 분명해졌다.

## Spring의 DEFAULT는 특정 격리 수준의 이름이 아니었다

Spring의 `@Transactional`에서 `isolation` 속성의 기본값은 `Isolation.DEFAULT`다.

```java
@Transactional(isolation = Isolation.DEFAULT)
public void changeRestaurant() {
    // 업무 로직
}
```

`Isolation.DEFAULT`는 `READ COMMITTED`라는 특정 격리 수준의 이름이 아니다. 연결된 데이터 저장소의 기본 격리 수준을 따르는 설정이다. Spring의 [Isolation 문서](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/annotation/Isolation.html)도 `DEFAULT`를 underlying data store의 기본 격리 수준을 사용하는 값으로 설명한다. `@Transactional`의 [isolation 속성 기본값](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/transaction/annotation/Transactional.html)도 `Isolation.DEFAULT`다.

PostgreSQL의 기본 격리 수준은 `READ COMMITTED`다. 다만 데이터베이스 설정은 변경할 수 있으므로 Spring의 기본 설정과 연결된 데이터베이스의 실제 기본값을 같은 것으로 단정하면 안 된다. “연결된 데이터베이스의 기본 격리 수준을 따르는 설정”이라는 표현을 그대로 기억하는 편이 안전했다.

## 오늘의 정리

오늘은 트랜잭션으로 묶는 것과 다른 트랜잭션의 변경을 언제 읽는지가 서로 다른 문제라는 점에서 시작했다. `READ COMMITTED`에서는 문장마다 스냅샷이 달라질 수 있어 같은 행을 다시 읽은 값이 달라질 수 있었다. 반면 미커밋 변경을 읽는 `Dirty Read`와 커밋된 변경 때문에 재조회 값이 달라지는 `Non-repeatable Read`는 커밋 시점을 기준으로 구분해야 했다. 조건에 맞는 행 집합이 달라지는 `Phantom Read`에서는 `WHERE` 조건과 새 행의 커밋도 함께 확인했다.

현상 이름을 먼저 떠올리기보다 T1의 첫 조회와 T2의 변경과 커밋과 T1의 재조회를 순서대로 적으니 구분이 쉬워졌다. `REPEATABLE READ`를 볼 때도 `BEGIN`만으로 스냅샷이 확정된다고 단정하지 않고 첫 조회나 데이터 변경 문장의 시점을 찾게 됐다.

SQL 표준의 보장과 PostgreSQL 18의 구현도 나누어 보아야 했다. `READ UNCOMMITTED`가 PostgreSQL에서 `READ COMMITTED`처럼 동작하고 `REPEATABLE READ`가 표준 표보다 강하게 `Phantom Read`를 방지한다는 차이를 확인했다. 안정적인 조회 결과와 직렬 실행에 해당하는 결과 보장도 같은 의미가 아니었다.

격리 수준을 선택할 때는 필요한 보장만 보는 것으로 끝나지 않는다. 충돌로 직렬화 실패가 발생했을 때 조회와 판단을 포함한 전체 트랜잭션을 다시 실행할 책임까지 함께 봐야 한다. 오늘의 예제들을 완전히 숙달했다고 말하기는 어렵지만 무엇을 읽었고 언제 커밋됐으며 어떤 결과를 보장받으려는지부터 확인하는 기준은 정리할 수 있었다.
