어제 [트리의 구조와 표현 방식 — 자식 관계와 순회 순서는 어떻게 달라질까?](/posts/tree-structure-representation-traversal/)를 공부하면서 일반 이진 트리의 구조와 네 가지 순회를 정리했다. 그때 중위 순회 결과가 `D B E A C F`로 나왔던 이유도 값의 크기와는 관계가 없었다. 일반 이진 트리는 자식 수만 제한할 뿐 값의 정렬 규칙을 갖지 않기 때문이다.

오늘은 그 차이에서 출발해 이진 탐색 트리(BST)를 학습했다. 값의 대소 관계가 정해지면 탐색할 방향을 선택할 수 있지만 트리의 모양이 자동으로 균형을 이루는 것은 아니었다. 이어서 Hash가 키를 저장 위치로 바꾸는 방식과 충돌을 처리하는 방법을 살펴보고 Java의 `HashMap`과 `HashSet`이 같은 키를 어떻게 판단하는지도 모의면접으로 확인했다.

오늘은 다음 질문을 따라가며 개념을 다시 나누었다.

- 일반 이진 트리와 BST는 어떤 규칙에서 갈라지는가?
- BST의 정렬 규칙은 바로 연결된 자식에게만 적용되는가?
- 삽입 순서가 달라지면 탐색 비용도 달라지는 이유는 무엇인가?
- 자식이 둘인 노드를 삭제할 때 어떤 키를 대체하고 남은 연결을 어떻게 조정하는가?
- Hash값과 버킷 인덱스는 무엇이 다르며 충돌은 왜 생기는가?
- 체이닝과 개방 주소법은 충돌을 어떻게 해결하는가?
- 부하율과 리사이징은 저장 위치와 연산 비용에 어떤 영향을 주는가?
- 키가 유일해도 `HashMap` 조회가 항상 `O(1)`은 아닌 이유는 무엇인가?
- ID 조회와 정렬 및 범위 조회에는 각각 어떤 자료구조가 맞는가?

오늘 BST나 해시 테이블을 서비스에 구현하거나 성능을 측정한 것은 아니다. 개념을 학습하고 숫자를 따라가며 구조를 그려 본 뒤 모의면접에서 처음 답한 내용을 교정한 기록이다.

## BST는 값의 대소 관계로 탐색 방향을 정한다

일반 이진 트리는 각 노드가 왼쪽과 오른쪽 자식을 최대 하나씩 가진다는 구조 규칙만 있다. 왼쪽에 더 작은 값이 와야 한다거나 오른쪽에 더 큰 값이 와야 한다는 조건은 없다. 그래서 특정 값을 찾으려면 어느 가지를 먼저 확인해야 하는지 구조만 보고 판단할 수 없다.

BST는 이진 트리의 자식 수 제한에 키의 정렬 규칙을 더한 구조다. 중복 키를 저장하지 않는 정책을 기준으로 현재 노드의 키를 `x`라고 하면 다음 관계가 성립한다.

- 왼쪽 서브트리 전체의 키는 `x`보다 작다.
- 오른쪽 서브트리 전체의 키는 `x`보다 크다.

여기서 중요한 단어는 직계 자식이 아니라 서브트리 전체다. 현재 노드의 왼쪽 자식 하나만 작으면 되는 것이 아니다. 왼쪽 자식 아래에 있는 모든 후손도 현재 노드보다 작아야 한다. 오른쪽도 같은 방식으로 현재 노드보다 큰 값만 들어간다.

예를 들어 다음 BST에서 루트가 `50`이라면 `30`은 물론 `30` 아래에 있는 값도 모두 `50`보다 작아야 한다. `80`의 왼쪽에 `60`이 있어도 `60`은 `80`보다 작고 루트 `50`보다 크므로 두 규칙을 모두 만족한다.

```text
       50
      /  \
    30    80
         /
        60
```

탐색은 현재 노드와 찾는 값을 비교하면서 진행한다. 찾는 값이 작으면 왼쪽으로 이동하고 크면 오른쪽으로 이동한다. 같으면 탐색을 끝낸다. 일반 이진 트리에서는 이 비교 결과만으로 가지 하나를 버릴 수 없지만 BST에서는 정렬 규칙 덕분에 반대쪽 서브트리를 보지 않아도 된다.

## 삽입 순서에 따라 BST의 높이와 비용이 달라진다

BST는 삽입할 때도 탐색과 같은 비교를 한다. 빈 자리를 찾으면 그 위치에 새 노드를 연결한다. 같은 값이 들어왔을 때의 처리는 자료구조가 정해야 한다. 이 글의 기본 숫자 예제는 중복을 저장하지 않는 정책으로 설명한다.

같은 세 값을 넣어도 순서가 다르면 모양이 달라진다. `30 → 20 → 10` 순서로 넣으면 매번 왼쪽으로 내려가 한쪽으로만 이어진다. 반대로 `20 → 10 → 30` 순서로 넣으면 `20`의 양쪽에 자식이 생긴다.

<img src="/assets/images/2026-10-09-bst-hash/bst-insertion-order.svg" alt="30, 20, 10과 20, 10, 30을 삽입한 BST를 비교한 그림. 10을 찾는 경로와 비교 및 이동 횟수를 함께 표시했다." loading="eager">

*그림 1. 같은 값도 삽입 순서에 따라 BST의 높이와 탐색 경로가 달라진다.*

탐색과 삽입 및 삭제의 비용은 노드 수만으로 바로 결정되지 않는다. 현재 노드에서 다음 노드로 내려가는 횟수가 트리의 높이 `h`에 의해 정해지므로 비용을 `O(h)`로 설명한다. 높이가 로그 수준으로 유지되면 `O(log n)`에 가깝지만 한쪽으로 편향되면 높이가 `n - 1`까지 늘어 최악의 비용은 `O(n)`이다.

비교 횟수와 간선 이동 횟수도 나누어 세어야 한다. 예를 들어 `50 → 40 → 30 → 20 → 10`처럼 다섯 노드를 따라가며 `10`을 찾는다면 각 노드에서 값을 비교하므로 비교는 5번이다. 루트에서 시작해 다음 노드로 이동한 간선은 4개이므로 이동은 4번이다. 반대로 찾는 값이 루트와 같으면 비교는 1번 필요하지만 간선 이동은 없다. 비교와 이동을 한 숫자로 묶어 말하면 이런 차이를 놓치기 쉽다.

전체 노드를 방문하는 중위 순회나 전위 순회 같은 작업은 탐색 경로 하나를 고르는 작업과 다르다. 순회는 노드 `n`개를 모두 방문하므로 별도로 `O(n)`이라고 설명한다. BST라는 이유만으로 모든 연산을 `O(log n)`이라고 말할 수 없는 이유도 여기에 있다.

## 중위 순회가 정렬 결과가 되는 이유

어제 일반 이진 트리의 중위 순회가 자동으로 오름차순이 되지 않는다는 점을 확인했다. 오늘 BST에서는 같은 중위 순회가 오름차순 결과를 만든다. 단순히 왼쪽 노드를 먼저 방문하기 때문은 아니다. 왼쪽 서브트리 전체가 현재 키보다 작고 오른쪽 서브트리 전체가 현재 키보다 큰 BST의 규칙이 핵심이다.

```text
       50
      /  \
    30    80
   /  \  /
  20  40 60
```

이 트리의 중위 순회는 `20 → 30 → 40 → 50 → 60 → 80`이다. `30`만 놓고 봐도 왼쪽 서브트리의 `20`을 먼저 처리하고 `30`을 처리한 뒤 오른쪽 서브트리의 `40`을 처리한다. `50`에 도착하기 전까지 왼쪽 서브트리 전체가 정렬 규칙 안에서 처리되므로 현재 키보다 작은 값이 먼저 나온다. 오른쪽도 같은 이유로 큰 값이 뒤에 나온다.

최솟값과 최댓값도 같은 규칙으로 찾는다. 최솟값은 왼쪽 자식이 없을 때까지 왼쪽으로 내려간 노드다. 최댓값은 오른쪽 자식이 없을 때까지 오른쪽으로 내려간 노드다. 일반 이진 트리에서는 가장 왼쪽에 있다는 사실만으로 값이 가장 작다고 말할 수 없다.

## 자식이 둘인 노드를 삭제하려면 연결까지 조정한다

BST의 삭제는 삭제 대상이 가진 자식 수에 따라 나누어 생각한다.

1. 자식이 없는 노드라면 부모가 해당 노드를 가리키던 참조를 끊는다.
2. 자식이 하나인 노드라면 부모가 삭제 노드의 자식을 직접 가리키도록 연결한다.
3. 자식이 둘인 노드라면 왼쪽 서브트리의 최댓값이나 오른쪽 서브트리의 최솟값을 대체 키로 선택한다.

자식이 둘인 노드의 자리에 임의의 후손을 가져오면 안 된다. 대체 키가 들어온 뒤에도 왼쪽에는 더 작은 값만, 오른쪽에는 더 큰 값만 남아야 하기 때문이다. 오른쪽 서브트리의 최솟값은 삭제할 노드보다 크면서 그 서브트리 안에서는 가장 작은 값이라 이 자리를 대신할 수 있다.

다음 예제에서 루트 `50`을 삭제한다고 하자. 오른쪽 서브트리의 최솟값은 `60`이다. `60`은 왼쪽 자식이 없으므로 그 자리를 더 내려가서 찾을 수 있다. 그렇다고 `60`에게 자식이 전혀 없다는 뜻은 아니다. 이 예제의 `60`에는 오른쪽 자식 `70`이 있다.

<img src="/assets/images/2026-10-09-bst-hash/bst-delete-two-children.svg" alt="BST의 루트 50을 삭제하면서 오른쪽 서브트리의 최솟값 60을 대체 키로 선택하고 70의 연결을 조정하는 과정" loading="eager">

*그림 2. 오른쪽 서브트리의 최솟값은 왼쪽 자식이 없지만 오른쪽 자식을 가질 수 있다.*

`60`을 새 루트로 올린 뒤 원래 `60`이 있던 위치에는 `70`을 `80`의 왼쪽 자식으로 연결해야 한다. 대체 키만 복사하고 원래 위치의 연결을 정리하지 않으면 같은 노드가 중복되거나 `70`을 잃을 수 있다. 왼쪽 서브트리의 최댓값을 사용하는 경우에도 오른쪽 자식이 없는 지점까지 내려간 뒤 남아 있는 왼쪽 자식을 기존 부모에 연결하는 같은 원리를 적용한다.

## 중복 키는 자료구조의 정책으로 정한다

BST에서 같은 키를 어떻게 다룰지는 모든 구현에 공통인 기본 동작이 아니다. 중복을 거절할 수도 있고 같은 키를 항상 왼쪽이나 오른쪽에 보내는 규칙을 정할 수도 있다. 같은 키의 개수를 노드에 `count`로 저장하는 방법도 있다.

횟수를 저장하는 사용자 정의 BST라면 같은 키를 넣을 때 새 노드를 만들지 않고 `count`를 증가시킨다. 삭제 요청이 들어와도 `count`가 1보다 크면 count만 줄인다. 마지막 하나를 제거할 때 비로소 자식 수에 따른 노드 삭제 규칙을 적용한다. 이 방식은 중복 정책을 직접 선택한 사용자 정의 자료구조의 예이지 모든 BST의 기본 동작은 아니다.

Java 컬렉션에서는 비슷해 보이는 중복 처리가 자료구조마다 다르다. `Map`은 같은 키로 다시 `put`하면 기존 값이 교체된다. `Set`은 같은 요소를 다시 추가해도 요소 수가 늘지 않는다.

```java
Map<Integer, String> map = new HashMap<>();
map.put(24, "A");
map.put(9, "B");
map.put(24, "C");

System.out.println(map.size());  // 2
System.out.println(map.get(24)); // C
```

`put`을 세 번 호출했지만 키는 `24`와 `9` 두 개만 남는다. 같은 키에 값이 여러 개 자동으로 쌓이는 것이 아니라 `24`에 연결된 값이 `A`에서 `C`로 바뀐다. 여러 값을 보관하려면 값의 타입을 `List<String>`처럼 설계하거나 별도의 중복 정책을 정해야 한다.

## Hash값과 버킷 인덱스는 구분한다

Hash는 키를 저장 공간의 위치를 고르는 데 사용하는 계산 방식이다. 흐름은 대략 다음과 같다.

```text
키 → 해시값 계산 → 버킷 인덱스로 변환 → 해당 위치에서 키 비교
```

해시값은 키에서 계산한 결과이고 버킷 인덱스는 실제 저장 공간의 범위 안으로 줄인 위치다. 서로 다른 키가 같은 인덱스를 만들 수 있으므로 버킷 인덱스가 같다는 이유만으로 두 키가 같은 것은 아니다.

학습용으로 음수가 아닌 정수 키를 저장하고 `bucketCount`가 5인 테이블을 생각해 보자. `index = key % bucketCount`라는 단순한 식을 사용하면 키 `1`, `6`, `11`은 모두 인덱스 `1`을 얻는다. 이것은 해시 충돌이다. 이 식은 흐름을 설명하기 위한 학습용 모듈러 해시 예제이며 Java `HashMap`의 실제 인덱스 계산식을 그대로 나타낸 것은 아니다.

## 충돌은 체이닝이나 탐사 규칙으로 해결한다

체이닝은 같은 버킷에 여러 엔트리를 연결해 저장하는 방식이다. 인덱스 `1`에 `1`, `6`, `11`이 모였다면 버킷 `1`을 찾은 뒤 그 내부의 엔트리를 차례로 확인해 원하는 키를 구분한다. 이때 버킷의 수보다 저장된 엔트리 수가 많을 수 있다.

개방 주소법은 충돌이 발생했을 때 테이블 안의 다른 슬롯을 탐사하는 방식이다. 선형 탐사라면 다음 인덱스를 차례대로 확인한다. 삭제가 있는 경우에는 슬롯을 두 종류의 빈 상태로 나누어야 한다.

- 한 번도 사용하지 않은 빈 슬롯을 만나면 정해진 탐사 규칙에서 해당 키가 없다고 판단할 수 있다.
- 삭제 표시가 된 슬롯을 만나면 뒤쪽에 같은 키가 남아 있을 수 있으므로 탐사를 계속해야 한다.

삭제된 슬롯을 진짜 빈 슬롯으로 바로 바꾸면 탐사가 중간에 끊긴다. 예를 들어 키 `1`이 슬롯 `1`에 충돌로 들어가고 키 `6`이 다음 슬롯에 들어갔다고 하자. 이후 `1`을 삭제하면서 슬롯 `1`을 완전히 비워 버리면 `6`을 찾을 때 처음 빈 슬롯을 보고 탐색을 끝낼 수 있다. 그래서 개방 주소법은 삭제 표시(tombstone)와 사용한 적 없는 빈 슬롯을 구분한다.

Java `HashMap`은 이런 개방 주소법의 선형 탐사로 동작한다고 설명하면 안 된다. Java `HashMap` API는 해시 테이블 기반 구현으로서 키가 버킷에 적절히 분산되면 기본 연산이 일정 시간에 가깝다고 설명한다. 충돌이 많아지면 내부 조건에 따라 버킷을 트리 형태로 관리할 수도 있으므로 모든 충돌을 연결 리스트 하나로만 단정하지 않는다.

## 부하율이 높아지면 리사이징하고 다시 배치한다

부하율은 저장된 엔트리 수를 버킷 수로 나눈 값이다.

```text
부하율 = 저장된 엔트리 수 / 버킷 수
```

체이닝에서는 한 버킷에 여러 엔트리를 저장할 수 있으므로 부하율이 `1`을 넘을 수 있다. 예를 들어 버킷이 5개이고 엔트리가 8개라면 부하율은 `1.6`이다. 부하율 `1.6`을 빈 버킷이 없다는 뜻으로 읽으면 안 된다. 평균적으로 버킷 하나에 1.6개의 엔트리가 배치된다는 의미에 가깝다.

리사이징은 버킷 수만 늘리고 기존 위치를 그대로 두는 작업이 아니다. 학습용 식 `key % bucketCount`에서 버킷 수가 `5`에서 `10`으로 바뀌면 기준 자체가 달라진다. 키 `1`과 `11`은 여전히 인덱스 `1`에 놓이지만 키 `6`은 인덱스 `6`으로 이동한다.

<img src="/assets/images/2026-10-09-bst-hash/hash-collision-resizing.svg" alt="학습용 모듈러 해시에서 키 1, 6, 11의 충돌과 버킷 5개에서 10개로 리사이징한 뒤의 재배치를 비교한 그림" loading="eager">

*그림 3. 버킷 수가 달라지면 기존 엔트리도 새 인덱스 기준으로 다시 배치해야 한다.*

Java `HashMap` API도 엔트리 수가 부하율과 현재 용량의 곱을 넘으면 내부 자료구조를 다시 만들고 버킷 수를 늘린다고 설명한다. 이 시점에는 기존 엔트리를 새 기준에 맞춰 처리하는 비용이 발생한다. 평소의 평균적인 `get`과 `put` 비용과 특정 리사이징 순간에 발생하는 비용을 같은 의미로 섞어 말하면 안 된다.

## HashMap 조회는 항상 O(1)이 아니다

오늘 모의면접에서 처음에는 “상품 ID나 사용자 ID는 중복되지 않으므로 `HashMap` 조회가 `O(1)`이다”라고 답했다. 하지만 키의 유일성과 해시 충돌은 다른 문제다. ID가 서로 다르더라도 해시 함수의 결과나 버킷 인덱스가 같아질 수 있다.

Java 21의 [HashMap API 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/HashMap.html)는 키가 버킷에 적절히 분산된다는 조건에서 `get`과 `put` 등의 기본 연산이 상수 시간 성능을 제공한다고 설명한다. 따라서 정확한 표현은 평균적으로 `O(1)`을 기대할 수 있다는 것이다. 키가 특정 버킷에 몰리면 한 버킷 안의 엔트리를 더 많이 비교해야 하므로 단순 체이닝 테이블에서는 `O(n)`까지 늘어날 수 있다.

Java `HashMap`은 충돌이 계속되는 버킷을 조건에 따라 트리 형태로 바꿀 수 있다. 그렇다고 모든 입력에서 무조건 최악 `O(log n)`이라고 일반화할 수도 없다. 실제 비용은 키의 분산 상태와 구현 조건 그리고 리사이징 여부에 영향을 받는다. 오늘의 핵심은 복잡도 하나를 외우는 것이 아니라 어떤 조건에서 그 복잡도를 말하는지 확인하는 데 있다.

## `equals`와 `hashCode`의 방향을 바로 잡다

Java의 객체를 해시 기반 컬렉션의 키로 사용할 때는 [Object API의 `equals`와 `hashCode` 계약](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Object.html)을 함께 봐야 한다. 오늘 처음에는 “해시코드가 같으면 `equals`도 같아야 한다”고 답했다. 방향이 반대였다.

- `equals`가 `true`인 두 객체는 같은 `hashCode`를 가져야 한다.
- `hashCode`가 같아도 `equals`는 `false`일 수 있다.

두 번째 경우가 해시 충돌이다. 해시값은 버킷을 빠르게 찾기 위한 1차 기준이고 같은 버킷 안에서 논리적으로 같은 키인지 확인하는 기준이 `equals`다. 그래서 해시코드가 같다는 사실만으로 키를 하나로 합치면 안 된다.

다음 예제는 모든 키가 같은 해시값을 반환하도록 만들어 충돌을 드러낸다. `record`가 생성하는 `equals`는 `id`를 비교하므로 `Key(1)`과 `Key(2)`는 서로 다른 키다.

```java
record Key(int id) {
    @Override
    public int hashCode() {
        return 1;
    }
}

Map<Key, String> map = new HashMap<>();
map.put(new Key(1), "A");
map.put(new Key(2), "B");

System.out.println(map.size());          // 2
System.out.println(map.get(new Key(1))); // A
```

모든 키가 같은 해시값을 반환해도 `equals`가 다르면 두 엔트리를 저장할 수 있다. 반대로 `equals`가 같다고 판단해야 하는 객체인데 `hashCode`를 다르게 만들면 같은 버킷을 찾아야 할 객체가 다른 위치로 흩어져 조회가 어긋날 수 있다. `equals`만 재정의하고 `hashCode`를 함께 재정의하지 말아야 하는 이유다.

`HashSet`의 중복 판단도 같은 흐름으로 이해했다. `HashSet`은 내부적으로 `HashMap`을 이용해 요소를 키처럼 관리한다. 같은 요소를 다시 추가해도 해시값만 보고 중복이라고 단정하는 것이 아니라 해시로 후보 위치를 찾은 뒤 동등성 판단을 거쳐 같은 요소인지 확인한다. 그래서 해시 충돌이 있어도 서로 다른 요소를 보관할 수 있다.

## 가변 키를 저장하면 조회 기준이 달라질 수 있다

키로 사용한 객체의 상태를 바꾸면 `equals`와 `hashCode`에 사용하는 필드도 함께 달라질 수 있다. 저장할 때 계산한 해시와 조회할 때 계산한 해시가 다르면 컬렉션은 새 값을 찾지 못할 수 있다. 그렇다고 객체가 `Map`에서 자동으로 제거되는 것도 아니고 바뀐 해시에 맞춰 자동 재배치되는 것도 아니다.

이 문제는 키 변경이 항상 조회 실패를 만든다고 단정하는 방식보다, 동등성과 해시에 영향을 주는 상태를 키로 사용한 뒤 바꾸면 조회 결과가 기대와 달라질 수 있다고 설명하는 편이 정확하다. `String`이나 `Integer`처럼 불변인 타입을 키로 사용하거나 키에 필요한 값을 생성 후 바꾸지 않는 이유도 여기에 있다.

## 조회 조건에 따라 자료구조를 선택한다

모의면접에서는 상품과 주문을 어떤 자료구조로 조회할지도 함께 질문받았다. 이때 HashMap 내부의 충돌 체인과 비즈니스 데이터의 일대다 관계를 섞지 않는 것이 중요했다.

- 상품 ID로 상품 하나를 찾는다면 `Map<ProductId, Product>`처럼 ID를 키로 두고 이름과 가격을 포함한 상품 데이터를 값으로 둘 수 있다.
- 주문 ID로 주문 하나를 찾는다면 주문 ID와 주문 데이터를 대응시킨다.
- 한 사용자에게 여러 주문이 있다면 `Map<UserId, List<Order>>`처럼 사용자 ID에 주문 목록을 연결하는 값 구조가 필요할 수 있다.
- 부서 ID에 직원 여러 명을 연결한다면 직원 한 명의 이름만 값으로 두는 구조로는 여러 직원을 표현하기 어렵다.

“여러 주문을 해시 충돌 체인으로 연결하면 된다”는 답변은 잘못된 방향이다. 충돌 체인은 자료구조가 같은 버킷의 키를 관리하기 위한 내부 처리이고, 사용자 한 명에게 여러 주문을 연결하는 것은 값의 타입과 도메인 관계를 설계하는 문제다.

정렬이나 범위 탐색이 필요하다면 HashMap과 다른 기준을 봐야 한다. [Java 21의 TreeMap API 문서](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/TreeMap.html)는 키의 자연 순서나 생성 시 지정한 `Comparator`에 따라 맵을 정렬하고 기본 연산에 `O(log n)` 시간 비용을 보장한다고 설명한다. 그래서 상품 ID를 키로 둔 `TreeMap`은 상품 ID 순으로 조회할 수 있지만 가격순 조회가 자동으로 해결되는 것은 아니다. 가격을 기준으로 정렬하려면 가격을 정렬 기준으로 구성하고 같은 가격을 가진 상품들을 어떻게 표현할지도 정해야 한다.

결국 자료구조를 고를 때는 키가 유일한지만 보는 것이 아니라 어떤 기준으로 찾고 정렬하고 범위를 잘라 볼지를 함께 봐야 한다. ID 하나를 빠르게 찾는 데는 HashMap의 평균적인 해시 조회가 어울릴 수 있고 키 순서나 범위가 중요하면 TreeMap처럼 정렬 기준을 유지하는 구조가 더 적합할 수 있다.

## 오늘의 정리

BST는 일반 이진 트리에 키의 대소 관계를 더해 탐색할 방향을 정한다. 왼쪽 서브트리 전체가 현재 키보다 작고 오른쪽 서브트리 전체가 크다는 규칙이 있기 때문에 비교 결과만으로 한쪽 가지를 선택할 수 있다. 이 규칙 덕분에 중위 순회가 오름차순이 되지만 일반 이진 트리의 중위 순회까지 정렬 결과가 되는 것은 아니다.

BST의 탐색과 삽입 및 삭제 비용은 높이 `h`에 따라 `O(h)`로 설명한다. 높이가 로그 수준이면 `O(log n)`이지만 삽입 순서에 따라 한쪽으로 편향되면 최악 `O(n)`이 된다. 자식이 둘인 노드를 삭제할 때는 대체 키만 가져오는 것으로 끝나지 않는다. 대체 노드가 원래 위치에서 가질 수 있는 자식을 기존 부모에 연결해야 한다. 중복 키를 저장하는 방식도 BST의 기본값이 아니라 거절과 count 저장 같은 정책으로 정한다.

Hash는 키에서 해시값을 계산하고 이를 버킷 인덱스로 연결해 저장 위치를 찾는다. 서로 다른 키가 같은 버킷에 들어갈 수 있으므로 충돌 해결이 필요하다. 체이닝은 한 버킷에 여러 엔트리를 연결하고 개방 주소법은 탐사 규칙에 따라 다른 슬롯을 찾는다. 개방 주소법에서 삭제된 슬롯과 사용한 적 없는 빈 슬롯을 구분하는 이유도 탐색 경로를 보존하기 위해서다.

Hash의 빠른 조회는 키의 유일성만으로 보장되지 않는다. 키가 적절히 분산되고 충돌이 관리된다는 조건에서 평균 `O(1)`을 기대한다. 부하율이 높아져 리사이징하면 버킷 수와 인덱스 계산 기준이 바뀌므로 기존 엔트리를 새 기준으로 다시 배치해야 한다. Java에서 `equals`가 `true`인 객체는 같은 `hashCode`를 가져야 하지만 해시코드가 같다고 `equals`가 `true`인 것은 아니다. 키의 동등성과 해시에 영향을 주는 값을 저장 후 변경하면 조회 기준이 어긋날 수 있으므로 불변 키를 사용하는 편이 안전하다.

오늘 모의면접에서 가장 크게 교정한 부분은 “트리면 `O(log n)`, ID면 `O(1)`”처럼 자료구조의 이름만으로 비용을 단정했던 습관이다. 실제로는 BST의 높이와 삽입 순서, Hash의 분산과 충돌, 그리고 정렬이나 범위 조회가 필요한지까지 확인한 뒤 자료구조를 선택해야 한다.
