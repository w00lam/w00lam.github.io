어제는 Strategy와 Composite, SOLID를 공부하며 객체의 행동과 계층 구조, 책임과 의존 관계를 나눠 보았다. 그 전에는 Template Method, Factory Method, Observer를 통해 실행 순서와 객체 생성, 상태 변경에 따른 후속 작업의 책임도 살펴봤다.

오늘은 애플리케이션 내부의 설계에서 실제 프로그램이 실행되는 환경으로 관점을 옮겼다. Linux 서버에서 명령어는 어떤 과정을 거쳐 실행되는지, 실행 중인 프로그램의 명령어와 데이터는 어떻게 처리되는지, 파일과 디렉터리 접근은 어떤 기준으로 제한되는지 이어서 정리했다.

세 주제는 따로 떨어져 있지 않았다. Shell이 명령어를 해석하고 운영체제에 실행을 요청하면 프로그램은 CPU와 메모리를 사용한다. 프로그램이 실행된다고 해서 모든 파일에 접근할 수 있는 것은 아니며, 파일의 소유자·그룹·권한에 따라 사용할 수 있는 자원이 달라진다. 명령어 사용법을 외우는 것보다 이 연결을 이해하는 데 초점을 맞췄다.

## 1. Linux Basic Command

### 1-1. Linux에서 명령어가 실행되는 환경

Linux 서버에서 명령어를 입력할 때 Terminal, Shell, Linux Kernel을 같은 대상으로 생각하기 쉽다. 하지만 세 구성 요소의 역할은 다르다.

| 구성 요소 | 역할 |
| --- | --- |
| Terminal | 사용자의 입력을 받고 프로그램의 출력을 보여 주는 인터페이스 |
| Shell | 입력된 명령어와 옵션을 해석하고 프로그램 실행, Pipe, Redirection을 설정하는 프로그램 |
| Linux Kernel | 프로세스, 메모리, 파일 시스템, 장치 같은 시스템 자원을 관리하고 프로그램의 요청을 처리 |

Terminal은 사용자가 Shell과 상호작용하는 입력·출력 창이다. 명령어를 직접 해석하는 주체는 Terminal이 아니라 Shell이다. Shell은 `ls`, `grep` 같은 실행 파일을 찾고 인자를 해석하며, `|`와 `>` 같은 문법도 처리한다.

Shell이 모든 일을 직접 수행하는 것도 아니다. `cd`처럼 현재 Shell의 작업 디렉터리를 바꾸는 내장 명령어도 있지만, 많은 명령어는 별도의 프로그램으로 실행된다. 실행 과정에서 프로세스 생성이나 파일 열기처럼 운영체제의 도움이 필요하면 Shell 또는 실행된 프로그램이 Kernel에 요청한다.

따라서 Terminal이 없어도 프로그램은 실행될 수 있다. 백그라운드 작업, 서비스, 스케줄러, 다른 프로그램의 실행 요청처럼 입력·출력 인터페이스를 직접 사용하지 않는 실행도 있기 때문이다. Terminal은 명령어 실행의 필수 구성 요소라기보다 사람이 Shell과 상호작용하는 한 가지 경로다.

### 1-2. 파일과 디렉터리 탐색

서버에서 파일을 찾고 백업할 때는 현재 위치와 경로를 먼저 확인한다.

```bash
pwd
ls
cd /var/log
mkdir backup
cp app.jar backup/
mv backup/app.jar backup/app-previous.jar
rm backup/app-previous.jar
find /var/log -type f -name "*.log"
```

`pwd`는 현재 작업 디렉터리를 보여 주고, `ls`는 현재 위치의 항목을 확인한다. `cd`는 작업 디렉터리를 이동하며 `mkdir`, `cp`, `mv`, `rm`은 각각 디렉터리 생성, 복사, 이동·이름 변경, 삭제에 사용한다. `find`는 지정한 경로 아래에서 조건에 맞는 항목을 찾는다.

`/var/log`처럼 `/`에서 시작하는 경로는 절대 경로다. 어느 디렉터리에서 명령어를 실행해도 같은 위치를 가리킨다. `backup/app.jar`처럼 `/`로 시작하지 않는 경로는 상대 경로이며 현재 작업 디렉터리를 기준으로 해석된다. 같은 명령어라도 `pwd`가 달라지면 상대 경로가 가리키는 대상도 달라진다.

`find /var/log -type f -name "*.log"`에서 `.log`와 `"*.log"`는 다른 조건이다. `.log`는 이름이 정확히 `.log`인 항목을 대상으로 하고, `"*.log"`는 임의의 이름 뒤에 `.log`가 붙는 패턴과 일치하는 파일을 찾는다. `*`는 Shell의 파일명 확장 대상이 될 수 있으므로 따옴표로 감싸 `find`가 패턴을 해석하도록 남겨 둔다. 명령어에 패턴을 전달할 때 Shell의 확장 시점과 프로그램이 패턴을 처리하는 시점을 구분해야 한다.

### 1-3. 로그 전체 확인과 검색

파일 전체를 확인하는 명령어와 필요한 줄만 찾는 명령어는 목적이 다르다.

```bash
cat app.log
head -n 20 app.log
tail -n 100 app.log
tail -f app.log

grep "ERROR" app.log
grep -n "ERROR" app.log
```

`cat`은 파일 내용을 한 번에 출력한다. 파일이 짧을 때는 간단하지만 로그처럼 내용이 긴 파일에서는 필요한 부분을 찾기 어렵다. `head -n 20`은 앞의 20줄, `tail -n 100`은 마지막 100줄만 보여 준다. 서버에서 최근 요청이나 종료 직전의 오류를 확인할 때는 전체 로그보다 마지막 부분이 먼저 필요할 때가 많다.

`tail -f app.log`의 `-f`는 파일에 추가되는 내용을 계속 확인하는 방식이다. 명령어가 끝나지 않고 새로운 로그가 기록될 때마다 화면에 이어서 보여 준다. `grep "ERROR" app.log`는 ERROR 문자열이 포함된 줄을 찾고, `grep -n "ERROR" app.log`는 그 결과에 줄 번호를 함께 표시한다.

Spring Backend 서버의 로그를 확인할 때도 같은 차이가 있다. 로그 전체를 읽는 대신 오류 메시지를 검색하고, 필요하면 줄 번호를 이용해 앞뒤 문맥을 다시 확인한다. 로그를 어떤 명령어로 볼지 결정하려면 “파일을 모두 읽어야 하는가, 최근 내용이 필요한가, 특정 문자열만 찾으면 되는가”를 먼저 구분해야 한다.

### 1-4. 표준 입출력과 Pipe

Linux 프로그램은 기본적으로 세 개의 표준 스트림을 가진다.

| 이름 | 파일 디스크립터 | 기본 의미 |
| --- | ---: | --- |
| Standard Input | `stdin`, `0` | 프로그램이 입력을 읽는 통로 |
| Standard Output | `stdout`, `1` | 정상적인 결과를 출력하는 통로 |
| Standard Error | `stderr`, `2` | 오류나 진단 메시지를 출력하는 통로 |

Pipe는 앞쪽 명령어의 stdout을 뒤쪽 명령어의 stdin으로 연결한다.

```bash
grep "ERROR" app.log | wc -l
```

예를 들어 `app.log`의 내용이 다음과 같다고 하자.

```text
INFO Application started
WARN Slow response
ERROR Connection failed
INFO Request completed
ERROR Request failed
```

`grep`은 ERROR가 포함된 두 줄을 stdout으로 내보내고, Pipe는 그 출력을 `wc`의 stdin으로 전달한다. `wc -l`은 전달받은 줄바꿈의 개수를 세므로 결과는 다음과 같다.

```text
2
```

이 결과를 “ERROR라는 단어의 개수”라고 단정하면 안 된다. 이 예제에서 한 줄에 ERROR가 한 번씩만 있기 때문에 숫자가 같을 뿐이다. 정확히는 grep이 출력한 줄의 개수를 센다. Pipe로 연결된 명령어는 단순히 왼쪽 명령어가 끝난 뒤 오른쪽 명령어를 실행하는 문법도 아니다. Pipe가 연결된 여러 프로세스는 데이터를 주고받으며 동시에 실행될 수 있다.

일반적인 `|`는 stdout만 다음 명령어의 stdin으로 연결한다. stderr는 별도의 Redirection을 하지 않으면 일반 출력 흐름과 분리되어 Terminal에 남는다. Bash 매뉴얼도 Pipe를 명령어의 출력과 다음 명령어의 입력을 연결하는 구조로 설명하며, `|&`처럼 stderr까지 연결하는 별도 문법을 구분한다.

### 1-5. Redirection

Pipe가 데이터를 다른 명령어에 전달한다면 Redirection은 입출력의 대상을 바꾼다.

```bash
grep "ERROR" app.log > error.log
grep "ERROR" app.log >> error.log
```

`>`는 표준 출력을 `error.log`에 기록하도록 파일을 열고, 기존 파일이 있으면 내용을 비운 뒤 새 결과를 쓴다. 파일이 없으면 생성될 수 있다. `>>`는 기존 내용을 유지한 채 파일의 끝에 결과를 추가한다. 이 파일도 없으면 생성될 수 있다.

두 문법을 비교하면 다음과 같다.

| 문법 | stdout의 대상 | 기존 `error.log` |
| --- | --- | --- |
| `>` | `error.log` | 비우고 새 결과 저장 |
| `>>` | `error.log`의 끝 | 기존 내용 뒤에 결과 추가 |

Redirection 설정은 명령어가 실행되기 전에 Shell이 처리한다. 그 뒤 `grep`은 자신이 stdout을 Terminal로 출력한다고 생각하고 결과를 내보내지만 실제 파일 디스크립터가 가리키는 대상은 `error.log`다. 그래서 Pipe와 Redirection을 같은 “출력 연결 문법”으로 묶기보다, Pipe는 프로세스 사이의 데이터 전달이고 Redirection은 입출력 대상 변경이라고 구분해야 한다.

### 1-6. 실행 중인 프로세스와 서버 상태 확인

명령어를 사용해 서버의 상태를 확인할 때는 무엇을 알고 싶은지에 따라 도구를 선택한다.

```bash
ps aux | grep java

top

kill -15 <PID>
kill -9 <PID>

ss -tlnp | grep "8080"

df -h
du -sh logs/

free -h
```

`ps aux`는 현재 실행 중인 프로세스 목록을 보여 준다. `grep java`를 Pipe로 연결하면 목록 중 Java라는 문자열이 포함된 줄을 필터링할 수 있다. `top`은 프로세스 목록뿐 아니라 CPU와 메모리 사용량이 변하는 상태를 실시간으로 확인하는 데 사용한다.

`kill -15 <PID>`의 `15`는 SIGTERM이다. 프로세스에 종료를 요청하는 신호이므로 프로그램이 정리 작업을 수행하고 종료할 기회를 가질 수 있다. 다만 SIGTERM을 보냈다고 항상 정상 종료되는 것은 아니다. 프로그램이 신호를 처리하지 않거나 종료하지 못하는 상황도 있다. `kill -9 <PID>`의 9는 SIGKILL이며 프로세스가 정리 작업을 수행할 기회를 주지 않고 강제 종료한다. 따라서 두 명령어는 같은 종료 방식이 아니다.

포트를 확인할 때는 데이터가 흐르는 방향이 중요하다.

```bash
# 잘못된 데이터 전달 방향
grep "8080" | ss -tlnp

# 올바른 데이터 전달 방향
ss -tlnp | grep "8080"
```

`ss -tlnp`가 TCP 리스닝 포트 목록을 출력하고, 그 결과를 `grep`으로 필터링해야 한다. 반대로 `grep`은 먼저 입력을 기다리게 되므로 확인하려는 서버 소켓 정보가 전달되지 않는다.

`df -h`는 파일 시스템별 전체 공간과 사용량, 남은 공간을 확인하는 명령어다. `du -sh logs/`는 특정 디렉터리인 `logs/`가 사용한 공간을 집계한다. `df`는 파일 시스템 관점, `du`는 디렉터리와 파일이 차지한 공간 관점이라는 차이가 있다.

`free -h`의 `available`은 단순히 아무 작업에도 사용되지 않는 메모리만 뜻하지 않는다. 운영체제가 캐시 등을 회수하는 상황까지 고려해 새 프로그램에 사용할 수 있다고 추정하는 메모리다. “사용 중”과 “당장 새 프로그램에 쓸 수 없음”을 같은 의미로 읽으면 안 된다.

Docker를 사용하는 환경에서는 컨테이너 상태와 애플리케이션 로그를 나눠서 확인한다.

```bash
docker compose ps
docker compose logs -f app
```

`docker compose ps`는 Compose가 관리하는 컨테이너의 실행 상태와 포트 매핑을 확인하는 데 가깝다. `docker compose logs -f app`은 `app` 서비스의 로그를 계속 확인한다. 하나는 컨테이너가 떠 있는지와 상태를 확인하고, 다른 하나는 컨테이너 안 애플리케이션이 어떤 출력을 내는지 확인하는 명령어다.

## 2. Von Neumann Architecture

### 2-1. 프로그램과 데이터는 어디에 저장되는가?

Linux 명령어를 실행하는 과정을 살펴보면 결국 프로그램이 CPU와 메모리를 사용해 동작한다는 질문으로 이어진다. 폰 노이만 구조를 공부한 이유도 여기에 있다. 프로그램의 명령어와 데이터가 메모리에 저장되고, CPU가 메모리에서 명령어를 가져와 해석하고 실행하는 저장 프로그램 방식을 이해하면 `java -jar app.jar` 같은 명령어를 더 낮은 계층까지 연결할 수 있다.

폰 노이만 구조를 단순화하면 다음 구성 요소로 볼 수 있다.

| 구성 요소 | 역할 |
| --- | --- |
| CPU | 명령어를 해석하고 연산을 수행하는 처리 장치 |
| Control Unit | 현재 명령어를 해석하고 구성 요소의 동작을 제어 |
| ALU | 산술·논리 연산 수행 |
| Register | CPU가 바로 사용할 값을 임시로 보관 |
| Main Memory | 실행할 명령어와 처리할 데이터를 저장 |
| Input/Output | 외부 장치와 데이터를 주고받는 경로 |
| Bus | 주소, 데이터, 제어 신호를 구성 요소 사이에 전달 |

저장 프로그램 방식에서는 프로그램을 실행 파일처럼 저장해 두고 필요할 때 CPU가 읽는다. 명령어와 데이터는 같은 Main Memory 안에 존재할 수 있으며, 여기서 “Instruction 영역”과 “Data 영역”은 학습을 위한 논리적 구분이다. 현대 컴퓨터의 모든 내부 구조가 단순한 폰 노이만 모델과 완전히 같다는 뜻은 아니다.

### 2-2. CPU와 메모리의 역할

Main Memory는 명령어와 데이터를 보관하고 CPU는 필요한 값을 가져와 처리한다. CPU 안의 Register는 메인 메모리와 같은 역할을 하는 큰 저장 공간이 아니라, CPU가 현재 처리하는 값을 빠르게 다루기 위한 작은 저장 공간이다.

이번 학습에서 사용한 레지스터를 단순화하면 다음과 같다.

| 레지스터 | 역할 |
| --- | --- |
| PC | 다음에 가져올 명령어의 위치 |
| IR | 현재 해석하거나 실행하는 명령어 |
| MAR | 접근할 메모리 주소 |
| MDR 또는 MBR | 메모리에서 읽거나 메모리에 쓸 데이터 |
| Accumulator | 연산 결과를 임시로 보관하는 레지스터 |

PC가 다음 명령어의 위치를 가리키고 IR이 현재 명령어를 보관한다는 차이가 중요하다. CPU가 메모리 주소를 읽을 때 MAR에 주소를 두고, 그 주소의 명령어나 데이터를 MDR에 옮긴다고 생각하면 주소와 실제 값이 섞이지 않는다.

### 2-3. Fetch, Decode, Execute

구체적인 ISA의 어셈블리 코드가 아니라 개념 이해를 위한 가상 명령어로 흐름을 표현해 보자.

```text
LOAD A
ADD B
STORE C
```

초기 데이터는 다음과 같다.

```text
A = 3
B = 5
C = 0
```

처리 흐름은 다음처럼 정리할 수 있다.

1. PC가 가리키는 명령어를 메모리에서 가져온다.
2. 가져온 명령어를 IR에 저장하고 Control Unit이 해석한다.
3. 필요한 데이터의 주소를 MAR에 두고 값을 MDR로 읽는다.
4. ALU가 필요한 연산을 수행하고 결과를 Register에 반영한다.
5. STORE 명령어가 실행되면 최종 결과를 메모리에 저장한다.

첫 번째 명령어인 `LOAD A`가 실행되면 A의 값 3이 Accumulator에 들어간다. `ADD B`는 B의 값 5를 읽어 3과 더하고 Accumulator를 8로 바꾼다. 마지막 `STORE C`는 Accumulator의 8을 메모리 C에 기록한다. 최종 결과는 `C = 8`이다.

이 흐름은 교육용으로 단순화한 CPU 모델이다. 실제 CPU가 항상 명령어 하나를 완전히 끝낸 뒤에만 다음 명령어를 가져온다고 단정할 수는 없다. 이번 정리에서는 파이프라이닝이나 비순차 실행의 상세 구현을 추가하지 않고, 명령어와 데이터가 CPU·메모리 사이를 오가는 기본 관계만 확인했다.

### 2-4. Von Neumann Bottleneck

폰 노이만 구조에서는 명령어와 데이터가 공유하는 메모리 및 전송 경로의 대역폭과 접근 지연이 처리 성능의 제약이 될 수 있다. CPU가 연산을 빠르게 수행해도 필요한 명령어나 데이터가 메모리에서 늦게 도착하면 CPU가 기다리는 시간이 생긴다. 이 문제가 Von Neumann Bottleneck이다.

핵심은 레지스터가 부족해서만 생기는 문제가 아니다. CPU와 메모리 사이를 오가는 명령어·데이터의 양과 접근 지연, 공유 경로의 대역폭이 함께 영향을 준다.

Harvard Architecture는 명령어와 데이터를 저장하거나 접근하는 경로를 분리하는 방향의 구조다. 폰 노이만 구조가 하나의 메모리와 경로를 공유하는 모델이라면, Harvard 구조는 명령어와 데이터의 접근을 나눠 병목을 완화할 수 있는 여지를 가진다.

앞서 [컴퓨터 구성 요소와 CPU의 명령어 처리 과정](/posts/computer-architecture-cpu-instruction-flow/)에서 CPU와 RAM, Bus, Register가 값을 주고받는 흐름을 정리했고, 이어서 [캐시 메모리와 지역성](/posts/cpu-cache-locality-mapping/)에서는 CPU가 매번 RAM까지 접근하는 비용을 줄이기 위해 Cache를 사용하는 이유를 살펴봤다. Cache는 반복되는 명령어나 데이터 접근을 가까운 저장 공간에서 처리해 메모리 접근 비용을 줄이는 데 도움을 준다. 시간 지역성과 공간 지역성은 이런 접근 패턴을 이해하는 기준이다.

CPU Cache와 Redis는 모두 반복 접근 비용을 줄인다는 목적에서 비슷하게 보일 수 있지만 같은 계층의 기능은 아니다. CPU Cache는 CPU와 메인 메모리 사이의 하드웨어 계층에서 동작하고, Redis는 애플리케이션이 네트워크를 통해 사용하는 별도의 데이터 저장 시스템이다. 목적이 비슷한 부분과 동작 계층을 구분해야 한다.

### 2-5. Java와 Spring Backend 프로그램 실행 연결하기

Linux에서 Java 애플리케이션을 실행하는 명령어를 생각해 보자.

```bash
java -jar app.jar
```

이 한 줄에 모든 구성 요소가 직렬로 한 번씩 호출되는 것은 아니다. 각 계층이 다른 책임을 맡은 채 서로 협력한다.

| 구성 요소 | 책임 |
| --- | --- |
| Shell | `java`, `-jar`, `app.jar`를 해석하고 실행 요청을 준비 |
| Operating System | Java 프로세스와 파일, 메모리, CPU 같은 시스템 자원을 관리 |
| JVM | Java 바이트코드를 실행하고 Java 런타임 영역과 스레드를 관리 |
| Spring Container | Bean을 생성하고 의존 관계를 연결하며 생명주기를 관리 |
| CPU | JVM이 실행하도록 만든 기계어 명령어를 실제로 처리 |
| RAM | 실행에 필요한 프로그램 명령어와 데이터, 프로세스 상태를 보관 |

JVM은 Java 바이트코드를 실행하는 가상 머신이고 CPU는 최종적으로 기계어 명령어를 처리하는 장치다. JVM이 CPU와 같은 역할을 하는 것은 아니다. [JVM 메모리 영역과 객체 생명주기](/posts/java-jvm-memory-lifecycle/)에서 정리한 Heap, Stack, Method Area 같은 영역도 Java 런타임의 관점에서 봐야 한다. Spring Container가 Bean과 의존성을 관리한다고 해서 운영체제의 메모리 관리나 프로세스 관리까지 담당하는 것은 아니다.

## 3. Permission

### 3-1. 파일 접근 권한이 필요한 이유

Linux 서버에는 여러 사용자와 프로세스가 존재한다. 모든 사용자에게 프로그램 실행, 설정 파일 변경, 민감한 정보 조회를 허용하면 한 프로세스의 실수나 오용이 다른 파일과 서비스에 영향을 줄 수 있다.

파일의 소유자와 그룹을 기준으로 접근 범위를 나누면 “누가 어떤 파일을 어떤 방식으로 사용할 수 있는가”를 제한할 수 있다. 실행 가능 여부와 파일 내용 읽기, 설정 변경 권한이 모두 같은 것은 아니다. 프로그램이 실행된다는 사실과 모든 시스템 자원에 접근할 수 있다는 사실도 다르다.

### 3-2. User, Group, Others

Linux 파일 권한은 일반적으로 파일 소유자, 파일의 소유 그룹에 속한 사용자, 그 밖의 사용자라는 세 범주로 나뉜다.

```text
-rwxr-x---
 |  |   |
 |  |   └─ Others
 |  └──── Group
 └─────── User
```

더 정확히 나누면 첫 번째 `-`는 파일 유형이고, 뒤의 9개 문자가 권한이다.

```text
- | rwx | r-x | ---
      User  Group  Others
```

첫 번째 문자는 일반 파일이면 `-`, 디렉터리면 `d`처럼 파일 유형을 나타낸다. 권한을 판단할 때는 먼저 실행 주체가 소유자인지, 소유 그룹에 속하는지, 둘 다 아닌지를 정해 적용할 권한 범주를 선택한다. User·Group·Others의 권한을 모두 합산해 적용하는 방식은 아니다.

### 3-3. 읽기, 쓰기, 실행 권한

`r`, `w`, `x`의 의미는 일반 파일과 디렉터리에서 다르게 읽어야 한다.

| 권한 | 일반 파일 | 디렉터리 |
| --- | --- | --- |
| `r` | 파일 내용 읽기 | 내부 항목 이름 목록 읽기 |
| `w` | 파일 내용 변경 | 내부 항목 생성·삭제 등 변경 |
| `x` | 프로그램으로 실행 | 경로 탐색 및 내부 항목 접근 |

디렉터리의 `x`는 파일처럼 “실행한다”는 뜻이 아니다. 해당 디렉터리를 경로의 일부로 통과하고 내부 항목에 접근할 수 있는 탐색 권한에 가깝다. 디렉터리 목록을 읽는 `r`이 있더라도 `x`가 없으면 해당 경로를 따라 내부 파일에 접근하기 어려울 수 있다.

디렉터리 내부 항목을 생성하거나 삭제하려면 일반적으로 `w`와 `x`가 함께 필요하다. `w`만으로는 이름을 가진 항목을 실제 경로로 탐색하거나 조작하는 데 부족할 수 있다. 또한 대상 파일 자체뿐 아니라 `/srv`, `/srv/backend`, `/srv/backend/config`처럼 상위 경로 각 단계에 필요한 탐색 권한이 있어야 한다.

### 3-4. 숫자 권한과 BitMask

Linux의 숫자 권한은 `r`, `w`, `x`를 독립적인 비트처럼 조합한다.

```text
r = 4 = 100
w = 2 = 010
x = 1 = 001
```

각 권한이 서로 다른 자리의 비트에 대응하므로 합으로 한 자리 숫자를 만들 수 있다.

| 숫자 | 계산 | 문자 |
| ---: | --- | --- |
| 7 | 4 + 2 + 1 | `rwx` |
| 6 | 4 + 2 | `rw-` |
| 5 | 4 + 1 | `r-x` |
| 4 | 4 | `r--` |
| 0 | 0 | `---` |

예를 들어 `640`은 User `6`, Group `4`, Others `0`을 뜻한다.

```text
640 = rw- r-- ---
       110 100 000
```

이 표현 방식은 [Dijkstra와 BitMask](/posts/dijkstra-bitmask/)에서 여러 boolean 상태를 비트로 묶어 관리한 것과 연결된다. 두 경우 모두 각각의 상태를 독립된 비트로 표현하고, 비트 조합을 숫자 하나로 읽는다. Linux 권한에서는 세 사용자 범주 각각에 대해 읽기·쓰기·실행 비트가 따로 존재한다.

### 3-5. chmod

`chmod`는 파일의 접근 권한을 변경한다. 숫자 방식은 User·Group·Others의 전체 `rwx` 조합을 지정하고, 문자 방식은 특정 범주의 권한을 현재 상태에서 추가하거나 제거한다.

```bash
chmod 700 deploy.sh
chmod 750 deploy.sh
chmod 640 application.yml
chmod 400 private.pem

chmod u+x deploy.sh
chmod g+w logs/
chmod g+x config/
chmod o+x deploy.sh
```

`chmod 700 deploy.sh`는 소유자에게 `rwx`, Group과 Others에는 권한이 없도록 전체 상태를 지정한다. `chmod 750 deploy.sh`는 `rwxr-x---`로 만든다. `application.yml`에 `640`을 지정하면 소유자는 읽기·쓰기, 그룹은 읽기, Others는 아무 권한이 없다. `chmod 400 private.pem`은 개인키를 소유자만 읽을 수 있게 제한하는 예다.

현재 권한을 유지하면서 한 비트만 바꿀 때는 문자 방식이 더 직접적이다.

```text
변경 전: 640 = rw-r-----
명령어: chmod u+x deploy.sh
변경 후: 740 = rwxr-----
```

여기서 `u`는 User, `+`는 권한 추가, `x`는 실행 권한을 뜻한다. `chmod u+x deploy.sh`는 나머지 권한을 다시 적지 않고 소유자에게 x만 추가한다. 권한을 실제로 판단할 때는 파일 유형, 실행 주체, 소유자·그룹, 상위 디렉터리까지 함께 확인해야 한다.

### 3-6. chown과 chgrp

접근 권한을 바꾸는 것과 파일의 소유 관계를 바꾸는 것은 다른 작업이다.

```bash
sudo chown ubuntu:spring logs/
sudo chgrp spring logs/
chmod 750 logs/
```

| 명령어 | 역할 |
| --- | --- |
| `chmod` | 파일의 접근 권한 변경 |
| `chown` | 소유 사용자 변경, `user:group` 형식이면 그룹도 함께 변경 |
| `chgrp` | 소유 그룹 변경 |

`chgrp`에 `ubuntu:spring`처럼 소유 사용자와 그룹을 함께 전달해 소유자를 바꾸는 것은 올바른 사용이 아니다. 소유 사용자와 그룹을 함께 바꾸려면 `chown ubuntu:spring logs/`를 사용하고, 그룹만 바꾸려면 `chgrp spring logs/`를 사용한다. 소유 관계 변경에는 실행 주체의 적절한 권한이 필요하다.

### 3-7. umask와 기본 권한

`umask`는 새 파일과 디렉터리가 만들어질 때 요청된 권한에서 일부 비트를 제거하는 마스크다. 이미 존재하는 파일의 권한을 바꾸는 `chmod`와 목적이 다르다.

```text
umask: 027

일반 파일의 요청 권한: 666
생성 권한: 640

디렉터리의 요청 권한: 777
생성 권한: 750
```

권한을 단순히 십진수나 팔진수에서 빼는 것으로 이해하기보다, 요청된 모드에서 마스크에 지정된 비트를 제거한다고 보는 편이 정확하다.

```text
result = requested_mode & ~umask
```

일반 파일에 기본 실행 권한이 반드시 부여되는 것도 아니다. 위 예제처럼 일반 파일은 `666`을, 디렉터리는 `777`을 요청 모드의 출발점으로 삼는 경우가 일반적이며 실제 초기 권한은 파일을 생성하는 프로그램이 요청한 모드와 umask에 따라 결정된다.

### 3-8. Spring Backend 서버 운영과 연결하기

배포 스크립트, 설정 파일, 로그 디렉터리, SSH 개인키는 서로 필요한 권한이 다르다.

```bash
ls -l application.yml
ls -ld logs/
ls -ld config/
id
```

`ls -l application.yml`은 파일 유형, 권한, 소유자, 그룹을 확인하는 데 사용한다. `ls -ld logs/`와 `ls -ld config/`는 디렉터리 자체의 권한을 확인한다. `id`는 현재 명령어를 실행하는 사용자의 UID, 기본 그룹과 소속 그룹을 확인하는 데 도움이 된다.

예를 들어 배포 스크립트는 실행 권한이 필요하지만 `application.yml`은 애플리케이션 실행 사용자가 읽을 수 있으면 된다. 로그 디렉터리는 애플리케이션 사용자가 접근하고 파일을 만들 수 있어야 하며, SSH 개인키는 소유자 외의 사용자가 읽지 못하도록 제한해야 한다. 이때 파일 소유자와 실행 사용자, 그룹 관계를 먼저 확인한다.

권한 오류가 발생했다고 무조건 다음처럼 바꾸면 안 된다.

```bash
chmod 777 application.yml
```

`777`은 모든 범주에 읽기·쓰기·실행 권한을 열어 문제의 원인을 가릴 뿐이다. 애플리케이션을 항상 root 사용자로 실행하는 것도 적절한 기본 대응이 아니다. 실행 사용자, 소유자, 그룹, 파일 권한, 상위 디렉터리의 탐색 권한을 차례로 확인하고 필요한 범위만 추가해야 한다.

## 4. 세 주제를 한 흐름으로 연결하기

오늘 배운 내용을 `java -jar app.jar`와 연결하면 다음과 같이 정리할 수 있다.

1. Terminal 또는 다른 실행 주체가 Shell에 `java -jar app.jar`를 전달한다.
2. Shell은 명령어를 해석하고 운영체제에 Java 프로세스 실행을 요청한다.
3. 운영체제는 프로세스와 메모리, 파일 접근을 관리하고 JVM이 실행될 환경을 제공한다.
4. JVM은 Java 바이트코드와 런타임 데이터를 사용하고, CPU는 실제 기계어 명령어를 처리한다.
5. 프로그램의 표준 출력과 오류는 Terminal이나 파일, 다른 프로세스로 연결될 수 있다.
6. 설정 파일과 로그 디렉터리의 접근 가능 여부는 실행 주체와 파일 권한, 상위 디렉터리 권한에 따라 달라진다.

Linux 명령어는 서버를 조작하는 문자열 모음이 아니다. Shell을 통해 프로그램 실행과 시스템 상태 확인을 요청하고, 표준 입출력의 흐름을 연결하며, 파일과 프로세스에 접근하는 방법이다. 실행된 프로그램은 CPU와 메모리의 상호작용으로 동작하지만, 실행 가능하다는 사실이 모든 시스템 자원에 대한 접근을 보장하지는 않는다.

오늘 학습을 세 가지 질문으로 다시 적어 보면 다음과 같다.

- Linux Basic Command: 실행 환경과 파일·프로세스 상태를 어떻게 확인하고 조작하는가?
- Von Neumann Architecture: 프로그램의 명령어와 데이터는 CPU와 메모리 사이에서 어떻게 처리되는가?
- Permission: 실행 주체는 소유자·그룹·권한에 따라 어떤 시스템 자원에 접근할 수 있는가?

백엔드 개발에서는 애플리케이션 코드의 동작만 보는 것으로 충분하지 않다. 그 코드가 어느 프로세스로 실행되고, 어떤 명령어와 메모리를 사용하며, 어떤 사용자 권한으로 파일과 디렉터리에 접근하는지까지 함께 이해해야 실행 환경을 정확히 설명할 수 있다. 오늘 모든 명령어와 서버 운영 능력을 익힌 것은 아니지만, 명령어·실행 구조·접근 권한을 하나의 흐름으로 바라보는 기준은 세울 수 있었다.

## 마무리

오늘은 Linux 명령어, 폰 노이만 구조, 파일 권한을 각각 외우기보다 “명령어가 실행되고, 프로그램이 처리되고, 접근 범위가 결정되는 과정”으로 연결했다. Shell은 명령어와 입출력 연결을 해석하고, 운영체제는 프로세스와 자원을 관리한다. CPU와 메모리는 프로그램의 명령어와 데이터를 처리하며, 파일 권한은 실행 주체가 접근할 수 있는 범위를 제한한다.

서버에서 어떤 문제가 보일 때도 이 흐름을 기준으로 질문을 나눌 수 있다. 명령어가 올바르게 해석되었는가, 프로세스가 실행 중인가, 필요한 데이터가 메모리와 파일에서 전달되었는가, 실행 사용자가 해당 파일과 디렉터리를 읽거나 쓰거나 탐색할 권한이 있는가를 차례로 확인하는 식이다. 아직 운영 경험을 완성했다고 말할 단계는 아니지만, 애플리케이션 코드 밖의 실행 환경까지 살펴봐야 하는 이유는 분명해졌다.
